## 1. 结论

`TG-OPT-G0` 已完成开发门：独立纯模块已提供五类版本化图投影、类型/命名空间校验、稳定 digest/trace 与正文 fail-closed 边界，且未接入调度或执行路径。它不依赖第二台 PC、真实模型、Tailscale、Linux 真机或额外显存。

`MT-LORA-N0` 已完成开发门：统一 CLI 现可只读检查单个 Safetensors LoRA 头并安全汇总 `ss_*` 元数据，未加载权重或进入 CUDA。`EX-N3-S0`、LLM 客观执行器、Qwen Q4 三轮校准、SD schema v1 报告桥接及 Gemma schema v2 静态计数桥接均已完成开发；记录只保存计数与审核状态，质量门默认不改变性能 gate。Qwen Q4 的校准地板极低，仅能证明该固定工件可重复执行，不能作为质量通过结论；SD/Gemma fixture 都不生成或理解图像，也不替代既有真机验收。Gemma 实际闭环仍待资源和真实三轮标定。其余主要事项已经进入真实硬件、网络、安装包或协议授权门。

## 2. 状态口径

| 状态 | 含义 |
|---|---|
| `Completed（开发）` | 代码、自动化和本地可复现开发门已完成；不隐含真实环境或发布验收。 |
| `Ready` | 前置设计、代码落点和自动化边界明确，可在当前开发机开始。 |
| `Conditional` | 技术上可写，但尚缺固定范围、指标或显式业务决策，不应直接开工。 |
| `Validating / Blocked` | 开发门已关闭或无法继续，下一步只能等待真实设备、网络、账户、资源或安装环境。 |
| `Frozen` | 有明确止损或双基线风险，恢复条件未满足前不推进。 |

以下分类按阶段门而非代码行数计算；真实验收缺口不会抵消已完成的本地开发，也不能被本地测试替代。

## 4. 可立即开发队列

`EX-N3-GEMMA-S1` 已完成：Gemma 质量证据 schema v2、模型/判题契约 SHA 绑定、敏感字段拒绝和 fixture 回归均已落地；不得将其视为 Gemma 调用或质量验收。当前没有可安全推进的 EX-N3 实现票：下一步是真实 SD→Gemma 三轮标定，需满足工件、执行资源和串行调度前置，且在此之前 `gemma_judge` 不能设为 `quality.required=true`。`TG-OPT-G1` 仍须有 shadow 消费者和 no-op 比较基线后才可提升。

### EX-N3-S0 实施结果

已新增 `scripts/experiment_core/quality.py`，并接入 record collector、报告和 `summary.json`。结果文件的可选 `quality_evidence` 只接受受限的对象：LLM 必须绑定当前 plan 的固定 prompt set ID/SHA-256，并以已评估/通过计数派生正确率和格式率；SD 只保留资产/工件标识、自动门状态及计数、人工审核状态和所需审核人数。适配既有 SD 质量门报告时不会转存 prompt、图像/路径、审核人或其它原始内容。

未提供证据会落为明确的 `not_collected` 原因；不匹配 prompt set、未知字段、错误计数或非预期结构会落为脱敏 `invalid`，不会将错误文本或结果正文带进 `metrics`、记录或报告。该状态只供报告聚合，现阶段不改变性能 gate。`schemas/experiment-record.schema.json` 允许历史 `{correct_rate, format_rate}` 记录继续读取。专项 `23 passed`，其中包含 JSON Schema v2020-12 的新旧记录兼容验证。

### MT-LORA-N0 实施结果

已新增 `scripts/model_tools/lora.py` 与 `sd15_lora_inspect` / `sd15-lora-inspect` CLI。检查器只读取 Safetensors 长度前缀与不超过 16 MiB 的 JSON header，精确检查 dtype/shape/data range、重叠与可选根目录边界而不读取权重；只输出数值训练参数、LoRA 结构计数和训练集/触发词聚合，禁止输出原始文本、文件名、路径、未知键名和可逆摘要。专项 `48 passed / 2 skipped`；实际 LoRA 的兼容性、合并和质量仍须另行人工验证。

### TG-OPT-G0 实施结果

已新增独立纯模块 `src/task_graph_optimization.py`，由当前 `StageSpec`、`WorkflowRecord.snapshot()` 与已有 attempt/winner/lease 字段构造安全投影，完成：

- `logical_dag`、`optimized_dag`、`analysis_view`、`attempt_graph`、`provider_topology` 的显式类型和独立 ID 命名空间；
- Stage/语义边/图摘要/优化 trace 的 schema v1，以及输入相同则摘要与 trace 稳定；
- 仅记录 Stage ID、类型、依赖、输入绑定摘要、模型/Provider 约束摘要、状态和计数；禁止保存 `root_input_overrides`、输出正文、attempt 原始错误、路径、URL、blob ID、grant 或密钥；
- 当前 `TaskGraphCoordinator.get()` / `list()` 的既有执行快照不变；新增投影只读，且任何投影异常不能影响工作流执行；
- 单元测试覆盖菱形图、不同图类型混用拒绝、摘要稳定、正文脱敏和现有 SIM/TaskGraph 回归不变。

专项 `33 passed`，TaskGraph API/并行/fencing/review 回归 `71 passed`。`TaskGraphCoordinator.get()` / `list()` 未改动。后续仅评估 `TG-OPT-G1` 的 shadow `optimize(graph) -> graph + trace`；G1 仍只产生建议，不替换实际执行图，暂为 `Candidate`，G2 及以后必须逐项重新准入。
