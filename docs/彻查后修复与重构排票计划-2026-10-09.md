## 2. 不可改变的架构不变量

后续所有修复、优化和重构必须同时满足以下约束：

1. **星状拓扑不变。** master 是唯一协调节点和 worker 数据转发中心；worker 不建立 worker peer 数据连接。
2. **D→L / L→L 多段逻辑接力不变。** 去掉的是 worker 直连能力，不是层段顺序，也不是跨框架接力能力。
3. **Route-A 产品主线不回退。** Route-A 继续由 master 顺序编排各段；task graph/workflow 保持实验入口，不重开为默认产品路由。
4. **执行契约必须可验证。** task、step、model、config、assignment 和相邻段关系必须由 master 的冻结契约校验，不能相信 worker 自报的目标或前驱。
5. **失败必须具名且只有一个终局。** 不允许在 API、scheduler、solver、worker 各层重写真因，或同一请求同时呈现多个互相矛盾的结果。
6. **未来重构与当前修复隔离。** 当前修复票可以在 `dev` 上局部落地；结构重构必须另建干净分支并设置行为特征测试门。

## 4. 审计后的风险地图

### 4.1 已确认缺陷

1. **legacy 层流水线仍残留 worker peer 数据能力。** 原实现既能发起 `pipeline_peer` 连接，也能接收非 master 的 `LAYER_FORWARD` / `CHAIN_FORWARD`。只删除发送函数不足以保证星状拓扑。该项由 `ARCH-STAR-01` 处理。
2. **引擎、模型路径、量化和层段能力没有联合裁决。** `.gguf`、PyTorch、量化和运行时能力在多个入口分别判断，已经出现同一输入在 load、switch、自动加载和 scheduler 得到不同答案的确定分叉。
3. **模型/工件一致性检查发生得太晚。** worker 工件与请求模型不一致时，可能进入 step 0 后才以 hidden width 或 stage error 失败；应在准备或加载阶段拦截。
4. **普通聊天与 SSE/interactive 的会话事实源分叉。** `full`、`fast`、`interactive` 各自维护上下文；模型切换清空内存历史后，当前会话 ID 未改变时 `_switch_session()` 可能直接返回，导致 SQLite 历史不被重新装载。
5. **发行角色和版本事实源分叉。** slim 子进程、安装向导、环境变量和默认角色之间缺少最终发行物合同；多个版本文件也存在不一致风险。
6. **Android 恢复能力不足。** SAF 授权丢失后缺少默认目录扫描和自动工件匹配；DataStore 损坏可能形成永久启动崩溃。

### 4.2 条件风险

1. 掉线或 opted-out 节点是否完整进入 `excluded_nodes`，以及 relay 覆盖是否被容量求解重复算成缺口，仍需先写 characterization test；当前只能作为 #84 N10/N11 候选，不能写成生产已发生。
2. bootstrap 密钥获取、`cluster_secret` 落盘、生产 TLS/鉴权和 Android 备份边界，在 loopback 诊断以外尚未形成完整威胁模型。
3. 多候选 auto-role、journal replication、quorum commit watermark 和物理故障恢复缺真实跨机证明，不能宣称生产 HA。
4. Surface 侧掉线、重连和严格半开时序仍缺外部设备复验；两机 Y700 证据不能自动推广到全部节点类型。

### 4.3 结构债

1. 引擎能力矩阵至少有多份实现，且别名、量化、层段模式和 runtime 条件并不一致。
2. 容量、覆盖、relay 段和失败 reason 被 scheduler、solver、API 和 UI 重算或改写。
3. assignment 生命周期仍混有 `_worker_assignments` 与 `_layer_config_expected/_acks` 读路径，且缺协议级 `assignment_id`。
4. 准备、accept、execute、relay、fallback 各自拥有超时常量，没有统一消费端到端剩余预算。
5. 模型切换的原子事务缺口已由 `MODEL-TXN-01` 在代码层闭合；按需下载和跨请求排队仍是后续能力缺口，不再与失败回滚混记。
6. 会话历史、当前 session、SQLite 持久化和各聊天模式没有统一上下文服务。

### 4.4 外部验收缺口

1. Windows/Linux 干净机、全新用户目录、新 shell 和双栈真实网络。
2. 当前新契约构建出的安装包、签名 release APK、native 库和包体边界扫描。
3. 至少两个不同远端节点的 Route-A 自动化产品门，要求连续有序两段、每段真实 handoff、`fallback=false` 和星状连接证据。
4. 多候选 auto-role、journal 复制和物理故障注入。
5. 9B 大工件真加载接力、大显存/CUDA 构建和真实运营商弱网。

## 5. 排票顺序

票序以“先封住拓扑旁路和伪成功，再统一事务与事实源，最后决定结构重构”为原则。外部验收单独成轨，不能拿设备缺口阻塞已完成的代码票，也不能拿本地 mock 冒充产品验收。

### 票 1：`ARCH-STAR-01` 星状数据路径硬化（P0，代码完成，未提交）

目标：移除 legacy 层流水线中的 worker→worker TCP 数据能力，同时保留 D→L / L→L 多段逻辑接力和 `CHAIN_FORWARD` 的 wire 名称。

范围：

- 删除 worker peer client、地址解析、连接缓存和主动直连函数。
- worker 只把中间 hidden 通过既有 master 连接上送，并用 `_relay_to` 声明下一逻辑段。
- master 校验连接身份、task/config/model/step 契约和相邻段关系，再向下一 worker 发送 `CHAIN_FORWARD`。
- worker 不接收非 master 来源的 `LAYER_FORWARD` / `CHAIN_FORWARD`。
- `pipeline_peer` 注册在协议层和 scheduler 层 fail-closed。
- 下发给 worker 的逻辑路由只含 `node_id`，不含 peer host/port。

完成定义：

- 代码中不存在 `_send_chain_forward`、`_chain_clients`、`_get_node_address` 的生产实现或调用。
- 非 master 数据帧不能执行模型、修改 KV/step 或发送成功 ACK。
- 三逻辑段测试证明实际顺序为 `master→w1→master→w2→master→w3→master`。
- Route-A 现有顺序接力行为不变。
- 专项测试、TCP 回归、API/Android gate 和文档检查通过。

不做：不重命名 `_relay_to`，不扩大 wire 协议，不改 Route-A 编排，不在本票拆 scheduler 大文件。

### 票 2：`ENGINE-RESOLVE-01` 引擎、路径、量化和层段能力联合裁决（P0，代码完成，未提交）

目标：一次解析同时产出 engine、model path、quant、runtime 和 layer-range mode，禁止入口各自纠正一遍。

完成定义：

- `.gguf` 不得进入 PyTorch loader；别名在 API、scheduler 和 worker 得到同一答案。
- `load_model`、`switch_model`、自动加载和分布式准备共用 resolver。
- 真实 resolver 行为有直接测试，不能只 monkeypatch。
- `fp32`、CUDA fp16/int8/int4 和 CPU-only 能力转换必须显式，禁止静默改变对拍精度。
- solver reason 在 scheduler/API 层只能追加上下文，不得覆盖原始 reason code 和缺口范围。

2026-10-09 实现与验收记录：

- 新增依赖轻量、不可变的统一 resolver，一次返回 model identity、effective engine、artifact path、effective quant、runtime、layer-range mode 和具名 reason；API 主服务、inference-svc、ModelHost/ModelManager、自动加载及分布式准备消费同一裁决对象，不再在实际 loader 前二次改判。
- 引擎请求别名单源化并 fail-closed；`llama_cpp` / `llama.cpp` / `llama-cpp` / `llama` / `gguf`、`pytorch` / `torch`、`island` / `tp_island` 在 API、task-worker wire、scheduler/worker 工件匹配和 RPC/pipeline node 合同中归一为同一 backend，未知值不再静默回退。
- backend 能力查询也改为 fail-closed：`external_api`、`speculative_assisted`、`relay_middle` 及拼写错误不再被默认映射为 llama.cpp，也不会获得 `FORWARD_LAYERS` 后误入层段拓扑；配置中的未知本地 engine 直接拒绝，不再按 CUDA/CPU 静默退化为 auto。
- 层段模式明确分为 PyTorch `dynamic`、llama.cpp `precut_artifact`、island `none`。通用层段请求按所选引擎保留对应实现；显式 llama.cpp 分布式请求不再被静默改成 PyTorch。
- inference-svc 与 legacy peer 的层段入口已去掉“先加载整模、再加载层段”的峰值错误：PyTorch 直接按 key 物化指定 Safetensors 层段；llama.cpp 先准备整模描述器，再按 manifest 选择预切 GGUF 工件。星状拓扑、master 顺序编排及 D→L / L→L 接力不变。
- 预切 GGUF 工件选择不再只按 `source_layer_range` 猜测：manifest 必须同时给出并通过 `source_model_sha256`、`artifact_sha256` 校验；同目录混放其他模型的同区间工件会被忽略，段文件被篡改会被拒绝，同一源模型出现多个有效同区间工件时 fail-closed，避免按文件名顺序静默选错。
- 段工件选择时强制重新计算工件 SHA，不复用跨次选择的摘要缓存；即使文件被同尺寸替换并恢复 mtime，也会在下一次选择时被拒绝。显式 llama.cpp 请求若给出非 `.gguf` 路径也直接拒绝，不再回退到全局遗留 GGUF。
- `.gguf` 进入 PyTorch 的路径在 resolver、ModelHost 和 ModelManager loader 三层 fail-closed；有注册画像的 model id 在画像路径失效时不再回退到另一个模型的全局遗留路径。
- CPU-only PyTorch 的 fp16/int8/int4 请求在裁决阶段显式转为 fp32；设备画像强制 edge/mobile/ultrabook 使用 CPU 时也执行同一裁决。CUDA 完整模型保留 fp32/fp16/int8/int4，其中 fp32 已真实传入 `torch.float32`；CUDA 动态层段的 int8/int4 请求显式转为 fp16。
- GGUF 的 effective/runtime quant 统一标记为工件所有的 `gguf`，不再把调用方传入的 `fp32` 等标签伪装成实际工件精度；原始请求仍保留在 `requested_quant`。
- 自动加载统一使用 artifact/CUDA preference；Safetensors-only 不再把 `gguf` 作为 PyTorch quant；inference-svc 的运行模式从生产 `RUN_MODE` 初始化，分布式裁决分支不再只存在于测试注入。
- 分布式 `/api/models/load` 省略 `model_id` 时，容量判定现在使用 resolver 已解析出的默认模型标识，不再把 `None` 当作“需求未知”后静默强制整模加载。
- resolver/API/host/manager/inference/capacity/task-worker/pipeline-contract（含 relay manifest 与 llama.cpp 预切工件）回归 `612 passed`，scheduler/TCP 回归 `429 passed`，reshard/inference-routing/relay/cut-layer 邻接回归 `79 passed`；相关模块 `py_compile`、文档检查与 `git diff --check` 通过。该证据是本地代码门，不替代后续真实 CUDA、Android 和跨机发行物验收。
- 复核残余边界：inference-svc 的直接分布式加载端点目前执行联合 resolver，但不执行主 API 的整模容量判定。当前未证明它承担 master 容量编排职责，暂不扩大本票；在票 4 `MODEL-TXN-01` 前先补角色 characterization，若它是公开主控入口，则必须共用同一加载形态决策。

### 票 3：`MODEL-PREFLIGHT-01` 模型与 worker 工件事前一致性（P0，代码完成，未提交）

目标：把 `model_id`、hidden size、tokenizer、artifact SHA、层区间和 segment mode 的一致性检查从每步 offer 热路径前移到准备/加载阶段。

完成定义：

- 选择或加载模型时即判断当前集群是否具备全部匹配工件。
- 不匹配时在进入 pipeline 前具名拒绝，并指出节点、模型和缺失区间。
- 第一阶段只做事前裁决；按需下载和多模型切换另归事务票，避免一次票面同时解决带宽、并发和缓存策略。

实施结果（2026-10-09，已完成）：

- 合同明确区分逻辑模型与物理工件：`source_model_id` / `hidden_size` / `tokenizer_sha256` 描述逻辑模型，原 `model_id` / `artifact_sha256` 继续描述具体 GGUF；`source_model_sha256` 绑定 L→L 各段共同来源的完整 GGUF。
- 自动容量计划和手动计划在 admission 后统一执行 `model_preflight`；校验逻辑模型 ID、hidden width、tokenizer 摘要、源模型摘要、工件摘要、精确层区间、segment mode 和对应的 `llama_cpp/gguf` 物理身份。失败计划清空可执行 assignments，同时保留 `proposed_assignments`、节点明细和 `missing_layer_ranges`。
- `/api/models/prepare-pipeline` 在返回成功前执行同一容量/模型裁决；失败返回具名 HTTP 409，原因包含节点、模型与缺失区间。票 3 完成时仍把“准备不污染现役模型、失败回滚”留给下一票；该缺口现已由票 4 `MODEL-TXN-01` 闭合。
- Route-A assignment 固化 `stage_model_identity` 与 `stage_capability_sha256`；token 循环不再逐 stage 扫描实时能力。运行前仍复核 readiness、工件合同和 provider；旧 `layer_ranges` 路径继续兼容，但只在进入循环前解析一次物理身份。
- PyTorch 描述符同时接受正式资产的 `schema_version` 与兼容清单的 `schema`，并现场重算 `tokenizer.json` 摘要核对清单，避免陈旧清单放行；GGUF 描述符从头部读取 hidden width，从旁车裁层 manifest 或注册表关联的已验 tokenizer 资产取得摘要，并用源 GGUF SHA 约束 L→L 各段同源。
- PC/Android 能力广告均支持新三元组且要求全有或全无；旧 manifest 仍可握手和广告，但一旦固定工件被选中而缺合同字段，会以 `model_preflight_contract_incomplete` 具名拒绝。切层脚本新增 `--source-model-id` 与 `--tokenizer-sha256`，新产物始终写 `hidden_size`。
- 边界保持不变：未引入 worker→worker 数据连接，星状拓扑不变；D→L / L→L 多段接力不变；本票不实现按需下载、多模型切换、排队策略或事务回滚。
- 验证：Python 模型/容量/协议/API/调度/GGUF 专项 `529 passed`；切层生产端 `38 passed`；Android 三个相关单测类 `43 tests` 全部通过；相关 Python 模块 `py_compile` 与主仓/Android `git diff --check` 通过。

### 票 4：`MODEL-TXN-01` 模型与 pipeline 资源原子切换（P0/P1，代码完成，未提交）

目标：统一模型、pipeline preparation、engine、quant、KV、RPC/relay session 和远端 assignment 的切换、提交与回滚。

完成定义：

- 准备阶段不污染当前可服务模型；全部节点 ready 后才提交。
- 任一失败或超时回滚到原模型和原 assignment，不留下半加载、旧 KV 或 orphan session。
- 多请求要求不同模型时有明确的拒绝或排队策略；不允许执行中卸载。
- load、switch、自动恢复和重连走同一事务状态机。

实施结果（2026-10-10，已完成）：

- `ModelHost` 新增独立候选 runtime，生命周期统一为 `prepare → materialize → commit → finalize`，任一提交前失败走 `abort`；候选准备和层段物化不替换现役 manager，commit 后仍保留旧 manager 作为精确回滚点，只有 finalize 才释放旧资源。
- master 与 worker 使用 prepare/commit 两阶段协议：worker 全部 prepared 后才提交各自候选；master 本地候选提交、reshard CAS 和 active plan 发布形成全局提交栅栏。任一步失败或超时都会恢复原 manager、原 assignment/ACK/retry 视图和原 active plan，不再留下“新模型已加载、旧控制面仍生效”或相反的半提交状态。
- pipeline 配置、engine/quant 全局配置、KV cache 与会话失效只在全局提交成功后更新；prepare、preflight、abort 不提前污染现役状态。实际 quant 以已提交 runtime 为准，避免请求 fp16、CPU 实际 fp32时继续对外宣称 fp16。整模 load/switch 失败也不再预先清空 assignment。
- 完整模型与层段状态拆开：`model_loaded=True` 只表示本地完整模型可执行整请求；`runtime_materialized=True` 可表示任意已物化 runtime；`pipeline_prepared=True` 表示 distributed-only runtime。partial PyTorch/GGUF 不再被 `/api/models/current`、普通 chat、SSE/interactive 或 inference-svc 当成完整模型直接执行，`local_only` 会在进入 `chat/chat_stream` 前 fail-closed。
- 终局清理从单个 mutable transaction 中拆出为持久化 cleanup ledger，记录 master/worker 的 `abort|finalize` 债务、精确 candidate/generation/cleanup identity、重试与重连状态。master 重启恢复 worker 债务；worker 断线不会让离线债务永久阻塞其余在线拓扑，重连时必须先重放 cleanup，收到精确 ACK 后才重新同步 assignment。
- commit/abort/finalize 均补齐系统级幂等：ready ACK 丢失后重复 commit（含 PyTorch 与 `relay_middle`）只重发 canonical ready ACK，绝不回滚已提交候选；worker cleanup 失败前不删除 rollback/prepared 凭据；master 本地 cleanup 失败进入后台重试并阻止新的冲突事务。
- 并发选择不同模型采用具名拒绝而非隐式覆盖：活动事务返回 `MODEL_TXN_CONFLICT`；master 或当前在线 worker 的前序清理未收敛时返回 `MODEL_TXN_CLEANUP_PENDING`。按需下载与跨请求排队仍未实现，继续作为后续能力票处理。
- 星状拓扑保持不变：未引入 worker→worker 控制或数据连接；master 仍是唯一协调与转发中心，D→L / L→L 多段接力、Route-A 顺序编排和既有 wire 语义均未改变。
- 最终本地回归：scheduler/assignment/capacity/Route-A `375 passed`；API/model unload/ModelHost `104 passed`；inference-service `121 passed`；相关模块 `py_compile` 与目标 `git diff --check` 通过。该证据为本地代码门，不替代后续真实跨机、真实模型和发行物验收。

### 票 14：`REFACTOR-DECISION-01` 单一事实源重构决策（P2）

前置：票 1～8 的行为边界稳定，关键 characterization tests 已建立，且剩余问题确实不能由局部修复安全收敛。

决策通过后：

- 从稳定提交或标记点创建独立干净分支，例如 `refactor/engine-plan-ssot`。
- 不把旧实验提交串、临时兼容层和未验证补丁直接合入新分支。
- 优先抽取声明式 `engine × runtime capability`、不可变 pipeline plan、结构化 reason 和会话上下文服务。
- 重构每一阶段都必须保持星状拓扑和 D→L / L→L 多段接力，使用行为测试对照旧稳定基线。

不得把“大文件拆分”“换框架”或“重新命名类”本身当作重构完成；完成标准是事实源减少、事务边界清晰、分叉判据消失，且产品证据不退化。

## 8. 执行纪律

1. 每张票先写不变量、触发条件和完成定义，再改代码。
2. 已闭合项只有出现新反证才重开；新证据必须说明旧证据为什么失效。
3. 条件风险先写最小复现或 characterization test，不能直接按生产 BUG 排最高优先级。
4. 代码票和外部验收票分开关单；两者通过里程碑关联。
5. 任一修复若引入新的事实源、隐式 fallback 或第二套状态机，默认视为未完成。
6. 当前不提交、不新建重构分支；第一票已经验证通过，提交边界由后续指令决定。
