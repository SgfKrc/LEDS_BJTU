## P0 阻断项

- **运行时去 torch 化的剩余门**：profile contract 已拆开，但默认 CPU SLIM 仍保持 `torch_cpu` 兼容行为；发行构建必须显式选择 `llama_cpp_only`，并让启动器/安装 manifest/能力广告使用同一 profile。Edge 入口的动态 import 与干净 venv 门仍未完成。
- **Linux 最小变体**：`packaging/packaging/linux/build-deb.sh:206-215` 当前无条件装 torch，且 `control-cpu` 宣传 PyTorch 备选引擎（`packaging/packaging/linux/control-cpu:14-16`）。应补 `llama-cpp-only`/edge 变体：只带受管 `llama-quantize`、`llama-cpp-python`（或纯 native RPC worker）、FastAPI/TUI 所需轻依赖；安装后执行 `python -c 'import importlib.util; assert ... torch is None'` 作为硬门。
- **动态导入审计**：对 Edge 入口及 `src/` 做静态扫描和干净 venv 运行扫描，禁止直接/间接 import `torch`, `transformers`, `accelerate`, `bitsandbytes`。不能只依赖 PyInstaller `excludes`，因为 SLIM 运行的是源码 `uvicorn src.api_server:app`（`packaging/packaging/qlh_launcher.py:199-218`）。
- **包体边界复验**：Windows/Linux 构建后逐文件检查不得出现 torch、CUDA DLL、开发脚本、测试、agent 配置；现有 `install_manifest.py` 签名清单只证明文件完整性，不证明依赖闭包，需增加依赖/ELF/PE 扫描报告并纳入发布附件。

## P1 平台审计与修复

### Windows

- 为 SLIM 增加 CPU-GGUF 首启路径：无网络或无 Python 时应能给出可操作失败，不得偷偷创建 torch runtime；外部 runtime 目录需记录 engine/profile 与版本锁。
- `qlh-slim.spec:59-64` 的排除列表应配套静态 import 检查；对 `_internal/src` 做 `compileall`、只读 CLI、API health 和 GGUF 单轮生成 smoke。

### Linux

- `build-deb.sh:25` 版本号与 `packaging/packaging/version.txt`、Launcher 版本存在漂移风险；构建前应由单一版本源生成 `.deb`/manifest/服务文件。
- `build-deb.sh:190-202` 在 ensurepip 不可用时在线下载 `get-pip.py`；最小离线发行必须提供受管 bootstrap 方案或明确把联网安装列为安装前置，并将 SHA-256/代理/证书失败写入验收门。
- `.deb` 需在 Ubuntu 22.04、Debian 12 原生主机分别做 `dpkg-deb --contents`、`ldd`、安装/升级/卸载、systemd 无头启动、桌面/TUI/API health 和 GGUF 生成；WSL 只能作为构建辅助，不能替代运行时证据。

### Android

- `android/app/build.gradle.kts:43-108` 当前只有 arm64 ABI；需明确设备矩阵（16 KB page、Android API、arm64 真机/模拟器）和 Full/Lite 包的模型/worker 能力差异。
- `scripts/android_validation.py:226-242` 的 `arm64_native_worker` 目前只由“安装+启动+ABI”推导，不能证明 JNI RPC worker 实际运行。应增加 logcat/JNI `nativeRpcStart`、模型分片请求、连续生成、取消、重连、热/电量采样证据。
- `android/app/src/main/AndroidManifest.xml` 开启 `usesCleartextTraffic` 和多个前台服务；发布前必须做 TLS/网络安全配置、最小权限审计、签名/anti-debug/备份策略审计，并验证 release APK 的 native 库和 proguard 规则。

### 本轮排除的 5 个真实障碍（**都会被重踩**，务必留档）

1. **Y700 部署缺依赖**：`llama_engine` / `relay_segment_info` / `src.relay_transport` /
   `src.relay_hidden_quant` 都不在设备上（只有旧的 `relay_transport`）⇒ 逐个 `scp` 补齐。
2. **Y700 的 `relay_mid_service.py` 是旧版**：遇到协议错误后 `reset()` ⇒ **进程退出**
   （日志现象是 `~llama_context` 析构 + `pgrep` 空），所以**探活一次就把服务弄死**。
   ⇒ 必须同步新版脚本（新版是 fail-closed 但**不退出**）。
3. ★ **Y700 的 llama.cpp 是 b8054**（2026-09-21 构建），与当前 shim 源码 **ABI 不匹配**
   ⇒ `GGML_ASSERT(lid < model.hparams.n_layer())` 崩溃。
   ⚠️ 关键判据：**新 shim 配 `qwen2` 也照崩**（交叉实验确认）⇒ 是 ABI 问题而**不是** hybrid 特有问题。
   ⇒ **在 Termux 上原生编译当前 llama.cpp**（`clang` + `cmake` 都现成，**不需要 NDK**）：
   `cmake -DBUILD_SHARED_LIBS=ON -DGGML_OPENMP=ON …` + `make -j8 llama`；
   ⚠️ 新版 `.so` 带 **SONAME**（`libllama.so.0`）⇒ 必须建符号链接；
   ⚠️ `cp` 复制**符号链接**只会得到 17 字节文件 ⇒ 用 `cp -L`。
4. ★ **Surface 的 `llama_cpp 0.3.35` 不支持 `qwen35`**（`llama_decode rc=-1`）。
   ⇒ **不需要重编**：`relay_mid_service.py` 本来就有 **`ShimTailRunner`**
   （`:483-490` —— **加了 `--keep-head-shim` 就走它**）⇒ Surface 只需在 tail 启动参数里
   加 `--keep-head-shim <我们的 dll>` + `--dll-dir <同目录>`，即用上已支持 hybrid 的构建。
5. **Y700 服务被 Android 杀掉**（`nohup` 不够）⇒ 用 **`setsid` + `termux-wake-lock`**。

**两个平台层小坑**：Windows 上 `Start-Process` 起的服务与 `ssh -L` 隧道都会随 shell 回收
⇒ Surface 用 **`schtasks`**（先写 `.bat`，因为 `/tr` 有 261 字符上限）；隧道用**持久后台进程**。

**方法论收获**：定位这类"数值错但不报错"的问题，**同机对照 + 梯度实验**最有效 ——
先做**同机三段 → PASS** 把范围锁到"跨机引入"，再**只让一台跨机**锁到具体环节。
否则极易在错误的层面改代码。
