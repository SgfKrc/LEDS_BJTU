# 桌面赛博哥特与安卓原生界面复核

> 复核日期：2026-08-23  
> 状态：现行审计结论；`CY-PKG-01` 本机开发门已完成，真实干净机/安装包首启仍后置
> 范围：`frontend_cybergothic/`、`frontend/`、`packaging/`、`src/api_server.py` 与 Android Compose UI

## 1. 结论

1. `frontend_cybergothic` 已是唯一的**产品前端源代码目标**，旧 `frontend/` 只保留为行为和接口迁移对照；`api_server.py`、Windows 主启动器、CPU/CUDA/Slim/Linux 打包规格现已默认使用 `frontend_cybergothic/dist`。旧前端只能通过显式 `QLH_FRONTEND_DIST` 覆盖做迁移对照。
2. `packaging/launcher_cybergothic.py` 已可服务 `frontend_cybergothic/dist`、反代 `/api/*`，并在 Windows 以 Edge WebView2 的 pywebview 窗口打开。这证明新前端与 PC pywebview **技术兼容**，但它是独立启动路径，不等同于默认 Launcher/安装包已经切换。
3. Android 仍保留原有的原生 Material 3 极简产品形态：深色黑底白字、浅色白底黑字、四个底部导航页、轻量列表和表单，未采用桌面版 canvas 场景、哥特装饰或高密度侧栏。这是面向触控、小屏和电量/性能约束的**明确设计选择**，不是新桌面风格未同步的缺陷。
4. 端间应统一的是能力语义、认证/失败边界和资产主权，不应强行统一页面构图。Android 仍有明显的运营控制面差距，应按移动端价值另行排期；不得以“视觉一致”为由把桌面运维台搬到手机。

## 2. 桌面 pywebview 与赛博哥特前端

| 核查项 | 证据 | 结论 |
|---|---|---|
| 新前端路由与视觉系统 | `frontend_cybergothic/src/app/routes.tsx`、`sceneRegistry.ts`、`AppShell.tsx` | Workbench、Overview、Tasks、Image、Models、Downloads、Cluster、Account、Audit、Settings、Help 等产品页已在赛博哥特前端实现。 |
| 独立桌面壳 | `packaging/launcher_cybergothic.py` | 可解析开发/打包后的 `frontend_cybergothic/dist`，本地反代 API，并以 pywebview/Edge WebView2 打开 `QLH · Cybergothic Console`。 |
| 默认桌面壳 | `packaging/launcher.py` | 主 Launcher 同样可用 pywebview，但窗口指向主后端服务，不负责选择或服务赛博哥特产物。 |
| 默认后端静态页 | `src/api_server.py` | 默认解析并挂载 `frontend_cybergothic/dist`；`QLH_FRONTEND_DIST` 是显式兼容覆盖。 |
| Windows/Linux 构建输入 | `packaging/qlh-cpu.spec`、`qlh-cuda.spec`、`qlh-slim.spec`、`packaging/linux/build-deb.sh` | 统一收集/复制 `frontend_cybergothic/dist`；旧前端不再进入标准默认包。 |

### 2.1 `CY-PKG-01` 实施记录（2026-08-23）

**结果**：已让“赛博哥特是唯一产品前端”的事实进入标准源启动、pywebview Launcher 和 Windows/Linux 安装包输入，而不是只存在于独立开发启动器。

**开发边界**：

- 标准静态页与打包资源默认输入已改为 `frontend_cybergothic/dist`；旧前端仅可通过 `QLH_FRONTEND_DIST` 显式覆盖。
- `api_server.py`、主 Launcher 与 `launcher_cybergothic.py` 现使用同一份产品构建产物，主 Launcher 通过后端静态挂载打开新前端，独立壳继续提供本地反代/调试入口。
- CPU/CUDA/Slim spec、Linux `.deb` 脚本和构建前置检查已切换，不改变 API、Android UI 或旧前端行为对照。
- 新增源码/冻结包路径、显式兼容覆盖和六个标准构建输入的自动化检查；真实干净 Windows/WebView2 与 Linux `.deb` 首启仍归发布验收。

**开发门结果**：开发模式和标准构建输入均默认加载赛博哥特首页；旧 `frontend/dist` 不再被默认静态挂载或打包；入口/资源路径/反代契约有定向回归；真实安装包首启记录后置到 E8。

## 3. Android 原生极简风复核

| 核查项 | 证据 | 结论 |
|---|---|---|
| 色彩与主题 | `android/app/src/main/java/com/qlh/inference/ui/theme/Color.kt`、`Theme.kt` | 明确是中性黑白 Material 3 主题：深色近黑底+浅色文字，浅色白底+深色文字；状态色不承担主题主色。 |
| 导航与布局 | `MainActivity.kt` | 仅“对话、图像、会话、设置”四个底部导航页，使用原生 `Scaffold`/`NavigationBar`，适合窄屏单手操作。 |
| 页面组件 | `ui/ChatScreen.kt`、`DiffusionScreen.kt`、`SessionListScreen.kt`、`SettingsScreen.kt`、`components/Common.kt` | 以紧凑列表、表单、状态条和系统组件为主，没有桌面 canvas、哥特装饰、固定三栏或高密度面板。 |

**产品决策**：Android 不复制赛博哥特桌面视觉。移动端应保持“原生、低干扰、弱网可读、触控优先”的极简风，同时复用深/浅色可读性、术语、Logo、状态语义与无障碍要求。未来可在启动页、图标和少量材质细节上体现品牌，但不得以背景动画或复杂画布牺牲耗电、滚动和信息可读性。

## 4. 功能映射与真实差距

| PC 赛博哥特页 | Android 对应 | 当前结论 |
|---|---|---|
| Workbench（会话、集群上下文、任务状态） | 对话 + 会话分列 | 基础会话具备；缺集群上下文、任务队列和流水线可观测性。 |
| Overview / Tasks / Activity | 设置中的有限状态、诊断和脱敏日志 | 无完整运营总览、任务尝试、审计时间线；这是 PC 控制台优先能力。 |
| Image Studio | `DiffusionScreen` | 已有远程 SD 请求、参考图/结果等开发路径；没有桌面资产目录、导入/许可、Inpaint/指令编辑、四宫格工作流和分布式遥测的完整操作面。 |
| Models / Downloads | Settings 中的 SAF、本地模型、主节点 GGUF Range/SHA 下载和只读模型舰队 | 已不再是“仅手工 SAF”；模型舰队可有界查看运行态、注册表、资产与已验签 GGUF，仍缺来源/许可/工件登记编辑、多资产部署和 Sidecar 管理。 |
| Cluster | 无专门页 | Full Worker、bootstrap/presence 有协议和开发门；没有面向用户的节点、角色、容量、层计划和入群管理控制面。 |
| Account | Keystore 会话/登录开发路径 | 已有凭据与会话基础，不等同于 Auth App QR/字符串引导、恢复码、成员和 Tailscale 绑定的完整账户页。 |
| Audit / Help | 无专门页 | 无审计工单、策略核验和帮助中心；移动端可后续提供轻量只读视图，不应复制桌面工作台。 |
| Settings | 原生设置页 | 覆盖连接、模型、更新、日志和诊断的一部分；RAG 高级控制、模型/集群运维、账户管理仍在 PC。 |

### 4.1 状态口径

- Android Full 的 `mtmd`/Gemma4、Worker Stage executor、远程 SD、GGUF Range/SHA 下载、Keystore、更新和脱敏日志均已有开发门；真实设备内存、图片语义、后台存活、网络切换、长时温控和发布链路仍待验收。
- Android Lite 继续是远程轻量入口，不承接 Worker、本地多模态或本地 SD。
- 以上移动端缺口是功能/验收差距，不是赛博哥特视觉迁移任务；任何新增 Android 票应优先补“移动端真正需要且可安全操作”的能力。
- `AND-CTRL-01/02` 已补齐只读集群概览和模型舰队；后续审计、账户与 owner/admin 管理分别采用最小权限的 `AND-CTRL-03..05`，不把桌面高风险操作复制到移动端。

## 5. 自动化工程的边界补充

工程自动化不只指测试。QLH 已将以下“懒人工具”纳入工程交付面：

| 工具类别 | 代表入口 | 解决的重复工作 |
|---|---|---|
| 隔离环境与依赖 | `scripts/setup_envs.py`、`setup_test_env.py`、各 Sidecar 环境脚本 | 按用途创建并检查测试、TUI、Qwen3、Gemma4 等隔离环境，避免主环境污染和手工配错依赖。 |
| 仿真、实验与质量门 | `scripts/run_simulation.py`、`run_experiments.py`、`experiment_core/`、SD/LLM 质量门 | 固定输入、调度、收集、报告和失败边界，避免靠手工复现并把单次绿灯误当结论。 |
| 离线资产与恢复 | `build_offline_bundle.py`、`package_sd15_assets.py`、各校验脚本 | 将模型/许可证/manifest/摘要打包、签名、校验和恢复，降低断网部署和资产迁移的人工成本。 |
| 交付与维护 | `generate_latest_manifest.py`、Launcher 诊断/更新、`tools/ssh_sync_deployment.py` | 生成更新清单、诊断安装环境、受控同步补丁，减少重复发布、排障和双机同步操作。 |
| 文档与接口治理 | `api_gap_scan.py`、文档维护 Agent 质量门 | 机械扫描接口归属、链接/证据与检索质量；结论仍受脚本门、人工复核和事实源约束。 |

这些工具与产品功能共享同一条原则：把资产、环境和执行证据留在用户可控制的本地边界内，并使重复操作可审计、可重放、可恢复。
