# 跨框架逐层接力：量化与加速手段的解耦分析（2026-09-16）

> 性质：**架构分析 + 现状核实**。回答三个问题：
> ① 跨框架接力需要考虑量化手段吗？② 量化方式不同，误差是否可接受？③ 加速手段能否"两边各玩各的"？
>
> 方法：基于 `src/relay_contract.py` / `relay_planner.py` 的合同约束 + 已有 relay 实测证据。**本文不新增实验**，只做推理与空白标注。

---

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| **① 要考虑量化吗** | **要，但不是"必须两侧相同"** —— 合同已明确允许两侧产物摘要不同（`relay_contract.py:211-216`）。真正的约束是**逻辑模型一致**（`:192`）、**`n_embd` 一致**（`:196`）、**`block_count`/`nextn` 布局匹配**（`:213-215`） |
| **② 量化不同误差可接受吗** | **已有证据支持"可接受"，但只覆盖了一侧低比特**：D→L 实测 **f16 裁层 + f32 torch hidden → 修复后 141/141**（严格 argmax）。**两侧同时低比特（NF4 torch + Q4_K_M llama.cpp）从未测过** —— 这是明确空白 |
| **③ 加速手段能各玩各的吗** | **大部分能，但"接口无关"≠"数值无关"**。KV cache / batching / RPC 天然解耦；**flash_attn、tf32、不同 attention 实现会改变浮点求和顺序** → 必须各自过一遍接力对拍，不能想当然 |

**一句话**：**接力点传的是 hidden state（激活），不是权重** —— 所以两侧权重格式**制度上可以不同**；但两侧**权重误差不同会各自累积到同一个 hidden 上**，因此"能否接受"必须**逐组合实测**，而这正是当前最大的空白。

## 1. 接力接口的本质（已核实）

### 1.1 传的是什么

`relay_contract.py:11-13` 三句话定义了全部设计：

```
* **boundary**  -- the engine-specific last layer is never handed off; hidden crosses only ...
* **acceptance** -- decided by per-token **argmax**, never by a cosine threshold;
```

即：

| 项 | 内容 | 证据 |
| --- | --- | --- |
| **交接物** | **hidden state 原始张量**（`n_embd × dtype`），**不是 token id、不是权重** | `RelayHiddenSpec` `:113-125` |
| **支持的 hidden dtype** | **仅 `float32`(4B) / `float16`(2B)** —— `_HIDDEN_WIDTH_BYTES` `:43` | `:124` 的 `supported` 判定 |
| **判据** | **per-token argmax**（行为等价），**明确不用 cosine 阈值** | `:30-31` `RELAY_ACCEPTANCE = "per_token_argmax"` |
| **诊断档** | `top_k_tolerant_argmax`（仅诊断，非准入） | `:35` |
| **不交接** | 引擎特有的最后一层（`boundary`） | `:11-12` |

### 1.2 合同强制的"一致性"与"允许的差异"

**必须一致**（否则拒绝）：

| 约束 | 位置 |
| --- | --- |
| **逻辑模型摘要** `model_sha256` | `:192` |
| **`n_embd`** | `:196` |
| **`nextn_predict_layers`**（MTP 层数，qwen3.5 风格通常 1） | `:215` |
| **`block_count` 关系**：`downstream = upstream - cut` | `:213-216` |
| hidden spec 可支持 | `:207` |

**明确允许不同**：

> `# A cut artifact is expected to differ in digest, but its GGUF layout must match the ...`（`:211-212`）

**→ 这就是"两侧量化可以不同"的制度性依据**：裁层产物（含其量化格式）**摘要允许不同**，只要 **GGUF 布局（block_count / n_embd / nextn）匹配**。

### 1.3 精度维度在哪里（关键区分）

```
权重（每侧私有）──┐
                  ├─→ 该侧 layer 计算 ─→ hidden（跨框架交接，dtype 受限 f32/f16）
激活/缓存（每侧私有）┘
```

- **两侧权重格式**：**接口不关心**（`model_sha256` 校验的是**逻辑模型身份**，不是量化格式）；
- **hidden dtype**：**接口强制**（仅 f32/f16）；
- **→ 所以量化对接口的影响路径是**：**各侧权重的量化误差 → 各自 layer 输出偏差 → 累加到同一个 hidden → 影响下游 argmax**。

## 2. 量化在接力中的实际影响

### 2.1 两侧量化体系本就不同（详见性能调研 §2）

| | PyTorch 侧（上游） | llama.cpp 侧（下游） |
| --- | --- | --- |
| 可用手段 | bitsandbytes **NF4**（`int4`）/ **llm.int8**（`int8`）/ fp16 | **GGUF k-quant**（Q4_K_M 等，**离线预量化**） |
| 运行时 | CUDA + bnb kernel（**无 CPU 实现**） | ggml（CPU/集显/Metal/Android） |
| 我们的实际用法 | `model_module.py:318-343` 真调 bnb | `llama_engine.py:46-52` **只选文件名、贴标签** |

**关键**：D→L 接力天然就是"**两种不同量化体系各管一段**"，这不是设计缺陷，而是**跨框架接力的定义**。

### 2.2 已有实测：只覆盖"一侧低比特"

| 实验 | 上游 torch | 下游 llama.cpp | 结果 |
| --- | --- | --- | --- |
| **f16 裁层（修复后）** | hidden **f32** | **f16** 裁层 GGUF | ✅ **141/141**（cosine_min 0.9999995） |
| **f32 对照** | hidden f32 | **f32** 裁层 GGUF | ✅ **141/141**（cosine_min 0.999999） |
| **f16 裁层（修复前）** | hidden f32 | f16 裁层 GGUF | ❌ **132/141**（首分歧 18） |

证据：`local_docs/CORE-RELAY-XFRAME-01-dl-fixed-prefill-141-2026-09-16.json`、`-dl-long-f16-*.json`、`-dl-long-f32-*.json`（`upstream_engine=pytorch` / `downstream_engine=llama.cpp`）。

**两条重要结论**：

1. **精度确实影响一致性** —— 修复前 f16 只有 132/141；
2. **但精度差异不是结构性障碍** —— 修掉 `pos` 越界根因（#28963）后，**f16 也能 141/141**（严格 argmax）。
   即：**只要没有实现 bug，f16 权重差异可被 argmax 判据吸收**。

> ⚠️ 注意 `cosine_min ≈ 0.9999995`（而非 1.0）说明：**两侧数值路径本就不同**（不同框架、不同 kernel），**判据必须用 argmax 而非 bitwise/cosine** —— 这与 `:11-13` 的设计一致。

### 2.3 明确的空白（最重要的一节）

**以下组合从未测过**：

| # | 组合 | 状态 | 风险 |
| --- | --- | --- | --- |
| **E2** | 上游 f32/f16 torch + 下游 **Q4_K_M**（真实低比特 k-quant） | ❌ **未测** | Q4_K_M（~4.9 bpw）权重误差远大于 f16 → 下游 layer 输出偏差放大 |
| **E3** | 上游 **NF4** torch（`int4`）+ 下游 f16 | ❌ **未测** | NF4 是**按标准正态分位**的非均匀码本，且 bnb 通常**不量化 embedding/lm_head** → 与 GGUF 侧处理不同 |
| **E4** | 上游 **NF4** + 下游 **Q4_K_M**（两侧都低比特） | ❌ **未测** ← **最关键** | 两侧误差**独立累积**到同一 hidden，无法互相抵消 |
| **E5** | 开 `flash_attn` 后是否仍 141/141 | ❌ **未测** | 见 §3.2 |
| **E6** | 开 `cache_prompt` 后多轮一致性 | ❌ **未测** | 见 §3.3 |

**E4 尤其关键**：如果两侧都低比特后 argmax 分歧显著上升，那么"跨框架接力 + 低比特"这条路就需要重新设计（例如：**接力边界两侧强制用同精度**，或**在接力点做误差补偿**）。

## 3. 加速手段能否"两边各玩各的"

### 3.1 判据：是否改变"层间接口的数值语义"

用户直觉是对的 —— **大部分加速手段确实可以两边独立**。但要精确化：**"接口无关"不等于"数值无关"**。

### 3.2 三档分类

**✅ 第一档：接口与数值都无关（安全各玩各的）**

| 手段 | 为什么安全 |
| --- | --- |
| **KV cache / prefix cache** | 只改变"是否重算前缀"，**不改变每步计算内容**；但**须保证被复用前缀的 KV 与重算一致**（这正是 `cache_unit_layout` 的"前缀稳定性自检"要防的） |
| **batching / continuous batching** | 改变**何时**算，不改变**算什么**；但**padding/attention mask 实现不当会引入差异** |
| **RPC / 跨机传输** | 只搬运张量 |
| **CUDA Graph** | 捕获的图与 eager **语义相同**（前提：无动态 shape 副作用） |
| **每侧权重格式** | 制度上允许（§1.2），**但会改变该侧测值** → 属于 §2.3 的待验证项 |

**⚠️ 第二档：接口无关，但数值会变（必须各自对拍）**

| 手段 | 风险机理 |
| --- | --- |
| **`flash_attn=True`** | 与 naive attention **浮点求和顺序不同** → 输出位级不同。⚠️ **这与 #28963 的 `embd` 位级非确定性是同类问题** |
| **`tf32` / fp16 累加** | 精度截断改变结果 |
| **不同的 SDPA 后端**（math / flash / mem-efficient） | 同上 |
| **KV cache 量化**（`--cache-type-k/v q8_0`） | **KV 被量化** → 长上下文累积偏差 |
| **算子融合 / torch.compile** | 融合改变运算顺序与精度（`torch.compile` 默认关闭，见性能调研 §3） |

**❌ 第三档：不可解耦（接口本身）**

| 项 | 原因 |
| --- | --- |
| **hidden 的 `n_embd` / dtype** | 合同强制（`:196`、`:43`） |
| **层边界（cut 定义）** | 必须 `downstream = upstream - cut`（`:213-216`） |
| **`nextn` (MTP) 布局** | 必须一致（`:215`） |
| **RoPE / M-RoPE 的 `pos` 处理** | #28963 的教训：`pos` 数组语义错位会让整条接力崩掉 |

### 3.3 对本项目的直接含义

1. **"两边各玩各的"成立，但需要一个前提**：**每个加速组合都要各自过一遍接力对拍**。因为 argmax 判据吸收的是"小幅数值扰动"，而 flash_attn 类的扰动**幅度未知**；
2. **`cache_prompt=True` 要特别小心**：它复用 KV，而 KV 是按**某一侧**的数值路径算出来的。跨框架接力下，下游复用的 KV 若来自不同路径，可能与重算不一致 → **正好是 `cache_unit_layout` 的"前缀稳定性自检"要拦的场景**（该自检目前只在**外置 harness**，未接主仓生产，见性能调研 §1.4）；
3. **`embd` 注入路径已被证明进程内位级非确定**（#28963）→ 这意味着**接力两侧的"同一输入"本身就可能位级不同**，所以**只有 argmax 类判据是现实的**。

## 4. 建议的实验设计（按优先级）

| 优先级 | 实验 | 目的 | 预期判据 |
| ---: | --- | --- | --- |
| **1** | **E2**：上游 f32 torch + 下游 **Q4_K_M** 裁层 | 验证"下游真实低比特"是否仍 141/141 | 严格 argmax；若 < 141，记录首次分歧位置 |
| **2** | **E5**：在已通过的 f16 组合上开 **`flash_attn=True`** | 验证算子级加速是否破坏接力 | 对比开/关的 argmax 序列与 cosine |
| **3** | **E4**：上游 **NF4** + 下游 **Q4_K_M** | 两侧都低比特的极限 | **这是"跨框架+低比特"是否可行的分水岭** |
| **4** | **E6**：`cache_prompt=True` 多轮对话一致性 | 前缀复用是否跨框架可靠 | 第 N 轮 argmax 与前缀重算一致 |
| **5** | **E3**：上游 NF4 + 下游 f16 | 隔离"上游低比特"的贡献 | 与 E2 对照，判断误差主要来自哪侧 |

**通用要求**（沿用现有纪律）：

- 判据**只用 per-token argmax**，cosine / top-k 交叠仅作诊断；
- **两侧都必须固定 commit 与产物 sha256**（现有证据 JSON 已含 `baseline_sha256` / `relay_sha256`）；
- 对照组必须包含**同组合的整模**（现有做法：`qwen35-2b-f16.gguf` 整模 vs 裁层）；
- **采样必须单侧**（D→L 采样矩阵已证：T>0 时共享 seed 非充分，见 `-dl-sampling-matrix-*.json`）。

## 5. 设计建议

1. **把"精度组合"写进接力合同的元数据**：`RelayModelIdentity` 已有 `model_sha256`，建议**再记 `quant_label`**（如 `f16` / `Q4_K_M` / `nf4`），并在证据里强制记录 —— 否则将来无法判断某个 141/141 是在什么精度下取得的；
2. **接力准入应该按"精度组合"维度开闸**，而不是"通过了就都通过"：`f16+f16` 通过 ≠ `NF4+Q4_K_M` 通过；
3. **"前缀稳定性自检"应从外置 harness 纳入主仓**：跨框架 + 前缀复用的组合，风险高于单框架；
4. **不要在接力边界引入超出 f32/f16 的 hidden 格式**（合同目前只支持这两种，`:43` —— 这实际上是**保护**）；
5. **加速手段上线前必须过接力对拍**：`flash_attn` / `KV cache 量化` / `torch.compile` 都属于第 2 档，**不能因为"单侧能跑"就默认接力也能跑**。

## 7. 未验证声明

1. **本文未运行任何实验**，E2–E6 全部为**建议**；
2. **E2/E3/E4/E5/E6 的状态为"未测"** —— 依据是对 `local_docs/CORE-RELAY-*` 证据文件与 `docs/跨框架层接力重启评估-2026-09-15.md` 的检索，**未穷尽**所有历史实验目录（`build/` 为 gitignored 的实验区，可能另有未归档数据）；
3. **"flash_attn 会改变数值"是基于浮点求和顺序的通用推理**，未在本项目实测；
4. **NF4 是否量化 embedding/lm_head** 未逐项核实（bitsandbytes 行为依版本而定），故 E3/E4 的风险描述为**待验证**；
5. 本文未评估**多模态（mmproj）**路径的接力一致性。
