# QLH 定位与模块归属终局决策（2026-09-14）

> 状态：**生效**（用户指示"必须现在敲定"；v2 修正见 §2 注）。本文档为模块归属的唯一裁决依据，冲突表述以本文为准。
> 创建日期：2026-09-14（v2 同日修正）
> 依据：五轮清理与审计 + 用户两轮指示（首轮"拆除管理/引擎两模块"→ **修正："引擎和管理器都放主仓；控制面与数据面虽分离但仍属同一项目；产品壳放支线；主做 TUI"**）。

## 1. 主项目定位（最终裁定）

**主项目 QLH = 轻量推理系统：引擎（数据面）+ 管理器（控制面），同仓同项目。**

- **一句话**：在边缘设备（无/弱 GPU）上跑轻量模型的完整系统——**数据面（双引擎）**：**L 档 = GGUF/llama.cpp 轻量引擎**（单机推理 + TUI 对话；无 torch，120MB venv 实测）与 **D 档 = PyTorch 分层分布式引擎**（层拆分 / 层流水线 / 多节点；**llama.cpp 不能做分层分布式推理，PyTorch 不抛弃**）——**按设备画像选档**；**控制面**（管理器：调度 / 集群 / 节点 / 控制入口）**架构分层、工程同仓**。
- **主交付（重心）**：**TUI 对话**——`qlh chat`（复用零第三方 `tui_chat`/`tui_sse`/`tui_shared` + llama.cpp 本地直连；`qlh_edge` 最小 HTTP 已备）。当前实现已接近，打通即交付。
- **唯一拆出物**：**产品壳**（前端/Android/打包）→ 支线。
- **纪律**：控制面与数据面在**代码组织上分层**（目录/包可辨识、依赖单向：控制面可调用数据面，反之禁止），**不拆仓、不拆 CI**；产品壳与知识库不再占主仓。新增功能准入问句："它服务这套推理系统（引擎或管理器）吗？"

## 2. 归属定案（两部分同仓 + 支线独立）

| 归属 | 层 | 角色 | 当前代码映射（文件级） |
| --- | --- | --- | --- |
| **主仓·数据面** | **QLH Engine（双档）** | **L 档（GGUF/轻量）**：跑模型 + 优化 + 对话面；**D 档（PyTorch/分布式）**：分层分布式推理 | **L 档**：`llama_engine.py` · `qlh_edge.py` · `paged_kv_cache.py` · `cache_unit_layout.py` · `speculative.py` · `tui_chat.py`/`tui_sse.py`/`tui_shared.py`（**TUI 对话**）· 量化工具 · 模型资产面。**D 档**：`model_module.py`（层拆分/张量放置）· `tcp_comm.py`（张量传输）· `qwen3_pipeline_*`/`qwen3_multimodal_*`（流水线/多模态运行时）· `task_worker_protocol.py`/`task_provider.py` · `inference_service/`（流水线宿主）· `schemas/` 引擎契约。**选档 = `device_profiler.py` 画像**（显存/内存/算力 → L/D） |
| **主仓·控制面** | **QLH Control** | 管理器：调度/集群/节点/控制入口 | `scheduler.py`（14k 调度核心）· `tcp_comm.py`（节点通信）· `device_profiler.py`（画像）· `scheduler_svc_http.py` · `api_server.py`（控制面端点：cluster 63 / logs / user / bootstrap / workflows / db / storage / system 等）· `review.py`/`email_notifier.py` · 任务链协议（管理侧） |
| **支线** | **QLH 产品壳** | 前端/端侧/打包：把系统组装成产品 | `frontend_cybergothic/`（独立仓）· `android/`（独立仓）· `packaging/`（UNI-A3）· 演示/答辩工具（UNI-A2） |

> 注（v2 修正）：首版曾把控制面列为"拆出模块"——**修正为同仓两部分**（控制面/数据面分离是**架构分层**，不是仓库拆分）。**产品壳是唯一拆出物**。两层的接口纪律（契约 + 单向依赖）保持 §4 所述。
> 注（v3 修正）：数据面为**双引擎**——**PyTorch 不抛弃**（llama.cpp 不能做分层分布式推理）；L 档（GGUF，无 torch）与 D 档（PyTorch）**按设备画像选档**；边缘基线（≤300MB venv）仅约束 **L 档**，D 档的 torch 依赖是分层分布式能力的正当成本。

## 4. 分层与接口（同仓两层怎么协作）

```
[主仓·控制面 QLH Control]                [主仓·数据面 QLH Engine]
  调度/集群/节点/控制入口  ──任务(REST/任务链协议)──▶  跑模型（llama.cpp+优化）
  设备画像/审计/审批                                   TUI 对话（qlh chat）
        │                                                  │
        └────── 契约：schemas/（推理请求/结果/任务协议）──────┘
[产品壳支线] 前端/Android ──▶ 面向用户（经控制入口或引擎面）
```

- **依赖方向（强纪律）**：控制面 → 数据面**单向**（管理器调用引擎执行任务；**引擎不得 import 控制面**）；同仓不同目录，可用一次性测试断言守住（import 检查）。
- **数据面对外**：`qlh chat`（TUI 对话，主交付）、`qlh_edge`（最小 HTTP）、models 资产面；
- **控制面对外**：cluster/scheduler/节点/审批面（`api_server` 控制侧端点）。

## 5. 实施路径（三轮，聚焦主交付）

| 阶段 | 动作 | 验收 |
| --- | --- | --- |
| **P1 TUI 对话**（主做，立即） | `qlh chat` 打通：TUI 对话接入引擎（复用 `tui_chat`（715 行零第三方）+ llama.cpp 本地直连；或极简新写） | 一条命令本地多轮/流式对话；venv ≤300MB（边缘基线） |
| **P1.5 双档与画像**（v3 新增） | 引擎双档显式化：`device_profiler` 画像 → 推荐/选择 L 档（GGUF）或 D 档（PyTorch）；TUI/`qlh_edge` 状态中显示当前档 | 不同画像设备自动/显式选对档；L 档无 torch、D 档分层分布式路径可用 |
| **P2 同仓分层整理**（可选，按需） | 目录级可辨识（如 `src/engine/` 与 `src/control/` 归档整理）+ import 单向断言测试；`api_server` 控制面端点归位 | 引擎目录零控制面 import；测试守住 |
| **P3 产品壳外置**（唯一拆仓） | cybergothic/Android/packaging 按既有清单外置（"dist 获取协议"先行） | 主仓 = 引擎 + 控制面 + 契约 + 实验体系 |

> 注：首版的"管理包化/独立仓"路径（P2/P3）**撤销**——控制面留主仓；未来若出现触发条件（独立交付/宿主外使用/CI 冲突），再按候选计划四条件评估。

## 6. 不变式（本次决策不改变的事）

1. Koakumix/docagent/bridge/spawnledger 的既有独立状态与纪律不变；
2. 实验体系（fixtures/experiments/MANIFEST/EX-N3 门）留主仓（引擎质量基建）；
3. 边缘基线（≤300MB venv / ≤15s 冷启动 / 无 torch）为数据面交付标准；
4. 文档双轨归档（docs/archive、_archive）与"先归档后删"纪律不变；
5. 控制面内部（scheduler 等）不因本决策改动行为；分层整理只动组织不动语义。
