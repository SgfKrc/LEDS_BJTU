# QLH 定位与模块归属终局决策（2026-09-14）

> 状态：**生效**（v5；本文与《主线开发计划》《支线开发计划》共同构成当前边界）。本文档是归属裁决依据，冲突表述以本文为准。
> 创建日期：2026-09-14（v5 重整）
> 依据：本地审计、功能存废清单、分布式形态调研、用户最新指示（主仓聚焦分布式推理优化；必须保留边缘版；TUI 为主交互；非核心功能独立并迁移至侧车/Koakumix）。

## 1. 主项目定位（最终裁定）

**主项目 QLH = 轻量分布式推理系统：引擎（数据面）+ 管理器（控制面）+ TUI/合同/验收基建，同仓同项目。**

- **一句话**：在边缘设备（无/弱 GPU）上默认用 <=1B GGUF/llama.cpp 模型本地完成推理，同时把 Edge/PC/工作站/Android 节点组织成可验证的 llama.cpp 模型分片系统，让更大模型由多个节点共同承载——**生产数据面 = GGUF/llama.cpp**（单机推理 + host/RPC 模型分片 + TUI 对话；默认无 torch）；**PyTorch/Safetensors 层流水线只保留 PC 对照实验**，不进入边缘默认安装或正式发行；**控制面**负责调度、分片合同、节点、租约和故障绕行。
- **主交付（重心）**：**TUI 对话与集群控制**——当前稳定入口是标准库 `tui_admin`，`CORE-TUI-01` 收口统一的 `qlh chat` 入口；两者都使用稳定协议调用本地或集群引擎。`qlh_edge` 只提供最小 HTTP/节点接入面；Edge 必须保留本地 <=1B 推理和 RPC worker 能力，不能退化为 HTTP 远程壳。Web/Android 是外部产品壳，不再定义主项目交付。
- **拆分原则**：控制面与数据面仍同仓分层；产品壳、知识库、图像生成、发布和运营工具独立为支线/子模块，Koakumix 接收小模型增强和生图侧车。
- **纪律**：控制面与数据面在**代码组织上分层**（目录/包可辨识、依赖单向：控制面可调用数据面，反之禁止），**不拆仓、不拆 CI**；产品壳与知识库不再占主仓。新增功能准入问句："它服务这套推理系统（引擎或管理器）吗？"

## 2. 归属定案（两部分同仓 + 支线独立）

| 归属 | 层 | 角色 | 当前代码映射（文件级） |
| --- | --- | --- | --- |
| **主仓·数据面** | **QLH Engine（llama.cpp 主线）** | <=1B Edge 本地推理、更大模型分片/RPC、CPU/弱 GPU 路径、KV/缓存和 TUI 对话 | `llama_engine.py` · `qlh_edge.py` · `paged_kv_cache.py` · `cache_unit_layout.py` · `tui_admin.py` · `tui_chat.py`/`tui_sse.py`/`tui_shared.py` · 模型资产面；RPC host/worker 适配与分片合同按主线票接入 |
| **主仓·对照数据面** | **Reference P（PC only）** | PyTorch/Safetensors 层流水线，用于正确性、性能和容量对照；不作为生产引擎 | `model_module.py` · `qwen3_pipeline_*` · `qwen3_multimodal_*` · `inference_service/` · `tcp_comm.py` 的参考路径；改造成功后从默认安装和默认路由剥离 |
| **主仓·控制面** | **QLH Control** | 管理器：调度/集群/节点/能力画像/任务租约/降级 | `scheduler.py` · `tcp_comm.py` · `device_profiler.py` · `scheduler_svc_http.py` · `api_server.py` 的核心控制端点 · 任务链协议（管理侧）；邮件通知已裁撤，运营面按支线维护 |
| **主仓·交互/验证** | **QLH TUI + evidence** | 主入口、模型舰队选择、能力显示、推理优化质量门 | `tui_admin.py`（当前稳定入口）及 `tui_chat.py`/`tui_sse.py`/`tui_shared.py`、模型 manifest/profile、必要实验与回归；演示 UI、图表和环境编排外置 |
| **支线** | **产品壳/侧车** | 把核心组装为可选产品或扩展能力 | Web/Android/packaging、Koakumix harness/生图、Patchouli/RAG、docagent、reasonix bridge、spawnledger、演示/网络/发布工具；具体迁移见支线计划 |

> 注（v2 修正）：首版曾把控制面列为"拆出模块"——**修正为同仓两部分**（控制面/数据面分离是**架构分层**，不是仓库拆分）。
> 注（v3 修正，历史）：当时将数据面定为 L/D 双引擎，PyTorch 为正式分布式路径；该结论由 v5 重新裁决。
> 注（v4 重整）：主仓不再以“产品壳唯一拆出物”为边界。主仓只保留推理核心、控制、TUI、模型合同和质量证据；所有非核心功能均按支线计划独立，生图唯一归 Koakumix。
> 注（v5 重整）：Silica Cluster 证明 Android + llama.cpp RPC 具备攻关入口。主线改为 llama.cpp 模型分片/RPC；任务图仅作整模临时回退；PyTorch 只保留 PC 对照，待 llama.cpp 单机/双进程/真机分布式门通过后再从生产路径退出。

## 3. 支线角色表（全部敲定）

| 支线 | 角色 | 现状/去向 |
| --- | --- | --- |
| **Koakumix**（harness） | 小模型增强对话工作台、可选多模态增强、图像生成和 MCP 侧车 | 独立维护；通过 API/模型合同接入 |
| **docagent** | 文档维护扫描器 | 已独立（子模块） |
| **reasonix-codex-bridge** | Codex↔Reasonix 受控桥 | 已独立（子模块） |
| **spawnledger** | 进程归属票据工具 | 已独立（子模块） |
| **Patchouli** | 文档库管理 TUI（规划） | 独立计划 |
| **SD 生图服务** | 图像生成 | 已归 Koakumix；QLH 主仓不再保留调用入口、引擎或生成任务协议 |
| **知识库/RAG 服务** | 文档检索（与 Patchouli 合流） | 已裁决独立 |
| **QLH 产品壳（Web/Android）** | 可选用户界面和端侧载体 | 独立仓；只消费 API/任务/模型合同 |
| **发布与运维工具** | 打包、更新、离线资产、演示、SSH、网络探针 | 独立工具仓；不成为主线运行时依赖 |
| **实验体系（EX-N3/度量）** | 引擎的**质量与优化验证基建**——**留主仓** | 不拆 |

## 4. 分层与接口（同仓两层怎么协作）

```
[主仓·控制面 QLH Control]                [主仓·数据面 QLH Engine]
  调度/集群/节点/控制入口  ──分片/模型/回退合同──▶  跑模型（llama.cpp 主线）
  设备画像/合同/降级                                    TUI 对话（qlh chat）
        │                                                  │
        └────── 契约：schemas/（推理请求/结果/任务协议）──────┘
  PC 参考环境（PyTorch） ───── 对照证据，不进入默认生产路径
[产品壳支线] Web/Android/Koakumix ──▶ 可选用户体验（经版本化合同）
```

- **依赖方向（强纪律）**：控制面 → 数据面**单向**（管理器调用引擎执行任务；**引擎不得 import 控制面**）；同仓不同目录，可用一次性测试断言守住（import 检查）。
- **数据面对外**：`qlh chat`（TUI 对话，主交付）、`qlh_edge`（最小 HTTP）、models 资产面；
- **控制面对外**：cluster/scheduler/节点/审批面（`api_server` 控制侧端点）。

## 5. 实施路径（先固化断点，再攻克 llama.cpp 分片）

| 阶段 | 动作 | 验收 |
| --- | --- | --- |
| **P1 TUI 对话**（主做，立即） | 收口 `qlh chat`：在现有标准库管理 TUI 基础上接入引擎和模型舰队；Textual `tui_chat` 仅作可选聊天界面，不进入 Edge 硬依赖 | 一条命令本地多轮/流式对话；Edge 无 torch 且不强依赖 Textual |
| **P1.5 断点与低耦合门**（v5） | 对功能裁切/引擎重写做入口、import、合同、测试、资源和外置子模块映射；确保 TUI/API/模型下载/模型选择不断线 | 旧前端、邮件、生图、微服务不再被主线引用；外置仓只经稳定协议接入 |
| **P2 llama.cpp 单机基线**（v5） | Edge/PC 先跑通单进程 GGUF，默认 <=1B：模板/thinking、流式、多模态按模型舰队选配、TUI/API、CPU/可选 GPU；记录质量/内存/吞吐 | 默认 Edge/PC 无 torch；与既有行为有可复现对照 |
| **P3 llama.cpp 双进程与真机分片**（v5） | 同机 host + RPC worker 双进程模拟，再做 PC 跨机，最后接 Android `librpc.so`；验证单机装不下、每节点部分驻留、租约/故障/安全 | 通过模型分片证据后才进入默认生产路由 |
| **P4 参考与收敛**（v5） | PyTorch 仅 PC 对照；任务图保持临时整模回退；成功后从默认安装/路由/发布中剥离 torch | 主仓生产发行 = llama.cpp + control + TUI + contracts + evidence |

> 注：首版的"管理包化/独立仓"路径（P2/P3）**撤销**——控制面留主仓；未来若出现触发条件（独立交付/宿主外使用/CI 冲突），再按候选计划四条件评估。

## 6. 不变式（本次决策不改变的事）

1. Koakumix/docagent/bridge/spawnledger 的既有独立状态与纪律不变；
2. 实验体系（fixtures/experiments/MANIFEST/EX-N3 门）留主仓（引擎质量基建）；
3. 边缘基线（≤300MB venv / ≤15s 冷启动 / 无 torch / TUI 可用）为数据面交付标准；
4. 文档双轨归档（docs/archive、_archive）与"先归档后删"纪律不变；
 5. 控制面内部（scheduler 等）不因本决策提前改动行为；先通过断点门，再逐步替换执行适配器。
 6. 分布式真机前必须完成 Edge/PC 单机与同机双进程模拟；失败时保留 Edge <=1B 本地 llama.cpp、其他节点分片或任务图回退，不得伪造分片成功。
