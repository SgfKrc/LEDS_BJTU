# QLH 边缘设备模拟环境计划（2026-09-15）

> 文档状态：**现行**
>
> 生命周期：**验证基础设施（Edge Simulation）**
>
> 适用范围：为 QLH 的 **llama.cpp/GGUF 主线**提供"受限资源"验证环境——用容器或虚拟机**模拟边缘节点**（低 CPU / 小内存 / 无 GPU / 无 torch），验证其默认 <=1B 本地推理、RPC worker 参与能力、单机与同机双进程，再进入真实 PC/Android 分片验收，把边缘基线从"口头约束"变成"可复现测量"。
>
> 上游事实入口：[QLH 定位与模块归属终局决策](QLH定位与模块归属终局决策-2026-09-14.md)（边缘基线 ≤300MB venv / ≤15s 冷启动 / 无 torch / TUI 可用，**仅约束 L 档**）、[主线开发计划：分布式推理与边缘优化](主线开发计划-分布式推理与边缘优化-2026-09-14.md)。

## 1. 目标与范围

| 项 | 内容 |
| --- | --- |
| **要验证的指标** | ① venv 体积 ≤300MB；② 冷启动 ≤15s；③ **无 torch**；④ <=1B GGUF 本地推理；⑤ TUI、节点注册和 RPC worker 在受限环境可用 |
| **要模拟的限制** | 少量 vCPU（1–2 核）、小内存（2–4GB）、无 CUDA、受限磁盘 |
| **不在范围** | PC PyTorch 对照路径的性能标定；真实手机/ARM 设备的最终验收（将来由真机承担） |
| **主线顺序** | `CORE-CUTOVER-01` → Edge <=1B 单机 → 同机 host + `ggml-rpc-server` 双进程；未完成前三项，不进入真实 PC/Android 分片验收 |
| **原则** | 模拟环境是**开发期手段**：便宜、可复现、可 CI；**不替代**真机验收，只替代"等真机才能发现问题"的低效循环 |

## 2. 手段对比

| 维度 | Docker Desktop + WSL2 | 虚拟机（VirtualBox/VMware/Hyper-V/QEMU） | 裸机 cgroup/任务限制 |
| --- | --- | --- | --- |
| 资源限制能力 | `--cpus/--memory/--pids-limit` + `.wslconfig` | vCPU / RAM / 磁盘**独立分配**（最"硬"） | `systemd-run` / `cgroup v2` |
| 是否独立内核 | 否（共享宿主内核） | **是**（真独立内存与网络栈） | 否 |
| 体积/冷启动保真 | **高**（依赖与文件系统与部署一致） | 中（磁盘 IO 与缓存不同） | 高 |
| CPU 性能保真 | **低**（宿主同核，频率/缓存不变） | 中（vCPU 仍是宿主核，但可限频/限核） | 低 |
| ARM/aarch64 模拟 | 否（仅 x86） | **可**（QEMU 系统模拟） | 否 |
| 网络拓扑模拟 | 弱（端口映射为主） | **强**（NAT/桥接/Host-only/内部网） | 无 |
| 多节点组网 | 需 docker network + 端口 | **自然**（虚拟机网段即拓扑） | 无 |
| GPU 透传 | WSL2 + nvidia-container-toolkit（可选） | PCI 直通（复杂）；QEMU 支持有限 | 宿主 GPU |
| 启动成本 | 低（秒级） | 高（镜像/系统安装，分钟级） | 极低 |

**结论**：**尺寸/依赖/冷启动类指标 → 容器**；**网络拓扑/多节点/ARM 类指标 → 虚拟机**。

## 3. 方案 A：Docker Desktop + WSL2（首选，阶段 1）

### 3.1 限制整个 WSL 分发（`.wslconfig`，位于 `%USERPROFILE%\.wslconfig`）

```ini
[wsl2]
memory=4GB          # 模拟小内存设备（宿主 16GB，留出余量）
processors=2        # 模拟 2 核设备
swap=2GB
```

改后需 `wsl --shutdown` 生效。**注意**：这会同时影响 Docker Desktop（其后端跑在 WSL2 上）。

### 3.2 逐容器限制（推荐，粒度更细、可写进脚本）

```bash
docker run --rm -it \
  --cpus=1 --memory=2g --memory-swap=2g \
  --pids-limit=256 --storage-opt size=8G \
  -v "$PWD:/work" -w /work \
  python:3.12-slim bash
```

### 3.3 边缘基线度量（容器内执行，作为验收证据）

```bash
python -m venv .venv-edge
.venv-edge/bin/python -m pip install -r requirements-edge.txt
.venv-edge/bin/python scripts/edge_preflight.py --python .venv-edge/bin/python --json
.venv-edge/bin/python qlh_edge.py --help
```

Windows 将上面的 `.venv-edge/bin/python` 替换为 `.venv-edge\\Scripts\\python.exe`。`edge_preflight.py` 会一次性检查 venv 体积、导入冷启动、必需模块、
禁用模块和 `/health`、`/status`、`/generate` 路由；主线 TUI 仍在主环境单独验收，不能由 Edge
最小环境中的 HTTP 进程替代。

### 3.4 局限（必须如实写进结论）

- **CPU 保真度低**：容器与宿主共享内核与 CPU，`--cpus=1` 只限**配额**，不改频率/缓存/内存带宽 → **不能**用它宣称"低端设备上的吞吐/延迟数字"；
- **无 GPU**：L 档本就无 torch、不依赖 CUDA，故**不影响**本计划的指标；若将来要验证多模态（vision）路径，需 WSL2 CUDA 透传（另行评估）；
- **文件系统差异**：容器内 ext4 vs Windows NTFS → 冷启动数字以容器内为准。

## 4. 方案 B：虚拟机（阶段 2，需网络拓扑时启用）

### 4.1 资源分配

- vCPU = 1–2、RAM = 2–4GB、磁盘 = 16–32GB（可快照回滚，便于"脏环境复现"）；
- 若要更接近 ARM 边缘（手机/树莓派类），用 **QEMU 系统模拟 aarch64**（速度慢，仅做兼容性验证，不做性能数字）。

### 4.2 网络模式与"网络问题"的处理

这是本方案唯一真正需要解决的问题——**QLH 的主从节点拓扑要在宿主与 VM 之间、或 VM 与 VM 之间组网**：

| 模式 | VM → 外网 | 宿主/局域网 → VM | 适用场景 |
| --- | --- | --- | --- |
| **NAT**（默认） | ✅ | ❌（需**端口转发** `hostfwd`/NAT 规则） | 只做单机受限资源验证 |
| **桥接（Bridged）** | ✅ | ✅（与宿主同网段，需 DHCP 或静态 IP） | 模拟"同局域网的两个节点" |
| **Host-only / 内部网** | ❌（可选第二张 NAT 卡） | ✅（私有网段，宿主↔VM、VM↔VM） | **主从节点私网模拟（推荐）** |

**推荐配法（主节点=宿主，从节点=VM）**：

1. 给 VM 两张网卡：**NAT**（供安装依赖/联网）+ **Host-only**（私有网段，如 `192.168.56.0/24`）；
2. Host-only 网卡配**静态 IP**（避免 DHCP 漂移破坏节点地址）；
3. QLH 侧用显式 endpoint 连接（`/api/cluster/connect`，host/port 明确）——**不要依赖自动发现**，模拟环境里 mDNS/广播常不通；
4. 需要从宿主访问 VM 内的服务端口（如 `--serve-port 8090`）：Host-only 直接可达；NAT 则加端口转发。

**已知坑**：

- **Hyper-V / WSL2 与 VirtualBox 互斥**：Hyper-V（含 WSL2 后端）启用后，VirtualBox 只能跑"Hyper-V 后端"（性能差），或必须**关闭 Hyper-V**（则 Docker Desktop/WSL2 不可用）→ **两方案需取舍，不能同时全速使用**；
- **防火墙**：Windows Defender 对 Host-only 网卡的入站规则需显式放行；
- **时钟/休眠**：VM 挂起恢复后时钟漂移会影响超时类断言（建议禁用宿主休眠或用 NTP 校时的镜像）。

## 5. 推荐路线（分阶段，成本递增）

| 阶段 | 手段 | 验证什么 | 何时做 |
| --- | --- | --- | --- |
| **阶段 1** | Docker Desktop + WSL2（`--cpus/--memory`） | venv 体积 / 依赖完整性 / 冷启动 / **无 torch** / TUI 可用 | **现在即可**（低成本，可写进 CI） |
| **阶段 2** | VM + Host-only（+ NAT） | 主从节点组网、弱网（`tc netem`）、节点地址持久化 | 需要验证分布式接入与网络行为时 |
| **阶段 3** | QEMU aarch64 | ARM 架构兼容性（非性能） | 有 ARM 目标需求时 |

## 6. 验收与证据口径

- 每个阶段的度量必须**留下可复现命令 + 原始输出**（体积、耗时、退出码），登记到实验记录/验收清单，而不是只写"已通过"；
- 容器/VM 配置（Dockerfile、`.wslconfig`、VM 规格与网卡设置）**随仓库或 `local_docs/` 记录**，保证他人可复现；
- 与边缘基线一一对应：≤300MB / ≤15s / 无 torch / TUI 可用 —— **任一项不达标即视为 L 档回归**。

## 7. 风险与未决事项

| 项 | 说明 | 处置 |
| --- | --- | --- |
| CPU 保真度 | 容器/vCPU 均不改宿主频率与缓存 | 性能类结论**只能来自真机**；模拟只做尺寸/依赖/启动 |
| Hyper-V 互斥 | Docker/WSL2 与 VirtualBox 不能同时全速 | 阶段 1 用容器；阶段 2 前决定是否需要临时关闭 Hyper-V |
| GPU 缺失 | 容器与多数 VM 无 CUDA | llama.cpp/GGUF 主线不受影响；PyTorch 只作 PC 对照，多模态按模型舰队另行评估 |
| 镜像获取 | VM/容器镜像与模型工件需可离线获取 | 复用离线资产包与签名 manifest 机制 |
| ARM 保真 | QEMU 模拟慢且非真机 | 仅做兼容性验证，性能与真机验收留待实体设备 |
