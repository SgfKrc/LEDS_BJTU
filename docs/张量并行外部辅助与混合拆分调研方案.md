## 1. 背景与问题定义

### 1.1 既有结论回顾（本文的出发点）

《混合规划》§2.1、§4.3 和《细化方案》§5.5 已经明确：

1. 张量并行每层需要多次 collective，只适合低延迟、高带宽、同构的设备组（《细化方案》§5.1）。
2. 网络准入表把 Wi-Fi、移动网络、Tailscale DERP 和 Android 设备**默认拒绝**加入 tensor group（《细化方案》§5.5）。
3. 张量并行不复用 `LAYER_FORWARD`/`CHAIN_FORWARD` 协议，作为独立 `TensorParallelProvider` 通过外部运行时接入（《细化方案》§5.2）。

本文把这些定性结论量化为通信数学，然后回答：**TP 不进 mesh，但可以在 mesh 之外"成岛"，由 QLH 编排。** 这正是 Megatron PTD-P 的经典原则在边缘场景的翻版：TP 留在快速互联内部（NVLink/同机/快速 LAN），PP（层间流水线）和任务级拆分跨慢速链路（arXiv:2104.04473）。

### 1.2 每 token 通信数学：TP 为什么在 mesh 内必死，层间流水线为什么能活

设隐藏维 H、层数 L、TP 并行度 N、流水线段数 S、激活字节宽 b（FP16 b=2，INT8 b=1）。

- **层间流水线（PP）**：每个 stage 边界每 token 传一次 hidden state，约 `H×b` 字节；每 token 全链路 hop 数 ≈ S（含结果回传）。
- **张量并行（TP，Megatron 切法）**：每层 forward 需要 2 次 all-reduce（attention 输出投影后、MLP down 投影后），每 token 每节点通信量 ≈ `2L × 2(N−1)/N × H×b`，且每次 all-reduce 是**同步栅栏**，至少付出一个 RTT。

代入本项目实际参数（Qwen-1.8B：H=2048，L=24；`分布式推理流水线实施计划.md` 实测单 token hidden state FP16 = 4KB）：

| 指标（decode，每 token） | 层间流水线（3 段） | 张量并行（N=2 跨机） | 张量并行（N=4 跨机） |
|---|---|---|---|
| 传输次数（同步点） | 3 次单向 hop | 48 次 all-reduce | 48 次 all-reduce |
| 每节点通信量 FP16 | ~12 KB（3×4KB） | ~192 KB（48×4KB） | ~288 KB（48×6KB） |
| 每节点通信量 INT8 激活 | ~6 KB | ~96 KB | ~144 KB |
| RTT 开销下限 @20ms | 3×20 = **60 ms** | 48×20 = **960 ms** | ≥960 ms |
| 传输时间 @100Mbps | ~1 ms | ~15 ms | ~23 ms |
| 纯通信 decode 上限 @100Mbps/20ms | ~16 tok/s | **~1 tok/s** | <1 tok/s |
| Prefill 512 token 通信量 | 每边界 2 MB，共 ~6 MB | ~96 MB | ~144 MB |
| Prefill 通信时间 @100Mbps | ~0.5 s | **~7.9 s** | ~11.8 s |

7B 级模型（H=4096、L≈32）把 TP 每 token 通信推到 ~512KB、64 次同步；PP 每 hop 仅 8KB。结论不随模型规模改善，反而恶化。

三个不可回避的定量事实：

1. **TP 的瓶颈是 RTT×同步次数，不是带宽。** 48 次/token 的同步栅栏在 Tailscale 5–50ms RTT 下，仅 RTT 就吃掉 0.24–2.4 s/token。带宽再翻十倍也无解。TPI-LLM（arXiv:2410.00531）同样结论："link latency, not bandwidth, emerges as the main issue"，其对策（星型 allreduce + 内存滑窗）优化的是家庭内网毫秒级 RTT，不适用于本项目跨 DERP 中继的场景。
2. **PP 每 token 只有 S 个同步点，且与计算天然重叠。** 60ms/token 的通信开销对 10–20 tok/s 的目标是可接受的固定税。
3. **异构 = straggler 在 TP 中被放大 48 倍/token。** TP 每次 all-reduce 等最慢 rank；PP 中慢节点只决定吞吐（流水段瓶颈），可用层数分配（`graph_orchestrator._assign_layers` 按 VRAM/算力比例）补偿。

因此："外部辅助"的唯一正确形态是：**TP 只发生在 mesh 之外的快速孤岛内部；孤岛与 QLH 集群之间只交换低频、大粒度的对象**——完整请求、任务链 Stage 输入输出、或（谨慎地）流水线段边界的 hidden state。

### 1.3 外部佐证（2024–2026 文献一致性）

- Megatron PTD-P：TP 限制在单服务器 NVLink 内、PP 跨服务器，是大规模训练/推理的标准组合（arXiv:2104.04473）。
- HexGen / HexGen-2（ICLR 2025，arXiv:2502.07903）：异构 GPU 集群用图划分 + max-flow 把 TP 放进高带宽组、组间用 PP 和 KV 传输，吞吐较同预算同构方案提升至 1.3–2.0×——**"TP 孤岛 + 岛间 PP"被学术界系统性验证**。
- Helix（ASPLOS 2025，arXiv:2406.01566）：异构 GPU + 异构网络建模为 max-flow/MILP，按请求走不同流水线路径；与本项目图算法（最大带宽生成树 + DFS）同族，可作为图算法组的进阶参考。
- prima.cpp（Lizonghang/prima.cpp，MIT）：家庭异构集群跑 30–70B，用的是**piped-ring 流水线 + mmap 预取**而非跨机 TP；Halda 调度器按算力/磁盘/内存/OS 分层。与 QLH 层间路线同判断。
- exo（Apache-2.0）：TP 只在 Apple Silicon + Thunderbolt/RDMA 上宣传收益（《混合规划》§5 已调研；2026 年上游仍以 Mac 集群 RDMA TP 为主线）。
- Galaxy（INFOCOM 2024，arXiv:2405.17245）：边缘 TP+SP 混合并行，实验前提是 125Mbps–1Gbps **局域网内毫秒级 RTT**，且靠 tile 级通信-计算重叠才可用——恰好说明 Tailscale 广域 RTT 下不可复制。
- EdgeShard（arXiv:2405.14371）：边缘协作推理选择**层拆分 + 动态规划选点**，不用 TP，延迟降 50%。

## 2. 外部辅助的三条路线

### 2.0 总览

```text
                         QLH 统一控制面 (api_server / scheduler / TaskGraphCoordinator)
                                            |
        +-----------------------------------+-----------------------------------+
        |                                   |                                   |
   路线 A: TP 孤岛                     路线 B: 外部推理服务               路线 C: 混合辅助
   同构 GPU 子集群/多卡单机            OpenAI 兼容 API Provider          投机解码 draft-verify
   对 QLH = 1 个逻辑高算力节点         对 QLH = 1 个 ExecutionProvider    外部 verify / 本地 draft
   承担最重层段或整段推理              承担整请求/长上下文/大模型          承担 token 校验或 prefill
        |                                   |                                   |
   接入点: NodeInfo/device_info        接入点: task_provider.py           接入点: scheduler 解码循环
   graph_orchestrator 超节点           ProviderRegistry + StageSpec       + 外部 API(需 logprobs)
```

| 维度 | A. TP 孤岛 | B. 外部服务 Provider | C. 投机解码/混合辅助 |
|---|---|---|---|
| 辅助粒度 | 逻辑节点（层段或整段） | 完整请求 / 任务链 Stage | token 批次（draft-verify） |
| 跨 mesh 通信 | hidden state / 请求对象 | prompt + 结果文本 | draft token 序列 + 校验结果 |
| 协议改动量 | 零～小 | 小（新增 Provider 类） | 中～大（改解码循环） |
| 对外部资源要求 | 同构 GPU + 快速 LAN | 任意 OpenAI 兼容端点 | 外部端支持 logprobs/批量校验 |
| 成熟外部件 | vLLM/SGLang/llama.cpp RPC | vLLM/SGLang/exo/云 API | SLED/DSSD 思路，需自研胶水 |
| 建议优先级 | **1（先做）** | **2** | 3（探索） |

### 2.1 路线 A：TP 孤岛（TP island）——对 QLH 呈现为单个逻辑高算力节点

**前提条件**：存在一组同构 GPU 设备（或一台多卡/大显存机器），彼此间是快速局域网（≥1GbE，RTT<1ms）或同机 PCIe/NVLink；其中一台可运行 QLH 节点客户端作为**网关（gateway）**。

**核心思想**：孤岛内部用成熟运行时跑 TP（或多卡 layer split），网关把整岛聚合算力/显存汇报为一个节点的 `device_info`。QLH 的图算法、层分配、MLFQ **完全不感知岛内并行**——只看到一个"特别强的节点"。这正是《混合规划》§8.1"统一控制语义，不统一内部 tensor ABI"的自然推论。

两种子形态，按改动量递增：

**A-1：孤岛承担层间流水线的最重连续层段（零～小协议改动）**

```text
QLH mesh (Tailscale, 10~100Mbps, 5~50ms)
  主节点 ──LAYER_FORWARD──> [网关节点 = TP 孤岛]───CHAIN_FORWARD──> 从节点C
   Emb+L0-3                     L4-19 (16 层)                        L20-23+LM Head
                                  |
                     岛内: 单机多卡 device_map / NVLink TP
                     或 llama.cpp RPC 聚合同 LAN GPU (GGUF 路线)
```

- 接入点（具体到模块）：
  - `tcp_comm.py` 客户端注册的 `device_info` dict（~853 行 `node_type`/`device_info`）：网关上报**聚合** VRAM 与算力权重；`device_info` 本就是自由 dict，加 `island_gpu_count`、`island_aggregate_vram_mb` 字段零协议破坏。
  - `graph_orchestrator._extract_vram_mb` / `_calc_node_weight`：读取聚合值后，`_assign_layers` 按 VRAM 比例自然把最重层段分给孤岛。**图算法零改动**——孤岛就是一个顶点，岛内拓扑不进入最大带宽生成树。
  - `model_module.forward_layers`：单机多卡需支持把本节点层段用 `device_map`/accelerate 分到多卡（小改动）；多机岛内 TP 承担 PyTorch 层段暂无现成运行时暴露"层段服务器"API，**近期只做单机多卡形态**。
- GGUF 变体：网关跑 llama.cpp 并用 `--rpc` 聚合同 LAN 的 rpc-server 设备（ggml-org 上游 README 确认支持权重/KV 按设备比例分布 + 本地缓存 + Linux RoCEv2 RDMA），对 QLH 仍是"一个本地 llama.cpp 节点"。注意上游持续警告 RPC 为 **fragile/insecure、不得暴露公网**——只允许在孤岛内网使用，且这不改变《混合规划》§13.3"GGML RPC 默认 No-Go 作为 QLH 主路线"的结论：这里 RPC 被封装在孤岛内部，QLH 不依赖其协议。
- 网关注册时 `device_info` 建议扩展（自由 dict，旧版本节点无感）：

```json
{
  "node_type": "pc",
  "device_info": {
    "gpu_name": "RTX 4090 x2",
    "vram_mb": 24576,
    "island": {
      "island_id": "lab-cuda-island-1",
      "gpu_count": 2,
      "aggregate_vram_mb": 49152,
      "internal_interconnect": "pcie|nvlink|lan_10gbe",
      "internal_benchmark_passed": true,
      "internal_runtime": "device_map|llama_rpc|vllm_tp"
    }
  }
}
```

  调度侧规则：`_extract_vram_mb` 在 `internal_benchmark_passed=true` 时才采用 `aggregate_vram_mb`，否则退回单卡值——防止"账面聚合、实际瓶颈"的画像失真。
- 预期收益：流水线容量上限提升（7B FP16/INT8 单卡装不下时，孤岛段可容纳 20+ 层）；straggler 从"最弱节点"变为"最弱 stage"，孤岛吸收最重层段后各 stage 耗时更均衡。
- 风险：网关成为单点（岛内任一卡/机故障 = 整个逻辑节点故障，走现有节点下线→重编排路径，故障域天然干净）；聚合画像失真（岛内互联慢于预期时层分配过重）→ 上述 benchmark 门控 + E1 实验校准。

**A-2：孤岛承担整段推理（作为完整推理 Worker）**

孤岛整机跑 vLLM/SGLang `--tensor-parallel-size N`（多机岛用 Ray + NCCL，vLLM 官方文档明确要求高带宽互联，正好匹配"孤岛内快、岛外慢"的边界），网关运行一个薄 shim 实现 QLH Full Worker 协议（`STAGE_OFFER/STAGE_RESULT`，见《细化方案》§4.6），把请求转发给岛内 OpenAI 端点：

```text
QLH 主节点 (TaskGraphCoordinator / scheduler)
      | STAGE_OFFER / STAGE_RESULT / LEASE_RENEW   (Tailscale, 低频控制消息)
      v
孤岛网关 shim (普通 QLH Worker 进程)
      | POST /v1/chat/completions                   (岛内 LAN)
      v
vLLM / SGLang TP 实例  <== NCCL collective ==>  rank1..rankN   (岛内高速互联)
```

对 QLH，这就是一个 `remote_full_worker`（`task_worker_adapter.py:404 RemoteFullWorkerProvider`，`supported_stage_types = {"full_inference","aggregate"}`）——**协议零新增**，只新增一个 Worker 实现。A-2 与路线 B 的区别：A-2 走 Worker 协议、有租约/续租/取消/迟到结果过滤语义，孤岛被当作集群成员管理；B 走 Provider 直连外部端点、语义更薄、不要求对方运行任何 QLH 代码。同一孤岛可以同时以 A-1（层段）与 A-2（整段）两种身份注册，但同一时刻只承担一种角色，避免显存双记账。

**路线 A 小结**：

| 要素 | 结论 |
|---|---|
| 前提条件 | 同构 GPU + 岛内 ≥1GbE/RTT<1ms；网关可跑 QLH 节点客户端 |
| 接入点 | `tcp_comm` 注册 device_info、`graph_orchestrator` 画像读取、`model_module.forward_layers` 多卡（A-1）；Full Worker 协议 shim（A-2） |
| 协议改动量 | A-1 零（画像字段为可选扩展）；A-2 零（复用 Worker 协议） |
| 预期收益 | 容量聚合进流水线 / 整段高吞吐后端；孤岛故障=节点下线，故障域干净 |
| 风险 | 网关单点、画像失真、岛内运行时版本锁定 |

### 2.2 路线 B：外部推理服务辅助（OpenAI 兼容 API Provider）

**前提条件**：可访问一个 OpenAI 兼容端点——租用 GPU 盒子上的 vLLM/SGLang、实验室服务器、exo 集群（《混合规划》§5.4 已规划 ExoProvider 即本路线特例）、或云 API。

**接入点（具体到类/行）**：

- 新增 `ExternalOpenAIProvider` 实现 `task_provider.py:186` 的 `ExecutionProvider` Protocol（`inspect/execute/cancel` 等），注册进 `ProviderRegistry`（`task_provider.py:626`）。能力声明示例：

```json
{
  "provider_id": "external_openai.lab-vllm-a",
  "provider_kind": "external_openai",
  "supported_stage_types": ["full_inference", "verify", "aggregate"],
  "max_concurrency": 4,
  "endpoint_fingerprint": "sha256(base_url + served_model + version)",
  "served_model": "Qwen2.5-7B-Instruct",
  "data_scope_required": "external",
  "healthy": true
}
```

- **必要小改动**：`ModelIdentity.__post_init__`（`task_provider.py:121`）目前 `engine ∈ {"pytorch","llama_cpp"}`，需扩展 `"external_api"`；外部模型没有本地 sha256，需允许以"端点指纹 + 服务端模型名 + 探活版本"替代摘要，并在统计中如实标注（不得伪装成本地 artifact）。
- QLH 语义 ↔ OpenAI API 语义映射（RQ4 的桌面初判）：

| QLH 契约 | OpenAI 兼容端点 | 缺口与对策 |
|---|---|---|
| `inspect()` 健康/能力 | `GET /v1/models` + 探活请求 | 无容量/排队信息 → 客户端侧并发闸门 `max_concurrency` |
| `execute()` 流式 | `stream=true` SSE chunk | chunk → 统一 token 事件，`usage` 落 metrics |
| `cancel()` | **无服务端原语**，断开 SSE | best-effort：记 `cancel_best_effort=true`，外部端可能继续算 |
| 租约/迟到结果 | 无 | Provider 层用 attempt_id 门控，断流后丢弃残余 chunk |
| 模型身份校验 | `model` 字段字符串 | 端点指纹入 journal，服务端换模型可被探活发现 |
| 错误分类 | HTTP 4xx/5xx/超时 | 映射 `ProviderExecutionError(retryable=...)`：429/5xx/超时可重试，4xx 不可 |

- 路由：任务链 `StageSpec.requirements.allowed_providers` 已支持按 Stage 指定 Provider（《细化方案》§4.3）；非任务链请求由 MLFQ 按特征路由——Q2 批量级（>512 token）、长上下文（超本地 `min_context_tokens`）、或显式指定大模型的请求进入外部 Provider，Q0 短交互留在本地（外部 RTT 固定税约 2×RTT+排队，对短请求不划算）。Mélange（arXiv:2404.14527）证明按"请求大小×流量特征"混配异构算力有 15–77% 成本收益，其请求分档思路与现有 MLFQ 三级分档同构，可直接借用作路由阈值设计参考。
- 数据作用域**硬约束**：《细化方案》§4.3 的 `local_only / trusted_pc / trusted_tailnet` 必须扩展 `external` 档位；默认所有会话数据**不**出 tailnet，只有显式标记的请求可路由到外部端点。这是安全边界，不是性能问题。
- 多轮会话粘性：外部服务不保留跨请求 KV（无状态 API 每轮全量 prefill；SGLang RadixAttention 的前缀缓存可缓解但不可承诺）。长对话反复走外部 = 每轮重付 prefill；调度应对同一会话保持 provider 粘性，或只把**新发起的长任务**路由出去（RQ8）。

**预期收益**：全模型级辅助——本地集群装不下/跑不动的 7B+ 模型请求可用；集群过载时的溢出泄洪；为任务链提供"高质量 verify/aggregate 后端"。
**风险**：可用性依赖外网；成本计量；输出与本地模型数值不可比（《混合规划》§8.3：逻辑模型同名不代表 artifact 等价），verify 类 Stage 跨引擎比较需按文本/结构化对象而非 logits。

> **实施状态（2026-07-26）**：已实施 阶段 1 PoC——`external_provider.ExternalOpenAIProvider` + 聊天路径按请求路由（`allow_external`/`prefer_external`），数据作用域 `deny/opt_in/allow_all` 默认 opt_in、取消为 chunk 边界断流（best-effort）；详见《外部推理服务Provider接入指南》。

### 2.3 路线 C：混合辅助——投机解码与 prefill 卸载

**C-1 draft-verify（本地 draft + 外部 verify）**：本地 Qwen-1.8B INT4 每轮生成 γ=4–8 个草稿 token（几十字节），发外部大模型一次性校验，接受则前进 γ 步，拒绝则取外部修正 token。跨 mesh 通信 ≈ **KB 级/轮 + 1 RTT/轮**，是三条路线中唯一把"外部大算力"折算进**每 token 质量**而非容量的路线。

```text
本地 (draft: Qwen-1.8B INT4)                    外部 (verify: Qwen-7B/14B TP 实例)
  |-- 生成 γ 个草稿 token (本地 KV 推进) --------|
  |== 上行: token ids ≈ γ×4B + 会话头 ==========>|  一次前向并行校验 γ 个位置
  |<== 下行: 接受数 k + 修正 token + logprob ====|  (外部 KV 推进 k+1)
  |-- 接受则一次前进 k+1 token；拒绝处回滚 ------|
  每轮跨 mesh 代价: ~1 KB + 1 RTT，摊薄到 k+1 个 token
```

  输出分布与 verify 模型一致（标准投机采样性质），因此 C-1 的语义是"**以本地小模型加速外部大模型**"——质量对齐外部端，速度受益于本地 draft。SLED（arXiv:2506.09397）在边缘异构设备 + 边缘服务器上验证该架构获 ~2.2× 系统吞吐；DSSD（arXiv:2507.12000）、分布式投机解码（arXiv:2509.04576）给出通信量化。
  - 前提：外部端支持批量校验并返回 per-token logprobs（vLLM/SGLang 支持 `logprobs`；纯 chat 接口不够，需 completion+logprobs 或自建 verify 端点）；外部端为会话维护 KV（有状态）否则每轮 verify 重付 prefill——这是最大工程难点。
  - 接入点：`scheduler.py` 本地解码循环（`model_module` 生成路径）需插入 draft-verify 状态机；**改动量中～大**，且触碰现有流水线最核心路径，必须以独立 `execution_mode=speculative_assisted` 门控，默认关闭。
  - 收益上界：加速比 ≈ 接受率×γ / (1 + RTT×每轮次数)。RTT 20ms、每轮 γ=6、接受率 70% 时理论 ~3–4× 于外部模型单独解码的质量-速度折中；**需实测，不承诺**。
  - **实施状态（阶段 0-1 探索性 PoC，2026-07-26）**：投机采样纯核心 + `SpeculativeSession` 状态机 + `ExternalVerifyClient`（`/v1/completions` + logprobs）已落地于 `src/speculative.py`，分布等价性由 20000 次 Monte-Carlo 实测（逐 token 偏差与总变差均 < 0.02）；配置为 `QLH_SPEC_*`，默认关闭，数据作用域复用路线 B 的 `QLH_EXTERNAL_DATA_SCOPE`。入口是**独立实验端点** `POST /api/experimental/speculative`，**未接入** `model_module` 生产解码循环——容器无 PyTorch 运行时，无法验证真实 draft 的 KV 推进/回滚，此时改核心路径风险大于收益。
  - 三处与本节估算/表述的实测偏差：① 标准 completions 的 `echo=true` 会回传整段 prompt 的 logprobs，下行是 O(context×top_k)（实测 ≈12KB/轮）而非 ~1KB/轮，要达本节量级须自建 verify 端点；② `PagedKVCache` 只有 `clear()`，缺"回滚最后 n 个 token"，接生产前须补 `truncate(n)`；③ 上句"输出分布与 verify 模型一致"**只在纯核心（拿到精确 verify 分布）时严格成立**——OpenAI 兼容接口只给 top-k logprobs。曾因把截断行按分布归一化（`p_verify = q/M`）使接受比值放大 `1/M`、草稿被橡皮图章（`M` 越小接受率越趋近 1.0，输出退化回 draft 分布），已修复为不归一化：**接受判定恒等于理论精确值且与 `top_logprobs` 参数无关**（实测 0.2819 vs 理论 0.2837；旧行为随该参数在 0.376–0.282 间漂移，是不可跨配置比较的假指标）；残余偏差只来自**修正 token 的残差采样**被截断到 top-k 支撑集，随 `top_logprobs` 增大收敛（20→TV 0.155、64→0.058、200→0.035、全量→0.035），自建端点返回完整 logits 可彻底消除。详见 [投机解码外部辅助实施说明](投机解码外部辅助实施说明.md)。
- **C-2 prefill 卸载（外部算 prefill，本地 decode）**：量化否决——Qwen-1.8B 每 token KV FP16 = 2×24×2048×2B ≈ 192KB；512 token prompt 的 KV ≈ **96MB**，@100Mbps 传输 ~8s，比本地慢速 prefill 还慢。KV INT8/INT4 量化（KVQuant，arXiv:2401.18079）压到 48/24MB 仍在秒级。**结论：prefill 卸载只在孤岛内部快速链路上成立（HexGen-2 的 prefill/decode 分离正是岛内玩法），跨 Tailscale mesh 不做。** 若外部端既做 prefill 又做 decode，那就是路线 B，不需要传 KV。

## 3. 任务链拆分 × 层间流水线 × 外部辅助：组合可行性

### 3.1 组合矩阵（哪些嵌套合法）

延续《细化方案》§6.1 铁律：**Stage 边界只传版本化业务对象；hidden state/KV/tensor shard 不跨 Provider**。

| 外层 \ 内层 | 本地完整 | 完整 Worker | PyTorch 层流水线 | TP 孤岛(A) | 外部 API(B) | 投机解码(C) |
|---|---|---|---|---|---|---|
| 任务链 Stage | ✔ 已实现 | ✔ 已实现(PC) | ✔ 允许（Stage 输入→流水线→Stage 输出） | ✔ A-1 经流水线 / A-2 经 Worker | ✔ 新 Provider | △ 待 C 落地后作为一种 Provider |
| 层间流水线的一个 stage | — | ✘（stage 是层段不是请求） | ✘ 流水线内不嵌流水线 | ✔ **A-1 即此**（孤岛=一个流水线节点） | ✘（API 不暴露层段） | ✘ |
| TP 孤岛内部 | 岛内自治，QLH 不感知 | 同左 | 同左 | 同左 | 同左 | 同左 |

三条关键判断：

1. **任务链 ⊃ 层间流水线：合法且已在架构中预留**（《细化方案》T4"Provider 组合"、§6.1 示例 `candidate_b (PyTorch layer provider)`）。实施上只需把现有流水线包装为满足 `ExecutionProvider` 契约的 `PyTorchLayerProvider`（《混合规划》H1 的既定工作），Stage 输入 = 完整 messages，输出 = 生成文本，内部 hidden state 流转不外泄。
2. **层间流水线 ⊃ TP 孤岛：合法，且这是路线 A-1 的本质**——流水线的一个 stage 由孤岛承担，但对流水线协议而言它就是一个节点。反之"流水线 stage = 外部 API"不合法，因为 OpenAI 端点不接收 hidden state。GGUF stage（Mesh-LLM sidecar，《混合规划》§6）如果落地，同理以整段/整链形式接入任务链，不与 PyTorch 流水线混层。
3. **任务链 ⊃ 外部辅助：合法且是外部辅助的主要消费场景**。典型混合图：

```text
retrieve (主节点)
   ├─> candidate_a: full_inference @ PyTorch 层流水线(含 TP 孤岛段)   ← mesh 内容量
   └─> candidate_b: full_inference @ ExternalOpenAIProvider(7B+)     ← 外部质量
            ↓
   verify: 外部大模型交叉校验 (B)   或  本地规则校验
            ↓
   aggregate: local_full_model (主节点，唯一正文输出者)
```

### 3.2 两级图调度：island 间 vs island 内

现有 `GraphOrchestrator`（最大带宽生成树 + DFS，见[图算法](图算法.md)）只处理 mesh 层拓扑。引入孤岛后采用**超节点（supernode）**模型：

```text
第一级: island 间 (QLH GraphOrchestrator, 边权 = Tailscale 实测带宽/RTT)

   [主节点 PC]───80Mbps───[从节点 B]
        │
      60Mbps
        │
   [孤岛网关 G]  ←—— 图算法只看到这个顶点 (聚合画像: 2×24GB, benchmark_passed)
   ┌─────┴──────────────────────────┐
   │ 第二级: island 内 (Provider 自治,│
   │  QLH 不感知)                    │
   │   GPU0 ══NVLink/10GbE══ GPU1   │
   │      vLLM TP=2 / device_map    │
   └────────────────────────────────┘

   [外部 API 端点]  ←—— 不入图；作为 Provider 由 registry 管理，只有健康/并发闸门
```

- **island 间（QLH 负责）**：图顶点 = {普通节点} ∪ {孤岛网关}；边权 = mesh 实测带宽/RTT（`graph_orchestrator._estimate_bandwidth/_get_node_latency`）。孤岛内部拓扑**不进入**该图——只以聚合画像（算力、显存、岛内互联基准通过标志）影响 `_calc_node_weight` 与 `_assign_layers`。
- **island 内（Provider/运行时负责）**：vLLM Ray placement、llama.cpp RPC 设备表、或多卡 device_map，由孤岛自己调度；QLH 只消费其 ready/健康信号（对应《细化方案》§5.7 的 rank ready 语义）。
- 改动量评估：`GraphOrchestrator` 核心算法零改动；新增的只是节点画像字段与准入校验。这与 HexGen-2 的"图划分定组、组内定并行"两级结构同构，但 QLH 把第二级完全外包给成熟运行时——**不自研 collective，是本方案与 HexGen/Helix 的刻意差异**。

### 3.3 KV cache 归属与会话粘性

| 执行位置 | KV 归属 | 多轮会话影响 |
|---|---|---|
| 层流水线各 stage | stage 所有者本地（现行设计，`核心技术原理.md` §3） | 拓扑重排 = KV 作废，整 attempt 重来（现行语义不变） |
| TP 孤岛 | 岛内运行时（vLLM paged KV 等） | 孤岛节点故障 = 会话 KV 丢失 → 从 messages 重建 |
| 外部 API | 外部服务，跨请求不保证保留 | 每轮全量 prefill；需 provider 粘性策略降低切换 |
| draft-verify | 双份：本地 draft KV + 外部 verify KV | 两侧必须同步推进；任一侧丢失即退出辅助模式降级本地 |

调度新增一条排序因素（并入《细化方案》§4.8）："KV 已驻留的 provider 优先"，避免多轮对话在 provider 间乒乓。

### 3.4 容错互扰分析

嵌套不改变故障域铁律（《细化方案》§2.2：attempt 边界切换 Provider）：

- 孤岛内 rank 崩溃 → 网关探活失败 → 该逻辑节点下线 → 复用**现有**节点下线→重编排→attempt 重试路径；QLH 不需要理解岛内 rank。
- 外部 API 超时/5xx → `ProviderExecutionError(retryable=True)` → `task_graph.py` 既有 Provider fallback 链换本地 Provider 重试该 Stage。
- 嵌套统计沿《细化方案》§6.2：外层 `execution_mode=task_graph` + 内层 `stage_provider=external_api/tensor_island`，两级都如实上报，不得把孤岛 4 卡算成 4 个参与节点（对 QLH 是 1 个）。

### 3.5 何时不值得结合

- **单机可满足的短交互**（Q0）：任何外部化都净增 RTT 税，Auto 决策顺序第 2 条已排除（《细化方案》§6.3）。
- **双候选小图**：当前 `dual_candidate` 图规模小，先按既定计划完成多 Worker 验收，不为它引入孤岛/外部混编。
- **流水线套流水线、Stage 间传 hidden state、Android 进任何 tensor 组**：维持既有禁令。
- **跨 mesh 的 prefill 卸载（C-2）**：§2.3 已量化否决。
- **外部服务不稳定（丢包/限额）时的 verify 关键路径**：verify 放外部会把外部可用性引入每条工作流关键路径，初期 verify 保留本地 fallback。

| 外部 GPU 成本/配额 | B/C 实验受限 | 按小时租用只跑 E2/E4 关键点；或用实验室共享机 |
| llama.cpp RPC 上游破坏性变更 | E1b 返工 | 锁定 commit（沿《混合规划》§14 惯例）；失败仅影响 GGUF 变体 |
| draft-verify 接受率过低（模型族不匹配） | C-1 无收益 | 换同族大模型（Qwen 1.8B draft ↔ Qwen 7B/14B verify）；仍低则结论"不适用"归档 |
| 外部数据外发合规 | B 默认不可用 | 作用域默认 `trusted_tailnet`，外部路由仅白名单请求 |

---

## 5. 结论与建议优先级

1. **先做 A（TP 孤岛）**：与既有架构零冲突——孤岛=一个逻辑节点，图算法、层协议、故障域全部复用；单机多卡形态今天就能启动；它同时是《细化方案》X0–X2 张量 Provider 路线的低成本前置验证。
2. **次做 B（外部服务 Provider）**：改动集中在 `task_provider.py` 新类 + `ModelIdentity` 小扩展，且直接复用《混合规划》H3 ExoProvider 的既定形态（exo 只是 OpenAI 端点的一种）；价值在"全模型级辅助"与任务链高质量后端，但数据作用域与取消语义必须先行。
3. **C（投机解码）纯探索**：draft-verify 是唯一 KB 级跨 mesh 通信的深度辅助形态，理论收益清晰，但触碰核心解码循环且依赖外部有状态 verify 端点，只以独立实验模式推进；**prefill 卸载跨 mesh 已被 KV 体积（512 token ≈ 96MB）量化否决，不立项**。
4. 任务链 × 流水线 × 孤岛的组合在架构上已被《细化方案》§6.1 规则覆盖，无需新协议，只需 Provider 包装、超节点画像与两级统计；混合编排放最后（阶段 3），且以"收益超过 B 直连"为存活条件。
