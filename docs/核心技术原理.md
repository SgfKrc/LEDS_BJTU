# 核心技术原理

> 状态：现行
> 更新日期：2026-07-26
> 适用范围：多引擎、三种分布式拆分与外部辅助路线的概念边界
> 定位：说明当前多引擎与分布式推理的概念边界；实现细节以源码和专项文档为准。

## 1. 推理引擎与模型工件

QLH 当前有两条本地推理引擎路径，另有两条把整请求交给外部运行时的辅助路径：

| 引擎 | 模型工件 | 主要设备 | 当前分布式能力 |
|------|----------|----------|----------------|
| PyTorch/Transformers | Safetensors | CUDA PC，也可按配置回退 CPU | PC 连续层段流水线 |
| llama.cpp | GGUF | CPU/集显 PC、Android | 当前为单节点完整推理 |
| `island`（TP 孤岛，阶段 1 PoC） | 无本地工件；由孤岛后端自管 | 网关 PC 节点 + 集群外张量并行运行时 | 整请求推理；对集群呈现为单个逻辑节点，不参与层拆分 |
| `external_api`（外部推理服务，阶段 1 PoC） | 无本地工件；由外部端点自管 | 任意服务节点 + 集群信任域外端点 | 整请求外发；按请求路由，受数据作用域门控 |

同一个逻辑模型名称不代表工件相同。一次 PyTorch 层流水线必须使用经过校验的同模型、同架构、同 tokenizer 和兼容运行时；GGUF 量化文件不能直接加入 `LAYER_FORWARD` 流水线。

后两条路径没有本地模型文件，因此模型身份不能用文件摘要表达：任务链 `ModelIdentity` 以“端点指纹 + 后端模型名”的 sha256 摘要替代（`format="openai_api"`），统计中必须如实标注，不得伪装成本地 artifact。

## 2. 量化与算子优化

- PyTorch 路线可以按硬件和模型能力选择 FP16、INT8 或 INT4；bitsandbytes 量化主要面向 CUDA。
- llama.cpp 使用 GGUF 量化，例如 Q4_K_M、Q5_K_M 或 Q8_0。
- `torch.compile` 只适用于满足当前门控条件的 PyTorch/CUDA 路径，不是所有模型和设备的无条件优化。
- 量化会改变内存需求、速度和输出误差，评测必须记录模型工件和量化方式，不能只记录模型显示名称。

## 3. Q、K、V 与 KV Cache

自回归注意力会为历史 token 保存 Key/Value，避免每生成一个 token 都重新计算完整历史。QLH 的 PyTorch 层流水线遵循 KV 所有权本地化：

1. 每个节点只维护自己层段产生的 KV cache。
2. 节点边界主要传 hidden states、位置和任务控制信息，不在每一步搬运全部 KV cache。
3. Prefill 处理完整输入并建立缓存；Decode 通常只推进新 token。
4. 任务完成、取消、失败或超时后必须清理对应缓存，迟到结果不能复活已结束任务。

`paged_kv_cache.py` 提供通用分页缓存结构；具体模型前向中的 `past_key_values` 生命周期由模型模块和调度器共同管理。不能把“存在分页缓存类”写成所有引擎都已经使用同一种 PagedAttention 实现。

## 4. 三种分布式拆分

| 方式 | 拆分对象 | 节点间传输 | 适合场景 |
|------|----------|------------|----------|
| 层间拆分 | 连续 Transformer 层段 | hidden states 与控制状态 | 同模型容量扩展，普通局域网可研究 |
| 任务链拆分 | 检索、生成、校验等业务 Stage | 文本、JSON、文档 | 异构设备、不同模型和不同引擎协作 |
| 张量并行 | 单层矩阵/tensor shard | 高频 collective | 同构加速器与高速低延迟互联 |

完整推理 Worker 不拆模型，而是把整个请求交给一台能独立加载模型的设备。以上方式的通信、失败恢复和性能模型不同，不能共用一个“分布式：是/否”字段替代真实执行信息。

### 4.1 外部辅助：把张量并行留在集群之外

张量并行在本项目的普通局域网/Tailscale 环境内不可行，这条结论没有变。已落地的是**外部辅助**形态——不把 collective 拉进 mesh，而是把整请求交出去：

| 路线 | 交出去的边界 | 信任域 | 当前状态 |
|------|--------------|--------|----------|
| A：TP 孤岛 | 整请求；孤岛内部自行做张量并行 | 孤岛在集群信任域内（内网/Tailscale） | 阶段 1 PoC，已实施并双节点验证 |
| B：外部推理服务 | 整请求 | 端点在集群信任域**之外** | 阶段 1 PoC，已实施；默认 `opt_in` 门控 |
| C-1：draft-verify 投机解码 | 每轮的草稿 token id 与校验结果 | 同 B，复用其数据作用域门控 | 阶段 0-1 探索性 PoC，**未接生产解码循环** |

区分 A 与 B 的关键是**信任域和数据边界**，不是性能：A 的会话数据不出 mesh，B 的会话数据会离开集群，因此 B 必须有显式授权门控，而 A 不需要。三条路线的通信数学与里程碑见[张量并行外部辅助与混合拆分调研方案](张量并行外部辅助与混合拆分调研方案.md)。

### 4.2 投机解码的分布等价与其边界

draft-verify 的规则是：本地小模型每轮起草 γ 个 token，外部大模型一次前向并行校验；逐位置以 `min(1, p_verify/p_draft)` 接受，首个拒绝处从归一化残差 `max(0, p_verify - p_draft)` 重采样一个修正 token 并结束本轮，全接受时再从 `p_verify` 采一个奖励 token。

**当 `p_verify` 是精确的 verify 分布时**，产出 token 的分布恒等于 verify 模型——本地 draft 只买速度、不改质量。但这条严格性质的作用域是**投机采样纯核心**：经 OpenAI 兼容接口只能拿到 top-k logprobs，此时接受判定仍然精确（草稿 token 概率由 `token_logprobs` 精确给出、不做归一化），而拒绝时的**修正 token 残差采样受 top-k 截断**，偏差随 `QLH_SPEC_TOP_LOGPROBS` 增大而收敛。文档和报告不得把它写成端到端的严格等价。

一个已修复的教训值得记住：曾对 top-k 行按分布逐行归一化，使接受比值被整体放大 `1/M`，草稿被系统性“橡皮图章”——接受率随截断参数漂移，成为不可跨配置比较的假指标，且质量退化回 draft 模型。现已改为只清洗不缩放。

## 5. PyTorch 层流水线约束

- 单条生成链具有逐层数据依赖；多节点不必然降低单请求延迟，主要价值可能是装下更大模型或提高多请求吞吐。
- 分层依据是实测计算能力、可用内存、Embedding/LM Head 成本和网络状态，不按节点数平均，也不按“主/从”角色先验地让主节点少算。
- 图算法只负责候选节点与路径编排；最终层数还需满足模型结构、内存和首末段职责约束。
- TCP 的可靠传输不等于应用级可恢复。系统仍需任务身份、超时、取消、ready ACK、幂等和迟到结果过滤。

`paged_kv_cache.py` 已提供 `truncate(n)`，按“移除尾部 n 个 token”语义同步截断页表、回退尾页 `used` 并回收完整空页。该基础能力已通过 CPU/CUDA 验证，但尚未接入真实 draft 模型与生产投机解码循环。

详细协议见[分布式推理流水线实施计划](分布式推理流水线实施计划.md)，多 Provider 路线见[混合分布式推理体系规划](混合分布式推理体系规划.md)。
