# 引擎性能对比：单序列 / prefill / 并发（2026-09-16）

> 背景（用户 2026-09-16 命题）：
> 「单序列 PyTorch 不开某些优化绝对赢不了 llama，但也是因为当前层流水线设计太傻；
> PyTorch 在单序列没优势；而 PyTorch 长于并发。」
>
> 性质：**实测**（新增 benchmark）。关联：[推理性能现状调研](推理性能现状调研-2026-09-16.md) · [跨框架接力与异构内存分层辨析](跨框架接力与异构内存分层-辨析-2026-09-16.md)

---

## 0. 结论速览

| 命题 | 实测判定 |
| --- | --- |
| 「单序列 PyTorch 不开优化绝对赢不了 llama」 | ✅ **成立** —— 开上最关键的 KV cache 后仍 **17.29 vs 74.40 t/s（输 4.3×）**；同精度 f16-vs-f32 对比下输 **3.0×** |
| 「PyTorch 长于并发」 | ⚠️ **部分成立** —— **相对扩展率略高（13.2× vs 11.4×）**，但**绝对吞吐全面落后（1.2–2.5×）** |
| 「PyTorch 没分块，llama 高度优化」 | ✅ **成立** —— llama.cpp 的 `-b 8` 让 prefill 从 **68 → 218 t/s（3.3×）**；torch prefill 无分块 |

**一句话**：**在 8 GB 单卡单机场景，llama.cpp 在单序列与并发两个维度都领先；
PyTorch 的优势体现在"扩展率"与"多卡/多节点潜力"（尚未验证）。**

## 2. 单序列生成速度

| 配置 | 精度 / attn | 设备 | **生成 t/s** | 峰值显存 |
| --- | --- | --- | ---: | ---: |
| torch naive（**每步重喂全序列，无 KV**） | f32 / eager | GPU | 10.0 | 7.06 GB |
| **torch + KV cache** | f32 / eager | GPU | **17.29** | 7.07 GB |
| torch + KV + 低精度 | f16 / **sdpa** | GPU | 7.76 ⚠️ | 3.56 GB |
| torch naive | f32 / eager | CPU | 1.12 | — |
| llama.cpp | f16 | CPU | 8.36 | — |
| llama.cpp | Q4_K_M | CPU | 11.80 | — |
| **llama.cpp** | **f16** | **GPU** | **50.33** | 3.62 GB |
| **llama.cpp** | **Q4_K_M** | **GPU** | **74.40** | 1.21 GB |

### 2.1 三个反直觉发现

1. **KV cache 是决定性的那一项**：torch **10.0 → 17.29 t/s（+73%）**。此前 `bench_forward.py`
   每步重喂全序列（**O(n²)**），而 llama.cpp 用 KV cache（**O(n)**）—— **这才是"不开优化"的实质**。
2. **`f16 + sdpa` 反而更慢（17.29 → 7.76）**：消费级 Ada 卡的 fp16 累加路径未必更快，
   且短序列下 `sdpa` 可能走非最优内核，另有每步 dtype 转换开销。
   **→ "开优化"≠更快；PyTorch 单序列最佳档是 `f32 + eager + KV cache`。**
3. **同设备同精度仍有 3 倍差距**：`llama f16 GPU (51.77) vs torch f32 GPU (17.29)` ——
   这不是量化造成的（Q4_K_M 组差距 4.3× 才含量化因素），而是**实现质量**（kernel 融合、图优化、调度）。

## 3. Prefill：**llama.cpp 早已实现"数据分块"**

`llama-bench -b N` 调的是 **prefill 的分块批大小**（对应 GPipe 式 micro-batching）：

| llama.cpp GPU Q4_K_M | `-b 1` | `-b 8` | `-b 16` | `-b 32` |
| --- | ---: | ---: | ---: | ---: |
| **prefill (pp5) t/s** | 68.30 | **217.57** | 214.49 | 226.37 |
| **生成 (tg24) t/s** | 74.40 | 73.11 | 74.54 | 74.78 |

**→ prefill 提升 3.3×，而生成速度几乎不变。**

**这正面印证用户"PyTorch 似乎没分块"的观察**：llama.cpp 的分块是**按 prefill 批**做的，
而本项目的 torch 路径**完全没有**（prefill 5 token 耗时 93 ms，未切分）。

**⚠️ 注意**：`-b` **不是并发序列数**，它只影响单序列 prefill 的内部分块。

### 4.1 llama.cpp GPU（`llama-batched-bench`，`-npl` = 并行序列数）

| 32 | **689.75** | 523.32 |

（`-npl 16` 处出现明显跃升，推测触发了更优的 kernel 路径。）

### 4.2 PyTorch（f16 + sdpa + KV cache）

| batch | **总吞吐 (tok/s)** | ms/step |
| ---: | ---: | ---: |
| 1 | 29.21 | 34.23 |
| 2 | 56.30 | 35.52 |
| 4 | 101.20 | 39.53 |
| 8 | 172.14 | 46.47 |
| 16 | **318.88** | 50.18 |
| 32 | 384.91 | 83.14 |

### 4.3 并排对比

| batch | **llama.cpp Q4_K_M** | **torch (f16+sdpa+KV)** | 倍率 |
| ---: | ---: | ---: | ---: |
| 1 | 71.93 | 29.21 | **2.46×** |
| 2 | 123.49 | 56.30 | 2.19× |
| 4 | 166.54 | 101.20 | 1.65× |
| 8 | 208.79 | 172.14 | 1.21× |
| 16 | 553.89 | 318.88 | 1.74× |
| 32 | 689.75 | 384.91 | 1.79× |

**同精度档（llama f16 vs torch f16）** 差距更小：**1.2–1.6×**（batch 1: 46.00 vs 29.21；batch 32: 523.32 vs 384.91）。

### 4.4 扩展率

| 引擎 | batch 1 → 32 | **扩展率** |
| --- | ---: | ---: |
| llama.cpp Q4_K_M | 71.93 → 689.75 | **9.6×** |
| llama.cpp f16 | 46.00 → 523.32 | **11.4×** |
| **PyTorch f16+sdpa** | 29.21 → 384.91 | **13.2×** ✅ |

**→ 用户判断的准确表述**：
> **PyTorch 的并发**扩展率**确实更高（13.2× vs 11.4×），但**绝对吞吐**在 8 GB 单卡上全面落后（1.2–1.6× 同精度档）。**
>
> 原因：llama.cpp 的**单序列起点太高**（46–72 t/s），已接近该卡的显存带宽上限；
> PyTorch 起点低，所以有更大的**相对**提升空间，但**天花板仍低于 llama.cpp**。

**→ "PyTorch 长于并发" 在**单机单卡**上不成立；其真正潜力应在**多卡/多节点**（D 档的层流水线场景），尚未验证。**

## 5. 对引擎双档策略（L / D）的含义

| 场景 | 结论 |
| --- | --- |
| **单机、单序列、≤8 GB** | **L 档（llama.cpp）明确最优** —— 全面领先，且量化后显存占用仅为 torch 的 1/6 |
| **单机、高并发（多请求）** | **仍是 llama.cpp 领先**，但差距收窄到 ~1.2–1.6×；若追求**大 batch 吞吐**而非延迟，值得再评估 |
| **多卡 / 多节点 / 层流水线** | **D 档（PyTorch）的领域** —— 本轮**未测**（llama.cpp 无对应能力，这也是 D 档存在的理由） |
| **跨框架接力（D→L）** | ⚠️ **当前实现下代价极高**：实测 **1.44 s/步**（64 步 92 s），其中约 **1.3 s 是 Python 进程间通信开销** —— 远超两侧计算的 101 ms |

**⚠️ 跨框架接力的性能警示**（本轮新发现）：
D→L 的瓶颈**不是层间串行**，而是**每步一次的 Python 进程往返**（序列化 + 管道 + 调度）。
按此实现，接力在**性能上完全不可用**；若要实用化，必须：
① 消除进程边界（同进程双后端）；或 ② 大幅减少往返次数；或 ③ 用共享内存 + 二进制协议替代当前管道。

## 6. 未验证声明

1. **torch 的并发测试用的是 `f16 + sdpa`**（该档在单序列反而慢，见 §2.1-2）——
   未测 `f32 + eager + KV` 的并发曲线，两者对比可能不同；
2. **未测 `torch.compile`、CUDA Graph、flash-attention-2** 等更高阶优化；
3. **未测多卡 / 多节点 / 层流水线的 PyTorch 性能**（D 档的真实场景）；
4. **未测 `llama-server --parallel` 的端到端延迟**（`llama-batched-bench` 只测吞吐）；
5. **未测长上下文**（本轮 prompt 仅 5 token，KV cache 优势在小上下文中不明显）；
6. **未测 Q4_K_M vs 同等量化 torch（NF4）** 的公平对比（torch 侧全为 f32/f16）；
7. `-npl 16` 处的吞吐跃升**原因未确认**（推测为 kernel 路径切换）。
