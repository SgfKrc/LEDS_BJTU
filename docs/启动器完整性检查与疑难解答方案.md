# 启动器完整性检查与疑难解答方案

> 目标：让 Launcher 在启动主应用前后能**检查文件完整性**、按症状给出**疑难解答建议**、
> 自动修复低风险损坏，修复不可行时才引导**保留数据的卸载重装**。
> 状态：`UP-N6.0 / UP-N6.1 / UP-N6.2 / UP-N6.3 Completed（开发门，2026-08-11） / UP-N6.4 Next`。已建立构建期签名安装清单、Windows/Linux 安装事务验签、运行时只读 quick/full/deep 复验、本地症状诊断，以及受签名发布源约束的单文件原子修复；数据保留重装尚未实现。本系列隶属[独立安装包启动器与自动更新方案](安装包自动更新引导器方案.md)工作流。

---

## 1. 背景与缺口

### 1.1 现有能力（已具备，复用不重造）

| 能力 | 位置/阶段 | 覆盖 |
|---|---|---|
| 下载校验 | UP-N2 | 下载时大小 + SHA-256，篡改 fail-closed |
| 清单签名 | UP-N2 | Ed25519 验签 `/latest.json`，key rotation |
| 版本原子切换 | UP-N3 | `versions/` + current/previous 指针、健康门、回滚 |
| 健康探针 | UP-N4 | `health.ok` + 隔离子进程 `--health-check` |
| 脱敏诊断包 | UP-N4 | 槽指针、有限日志，token/secret 脱敏 |

### 1.2 缺口（本方案补什么）

1. **安装后没有文件级完整性基线**：下载时校验过，但装完被删/被杀软误删/被改后无从对比；
2. **错误只报"失败"，不告诉用户"怎么办"**：缺 DLL、版本不匹配、权限、磁盘满等不同症状需要不同建议；
3. **没有自动修复**：小范围损坏（一个文件）也要用户手工重装；
4. **卸载重装丢数据**：`models/`（约 5.8GB，含外部导入的 SD 资产）重下成本高，重装引导必须保留数据。

**设计定位**：健康探针回答"能不能启动"，`verify` 回答"为什么不能启动"，`diagnose` 回答"怎么办"，`repair` 回答"能不能自动修"，全部失败才到"保留数据的卸载重装"。

## 2. 方案设计

### 2.1 安装清单 `install-manifest.json`（新增）

- **已完成生成与结构门**：`packaging/install_manifest.py` 在最终安装树上生成 schema v1：`app_id/version/platform/variant/package_kind/generated_at`、规范排序的 `files[path,size,sha256,kind]`、`scope=application_files_only` 和 UP-N2 `key_id/signed_at/signature`。路径必须为安全 NFC 相对路径；链接/reparse point、路径逃逸、大小写碰撞、非普通文件、扫描期间变化、未知字段和自指向清单均 fail-closed。
- **位置**：安装目录 `manifest/install-manifest.json`；清单自身不参与哈希，其他程序文件均在签名范围内。
- **已完成签名与落盘门**：构建命令缺 `QLH_SIGNING_KEY` 时拒绝发布；签名后立即按内置/指定 UP-N2 信任集复验并原子落盘。CPU、CUDA、Launcher ZIP/Setup 和 Linux `.deb` 都已接线。Windows 三个 Inno Setup 在 `ssPostInstall` 运行独立冻结验签器，Linux `postinst` 用包内 venv 验签；异常退出码会中止安装事务。Launcher 远端 A/B 自更新要求带签名清单，且签名清单的版本、变体和包身份必须与 staging 请求一致；历史无清单 bundle 只保留手动兼容入口，不能进入远端自动更新路径。
- **排除**：`models/`、`chat_history/`、`logs/`、`config/`、`local_docs/` 同时从构建扫描和清单契约中拒绝；即便重签也不能把这些用户数据路径写入 `files`。
- **阶段边界**：UP-N6.0 建立并验证基线签名，UP-N6.1 只读比对该基线；UP-N6.3 只可使用该已验签基线限制写入路径、大小和哈希，绝不重写清单本身。

### 2.2 完整性检查 `verify`（新增命令）

`qlh-launcher verify [--root <安装目录>] [--level quick|full|deep] [--json]`（`bjtu verify` 同样提供；Windows 仅主应用的兼容安装直接调用同包冻结验签器）

| 级别 | 耗时 | 检查内容 |
|---|---|---|
| `quick`（默认，秒级） | 快 | 清单签名、`version.txt`、应用/Launcher 入口、Launcher `health.ok`、关键 Python runtime、独立验签器；仅哈希这些清单内关键文件 |
| `full` | 中 | 清单全部文件：不大于 64MiB 的文件全量 SHA-256；大文件验证大小并读取首/中/尾固定区段，证明可读性 |
| `deep` | 慢 | 全量 SHA-256（怀疑磁盘损坏/杀软批量误删时用） |

- 输出：`passed/failed` 列表（路径、期望 vs 实际、类别 `missing|size|hash|signature|unsafe|io|version`）、修复建议、`--json` 供 GUI/TUI；完整性不通过时 CLI 退出码为 `3`。
- **采样边界**：schema v1 只保存整文件 SHA-256，没有发布方签名的抽样摘要。因此 `full` 的大文件采样只能发现不可读扇区或 I/O 错误，不能声明发现所有同尺寸篡改；需要防篡改保证时必须使用 `deep`。后续若增加抽样摘要，必须提升清单 schema 并保持旧版本 fail-closed。
- **触发时机**：Launcher 的启动调用抛出异常后自动跑 `quick` 并把首个完整性故障附入错误信息；用户可手动跑任意级别。检查不进入正常启动成功路径，也不等待或干预已成功拉起的主进程。
- **扫描边界**：三个级别都只访问已签名清单枚举的程序路径，不递归遍历安装树；`models/`、`chat_history/`、`logs/`、`config/`、`local_docs/` 不会被读取、列举或写入。

### 2.3 疑难解答知识库 `diagnose`

`qlh-launcher diagnose [--root <安装目录>] [--error <本地错误文本>] [--json]`（`bjtu diagnose` 同样提供）

症状 → 检查项 → 建议的映射表（v1 内置、10 类、后续可扩展）：

| 症状 | 自动检查 | 建议 |
|---|---|---|
| 安装清单签名失效 | `quick verify` 的 `signature` | 停止使用该目录，从可信源覆盖安装 |
| 程序文件缺失/篡改 | `quick verify` 的 `missing/size/hash/unsafe/io` | 可显式执行 `repair`；`unsafe/io`、无可信源或超阈值时改用覆盖安装 |
| 版本不匹配 | `quick verify` 的 `version` | 走 UP-N3 更新或回滚（`bjtu update`） |
| DLL/pyd 加载失败（Windows） | 仅匹配本地启动错误症状 | 修复 VC++ Redistributable；确认 CPU/CUDA 变体 |
| 显存/驱动异常 | CUDA 安装包才受限调用无 shell 的 `nvidia-smi` | 修复 NVIDIA 驱动；无 GPU 时改用 CPU 包 |
| 磁盘空间不足 | 安装卷可用空间（低于 2GiB）或本地错误症状 | 清理磁盘；模型清理先运行 `models_clean` dry-run |
| 更新/网络失败 | 仅匹配本地错误症状，不发起网络请求 | 换源、手动下载；校园网场景检查 DERP/WSS |
| 权限不足 | 安装目录 `os.access` 与本地错误症状 | 改用可写用户目录或管理员权限 |
| 疑似杀软隔离 | **可信签名基线**下出现 `missing` | 检查隔离记录、加白安装目录后重跑 verify |
| 模型资产问题 | 仅匹配本地错误症状 | 运行 `gguf_verify`/`models_sweep`；不自动下载或扫描模型 |

- 输出：稳定 JSON 问题清单（严重度、`auto_repair_available=false`、证据类别和人工步骤），或 CLI/TUI/GUI 人类可读摘要；有问题时退出码为 `3`。启动错误文本只用于本次症状匹配，**不会原样进入 JSON 或 ZIP**。
- 诊断包：Launcher 导出 UP-N4 脱敏 ZIP 时，自动生成状态目录内的 `qlh-diagnose-*.json`，并以 `diagnosis/` 条目附入；该摘要剔除安装根路径与失败文件路径，仍经既有 secret/token 脱敏。
- 边界：不访问更新源、不下载、不修复、不递归扫描安装树；除安装清单列举的程序文件外，不读取 `models/`、`chat_history/`、`logs/`、`config/`、`local_docs/`。

### 2.4 自动修复 `repair`（推荐替代"直接卸载重装"）

`qlh-launcher repair [--root <安装目录>] [--source <latest.json>] [--json]`（`bjtu repair` 同样提供）是显式维护操作；正常启动和 `diagnose` 都不会自动触发写入。

- **本机前置**：先执行 `deep verify`，再直接验签本机 `install-manifest.json`。只有 `missing`、`size`、`hash` 三类、且路径已列入该基线的失败项可以进入候选集；`signature`、`unsafe`、`io`、`version` 或未知失败均 fail-closed 并建议覆盖安装。
- **发布源前置**：从配置的更新源取得已通过 UP-N2 Ed25519 验签、且 `tag` 与本机基线 `version` 完全相同的更新清单，选择 `kind=repair-index` 资产。该索引自身先经过外层已签名清单的大小/SHA-256 校验；索引中的 `app_id/version/platform/variant`、每个相对路径、大小和 SHA-256 还必须逐项匹配本机基线。载荷 URL 仅可留在索引同一 origin，不能借索引转向第三方下载源。
- **策略**：先下载并校验全部候选载荷，再逐文件复制到同目录临时文件并 `os.replace` 原子替换；已有旧文件先复制到 Launcher 状态目录 `repair-backups/<timestamp>/*.bak`。任何替换异常或最终复验失败都会尽力从 `.bak` 回滚已改项目。
- **阈值**：损坏文件数 > 10 或修复总量 > 64MiB → 不联网、不写入，升级建议"整包修复/重装"，避免逐文件低效。
- **复验**：修复完成后自动重跑 `deep verify`，不是仅运行 quick；仍失败时回滚并进入 2.5 兜底。
- **保护**：只遍历、下载和写入签名程序路径；**绝不读取或触碰** `models/`、`chat_history/`、`logs/`、`config/`、`local_docs/`。CPU/CUDA 载荷变体由本机签名基线而非 GPU 自动探测选择。

发布方使用 `python packaging/repair.py build-index --root <最终应用树> --output packaging/dist/QLH-Edge-Inference-Repair-v<version>-<platform>-<variant>.json --payload-dir packaging/dist/repair/<version>/<platform>/<variant> --url-prefix /repair/<version>/<platform>/<variant> --trusted-keys-dir packaging/pubkeys` 生成索引和去重载荷。`serve.py` 只将顶层索引作为当前版本 `repair-index` 资产发布；静态载荷只由该索引引用。该生成步骤会先对最终应用树执行 `deep verify`，拒绝从损坏树发布修复内容。

### 2.5 兜底：保留数据的卸载重装引导

> 比"直接卸载重装"更好的方案：**数据保留 + 自动重装 + 数据重新关联**，模型/聊天记录一次都不丢。

1. **卸载不删用户数据**：卸载器只删程序目录、注册表/环境变量条目、快捷方式；`models/`、`chat_history/`、`logs/`、`config/` 若位于安装目录内，先迁移到 `%LOCALAPPDATA%/QLH-Edge-Inference/data/` 再删程序目录（与 UP-N1.1"卸载 Launcher 不误删模型、配置、日志"规则一致，此处显式化为流程）。
2. **自动重装**：诊断报告 → 一键卸载（数据已保留）→ 从更新源拉取最新稳定包（复用现有下载/验签管线）→ 静默安装。
3. **数据重新关联**：安装后首次启动检测到保留的数据目录，自动重建配置指向（`QLH_MODELS_DIR` 或 junction 重挂），不要求用户手工搬文件。
4. **人工兜底**：自动重装也失败时，输出保留数据的路径清单 + 手工安装步骤，用户可随时自行重装并关联。

### 2.6 用户数据保护红线（贯穿所有阶段）

- 任何 `verify`/`repair`/`uninstall`/重装路径**不得删除、覆盖、迁移** `models/`、`chat_history/`、`config/`、`local_docs/`；
- `repair` 只写程序文件，写前快照 `.bak`；
- 数据目录位置发生变化必须显式告知用户并确认。

## 5. 边界

- 不进入主应用正常启动关键路径（quick 检查只在启动失败时自动触发）；
- 不自动下载/修复模型，模型问题只提示并联动模型工具（`gguf_verify`、`models_sweep`，见[模型通用小工具调研与方案](模型通用小工具调研与方案.md)）；
- 修复源与更新源一致，全部受 UP-N2 签名门控，不允许未签名内容落地；
- Android 更新仍归 UP-N5，不涉及本方案。
