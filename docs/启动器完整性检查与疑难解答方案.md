# 启动器完整性检查与疑难解答方案

> 目标：让 Launcher 在启动主应用前后能**检查文件完整性**、按症状给出**疑难解答建议**、
> 自动修复低风险损坏，修复不可行时才引导**保留数据的卸载重装**。
> 状态：调研完成，待实施（登记为 UP-N6 系列，隶属[独立安装包启动器与自动更新方案](安装包自动更新引导器方案.md)工作流）。

---

## 1. 背景与缺口

### 1.1 现有能力（已具备，复用不重造）

| 能力 | 位置/阶段 | 覆盖 |
|---|---|---|
| 下载校验 | UP-N2 | 下载时大小 + SHA-256，篡改 fail-closed |
| 清单签名 | UP-N2 | Ed25519 验签 `/latest.json`，key rotation |
| 版本原子切换 | UP-N3 | `versions/` + current/previous 指针、健康门、回滚 |
| 健康探针 | UP-N4 | `health.ok` + 隔离子进程 `--health-check` |
| 脱敏诊断包 | UP-N4 | 槽指针、有限日志，token/secret 脱敏 |

### 1.2 缺口（本方案补什么）

1. **安装后没有文件级完整性基线**：下载时校验过，但装完被删/被杀软误删/被改后无从对比；
2. **错误只报"失败"，不告诉用户"怎么办"**：缺 DLL、版本不匹配、权限、磁盘满等不同症状需要不同建议；
3. **没有自动修复**：小范围损坏（一个文件）也要用户手工重装；
4. **卸载重装丢数据**：`models/`（约 5.8GB，含外部导入的 SD 资产）重下成本高，重装引导必须保留数据。

**设计定位**：健康探针回答"能不能启动"，`verify` 回答"为什么不能启动"，`diagnose` 回答"怎么办"，`repair` 回答"能不能自动修"，全部失败才到"保留数据的卸载重装"。

---

## 2. 方案设计

### 2.1 安装清单 `install-manifest.json`（新增）

- **生成时机**：安装器/更新器成功落盘后，扫描程序目录生成：相对路径、大小、SHA-256、所属资产 kind、平台、变体、版本、时间戳。
- **位置**：安装目录 `manifest/install-manifest.json`（与 `version.txt` 同级，随程序目录走）。
- **签名**：清单本体由发布方在构建时签名（沿用 UP-N2 Ed25519 体系），安装时验签后落盘；本地只读，repair 不重写清单本身。
- **排除**：`models/`（用户数据，可迁移/外部导入，不冻结哈希，只记录"期望存在"提示）、`chat_history/`、`logs/`、`config/`、`local_docs/`。

### 2.2 完整性检查 `verify`（新增命令）

`qlh-launcher verify [--level quick|full|deep] [--json]`

| 级别 | 耗时 | 检查内容 |
|---|---|---|
| `quick`（默认，秒级） | 快 | 清单签名、`version.txt`、入口 EXE、`health.ok`、关键 dll/pyd/venv python、槽指针 |
| `full` | 中 | 清单全部文件：小文件全量哈希，大文件（>64MiB）大小 + 抽样哈希 |
| `deep` | 慢 | 全量 SHA-256（怀疑磁盘损坏/杀软批量误删时用） |

- 输出：`passed/failed` 列表（路径、期望 vs 实际、类别 `missing|size|hash|signature`）、修复建议、`--json` 供 GUI/TUI。
- **触发时机**：主应用启动失败时自动跑 `quick`；用户可手动跑任意级别；不进入正常启动关键路径。

### 2.3 疑难解答知识库 `diagnose`（新增命令）

症状 → 检查项 → 建议的映射表（v1 内置，后续可扩展）：

| 症状 | 自动检查 | 建议 |
|---|---|---|
| 启动即崩 / 缺模块 | `quick verify` 缺文件 | 走 `repair`；修复失败再引导重装 |
| DLL/pyd 加载失败（Windows） | 检查缺失项 + 变体 | 重装对应 VC++ Redistributable；确认 CPU/CUDA 变体与驱动匹配 |
| 版本不匹配 | `version.txt` vs 清单 vs 更新源 | 走 UP-N3 更新或回滚（`bjtu update`） |
| 显存/驱动异常 | `nvidia-smi` 存在性与版本 | 提示驱动版本要求、CUDA 变体选择 |
| 磁盘满 | 剩余空间 vs 需求 | 提示清理（可联动模型工具 `models_clean` 的 dry-run） |
| 更新/网络失败 | 区分无网 / UDP 封锁 / 源超时 | 换源、手动下载、校园网场景给 DERP/WSS 提示 |
| 权限不足 | 目录可写性 | 提示修复到用户目录或管理员权限 |
| 杀软误删 | verify 缺文件且无更新记录 | 加白名单 + `repair` 补文件 |
| 模型缺失/损坏 | `models/` 存在性 + 哈希侧车 | 提示用模型工具 `gguf_verify`/`models_sweep`，不自动下载模型 |

- 输出：问题清单 + 每项"严重度 / 可自动修复 / 人工步骤"，GUI/TUI 可展示；`--json` 供诊断包引用。

### 2.4 自动修复 `repair`（推荐替代"直接卸载重装"）

- **前置**：清单签名有效、更新源可达（受 UP-N2 签名门控）。
- **策略**：逐文件处理——`missing/hash` 不匹配的文件从当前版本对应资产重拉（复用现有 `.part` + SHA-256 + 原子替换管线），**不整包重下**。
- **阈值**：损坏文件数 > 10 或修复总量 > 64MiB → 升级建议"整包修复/重装"，避免逐文件低效。
- **复验**：修复完成后自动重跑 `quick verify`；仍失败才进入 2.5 兜底。
- **保护**：只写程序文件；被替换文件先入 `.bak` 槽；**绝不触碰** `models/`、`chat_history/`、`config/`、`local_docs/`。

### 2.5 兜底：保留数据的卸载重装引导

> 比"直接卸载重装"更好的方案：**数据保留 + 自动重装 + 数据重新关联**，模型/聊天记录一次都不丢。

1. **卸载不删用户数据**：卸载器只删程序目录、注册表/环境变量条目、快捷方式；`models/`、`chat_history/`、`logs/`、`config/` 若位于安装目录内，先迁移到 `%LOCALAPPDATA%/QLH-Edge-Inference/data/` 再删程序目录（与 UP-N1.1"卸载 Launcher 不误删模型、配置、日志"规则一致，此处显式化为流程）。
2. **自动重装**：诊断报告 → 一键卸载（数据已保留）→ 从更新源拉取最新稳定包（复用现有下载/验签管线）→ 静默安装。
3. **数据重新关联**：安装后首次启动检测到保留的数据目录，自动重建配置指向（`QLH_MODELS_DIR` 或 junction 重挂），不要求用户手工搬文件。
4. **人工兜底**：自动重装也失败时，输出保留数据的路径清单 + 手工安装步骤，用户可随时自行重装并关联。

### 2.6 用户数据保护红线（贯穿所有阶段）

- 任何 `verify`/`repair`/`uninstall`/重装路径**不得删除、覆盖、迁移** `models/`、`chat_history/`、`config/`、`local_docs/`；
- `repair` 只写程序文件，写前快照 `.bak`；
- 数据目录位置发生变化必须显式告知用户并确认。

## 3. 阶段计划

| 阶段 | 状态 | 内容 | 完成判据 |
|---|---|---|---|
| UP-N6.0 安装清单 | Candidate | 构建时生成签名 `install-manifest.json`，安装/更新时验签落盘 | 契约测试：字段齐全、篡改拒绝、models 等数据目录不在清单 |
| UP-N6.1 verify | Candidate | quick/full/deep + `--json`；启动失败自动 quick | 故障注入：删文件/改哈希/删 health.ok 各场景输出正确类别与建议 |
| UP-N6.2 diagnose | Candidate | 知识库 v1（2.3 表）+ GUI/TUI 展示 | 10 类症状各有映射与人工步骤；诊断包引用 JSON |
| UP-N6.3 repair | Candidate | 单文件重拉修复 + 阈值 + 修复后复验 | 注入 1-3 个损坏文件修复成功；超阈值升级建议；数据目录零触碰断言 |
| UP-N6.4 数据保留重装 | Candidate | 卸载数据迁移、自动重装、数据重新关联 | 端到端：安装→破坏→repair 失败→卸载（数据在）→重装→数据关联成功 |

## 4. 测试与发布门

- 沿用 `tests/test_launcher_slots.py`、`tests/test_signing.py` 风格补契约测试；
- 故障注入矩阵：删关键文件、篡改哈希、模拟杀软、磁盘满、断网、权限拒绝；
- 发布门：Windows 干净机 + Linux `.deb`；"数据保留重装"端到端门（重装后 `models/`、`chat_history/` 完整且被重新关联）。

## 5. 边界

- 不进入主应用正常启动关键路径（quick 检查只在启动失败时自动触发）；
- 不自动下载/修复模型，模型问题只提示并联动模型工具（`gguf_verify`、`models_sweep`，见[模型通用小工具调研与方案](模型通用小工具调研与方案.md)）；
- 修复源与更新源一致，全部受 UP-N2 签名门控，不允许未签名内容落地；
- Android 更新仍归 UP-N5，不涉及本方案。
