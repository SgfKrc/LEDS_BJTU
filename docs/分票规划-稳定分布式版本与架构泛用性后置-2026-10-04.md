# 分票规划：稳定分布式版本优先（2026-10-04）

本规划落实《关键架构泛化与分布式调度可用性审查报告》的裁定。近期目标是做出一条可重启、可重连、可验收的分布式生产链；模型架构泛用性和 KTransformers 优化均后置到同一优先级，不与稳定性收敛抢占主线。

## 产品裁定

1. **A1 relay 从产品调度入口剔除。** A1 依赖 probe/SSH 隧道和 loopback 段服务，保留为技术探针与历史证据，不再作为 `/api/chat` 的生产候选、容量来源或可用性证明。探针脚本、工件和证据暂不删除，避免丢失复现材料；后续单独做归档票。
2. **A3 Route A 是本阶段唯一生产主线。** 生产请求只允许统一的 `stage_offer_v3`/task-worker 链；legacy layer relay 不再与 A3 并列参与同一调度域。暂不支持的节点应明确处于不可用状态，而不是进入另一套 relay 协议。
3. **“分布式可用”必须 fail-closed。** 只有 `distributed_used=true`、`fallback=false`、`claimed_layers` 非空并通过逐 token 对拍，才能计为成功；本地整模回退、探针成功和 HTTP 200 均不能替代该门槛。

## P0：近期必须完成

### DIST-0：生产线路收敛与 A1 退场

**状态：已完成（2026-10-04）。** 生产入口默认 probe-only，A1 不再作为生产候选；实现与回归见 `PIPELINE_RELAY_PROBE_ONLY` 及 relay 线路测试。探针代码和证据仍保留。

**目标**：删除 A1 对生产调度的影响，保留探针能力但与产品路径隔离。

- 在 scheduler 的候选、readiness、assignment、forward 和 fallback 判据中禁止读取 `QLH_RELAY_ENABLED`/`QLH_RELAY_SEGMENTS` 作为生产能力。
- 将 relay 入口标成 probe-only；生产请求若检测到该配置，只记录具名诊断并继续走 A3，不能悄悄切换到 A1。
- 清理或隔离 scheduler 侧无效 relay session/cache；探针脚本继续使用独立入口。
- 更新线路清单和运行手册，明确 A1 证据不计入产品验收。

**验收**：开启 A1 环境变量不会改变生产 assignment；混合 legacy/A3 不再进入半可用状态；生产日志不出现 A1 relay 委派；A3 的候选、层声明和错误原因可独立追踪。

### DIST-1：配置生命周期单一事务源

**状态：恢复路径已实测通过（2026-10-05，两段链）；完整的单一事务状态机仍未合并。**

实测结论（2026-10-05，master pytorch `[0,16)` + Surface GGUF `[16,24)`，两段）：重启后闸门按设计挂起、worker 重连 hello 触发权威重发、闸门解除、请求成功（`distributed_used=True` / `fallback=False` / `claimed_layers=[16,24]`）。**这条路径此前从未实测过**（`:34` 自述「三机重启实测仍待执行」），首次实测即暴露出**两个此前未知的缺陷**，均已修复：

1. **恢复闸门死锁**：闸门解除要求「新代际的权威重发」，而重发**只在请求路径**触发、请求又被闸门自身拒绝 ⇒ 没有任何路径产生新代际（实测：三机全在线、TCP 已重连、`hello accepted=True`，请求仍返回 `pipeline_recovery_pending` 直到超时）。修法：worker 重新 hello 是「节点回来了」的权威信号，在 `_handle_task_worker_message` 的 hello 分支里、恢复期补一次 `request_authoritative_layer_sync(require_distributed=True)`（`3ddb3695`）。
2. **双栈下进程内两套 `TCPServer`**：`run_api_servers()` 在通配地址下为 `0.0.0.0` 与 `::` 各起一个 `uvicorn.Server`（共享同一 `app`）⇒ lifespan 跑两次 ⇒ `scheduler.start()` 跑两次（无幂等保护）⇒ 两个实例同时监听 8888，`_tcp_server_default` 被覆盖，而 worker 的连接只被其中一个 accept。请求线程读到空 `clients`，连锁导致 `worker_tcp_disconnected`、assignment 拿不到 `execution="stage_offer_v3"`、capacity 求解器从未被调用而退化成 `simple_weight` 分配（`Layer 13-20` / `15-24` 即由此而来）。修法两层：`Scheduler.start()` 加**并发**幂等守卫（锁内「检查 + 占位」，`9dcd1e04`）+ 根因面让 `_lifespan` 的启动/关闭**进程级只执行一次**（`5fb024cb`）。

顺带修掉一个误导诊断的展示缺陷：stage-only 提交漏回写 active plan 的 `transaction_phase`（legacy 路径有、Route A 没有），使 `/api/cluster/pipeline-capacity` 恒定返回求解器初值 `planned` 且投影里没有 `config_id`/`generation` ⇒ 看上去像「事务不存在」（`2bd885ac`）。

**仍未完成**：`_layer_config_*` 那 ~20 个状态集合没有合并成单一显式状态机；`assignment_id` 维度仍未引入（`:38` 的版本三元组只落实了前两维）。

本轮实现：REGISTER ACK 后被标记为 pending 的新连接，即使 hello 能力内容与上一代完全相同，也会被视为一次连接代际变化并触发层配置重新发布；同一连接内的重复 hello 仍保持幂等，不会形成自激重推。

本轮继续实现：容量事务以 `pipeline_config_lifecycle_v1` 写入本地 SQLite，记录 `config_id/generation/phase/worker_ids` 等受限元数据；master 启动时若发现上次事务处于 `preparing/committing/ready`，先挂起分布式就绪与普通整模回退，等待基于当前在线节点重新发布并完成 ACK。旧记录只作为恢复闸门，不会被直接当作新连接的活动配置；恢复失败保持 fail-closed。

本轮新增回归契约：重启后旧 `config_id` 不得直接使 readiness 变为 ready；新代际在所有期望 worker 完成确认前不能解除闸门；Route A stage-offer worker 需重新满足当前健康/能力判据；持久化记录不携带 set、模型路径或执行器对象；生命周期写入失败时，即使内存事务到达 ready 也不得解除闸门，只有 ready 状态成功落库后才能继续；相同或更旧的持久化 `(config_id, generation)` 不能被当作新活动配置。验证已完成：`tests/test_scheduler.py` 318 passed，`tests/test_local_store.py tests/test_task_worker_adapter.py` 90 passed，另有编译检查和 `git diff --check`；三机重启实测仍待执行。

**目标**：消除 master 重启后 release 与 re-ACK 互相打断、节点没有已确认活动配置的问题。

- 以 `(config_id, generation, assignment_id)` 作为唯一活动配置版本，任务只引用已 commit 版本。
- 将 push、ACK、release、re-ACK、restart rehydrate 合并到一个显式状态机；旧 generation 的 ACK/release 必须幂等忽略。
- master 重启后先恢复配置事务，再开放新请求；恢复失败必须具名 fail-closed。

**验收**：重启/重连窗口内无 stale active config、无旧 ACK 污染；同一配置重复 ACK 和重复 release 均幂等；连续请求不会因配置生命周期竞态回退。

### DIST-2：节点可用性与故障收敛

**目标**：将 heartbeat、task-worker lease、presence、layer readiness 收敛为可解释的可用状态。

**状态：部分完成（2026-10-05）。** 本轮按「先收拢现状」落地六项，均有回归覆盖；**完整状态机与唯一超时来源尚未达成**。

本轮实现（两段链实测：`distributed_used=True` / `fallback=False` / `claimed_layers=[16,24]`，重启前后均正常）：

1. **容量候选接入心跳新鲜度**（`8b33b950`）。容量规划此前只看 `NodeInfo.is_available()`（`state == ONLINE`），完全不看心跳；而 TCP 半开要等巡检约 129s 才置 OFFLINE ⇒ 静默节点在这段窗口里**一直占容量**，求解器会分配出既非声明区间、层数也不对的结果（实测：Y700 被带走后给出 `Layer 13-20` / `Layer 15-24`）。现在容量候选与 readiness 共用 `WORKER_HEARTBEAT_MAX_AGE`，常量已上移到 `scheduler_types`。
2. **stage worker 不再跳过 readiness 判定**（`e03c9a11`）。`:4095` 的裸 `continue` 让 v3 层段 worker 跳过**整个** failure 判定 ⇒ `worker_stage_offer_not_ready` 永远不可达 ⇒ stage worker 不健康时 readiness 仍可能报 `ready=True`（静默伪成功面）。改为基础存活检查照常参与，`worker_layer_load_failed` 只对非 stage worker 生效。
3. **force 路径下不可恢复原因快速失败**（`dc20f11f`）。`not force_distributed_assignment and reason not in recoverable` 的组合让 force 路径**连** `worker_offline` / `worker_tcp_disconnected` / `worker_heartbeat_stale` **也等满 60s** —— 而重连本身会触发权威重发，死等只是把确定的失败延迟成超时。
4. **节点掉线主动回收 reservation**（`6da6c601`）。`notify_disconnect` 此前只唤醒 pending，释放依赖上层 `task_graph._run_stage` 的 `finally` ⇒ 上层未走到就永久泄漏「已预留未执行」槽位。现在唤醒 pending 后在锁外主动 `release()`（纯本地操作，不发网络）。
5. **收拢 `NodeState`**（`7aff05d3`）。删掉从未被置位的 `BUSY` / `ERROR` 及其恒假分支，并在 docstring 写明**实际生效的是两维判据**：`NodeState`（`ONLINE`/`OFFLINE`）+ 心跳新鲜度；规划里那套 `registered/admitted/ready/leased/draining` **尚未进枚举**，语义散在 task-worker 的 `accepted`/`selected_version` 与 `Reservation`/`lease_epoch` 上。
6. **超时常量提为具名 + 写清层次关系**（`06a32e8f`）。控制面 health 的 `30.0` 裸字面量 → `TASK_WORKER_HEALTH_TIMEOUT_FLOOR_SECONDS`，并写明**为何不与 120s 合并**：两者语义与层次不同（控制面管「要不要派 stage」，流水线层管「还算不算数」），**有意让控制面更短**——先停派活、再退规划；并成一个数会让节点处于「仍被规划进层区间但已不接受 stage」的状态。

**仍未完成**：

- **唯一超时来源未达成**：进程内仍有 8 套判据，本轮只收敛 2 处。其余为 TCP 巡检 129s / recv 131s（`tcp_comm`）、Android presence lease 120s 与心跳 45s、`PIPELINE_MODEL_SYNC_TIMEOUT=60`、worker 控制面心跳 15s、PC TCP 心跳 3s。
- **其中一条判据与平台不匹配**：129s 是按 PC 的 3s 心跳（42 跳）设计的，套到每 15s 才发一次的 Android 上等价于只容忍 ~8.6 跳。未处理。
- **完整状态机未接**：规划里那套状态转移没有进 `NodeState`。
- **验收未做**：断线 / 重连 / 后台残留的「固定时间收敛」需要真机（Surface + Y700）计时验证；本轮单测覆盖了 provider 层（预约回收）与判据层（心跳新鲜度、快速失败），但没有端到端计时证据。

- 定义 `registered -> admitted -> ready -> leased -> draining/offline` 状态转移及唯一超时来源。
- 节点掉线、任务取消、配置失效必须释放 lease 并阻止旧任务结果回写。
- readiness 不满足时快速返回具名错误，禁止等待多个互相独立的超时后才 fallback。

**验收**：Surface/Y700 断线、重连、后台任务残留和 master 重启均能在固定时间内收敛；无重复分配、无旧任务结果串台。

### DIST-4：可观测性与发布闸门

## P1：稳定版之后并行开发

### GEN-1：架构适配器与模型描述符契约

把模型适配从 Qwen 分支提升为 descriptor/adapter 注册契约，覆盖 tensor layout、layer loader、forward/cache、norm/head、prompt 和 KV 语义。第一阶段先选择一个非 Qwen decoder 做完整对拍，不以“能加载”作为支持标准。

**分类依据：按「计算图契约」分，不按模型系列名分。**

对齐 llama.cpp 的做法（依据：`llama-arch.h` 的 `LLM_ARCH_*`，桌面侧 b10431 实测 ~150 项）——它新增一个 arch 的判据是**图能否复用**，不是名字像不像。同类证据：

- `LLM_ARCH_MISTRAL3` / `MISTRAL4` 存在，但**没有** `LLM_ARCH_MISTRAL` / `MISTRAL2` ⇒ **Mistral 1/2 直接复用 `LLM_ARCH_LLAMA`**（与 Llama 同构）。
- MoE 在**图不同时**才是独立 arch（`QWEN2MOE` / `GLM4_MOE` / `GRANITE_MOE` / `PHIMOE`），图相同时靠 `n_expert` 参数表达（Mixtral 即如此复用 `LLAMA`）。
- 多模态里**改了位置语义的**才独立（`QWEN2VL` / `QWEN3VL`，M-RoPE）；视觉编码器是独立 `LLM_ARCH_CLIP` + 独立 mmproj 文件，不进主模型图。
- 混合 SSM 独立（`MAMBA` / `JAMBA` / `FALCON_H1` / `GRANITE_HYBRID`）——state 语义不同。
- **`LLM_ARCH_RWKV6QWEN2`**：一个 arch 名里带**两个系列** ⇒ 命名服务于图而非系列。
- **RoPE 变体本身不是 arch**，是 `rope.scaling.type` 参数。

因此 descriptor 契约的维度应按「每一维都是『图会不会变』」来定：

1. **attention**：MHA / GQA / MQA / sliding-window / linear-attn / 混合 SSM
2. **norm**：类型（RMSNorm / LayerNorm）+ 位置（pre / post）
3. **FFN**：dense / MoE（含路由方式）
4. **RoPE**：变体，特别是 `n_pos_per_embd`（M-RoPE = 4）
5. **head**：tied / untied
6. **KV 语义**：纯 attention / recurrent state / 混合

**QLH 比 llama.cpp 多一个维度：层接力可行性。** llama.cpp 的 arch 只回答「能不能加载」，不回答「能不能跨节点接力」。典型反例是 `qwen3*` 的 keep-head 挂点在 `output_norm` **之后**（`docs/已知问题记录.md` `#35`），所以它在 GGUF 上能加载、却**不能**做层接力上游。⇒ QLH 需要的状态表是 **arch × 层接力可行性** 的二维，而不是 arch 一维。

### GEN-2：非 Qwen 适配矩阵

建立**非 Qwen decoder** 的明确状态：已支持并对拍、协议可用但未验收、或安全拒绝。每个架构必须通过 descriptor → assignment → prefill → decode → full-model 对拍门。

**矩阵的行按 GEN-1 的图契约维度取，不按 `Llama/Mistral/Phi/Gemma` 这类系列名取**——那个列法会误导适配边界：Mistral 1/2 与 Llama 同构，不是独立基座；反过来同一个系列可以有多个 arch（Qwen2 / Qwen2MoE / Qwen2VL）。

矩阵每个格子要同时给两列状态：

- **加载/前向可行性**（对齐 llama.cpp 的 arch 判据）；
- **层接力可行性**（QLH 独有：能否作为 `stage_offer_v3` 的上游/下游段，含 keep-head 挂点是否在 `output_norm` 之前）。

第一阶段的候选应优先选**图最简单、且挂点在 norm 之前**的非 Qwen decoder（如与 Llama 同构的 dense 模型），把「图契约 + 接力」两条链一并走通，再扩到 MoE / VL / 混合 SSM。


### GEN-3：非稠密模型（MoE / 混合 SSM）的层接力可行性

**归入多模型 / 计算图支持的同一序列**（GEN-1 定契约维度、GEN-2 填非 Qwen 矩阵、本票处理
「非稠密」这一维度）。定性结论见 `docs/跨框架接力数值差异机理-2026-10-05.md` §10。

**先分清两件事**：**层接力（PP）与专家并行（EP）是两种切法。**

- 把**整层（含其全部 expert）**放在一个节点上 ⇒ **hidden 传递机制本身不受 MoE 影响**（传的是
  层输出残差流，与这层内部激活哪些 expert 无关）；
- 只有**专家跨节点分布**（MoE-EP）才需 all-to-all —— 该方向本仓已定量否决

⇒ **MoE 对层接力并非天然不友好**，本票要回答的是「**整层放置**前提下还有哪些真实障碍」。

**已知的真实障碍**：

1. **切点画像失准**：`src/relay_cut_objective.py` 的段画像模型是「固定开销 + 边际每层耗时」，

2. **容量判据从定值变分布**：从 dense 的「权重和 ≤ 内存」变成「权重 + KV + 热点 expert 驻留」的

3. **路由不均衡放大异构 straggler**：这是跨节点场景下的真问题。
4. **混合架构的切点约束**：`full_attention_interval` 的约束**机制通用**（`scripts/cut_layers.py`

5. **⚠️ 前置阻塞点（比 MoE 本身更紧迫）**：`scripts/model_tools/keep_head_shim/qlh_keep_head.c:22-24`

   `layer input tensor not null` 断言。⇒ **「上游能交出正确 raw hidden」这一端的架构覆盖极窄**。
   多基座方向首先要解决的不是「MoE 能不能切」，而是「**这个 arch 有没有一个在 `output_norm`
   之前的合法 hidden 挂点**」（`qwen3*` 的挂点在 norm 之后，因此能加载但不能做上游）。

**交付 / 验收**：对 `qwen35moe`（或等价的开源 MoE）给出**「加载/前向可行性」与「层接力可行性」

### XFRAME-2：算子级共享 kernel 的可行性（对应 L3-i）

**性质：实验票。** 依据：`docs/跨框架接力数值差异机理-2026-10-05.md` 的 §9——「让两侧收敛到
**同一个实现**」是算法上可行的路线之一，且本仓已有**最小可行样板**：`qlh_keep_head.c` 的
C ABI + `src/llama_keep_head.py` 的 ctypes 组合。

- **最小实验**：只共享 **RMSNorm** 一项（它是放大链的**种子**所在：2.7e-8 → 2e-6，放大约 72×）。
  把它做成一份 C 实现、两侧共用，测**首分歧步是否显著推迟**。
- **必钉的数值细节**（取自机理文档 §9）：累加器类型与归约顺序（注意 ggml 侧用 `double`、
  torch 侧用 f32，这是**精度类**差异而非顺序差异）、`eps` 的加法位置、`1/sqrt` vs `rsqrt`。
- **验收**：同一 prompt 集上，首分歧步相比现状明显推迟（给出基线值与改进值）。
- **不接入产品**：即便有效，也只作为后续正式改造的**可行性证据**。

**状态：最小实验已跑，结果为「无改善」（2026-10-05）。**

方法：给 `XFRAME-1` 的驱动器加了 `--hf-rmsnorm {hf,ggml-like}`。`ggml-like` 把模型内
**全部 49 个 RMSNorm** 换成复刻 ggml 语义的版本（`double` 累加 + `1/sqrt(mean+eps)`）——
这是从 KT 文档源码核对与 §9 的必钉清单里取得的、位于**放大链种子位置**的那一项。

对照结果（4 prompt × 16 token）**逐条完全相同**：

| 配置 | Count | primary colors | capital / hello |
|---|---|---|---|
| 基线（原生 RMSNorm） | 首分歧@2，hf margin **0.546** | 仅长度不同（EOS 决策） | 一致 |
| ggml-like RMSNorm | 首分歧@2，hf margin **0.546** | 仅长度不同 | 一致 |

⇒ **单独钉死归一化这一环不足以让分歧推迟。** 两个原因：

1. 归约顺序的敏感点**不止 RMSNorm** —— GEMM 的 K 维累加（`o_proj` 后放大 ~50×）与
   SwiGLU 非线性（~19×）同样在放大链上，任一环没对齐，种子就会在别处重新长出；
2. 本实验是**单向逼近**（只改 HF 去拟合已编译好的 ggml），而本票的本意是**共享同一份
   kernel**（两侧跑同一个二进制）——那是结构性对齐，不是逐算子模仿。

⇒ **结论：`XFRAME-2` 需要真正实现「共享 kernel」才能判定**；本次语义模拟的价值在于
**排除了「改几处语义即可对齐」这条便宜路径**。

**同轮补充：敏感度探针（结果同样是否定的）。** 给驱动器加了 `--noise-layer` /
`--noise-sigma`，在 HF 指定层的输出上注入**确定性**相对噪声（按该张量 `|x|` 均值缩放，
固定 seed）：

| sigma | 完全一致 | 首分歧步 |
|---|---|---|
| 0（基线） | 2/4 | [2] |
| **1e-3** | **2/4** | **[2]** |

**在 `layers[0]` 输出上注入 1e-3 的相对噪声，画像完全没有变化。** 原因是注入点的下游紧接着
`input_layernorm` —— RMSNorm 会把整体尺度重新归一化，**相对**扰动被吸收。

⇒ 由此得到一条**方法论结论**：「相对噪声」对**层内中间张量**不是有效的敏感度度量，因为
归一化环节会吃掉它。这也从侧面印证 §4 的判断 —— **种子不在「尺度」而在「归约顺序/精度」**：
单纯缩放某个张量不会被下游放大；而跨引擎差异（1e-3 量级、能翻转 argmax）之所以不同，
是因为它是**逐元素、非共模**的差异，归一化吃不掉。该探针保留为工具能力，但**「相对扰动」
这一维度不构成有效判据**。

### XFRAME-3：定点 / 网格对齐的可行性（对应 L3-ii）

**性质：实验票。** 这是唯一**跨架构也成立**的算法形态（整型累加满足结合律、无 ISA 依赖），
但本仓**尚无实测**：已有的 `int8/f16 hidden 32/32、512/512` 结论全部是**同引擎**（llama→llama）
链路上的，不能外推。

- **最小实验**：把跨引擎跳的 hidden 量化到**同一网格**（f16 / int8 block-wise），两侧用同一份
  量化与反量化函数，测分歧是否被**重置**（而非仅仅不放大）。
- **关键判据**：量化前的两侧差值必须小于**半格**，否则网格一粗就毁掉 argmax（本仓 `int4` 档实测
  23/32 失败可作反例）。
- **验收**：给出「跨引擎 + 跨架构」下 argmax 一致率与首分歧步，明确该路线的**有效网格位宽下限**。
- **不接入产品**：`src/relay_hidden_quant.py` 是现成构件，但本票只做可行性判定。

**首轮实测（2026-10-07，`build/keephead/xframe3_grid_probe.py`；K=12、qwen25-05b、7 tokens）：**

```
[cross-engine] delta max=0.1539 mean=0.0004889  |h_hf|max=1663   rel_err=9.667e-05
[int8] 量化前差<半格 100%  最坏 差/半格=0.027  ⇒ 量化后差 max 0.3191（变大）
[int4] 量化前差<半格 100%  最坏 差/半格=0.001  ⇒ 量化后差 max 0.8915（变大）
[shared scale] int8 同格率 6264/6272 (99.9%)；int4 6272/6272 (100%)
[per-channel] scale 中位=1.467 最大=1663 最大/中位=1133.8x
[per-channel] int8 5998/6272 (95.6%)；int4 6263/6272 (99.9%)
```

**三条结论：**

1. **「两侧用同一份 `encode_hidden`」≠「同一网格」**：该函数的 per-block `scale` 取自**各自数据**
   的 `max|x|` ⇒ 两侧 scale 不同 ⇒ 网格逐 block 偏移 ⇒ **量化反而放大分歧**。要真正对齐网格，
   **必须共享 scale**。
2. **判据「量化前差 < 半格」不充分**：本实验 100% 满足（最坏 `差/半格`=0.027），量化后差仍变大。
3. **共享 block-level scale 后同格率 int4 100% / int8 99.9% —— 但这是离群值假象**：
   `|h_hf|max=1663` 把 per-block scale 撑得极大，格宽随之变粗。改用**逐通道（per-channel）**
   robust 共享 scale（`scale_j = max(|h_hf[:,j]|, |h_ll[:,j]|)`）后 —— **scale 最大/中位 = 1133.8x**
   （确实存在 massive activation）—— 同格率降为 **int8 95.6%（5998/6272）、int4 99.9%（6263/6272）**。
   ⇒ **没有任何档位能完全重置分歧**；block-level 的「int4 100%」是**假象**。逐通道 scale 下
   **int8 仍有 4.4% 元素落不同格**，这是本票目前能给的最强「有效网格位宽」
   相关信号：block+int8 不够，逐通道仍差 4.4%。

**待做**：① 端到端 argmax 一致率与首分歧步；② 非 qwen2（hybrid）切点。无 ①② 前不给完整的
「有效网格位宽下限」。

**前置：本票比前两票多一层依赖——需要「跨引擎的 hidden 注入」。** 即「HF 前段产出 hidden
⇒ 量化 ⇒ 喂 llama.cpp 后段」。`llama_cpp` 的 `eval()` 吃 token id 而非 hidden，实际通道是主仓的
`LlamaCppEngine.forward_layers_from_hidden()`（`src/llama_engine.py:2046`，走
`llama_batch.embd`）。因此要在 `XFRAME-1` 之上再补一层「分段执行」能力 —— 这与
`XFRAME-1` 里 `same-engine` 模式的接线是**同一件事**，应合并实现。

## 执行顺序

`DIST-0 → DIST-1 → DIST-2 → DIST-4 → DIST-3` 为稳定版主线；`DIST-3` 之前不得宣称“稳定可用”。

**DIST 系列之后**按并行推进，顺序如下：

1. **`XFRAME-1 → XFRAME-2` / `XFRAME-3`**（跨框架数值对齐实验）—— 排在 `GEN-*`、`KT-1` 与
   KT 文档的 torch 实验票**之前**。理由：它直接决定「跨引擎混搭能否作为长期部署形态」，而
   `XFRAME-1` 又是其余两票与 `GEN-3` 的判据前置。三票均为**实验性质**。
2. **`GEN-1 → GEN-2 → GEN-3`**（多模型 / 计算图支持；`GEN-3` 覆盖非稠密）。
3. **`KT-1` 与 torch 实验票**（`TORCH-OP-PROFILE-01` 等）同批后置。
4. `RELAY-ARCHIVE` 与 `LEGACY-RETIRE` 在主线验收后处理。

**共同纪律**：以上 1–3 全部是**实验先行**——未取得确定成果前不接入产品实现，不写进稳定合同。
