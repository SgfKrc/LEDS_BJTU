**要不要重写：重写"骨架与角色"，不改写"已验证的能力"。**

**判断**：整体覆写（把 9 万行按新架构重排一遍）**成本高于重写** —— 因为其中约 3.6 万行（Reference P + 任务图）按 v5 已不是生产路径，重写它们没有意义；真正需要重写的是**角色与骨架**（节点角色、档位边界、入口收口），约覆盖 4 个模块群。

**因此本方案主张"定点重写 + 迁移"**：新骨架承载引擎/调度/节点角色；已验证模块（llama 引擎、调度器核心、TUI、模型合同、测试与实验体系）**原样迁移**，不重写；对照与已裁撤能力**退出生产路径**（归档或外置），不参与重写。

## 1. 目标形态

### 1.1 节点角色（两级 + 边缘形态）

```text
                 ┌──────────────────────────────┐
                 │  主节点（Control）            │
                 │  调度 / 合同 / 舰队 / 租约     │
                 │  compute = optional（可关）   │
                 └───────────┬──────────────────┘
                             │  合同：任务 / 分片 / 模型
        ┌────────────────────┼────────────────────┐
        │                    │                    │
┌───────▼────────┐  ┌────────▼─────────┐  ┌───────▼──────────┐
│ 算力节点 W-GGUF │  │ 算力节点 W-torch │  │ 边缘节点 Edge     │
│ llama.cpp/RPC   │  │ PC only（D 档）  │  │ ≤1B 本地推理      │
│ 全平台          │  │ 层流水线/层接力  │  │ + 可选 RPC 席位   │
└────────────────┘  └──────────────────┘  └──────────────────┘
```

- **角色与引擎解耦**：`node_role ∈ {control, control+compute, compute, edge}` 是**运行时身份**（配置 + 注册时声明），不是安装包差异；同一安装包可跑任意角色（Edge 无 torch 预检仍成立）。
- **主节点默认只调度**：`compute=false` 为默认；开启后才参与计算（保留单机演示与小组网形态）。
- **按画像选档**（沿用 v3/v5 的画像策略）：`device_profiler` 结论 + 模型档位 → 决定节点以 L 档（GGUF）还是 D 档（torch）参与；**画像不足或 torch 不可用时一律回落 L 档**，不得因 D 档不可用导致节点不可用。

### 1.2 引擎档位与 torch 按需（进程内延迟加载）

| 档位 | 依赖 | 参与能力 | 可用平台 |
| --- | --- | --- | --- |
| **L 档** | 无 torch（**硬约束**） | 单机 GGUF 推理、RPC 模型分片（host/worker）、TUI 对话 | Edge / PC / Android |
| **D 档** | torch（**按需引入**） | PyTorch 层流水线、跨框架层接力（PC 内双进程） | PC only |

实现约束（可测）：

1. **入口模块顶层不得 `import torch`** —— `llama_engine.py` / `qlh_edge.py` / TUI / 调度器入口全部满足；torch 只在 D 档执行路径内部延迟导入。
2. **可断言**：新增 import 检查测试（无 torch 环境下启动 Edge 入口并断言 `"torch" not in sys.modules`），接入现有边缘基线门（≤300MB venv / ≤15s 冷启动 / 无 torch）。
3. **Android 不引入 torch**：保持现有 llama.cpp + JNI 形态，本文档不为 Android 增加 torch 计划。

### 1.3 调度与算力解耦（主节点 + 可选算力）

- 调度器不假设"自己所在节点必然参与计算"：分片/层分配只依据**注册能力表**（引擎、模型、层驻留、内存、加速器）。
- 主节点关算力时：自身不出现在候选算力集；`control+compute` 时按普通算力节点参与（同一套画像与容量门）。
- **租约/故障语义不变**：单请求内任一环节失败即结束 attempt 并按可恢复边界重试或降级（沿用现行纪律）。
- 交付形态不变：`qlh chat`（TUI）与最小 HTTP（`qlh_edge`）继续是数据面对外面。

### 1.4 层接力（新能力，依托 §7.8/§7.9）

- **形态**：`节点 A（llama.cpp，算 layer 0..k）→ hidden → 节点 B（llama.cpp 裁层模型 + `embd` 注入，算 k+1..N）`；跨框架形态（A=torch / B=llama.cpp）同样成立。
- **已具备**：注入通道（§7.8）、裁层模型可加载可注入（§7.9）、两侧 hidden 语义一致（§7.2，fp16 cosine = 1.000000）。
- **未具备（本方案新增项）**：跨节点传输与同步、调度重建代价、误差累积、异构算力配比 —— 即 §7.3.1 的 ④ 四项。
- **定位**：**可选能力，PC only，先做同机双进程 PoC**；不进入 Edge 默认路径，不替代 llama.cpp 原生 RPC 分片（那条线独立成立且在推进：票 7 已完成、票 8 进行中）。

纪律（沿用 v5 与迁移安全规则）：

1. 每阶段先固化断点再动结构；**不删能力，只改归属与默认可达性**；
2. 现有测试是回归门（全量测试作为 R1–R6 的每阶段门）；
3. 不伪造：④ 类未测项不得在文档或汇报中写成已达成；
4. 高危变更（大范围移动/删除）先 dry-run（列清单 → 确认 → 执行后验证）。

## 4. 风险与诚实边界

| 风险 | 事实依据 | 处置 |
| --- | --- | --- |
| 重写规模失控 | `src/` 9 万行；`scheduler.py` 单文件 1.4 万行 | 只重写骨架（4 个模块群），其余迁移；每阶段以测试门收口 |
| 破坏已验证能力 | 全量测试 3032 passed 是资产 | 迁移阶段保持全量测试通过；降级模块"退出默认路由"而非删除 |
| 角色解耦引入新故障面 | 主节点不再算力时，分片/租约路径依赖注册表 | R2 单独阶段 + 集群定向回归；`compute=true` 与旧行为等价对照 |
| torch 按需破坏 D 档 | torch 延迟导入易被顶层 import 稀释 | 断言测试 + CI 门；D 档路径在 PC 实测 |
| 层接力被过度承诺 | ④ 四项全未测 | 定位为 PoC；结论只按实测写 |
| Edge 基线回退 | 现基线：≤300MB venv / ≤15s 冷启动 / 无 torch | R3/R4 复跑边缘基线作为门 |

**诚实边界**：本方案是**骨架重写方案**，不是"性能承诺"；跨框架层接力的性能类问题（④）在 R5 之前全部为未知；`qlh-android` / `qlh-shell` / `qlh-release` / `qlh-toolbox` 四个外置仓不在本方案范围内（只在需要对齐合同时提及）。

## 5. 明确不做（本期排除）

1. 不重写已迁移为外置仓/子模块的能力（产品壳、Android、发布、Koakumix、docagent、bridge、spawnledger）；
2. 不为 Android 引入 torch；
3. 不扩展 `LAYER_FORWARD` 为通用张量协议（沿用整体架构 §5 的边界）；
4. 不让任务图体系回到默认路由；
5. 不把层接力写进 Edge 默认路径。
