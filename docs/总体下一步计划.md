## 1. 生命周期规则

### 1.1 文档生命周期

```text
草案 Draft → 生效 Active → 冻结 Frozen → 历史 Archived → 废弃 Retired
                    └──────────────► 被新版取代 Superseded
```

| 状态 | 进入条件 | 维护要求 | 退出条件 |
|---|---|---|---|
| 草案 `Draft` | 目标和验收口径尚在讨论 | 不作为排期或能力承诺 | 负责人、依赖、判据确定后转 Active |
| 生效 `Active` | 已作为统一执行入口 | 每次状态迁移同步更新日期、证据和变更记录 | 阶段暂停、归档或由新版接替 |
| 冻结 `Frozen` | 外部依赖长期不可用，或止损判据触发 | 保留原因和恢复条件，不继续投入实现 | 恢复条件满足后转 Active，或转 Archived |
| 历史 `Archived` | 所辖工作全部完成/取消，内容仅供追溯 | 不再修改当前状态，只允许勘误 | 无；必要时转 Retired |
| 被取代 `Superseded` | 新总计划已生效 | 文件头必须链接替代文档 | 清理周期内转 Archived/Retired |
| 废弃 `Retired` | 已无有效引用价值 | 从 README 推荐索引移除 | 按维护规则人工删除 |

本文件当前为 `Active`。当 L0–L4 全部进入 `Completed / Cancelled / Frozen`，或项目发布新的总计划时，本文件必须迁移为 `Archived` 或 `Superseded`，不得继续以“现行计划”存在。

### 1.2 工作项生命周期

```text
候选 Candidate → 就绪 Ready → 进行中 In Progress → 验证中 Validating → 已完成 Completed
                         │              │
                         ├→ 阻塞 Blocked┘
                         ├→ 冻结 Frozen
                         └→ 取消 Cancelled
```

| 状态 | 判定规则 |
|---|---|
| 候选 `Candidate` | 有价值，但不在当前承诺范围，或前置决策尚未完成 |
| 就绪 `Ready` | 前置条件齐备，可立即开始 |
| 进行中 `In Progress` | 已有实际实现、测试或联调活动；只有明确证据才能进入 |
| 阻塞 `Blocked` | 目标仍有效，但缺硬件、外部端点、权限或上游产物 |
| 验证中 `Validating` | 实现已完成，正在执行完成判据；不得提前写“已完成” |
| 已完成 `Completed` | 本文所列完成判据全部满足，并有可定位证据 |
| 冻结 `Frozen` | 止损判据触发或短中期不再投入；必须写明恢复条件 |
| 取消 `Cancelled` | 目标不再需要；必须记录替代方案或取消理由 |

状态迁移必须同时更新：本表状态、证据链接/命令、阻塞原因、下一动作、最近复核日期。代码合入不等于完成；自动化通过也不能替代要求中的真机、真实模型、安装包或目视验收。

### 2.2 总目标

按顺序达成四个生命周期门：

1. **基线可信**：测试结果可重复，3 个环境敏感失败有稳定结论，文档口径统一。
2. **真机可验**：控制面、TUI、层间流水线和 PC Full Worker 在物理设备上完成故障与性能验收。
3. **版本可交付**：Android Full/Lite、PC 集显/独显和 Linux 包按同一版本构建并完成最小安装验证。
4. **扩展可决策**：外部 Provider、TP 孤岛和投机解码用真实模型数据决定生产化、冻结或取消。

### 4.5 L4：后续探索

以下项目保持 `Candidate`，只有前置阶段完成后才能提升为 `Ready`：

- **L4-SD1.5：Diffusers SD 1.5 图像引擎与分布式批次展示**：仍为 `Candidate`，但 `SD-N0` 固定资产下载/识别与 `SD-N1` 本地单机 SD 1.5 已在 RTX 4060 Laptop GPU 8 GB 上完成真实生成基线；本轮还验证了仅 U-Net Linear 范围的 bitsandbytes 8-bit 量化和 Diffusers QKV 投影融合。LLM 的 `PagedKVCache` 不适用于逐步变化 latent 的 SD U-Net，`torch.compile` 因当前 Windows CUDA sidecar 缺少 Triton 而在加载前显式拒绝。未接入 API/UI、发布包、图片 blob、TaskGraph 或 PC Worker，不能显示或统计为分布式。跨 PC 展示依赖 L1-1 控制面、L1-2 Worker 故障边界和新的图像 Stage/blob 协议通过评审。第一阶段使用完整 SD Worker 按固定 prompt/多 seed 扇出并行，证明真实多节点吞吐，不拆单张图的 U-Net 去噪循环。支持本机任意绝对路径或 Diffusers 目录，先区分完整 SD checkpoint、DreamBooth full fine-tune、LoRA 和 ControlNet 组件；`control_v11e_sd15_ip2p_fp16.safetensors` 只作为 SD 1.5 ControlNet 辅助资产，不得误当完整模型。原版 SD 1.5 与固定 `retrovers` 90 年代日式动漫 DreamBooth 演示 preset 均保留；实现、模型资产、协议与验收细节见 [SD 1.5引擎与分布式图像生成实施计划](SD%201.5引擎与分布式图像生成实施计划.md)。
- **L4-QUANT-LOWBIT：2/3-bit 与 4-bit 量化路线评估**：当前 PyTorch 仅支持 FP16/INT8/NF4 4-bit，不能把 `int2`/`int3` 当作 bitsandbytes 开关；2/3-bit 正式只面向计划中的 14B 及以上模型（Qwen2.5-14B、DeepSeek-R1-Distill-Qwen-14B/32B、DeepSeek V2-Lite/Coder V2-Lite 等），Qwen-1.8B/1.5B/7B 只保留转换和 loader smoke 入口，日常不建议给小模型降智。第一阶段从原始 F16/BF16 直接生成 GGUF `Q3_K_M`、`Q2_K`、`IQ2_XXS`、`IQ2_XS`，与 F16、`Q4_K_M` 做质量、有效 bpw、内存、速度和 Android 兼容性对照。2-bit 不因“浮点”而默认比 4-bit 精度高，AQLM/QuIP# 属于独立 sidecar，BitNet b1.58 属于重新训练的三值模型；详细阶段、artifact 身份、分布式边界和止损门见 [2-bit、3-bit 与 4-bit 量化调研与实施计划](2bit与4bit量化调研与实施计划.md)。
- E3 混合任务链：依赖 L1-2，且 L3-1/L3-2 至少一条通过。
- 超节点画像与 A-1 层段孤岛：依赖 L3-1 通过真实收益门槛。
- 自建 verify 后缀端点：依赖 L3-3 未触发止损。
- TC-N3.1 第二个固定 DAG 模板：依赖 L1-2。
- 激活/KV INT8 传输量化：依赖 L1-3 的真机基线。
- Android 完整 Worker：依赖 L1-2，且不得改变 Android 不参与 PyTorch 层拆分的边界。

## 5. 责任、依赖与执行节奏

| 工作流 | 主责 | 关键依赖 | 周期输出 |
|---|---|---|---|
| L0-1、L1、L3-1 | 分布式架构组 | PC 从节点、Tailscale、多卡环境 | 测试日志、故障记录、性能表、准入结论 |
| L0-4、L3-3、L4 量化 | 模型优化组 | 真实模型、共享 tokenizer、verify 端点 | 正确性测试、基准、止损结论 |
| L4-SD1.5 | 模型优化组 + 分布式架构组 + 前端组 | CUDA PC、SD 1.5 资产、图像 blob 协议、物理 Worker | 固定 preset、单机/分布式图像、吞吐与故障证据 |
| L4-QUANT-LOWBIT | 模型优化组 + GGUF/Android 维护者 | 14B+ F16 源工件、锁定 llama.cpp、校准集、真实设备 | Q2/Q3/Q4 对照、有效 bpw、质量/速度/内存门、Go/No-Go |
| L0-2、L0-3、L2、L3-2 前端 | 前端与文档组 | Android 环境、打包环境、发布版本 | APK/安装包、截图、索引、发布说明 |

执行节奏：

1. 每次开始工作前确认该项为 `Ready` 或 `In Progress`，并记录所用 commit、环境和模型工件。
2. 每次合入后只把状态推进到 `Validating`；完成判据全过后才能转 `Completed`。
3. 每周至少一次复核 Blocked 项；阻塞解除后按 L0 → L1 → L2 顺序抢占资源。
4. 真实设备或外部算力窗口到位时，优先运行预先冻结的验收矩阵，不在窗口内临时扩需求。
5. 任何止损判据触发后立即转 `Frozen`，记录数据和恢复条件，不以“已投入很多”为由继续。

## 6. 发布门与不可越过的边界

以下任一条件成立时，不得宣称“生产可用”或“分布式已完成”：

- Python 全量回归仍有未解释失败。
- TC-N2.4 未通过，却把 `adapter_connected` 或默认任务派发状态改为 true。
- 只有单机双进程证据，却宣称真机分布式验收完成。
- Android 只有 Kotlin 编译证据，却宣称 APK/交互验收完成。
- TP 孤岛、外部 Provider 或投机解码只有 mock/实验端点证据，却宣称有性能收益。
- 路线 B/C 未经用户显式授权让内容出集群，或把默认数据作用域改为 `allow_all`。
- 发布包没有对应 commit、依赖版本、哈希、测试摘要和已知限制。
