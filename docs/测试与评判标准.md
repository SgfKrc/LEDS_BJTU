# 测试与评判标准

> 状态：**现行**
>
> 更新日期：2026-10-02
>
> 适用范围：主仓 llama.cpp 主引擎、PC 对照引擎、模型分片、TUI、模型合同、边缘基线与回退 Provider 的证据规范。

Web/Android UI、安装包、演示和图像生成不构成主仓质量门。主仓先通过 llama.cpp/GGUF/CPU/无 torch/TUI 的单机验收，再通过同机双进程与 PC/Android RPC 模型分片验收；PyTorch 只记录 PC 对照证据，图像生成在 Koakumix 验收。

## 1. 测试记录的必要信息

每次结果必须同时记录：

- 逻辑模型、模型工件哈希、格式、量化方式、tokenizer 和上下文长度；
- 节点设备画像：CPU、GPU/NPU、内存、操作系统与运行引擎；
- 实际执行模式和参与节点，不写"分布式：是 / 否"；
- 网络路径、RTT、吞吐、丢包/重连情况以及是否经过 Tailscale；
- Prompt token、生成 token、并发数、随机参数和是否流式输出；
- 是否发生重试、降级、节点替换或模型重新加载。

设备可以是台式机、工作站、服务器、笔记本、Android 手机或平板。测试分组按能力和执行模式建立，不按设备外形建立。

## 2. 当前对照组

| 组别 | 执行方式 | 用途 |
|------|----------|------|
| 本地基线 | llama.cpp 单节点完整模型、默认优化 | 正确性与最终降级基线 |
| 单机优化 | 不同量化、编译和 KV 策略 | 测量内存、速度和质量变化 |
| llama.cpp 双进程模拟 | 同机 host + RPC worker、模型分片 | 分布式真机前的容量、部分驻留和正确性门 |
| llama.cpp PC/Android RPC | 不同节点的 GGUF 分片与 RPC | 主线模型分片、故障、安全和收益验收 |
| PyTorch 层流水线 | 同一模型工件、不同层分配与节点路径 | 仅 PC 正确性、容量和性能对照 |
| 故障与降级 | 注入断连、超时、模型不一致、节点崩溃 | 验证失败边界和恢复能力 |
| 异构客户端 | Android 本地 GGUF、Android RPC worker、Android 远程 PC | 区分单机、模型分片和临时 HTTP 回退 |
| TP 孤岛（`island`） | 网关节点承担整请求，孤岛内部自行张量并行 | 整请求路径、画像加权与"不参与层拆分"的双保险 |
| 外部推理服务（`external_api`） | 整请求路由到集群信任域外端点 | 数据作用域门控、触发条件、流式与失败回退 |
| 投机解码实验端点 | 本地 draft + 外部 verify，独立实验入口 | 接受率与分布偏差；不计入任何产品路径统计 |

完整 Worker、任务链、张量并行或 GGUF Stage 落地后分别增加独立对照组，不并入"层流水线"统计。后三组独立统计，并额外记录：

- 孤岛/外部端点的后端运行时、模型名、声明的聚合 GPU 数与显存（孤岛画像由部署者声明，主节点无法探测，报告中必须标明来源为声明值）；
- 请求是否经数据作用域门控放行、触发原因（`prefer_external` 还是长度阈值）、是否发生外部失败回退及 `fallback_reason`；
- 取消语义为 chunk 边界 best-effort：OpenAI 兼容端点无服务端取消原语，外部端可能算完整个请求，统计不得按"已取消"记为未执行。

投机解码的质量结论必须区分作用域：纯核心的分布等价性可用 Monte-Carlo 验证，端到端链路只能声称"接受判定精确、修正采样近似"。当前 PoC 的 draft 侧是占位实现，不承诺加速比。

## 3. 核心指标

### 3.1 正确性

- 层覆盖连续、无重叠、无缺层；Embedding 和 LM Head 所有权正确。
- 流水线与完整模型在确定性设置下达到约定的 token/logit 一致性；接力链路的判据是逐 token argmax。
- 参与者使用同一认证模型工件；不兼容节点在执行前被排除。
- 用户看到的流式文本不重复、不乱序，失败 attempt 的迟到结果被丢弃。

### 3.2 性能

- 首 token 延迟、逐 token 延迟、端到端时延和 tokens/s；
- 单请求延迟与多请求吞吐分别统计；
- CPU/GPU/内存/显存占用和模型加载时间；
- 每个节点的计算时间、等待时间、传输字节和慢节点占比；
- 编排、模型同步、层加载与 ready 等准备时间单独统计。

### 3.3 稳定性与容错

- 节点发现失败、数据库不可用、TCP 断开和模型同步失败不能拖垮本地推理入口；
- 未 ready 节点不能收到层任务；取消/超时后释放 KV、锁、租约和队列状态；
- 故障恢复必须标明是同 attempt 续跑、整次重试还是降级重启；
- 长时间运行检查内存增长、线程泄漏、重复注册和任务统计漂移。

### 3.4 输出质量

- 固定问题集上的任务正确率、格式遵循率和人工偏好；
- 不同量化/Provider 的输出差异与拒答、幻觉情况；
- 质量结论绑定具体模型工件，不推广到同名的其他格式或量化版本。

## 5. 展示要求

前端和报告至少展示 `execution_mode`、`provider`、`attempt_id`、参与节点、实际层段/Stage、回退原因和各节点任务计数。只有确实进入相应执行 Provider 的任务才计入其分布式统计。
