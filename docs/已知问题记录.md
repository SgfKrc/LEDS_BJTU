## 问题 #1：从节点也能自定义管理员邮箱（仅主节点可配置）

> **状态**：历史条目（原权限问题已关闭；邮件功能于 2026-09-15 裁撤）
>
> **登记日期**：2026-08-07
>
> **严重程度**：中（配置一致性 / 权限边界）
>
> **发现途径**：人工走查管理页面（分布式模式下从节点端）

### 1.1 问题概述

管理员收件邮箱是**集群级**配置（主节点宕机/恢复告警、审查投票邮件的收件人），但当前**从节点端管理页面同样显示并可修改该配置**，且后端接口对任何节点开放。预期行为：**只有主节点能显示并修改该条目，从节点不显示**。

### 1.2 复现路径与代码位置

1. **前端**：`frontend/src/components/AdminPanel.jsx` 第 1935 行起"📧 邮件告警"section，注释明确写着 `{/* ---- 邮件告警配置与测试（所有节点） ---- */}`，渲染无 `isMaster` 过滤——而同一文件中其它主节点专属 section 均以 `{isMaster && ( ... )}` 包裹（如 363 行 `const isMaster = myRole?.is_master ?? false;`，1126/1511/1538/1580/1696/1810/2015/2116 行等）。
2. **后端**：`src/api_server.py`
   - `GET /api/cluster/email-config`（6942 行）——查询，无角色校验；
   - `POST /api/cluster/email-config`（6965 行）——`set_admin_email` 持久化到**本机** `node_config.json`，无角色校验；
   - `POST /api/cluster/email-test`（6915 行）——测试邮件，注释"任何节点均可调用"，无角色校验。
3. **语义矛盾**：`src/email_notifier.py` 第 8 行"收件邮箱优先 node_config.json 的 admin_email（UI 可配置），回退 QLH_SMTP_RECIPIENT"；而主节点宕机告警实际由**从节点**触发发送（`src/scheduler.py` 11617-11634：client 侧检测宕机 → `send_master_down_alert`）。于是从节点各自配置的邮箱会成为该节点发送告警的收件人，集群内收件人可能不统一。

## 问题 #3：PyTorch 分层流水线从节点本地模型状态会粘滞退出，导致主节点静默单机回退

> **状态**：已修复，待使用新 PC 包进行双机实测
>
> **登记日期**：2026-08-08
>
> **严重程度**：高（表面显示集群在线，实际分布式推理未使用从节点）
>
> **影响范围**：PyTorch 层间流水线的 Qwen-1.8B、DeepSeek/Qwen2 系列；GGUF/llama.cpp 不涉及层间拆分。

### 3.1 现象与证据

2026-08-07 的 Qwen-1.8B INT4 请求中，主节点加载后曾下发 `master: 0-21`、`client: 21-24` 的层配置；随后从节点上报“从节点已退出 PyTorch 分层计算”。主节点将该节点排除，日志显示“未分配任何 PC 从节点参与模型层计算”，继而以 `fallback full master` 完成 186 tokens。

该请求没有任何 `LAYER_FORWARD`、张量传输或层结果日志。因此“回答混乱”不是中间 hidden states 丢失造成的：从节点根本没有参加本次推理。小模型 INT4 的输出质量、采样参数和旧会话上下文仍需作为独立质量问题排查。

### 3.2 根因

从节点通过本地模型加载、切换或卸载接口后，会调用 `release_pipeline_worker_for_local_model()` 并向主节点发送 `LAYER_WORKER_OPT_OUT`。此前该退出状态在从节点和主节点均为粘滞状态：后续普通层配置仍被从节点拒绝，主节点也持续把它排除出层分配。即使主节点后来已加载同款模型，也没有一条“主节点重新接管分层 worker”的权威同步路径。

### 3.3 已实施修复

1. 新增一次性主节点权威同步：`Scheduler.request_authoritative_layer_sync()` 在主节点完成 PyTorch 模型加载后调用；收到分布式推理请求而流水线未就绪时也会调用一次。
2. 权威配置包含模型清单：`model_id`、`model_sha256`、`model_type`、`total_layers`、`engine`、主节点量化方式、层范围和配置代际。Qwen 与 DeepSeek/Qwen2 共用同一协议，仍以 SHA256 和层数校验同款模型。
3. 在线、空闲的 PC 从节点收到 `authoritative_sync=true` 后自动撤销旧 opt-out，按现有模型同步流程校验/获取模型并执行 `load_layer_range()`；加载完成后必须回传对应 `config_id` 的 ready ACK 才能参与推理。
4. CPU 从节点允许运行时自动回退 FP32；它不必与主节点 INT4 的运行 dtype 完全相同，但模型身份、架构和权重摘要必须一致。
5. 分布式请求最多等待 `QLH_PIPELINE_MODEL_SYNC_TIMEOUT` 秒（默认 60，范围 1-600）以等待同步 ACK；超时、模型下载/加载失败、连接断开时保持既有主节点全模型安全回退。
6. 同步请求采用计数而非布尔标记，避免并发请求把后一个权威配置错误降级为普通配置。旧安装包若再次明确 opt-out，主节点立即回退，不再无谓等待完整同步超时。

### 3.4 兼容性与实机验证

旧版从节点不认识 `authoritative_sync`，仍可能保持 opt-out；主节点会立即降级为单机推理。这不是张量损坏，必须更新主节点和 PC 从节点到包含本修复的同一版本后再测试。

验收步骤：

1. 主、从节点都启动并显示 TCP 在线；从节点可以先加载完整 PyTorch 模型以模拟旧场景。
2. 主节点加载 Qwen-1.8B 或 DeepSeek/Qwen2 的 PyTorch 模型，确认日志出现“主节点权威模型同步重新启用分层 worker”。
3. 等待从节点完成模型校验/层加载并回传 ready ACK，集群状态应显示其层范围而不是“已退出”。
4. 发起新会话的分布式请求，日志必须出现层前向与从节点任务/worker 指标；若同步失败，响应 metrics 必须明确为 fallback，而不能伪称已分布式执行。

### 3.5 后续演进

当前修复以“主节点加载完成 + 请求前兜底同步”为触发点。后续将模型清单升级为持久化版本（模型版本、权重 SHA256、tokenizer/revision、引擎兼容版本、层配置 generation），由主节点维护期望状态，从节点在注册、重连和模型状态变化时上报实际状态。主节点仅对空闲 worker 执行切换；忙碌 worker 保留当前任务，完成后再对齐，避免打断本地任务或正在进行的流水线。

## 问题 #4：流水线零温度采样触发 CUDA invalid argument 并破坏本地回退

> **状态**：已修复，已完成双机复测
>
> **登记日期**：2026-08-08
>
> **严重程度**：高（真实分布式请求在首个 token 失败，CUDA 上下文失效后完整模型回退也失败）

### 4.1 受控复现

固定 Qwen-1.8B、提示词、空会话、`max_new_tokens=24`、`temperature=0`、`top_p=1`。`local_only` 正常生成“2+2等于4。”；`distributed_required` 完成主节点 `Layer 0-21`、从节点 `Layer 21-24` 的 step 0 前向并收到结果后，在主节点 `torch.multinomial` 报 `CUDA error: invalid argument`。

这证明层配置、首段前向、hidden states 传输和从节点尾层均已执行，错误发生在主节点 token 采样，而不是张量丢失。

### 4.2 根因与修复

单机生成把 `temperature <= 0` 解释为 `do_sample=False` 的贪心解码；流水线此前却将温度钳制为 `1e-8` 后仍执行 softmax + multinomial。FP16/BF16 logits 除以极小值可能产生 Inf/NaN，CUDA multinomial 报错并使同一进程内后续 bitsandbytes 完整模型重载也失败。

流水线现已统一采样语义：零温度直接 `argmax`；正温度先将 logits 转 FP32，再执行 top-p，并在 multinomial 前检查 logits、概率与候选概率和均为有限有效值。异常概率会在破坏 CUDA 上下文前明确终止。

### 4.3 修复后双机验收

在从节点 `client_TABLET-2TLUCNU8` 在线、模型配置同步确认后，使用与复现完全相同的提示词和推理参数重新请求 `distributed_required`：

- HTTP 200，`execution_mode=distributed_pipeline`，`distributed_used=true`，无回退；
- 主节点执行 `Layer 0-21`，从节点执行 `Layer 21-24`，从节点结果 step 0 至 step 6 均返回 `error=none`；
- `workers_used` 包含 `client_TABLET-2TLUCNU8`，任务统计同时计入 `master` 和该从节点；
- 生成结果为“2+2等于4。”，共 6 个 token，未出现张量传输缺失或 CUDA 上下文失效。

因此本次问题已完成真实双机验收；后续仍需在 PC 安装包环境中做一次同参数回归，以覆盖打包后的 CUDA/依赖组合。

## 问题 #27：llama.cpp RPC 无错误恢复 —— 任一 socket 失效即 `abort()` 整个进程（2026-09-25 登记）

> **状态**：**`上游缺陷 / 非本仓 bug`** —— R-R6 跨机复测复现，已定位到上游源码与 issue；**本仓无需修复**，但验收时必须按此解释退出码
>
> **严重程度**：**对本仓验收=低**（不影响任何判据）；**若将 RPC 用作生产 supervisor=高**（单点失败杀全进程）

### 27.1 现象（本仓实证）

`CORE-LLAMA-PC-RPC-01` 跨机 RPC（本机 `llama-server.exe --rpc <host>:<port> --device RPC0` 作 host；
Surface 上 `ggml-rpc-server.exe --device CPU` 作 worker）在**请求全部成功完成后、收尾/停止阶段**崩溃：

- 本机 host 退出码 **`3221226505`**（十六进制 `0xC0000409`）
- 远端 worker 退出码 **1**
- host 日志末尾：`ggml-rpc.cpp:569: Remote RPC server crashed or returned malformed response`
- worker 日志：大量重复 `Accepted client connection` / `Client connection closed`

⚠️ **但请求与全部判据均已完成** —— report 的 `status` 仍为 `passed`（0.6b 与 2b、标准档与长时档
四种组合全部如此）。证据 `local_docs/evidence/llama-pc-rpc/rr6-*.json`。

### 27.2 根因（本地源码 + 上游 issue）

**不是栈破坏** —— `0xC0000409` 在本例中是 `abort()` 的后果：

1. llama.cpp RPC 把「远端 socket 已失效」当**致命错误**：宏 `RPC_STATUS_ASSERT`（`ggml-rpc.cpp:30`）
   失败 ⇒ `GGML_ABORT` ⇒ `abort()`；
2. 底层 `transport.cpp:462-504`：`send()` 返回 < 0 打印 `send failed (...)`；`recv()` 返回 < 0 打印
   `recv failed (...)`；**`recv()` 返回 0（对端关闭）则静默返回 false**（仅 `GGML_RPC_DEBUG` 下打印）；
3. `ggml.c:252-272` 的 `ggml_abort` 最终调 `abort()`；Windows/UCRT 上 `abort()` 走
   `__fastfail(FAST_FAIL_FATAL_APP_EXIT = 7)`，其用户态异常码**正是 `0xC0000409`**
   （本机 SDK 佐证：`winnt.h:23043` `FAST_FAIL_STACK_COOKIE_CHECK_FAILURE 2`、
   `winnt.h:23048` `FAST_FAIL_FATAL_APP_EXIT 7`）。

**判别法**：异常参数 `0x7` ⇒ abort；`0x2` ⇒ 真栈破坏。真正的 `/GS` 栈破坏**不会**先打印 llama.cpp
的 `file:line: msg`，本例打印了 ⇒ 走的是 abort 路径。

**上游已知**：issue **#26384**（b10208，closed as not planned）逐字引用了该宏并给出结论
「**any worker-side failure kills the whole multi-host deployment … RPC has no error recovery**」，
并建议：worker 侧应返回错误帧而不是断言关连接；coordinator 侧应把失败/断开 socket 当作**该请求**
失败（HTTP 5xx）而不是杀进程。**#27905**（b10675）/ **#28808**（b10707b10920）/ **#28047**（master）
是同一个 abort（行号 566，伴随 `recv failed (bytes_recv=0, size_to_recv=8)`）。

**另：worker 退出码 1 与本缺陷无关** —— 来自探针脚本的 `Stop-Process -Force`（所有 run 一致，
**包括判定为 `passed` 的 run**）。

### 27.3 影响与处置

- **对本仓验收：不影响**。探针在请求完成即判定 `status`，收尾崩溃不参与判据（已在验收清单 D20 标注）。
- **不冒充**：不得把该崩溃写成「已验证无问题」；也不得据此判定 RPC 不可用 —— **请求路径本身是好的**。
- **禁止绕过**：若将来把 `ggml-rpc` 用作**生产 supervisor**，必须先解决「单点 socket 失败杀全进程」。
  这需要上游改动，或自建 supervisor（监控/重启 + 请求级错误隔离），**不能靠本仓补丁掩盖**。
- **可选规避（未采纳）**：显式 orderly shutdown、调整停止顺序（先让 host 退出再停 worker）可减少
  该崩溃发生，但**不改变根因**；本轮由子 agent 源码调查确认。

- **状态**：`Validating`（2026-08-17；UX-01 至 UX-07 开发票均已完成；Android 真机视觉/触控/IME 验收仍单列为 L0-2 后置）
- **现象**：安卓客户端页面与 PC Web 前端风格差异较大，视觉语言不统一；两端普遍使用较多 emoji 作为导航/状态标识，缺乏美感，与项目"极客/工程化"定位不符。
- **期望风格**：统一为**极客风格**——减少 emoji，改用**简洁优美的图案与线条**（几何线条、细边框、克制的渐变），**科技感主要由侧边栏承载**（导航/状态/系统信息聚合到侧边栏，主内容区保持干净）。参考方向：**SillyTavern 风格**（用户认可，暗色为主、线条与排版克制、信息密度合理）；可调研同类极客风前端（如终端/监控类 dashboard、Codex/CLI 系 UI 的视觉语言）再定稿。
- **范围**：PC Web 前端（`frontend/`）与安卓客户端（`android/`，Material 3 主题体系之上做风格统一）双端同步；样式 token（色板/间距/线条/图标集）先抽象为共享规范，再逐屏迁移。
- **验收（拟）**：两端主屏截图对比风格一致；emoji 使用量显著下降（导航/状态图标改为线条图标或文字标识）；侧边栏承担导航+系统状态；无视觉回归（功能不变）。
- **备注**：风格统一是纯前端工作，不涉及协议/数据层；可与安卓差距清单（A1 图像理解等）并行。

## 问题 #28：worker 实时 `models` 为空导致远端 Stage 被误拒（`model_identity_mismatch`）（2026-09-26 登记）

> **状态**：**`已确认 / 待修（代码修复未完成）`** —— R-R3 复验暴露，行号级定位完成，**已实测复现**，
> 且经只读调查证实「层段加载/释放路径**从不通知** capabilities」是**真实缺陷**（见 28.2）。
> 用户裁定：**必须修**。
>
> **⚠️ 2026-09-26 的修复尝试失败并已整体回退**（`db443dc`）：按用户裁定的 **A + B** 实现、单元测试
> 全绿（373 passed）、并真机部署，但**真机验证把两者都否掉了** —— 均会引发 `hello`/`release`
> **死循环**（详见 28.4）。所以本条目**仍为待修**，代码**未改**。
>
> **当前唯一可用手段 = 操作顺序规避**：两端各自起服务 ⇒ 各自**完整加载整模（不带层段）** ⇒
> **之后** Surface 才 `/api/cluster/connect` ⇒ 随即取到 `distributed_used=true`（见 22.10）。
>
> **严重程度**：**高** —— 会让"两端模型摘要**逐字段完全一致**"的远端 Stage 被拒，直接把 `distributed_used` 打成 false

### 28.1 现象

双机 `dual_candidate`（`candidate_a` 走远端 Full Worker）时，两端摘要**完全一致**却仍被拒：

| 侧 | 值 |
| --- | --- |
| master 发出的 offer（`src/task_worker_adapter.py:798`）| `{model_id: qwen2.5-0.5b, engine: pytorch, format: safetensors, revision: local-415c5381b284, sha256: 415c5381b284…}` |
| 独立复算（两端 `model_sync.compute_model_sha256`）| **digest 完全相同**（`415c5381b284e611…`，24 个文件逐一相符） |

stage 结果却是 `state=failed` / `error=model_identity_mismatch: remote worker rejected the Stage offer`。

### 28.2 根因（行号级）

Surface 侧校验（`src/scheduler_task_worker.py:480-482`）：
```python
elif offer["model_identity"] not in capabilities["models"]:
    reject_reason = "model_identity_mismatch"
```
而 `capabilities["models"]` 由 `_task_worker_capabilities()` **实时**构造，其中（`src/scheduler_task_worker.py:100-102`）：
```python
full_model_loaded = bool(
    full_model_loaded and getattr(self._host, "layer_range", None) is None
)
```
⇒ **只要 worker 上残留非 `None` 的 `layer_range`，它实时上报的 `models` 就是空** ⇒ 任何 offer 的
identity 都 `not in []` ⇒ **必然被拒**。

**⚠️ 关键更正（只读调查结论，纠正本条目初稿）**：初稿写"完整加载后 `layer_range` 未被清除"**不准确**。
实测与代码核实为：
- `layer_range` 在 `src/model_module.py` 只有 5 个写点，其中 **`unload_model()`（:1303）与
  `_load_pytorch()` 尾部（:2790）会在完整加载路径上无条件置 `None`** ⇒ **经 `/api/models/load`
  完整加载后 `layer_range` 必为 `None`**（本轮实测 `/api/status` 的 `layer_range` 确为空，已证）。
- ⇒ 所以残留**只能来自"层段加载路径"**（含被当作层段的 `[0,24]` 全范围加载）。
- ⇒ **真正的缺陷是：层段加载/释放路径一处都没有调用 `refresh_task_worker_capabilities()`
  （`src/scheduler_task_worker.py:169-189`，它才是"实时重算 capabilities + **重发 hello**"的入口）**
  ⇒ worker 的角色变化**从不通知** master，两侧状态长期不一致。

### 28.3 口径不一致（加剧误判）

master 的 `_task_worker_full_model_ids()`（`src/scheduler.py:2964-3001`）用的是 **hello 上报的快照**
⇒ 它判定 Surface 是 Full Worker（`full_model_worker_count=1`）；而 Surface **实时**快照为空。
**同一节点、两处口径相反** ⇒ 准入判定与执行校验互相矛盾（一个放行、一个拒绝）。
调查结论：这**是** bug（同一语义的双源真相 + 无失效通知；且 master 侧依赖 `layer_forward`/`layer_ranges`
的 `has_layer_stage` 分支在当前 worker 上报下**不可达**）⇒ **应以 worker 实时侧为准**，master 快照须带
时效性/失效路径。

### 28.4 修复尝试与实测结论（A + B 已实现、真机验证失败、整体回退）

用户裁定范围为 **A + B**（worker 侧两项，不动 master）。二者都已实现、单测全绿（373 passed）、
并真机部署验证，**结果两者都被真机否掉**，已整体回退（`db443dc`）。

| 方案 | 实现位置 | 真机结果 |
| --- | --- | --- |
| **B**：`release` 时若 `layer_range` 非 None 就 `unload_model()` | `_handle_layer_config_locked` 的 release 分支 | **立刻死循环**：835 次「从节点已确认退出分层 worker」+ 855 次 `task_worker_hello_acked`，约 20 次/秒 |
| **A**：层段加载完成 / `release` 之后各补一次 `refresh_task_worker_capabilities()` | 加载 `status=ready` 的 ack 后、release `status=released` 的 ack 后 | 回退 B、只留 A 后**仍然循环**：25 秒内各 +209（约 8 次/秒），**持续不停** |

**A 为何也不行（这个闭环单独由 A 就能成立）**：
```
Surface 载层段 → A: 重发 hello（此刻实时 models 为空）
  → master 用这份新 hello 快照重算分层 ⇒ 推送层配置 / 发 release
  → Surface 收 release → A: 重发 hello
  → master 再用新快照重算 ⇒ 回到起点
```
⇒ `refresh_task_worker_capabilities()` 会**触发主节点重算分层**，而重算结果又回到 Surface、再由
重发 hello 触发下一次重算 ⇒ 只要 worker 处于「层段 ⇄ release」的过渡态，**重发 hello 就是一个正反馈**。
原先的 hello 只在**整模变更**时发（`api_server.py` / `routes_models.py` / `engine_host.py` 等共 10 处），
过渡态下不会连发，所以这个问题被长期掩盖。

**B 为何也不行**：节点是否被排除在自动分层之外，由 `scheduler_pipeline.py:104-121` 的
`_task_worker_full_model_ids()`（health + 已认证 + **hello 里含完整模型**）判定并写入
`_pipeline_worker_opt_out`。**B 的卸载**让节点回落到「无完整模型」⇒ 掉出 `opt_out` ⇒ 主节点立刻
重新分层 ⇒ 与 A 的刷新互相激发。

**⚠️ 一个必须保留的正面观察（原始诉求本身成立）**：单独看，A 确实让 master 快照变正确 ——
`13:50:23` 层配置就绪后紧接一次 `hello_acked`，且 master 的 `worker_protocol` 随之变为
`full_model_worker_count=0` / `workers_missing_full_model=[client_TABLET-2TLUCNU8]` /
`worker.capabilities.models` 为空（与「本机已是层段」一致）；而旧代码此处会**错误地**显示非空。
⇒ **问题不在于"要不要通知"，而在于"通知会驱动主节点重算"这个正反馈。**

**若要继续修，剩下的是 master 侧方向（C，需先设计再动手）**：
- 让 master 对**重复 / 幂等的 hello 不触发重算**（快照带版本或序列号，内容未变则跳过）；
- 或给 `_task_worker_full_model_ids()` 与 offer 校验提供**同源且带时效性**的快照；
- 或让 worker 在**进入/退出层段角色时同步 `opt-out` 语义**（而不是刷新 hello），使主节点无需重算。

**当前规避（仅针对 Full Worker / task-graph 路径，实测有效）**：**先载整模，后连集群**（或先卸载再载），避免节点先被分配普通 PyTorch 层段。

**2026-09-26 relay_middle 边界修复**：`relay_middle` 不再要求 scheduler 的 `ModelHost` 先载整模或层段模型；它登记逻辑层段合同，由独立 `relay_mid_service` 持有段工件并接收 hidden 转发。该修复不等同于 #28 的 Full Worker/task-graph 自动准入已完成；后者的双机 workflow 仍按上面的操作序列验收。

### 28.5 恢复集群的正确操作序列（2026-09-26 实测，供再次拉起时照做）

为免再次踩到 #28，按以下顺序操作（**顺序是本文档里唯一被实测证明可用的手段**）：

1. **两端各自起服务**，都带 `QLH_TASK_GRAPH_ENABLED=true`、
   `QLH_TASK_WORKER_EXPERIMENTAL_ENABLED=true`；Surface 另设 `QLH_NODE_ROLE=client`，
   master 设 `QLH_NODE_ROLE=master`。**此时两端都不载模型。**
2. **两端各自完整加载整模**（不经层段）：
   `POST /api/models/load`，body `{"model_id":"qwen2.5-0.5b","engine":"pytorch"}`。
   校验：`GET /api/status` 的 `layer_range` 必须为**空**（非空即说明走了层段加载路径，见 28.2）。
3. **之后** Surface 才 `POST /api/cluster/connect`，
   body `{"master_host":"<tailnet-ip>","master_port":8888}`。
4. 校验 master 的 `GET /api/workflows`：`worker_protocol.full_model_worker_count == 1`、
   `workers_missing_full_model == []`、`worker_readiness_reason == "task_worker_manual_dispatch_ready"`、
   `manual_stage_dispatch_enabled == true`，且 worker 的 `capabilities.models` **非空**。
5. 执行任务图：`POST /api/chat` 必须**显式**带
   `{"routing_preference":"distributed_required","execution_mode":"task_graph"}`（原因见 #29）。
6. 校验结果：`metrics.distributed_used == true`、`fallback == false`、`partial_result == false`，
   且 workflow 的 `candidate_a.provider` 以 `remote_` 开头并且 `state=completed`。

**若顺序被弄反**（Surface 先 connect、先被当作层 worker）：**停掉两端服务后重新按 1→6 执行**。
当前代码下**没有**自动纠正手段 —— A/B 两条自动纠正路径均已实测会引发 `hello`/`release` 死循环（见 28.4）。

### 31.6.1 单机探针已验结论（2026-09-26）

用**真 `transformers 5.17.0` + 真 `qwen3-5-2b` 工件 + 真主仓引擎**（`model_module.ModelManager`
+ `load_layer_range(0,12, has_embedding=True, has_lm_head=False)` + `forward_layers`，FP32/CUDA，

**① M3 的依据成立（"分量归零"是如实反映结构，不是绕过闸门）**

- 顶层子模块 = `['model','lm_head']` ⇒ **不含 `mtp`**；`model` 子模块 =

  （`Qwen3_5PreTrainedModel = ['^mtp.*']`）⇒ **transformers 侧明确忽略这两类 key**；
- `model` 参数 = **1,881,825,088（1.88B）**，与"mtp / visual 不在前向结构里"一致；
- 层类型分布（24 层）= `LLL F` × 6 ⇒ **`full_attention_interval=4`** 现场可复核（也解释了
  `cut_layers` 那条"切点必须是 4 的倍数"的硬约束）。

**② M4 的前提成立，但危险点的位置要修正**

- `result["past_key_values"]`（tuple）**12 层里 9 层是 `None`**，且 **第 0 层就是 `None`** ——
  分布恰为 `LLL F LLL F LLL F`，与层类型一一对应 ⇒ `past_kv[0][0].shape` 即 `None[0]` **必崩**
  ⇒ `31.1 ④` 成立；
- `result["cache"]` **存在**，是 `DynamicCache`，`cache.layers[0]` 为 **`LinearAttentionLayer`**
  （**完整，不是 `None`**）⇒ **M4「优先持有 `result["cache"]`」的依据成立**；
- ★ **修正**：把 tuple **原样喂回** `forward_layers` **并不崩**（返回值照常）⇒ **崩的不是
  `forward_layers` 本身，而是 consumer 里读 shape 的那几行**（`scheduler_pipeline.py:2307` 的
  `past_kv[0][0].shape`、`:2340-2343`）。**改 M4 要改的是读侧，不是喂侧**。
- ★ **原「待确认点」已答（2026-09-26 续测）**：`cache.layers` 的长度虽然是 **24**（全模结构），
  但各段用的是**段内局部索引（0-based）** —— 实测前段 `0..12` 与后段 `12..24` 写入的槽位
  **都是 `[3, 7, 11]`**（= 段内 `LLL F` 里 full_attention 层的位置），后段**并不**按 12 偏移
  ⇒ **段间搬运不需要偏移**，直接 `cache = out["cache"]` 传给下一段即可。
- ★ **要保的东西有确定载体**：`cache.layers[i]` 分两类 —— `DynamicLayer`（full_attention，状态在
  `keys` / `values`）与 `LinearAttentionLayer`（linear_attention，状态在 **`recurrent_states` /
  `conv_states` 两个 dict**，另有 `is_*_initialized` / `has_previous_state`）
  ⇒ **recurrent state 就在 cache 对象内部** ⇒ **M4 只需持有 `result["cache"]` 即可**，
  **无需**额外搬运模块侧 / 全局状态。
  ⇒ **M4 的可行性完全确定**：改**读侧**（`cache = result.get("cache") or result["past_key_values"]`，
  取 shape 时跳过 `None`）即可，**不需要**动 `forward_layers` 的喂入侧。

**③ M5 未验**：master 保留 LM Head 路径需要 `has_lm_head=True` 的另一套加载，本轮未做。
