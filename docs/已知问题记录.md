### #37 A1 relay 链与 A2/A3 层段 Stage 是同一件事的两套机制，角色判据散落且无互斥

- 现象：三条线路做的是**同一件事**（把模型层切分到多节点、节点间传残差流），却各有角色判定与状态。改一个开关时另一条线路会接管。2026-10-04 实测：把 `QLH_RELAY_ENABLED` 置 0 重启后，请求没有落到本地推理，而是走了 Route A，撞上 Route A 自己的 `.detach()` 残留（已修，见「已修复」表），失败后回退到全层主节点模式并产出垃圾。
- 三者关系（子 agent 调查）：**A1 是独立的一套数据面**（legacy `LAYER_CONFIG` 推送 + `LAYER_FORWARD` TCP，节点角色靠 `engine="relay_middle"` 标记，远端跑 `scripts/relay_mid_service.py`）；**A2 只是协议 + worker 侧执行端**（`src/task_worker_protocol.py` 的 `layer_forward`、`src/inference_service/engine_host.py:_execute_layer_forward_stage`）；**A3 是 A2 的唯一产品驱动端**（`src/scheduler_pipeline.py:_run_route_a_stage_pipeline`，构造 offer、持有 prefill/decode/KV 状态机）。`_execute_layer_stage_offer` 的唯一非测试调用点在 A3 循环内 ⇒ **A2 脱离 A3 不构成独立产品路径**。
- 注意：`execution_mode=route_a_stage_offer_v3` **不是请求字段**（`ChatRequest.execution_mode` 只有 `{auto, task_graph}`），它只是 `metrics.execution_mode` 的输出。
- 路由入口：**没有单一路由函数**。分流散在 `_run_pipeline`（stage vs legacy，`:5234-5268`）、`_push_layer_config_to_clients_locked`（角色标记，`:553-648`）、`_relay_segment_for_worker`（`:4386`）。唯一**角色判据入口**是 `_is_relay_host()`（`:4415`），但仍有 ≥13 处**内联** `_relay_segment_for_worker(...) is not None` 绕开它。
- 已识别缺口（均未修）：
  1. **`_is_relay_host` 的 node_id 名字空间不归一** —— `scheduler_pipeline.py:4413` 直接用 env 字符串查表，而 worker 注册的 `client_id` 形如 `client_<hostname>`（`peer.py:74`）。`QLH_RELAY_SEGMENTS` 写节点名而非 `client_*` 时判据恒 False ⇒ `:572` 的「relay 优先于 stage」豁免失效 ⇒ 该节点被标 `stage_offer_v3`，而 worker 侧可能仍持有 `engine=relay_middle` 旧配置 ⇒ **双重角色**。
  2. **relay_worker_ids 只从 `node_type=="pc"` 集合取**（`scheduler_pipeline.py:359-364`、`:387-390`）⇒ relay 宿主注册成别的类型时豁免全部失效（`#33` 症状可复发）。
  3. **无 A1↔A2/A3 互斥检查** —— `QLH_RELAY_ENABLED` 与 `QLH_TASK_WORKER_EXPERIMENTAL_ENABLED` 从未出现在同一条件里。且后者**可运行时热切换并持久化**（`api_server.py:_set_task_graph_runtime_settings`），前者是 **import 期常量**（`config.py:452`）⇒ 运行中切开关会**改变节点角色集合**。
  4. **可用性陷阱**：集群同时存在 relay 宿主与 stage worker 时，capacity plan 同时含 relay 零层条目与 stage 条目 ⇒ `stage_offer_nodes ≠ pipeline_nodes` ⇒ **所有分布式请求 fail-closed**（`scheduler_pipeline.py:5263`）。
  5. **`_relay_segment_map_cache` 无惰性初始化保证**（`scheduler.py:2224`/`:2300` 直接读）⇒ 首次调用顺序不利时静默按「无 relay 段」处理（fail-open，与同函数 fail-closed 的意图矛盾）。
  6. **手动分层与手动容量计划零 relay 感知**（`scheduler.py:3303-3410`、`:3120-3190`）⇒ 无法表达「`[k,N)` 由远端段执行」，relay 认领层会被算回本机。
  7. **两套 worker 实现判据集合不对称**：`peer.py` 没有 `scheduler_pipeline.py:1905-1939` 的 `QLH_LAYER_GGUF` 拒绝判据，也没有 `:2947-2962` 的保守 relay 委托，且不校验每步下发的 `relay_segment`。
- 待做：向「同一件事只有一套机制」收敛；至少要把角色判据收进唯一入口并补齐上述豁免，外加一条「A1 与 A2/A3 不同时生效」的互斥检查与回归用例。

### #35 relay 链的上游段取的是 `output_norm` 之后的 hidden，接力第一步即分叉

- 现象：relay 段委托**从未产出过正确 token**——master 每步收到的 token 恒为 `68132, 30779, 68132, 30779…` 交替，与 prompt 无关，确定性复现；因 pipeline 返回空响应被 `回退到本地推理` 掩盖，长时间被误读成「relay 成功」。
- 根因：relay 链要求上游交出**末层输出、`output_norm` 之前**的残差流，而 `src/llama_engine.py:LlamaCppEngine.forward_layers_to_hidden` 走的是 pip 绑定的 `llama_set_embeddings(ctx, True)` + `llama_get_embeddings_ith`（`src/llama_engine.py:1910`、`:1926`、`:1933`），该通道返回的是 **`output_norm(H)`**。下游段拿到已 norm 的 hidden 再跑自己的 `blk.8..23` 与 `output_norm` ⇒ 残差流被错位。
- 证据：`src/llama_keep_head.py:1-15` 明确记载该通道语义与量化偏差（`scripts/relay_diag_head_norm.py` 测得 `rel_err=0.0018` / `cos=0.999998`）；`src/relay_segment_client.py:222-224` 亦早已警告「远端语义必须与本机 keep-head 一致（末层输出、`output_norm` 之前）——否则接力首步即分叉」。
- 已接线（2026-10-04）：`src/llama_engine.py:LlamaCppEngine._keep_head_upstream` 惰性构造 `KeepHeadUpstream`（`forward_tokens_to_hidden()` 在 `:411`），按「工件路径 + 层数」缓存；`forward_layers_to_hidden()` 优先走它，不可用时告警并退回 embeddings 通道。新任务（`n_past == 0`）先 `reset()` —— worker 同进程跨任务复用，不清记忆会撞残留位置（`llama_decode rc=-1`，与 relay tail 段的 `_pos` 泄漏同族）。
- 两个接线时必须知道的约束（原先只写在别处，接线方看不到）：shim 本体是 `build/keephead/build-cpu/bin/qlh_keep_head.dll`（`qlh_kh_*` 入口在它里面），**不是**同目录的 `libllama.dll`；`layer_inp` 模式被 shim 限制为 `cut_layer < n_layer`（`scripts/model_tools/keep_head_shim/qlh_keep_head.c:111`），取不到需要的 `lid == n_layer`，故用 `nextn`（qwen2 挂点恰在 `output_norm` 之前）；`qwen3*` 挂点在之后，代码显式拒用。
- 实测（2026-10-04，本机 master + Surface tail 段，SSH 隧道 50283）：prompt「Count from 1 to 5, separated by commas.」⇒ `content="1,2,3,4,5."`，逐 token `16/11/17/11/18/11/19/11/20`；连续多次请求均成功且无回退。该形态此前从未产出过正确 token。
- 待做：同一 prompt 下 relay 链与整模**逐 token 对拍** —— 当前只验到「生成了正确文本」，尚未与整模逐位对照。

### #34 relay 链的会话状态有两套缓存，其中一套是死代码

- 现象：relay 段委托的会话关闭逻辑看似健全，实际从不生效；排查时极易被引到错误方向（2026-10-04 本轮曾据此误判为「`_pos` 跨任务累积」）。
- 根因：同一份会话状态被两处各存一份、互不可见。
  - `src/scheduler_pipeline.py:_relay_segment_client_for_task` 写 `self._relay_segment_clients`，`src/scheduler_pipeline.py:_close_relay_segment_client` 读同一属性 —— 但**该写入路径从未被执行**，属性恒为 `None`，`_close_relay_segment_client` 于是成了死代码。
  - 真正执行 relay 段委托的是 `src/inference_service/peer.py`：`:673-686` 写 `self._relay_sessions`，`:771` `_close_relay_session()` 关它，只在 `:999` `_handle_pipeline_done()` / `:1012` `_handle_pipeline_abort()` 与三条错误路径（`:701`/`:711`/`:754`）触发。
- 证据：master 日志 `关闭 relay 段会话: task=… 无缓存（cache=None cache_id=None …）`（`cache` 为 `None`，即属性从未被赋值）；tail 侧 `[session] … closed_cleanly=True` 证明真正的 `CLOSE` 帧由 peer 路径发出。
- 影响：relay 链的会话生命周期只有一个真实来源（peer），调度侧的清理路径会**静默空转**；任何在调度侧新增的「任务结束即释放 relay 会话」逻辑都会无声失效。失败原先只落 `logger.debug`（`src/scheduler_pipeline.py:_close_relay_segment_client`），2026-10-04 已提到 `warning` 以便暴露。
- 待做：把 relay 会话所有权收敛到单一来源（或让调度侧清理路径能触达 peer 的会话表），并补一条「任务结束时 relay 会话必须被关闭」的回归用例。

## 3. 上游缺陷

### #27 llama.cpp RPC 无错误恢复：任一 socket 失效即 `abort()` 整个进程

- 现象：跨机 RPC 请求全部成功后的收尾阶段，host 退出码 `3221226505`（`0xC0000409`）、worker 退出码 1，请求判据仍 `passed`。
- 根因：`0xC0000409` 是 `abort()` 经 `__fastfail(FAST_FAIL_FATAL_APP_EXIT=7)` 的用户态异常码；`ggml-rpc.cpp:30` 的 `RPC_STATUS_ASSERT` 失败即 `GGML_ABORT`，`transport.cpp` 对 `recv() == 0` 静默返回 false。上游 #26384 记录该宏并结论"RPC has no error recovery"。
- 处置：本仓不改（上游设计缺陷）；作为生产 supervisor 使用前需上游修复或自建 supervisor。
- 证据：`local_docs/evidence/llama-pc-rpc/rr6-*.json`；另见[验收清单](验收清单与资源限制登记.md) D20。
