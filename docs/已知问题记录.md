## 问题 #1：从节点也能自定义管理员邮箱（仅主节点可配置）

> **状态**：待修复
>
> **登记日期**：2026-08-07
>
> **严重程度**：中（配置一致性 / 权限边界）
>
> **发现途径**：人工走查管理页面（分布式模式下从节点端）

### 1.1 问题概述

管理员收件邮箱是**集群级**配置（主节点宕机/恢复告警、审查投票邮件的收件人），但当前**从节点端管理页面同样显示并可修改该配置**，且后端接口对任何节点开放。预期行为：**只有主节点能显示并修改该条目，从节点不显示**。

### 1.2 复现路径与代码位置

1. **前端**：`frontend/src/components/AdminPanel.jsx` 第 1935 行起"📧 邮件告警"section，注释明确写着 `{/* ---- 邮件告警配置与测试（所有节点） ---- */}`，渲染无 `isMaster` 过滤——而同一文件中其它主节点专属 section 均以 `{isMaster && ( ... )}` 包裹（如 363 行 `const isMaster = myRole?.is_master ?? false;`，1126/1511/1538/1580/1696/1810/2015/2116 行等）。
2. **后端**：`src/api_server.py`
   - `GET /api/cluster/email-config`（6942 行）——查询，无角色校验；
   - `POST /api/cluster/email-config`（6965 行）——`set_admin_email` 持久化到**本机** `node_config.json`，无角色校验；
   - `POST /api/cluster/email-test`（6915 行）——测试邮件，注释"任何节点均可调用"，无角色校验。
3. **语义矛盾**：`src/email_notifier.py` 第 8 行"收件邮箱优先 node_config.json 的 admin_email（UI 可配置），回退 QLH_SMTP_RECIPIENT"；而主节点宕机告警实际由**从节点**触发发送（`src/scheduler.py` 11617-11634：client 侧检测宕机 → `send_master_down_alert`）。于是从节点各自配置的邮箱会成为该节点发送告警的收件人，集群内收件人可能不统一。

### 1.3 影响分析

1. **告警丢失/错投**：从节点若被（误）配置了非管理员邮箱，主节点宕机告警与恢复通知将发到错误地址，管理员收不到。
2. **投票通道失效**：`email_notifier.py` 第 569-572 行 IMAP 轮询只接受"发件人 == 管理员邮箱"的 Y/N 投票；不同节点管理员邮箱不一致时，管理员对部分节点发起的投票会被忽略。
3. **权限边界**：集群关键配置（管理员邮箱）不应由任意从节点单方面改写；与"只有主节点能注册节点/转让身份"等既有约束不一致。
4. **误导性 UI**：从节点页面显示"当前生效：xxx（本机配置）"，暗示该节点可独立控制集群告警收件人。

### 1.4 修复方向

**最小修复（权限控制，推荐立即做）**

1. **前端**：`AdminPanel.jsx` 邮件 section 外包 `{isMaster && ( ... )}`，与其它主节点 section 一致；从节点完全隐藏"管理员收件邮箱 / 发送测试邮件"条目。删除 `（所有节点）` 注释。
2. **后端**：
   - `GET/POST /api/cluster/email-config`、`POST /api/cluster/email-test` 增加主节点校验，非主节点返回 `403 {"detail": "仅主节点可配置管理员收件邮箱"}`；
   - 校验实现复用现有角色判定（`api_server.py` 2863 行 `scheduler._effective_role()` 与 `my-role` 端点返回的 `is_master`，见 6587 行 `/api/cluster/my-role`），或新增 `_require_master()` 辅助函数统一收口。

**语义修复（配置一致性，与最小修复同批或紧随）**

3. 宕机告警的收件人统一为**集群管理员邮箱**：从节点发送 `send_master_down_alert` 时，收件人取主节点下发的集群配置（经现有配置同步通道）或环境变量回退，**不再使用从节点本地 `node_config.json` 的 `admin_email`**。
4. 清理残留：升级后忽略从节点 `node_config.json` 中已存在的 `admin_email` 键（或启动时由主节点配置覆盖），避免旧数据继续生效。
5. 文档同步：`SMTP.md` / 从节点部署指南注明"管理员邮箱仅在主节点管理页面配置"。

### 1.5 验收标准

1. 分布式模式下，从节点管理页面**不显示**邮件告警配置条目（含测试邮件按钮）。
2. 从节点直接调用 `GET/POST /api/cluster/email-config`、`POST /api/cluster/email-test` 返回 403。
3. 主节点页面功能回归：查询/保存/测试邮件正常，保存后 `node_config.json` 更新。
4. 主节点宕机模拟：从节点发送的告警邮件收件人 = 主节点配置的管理员邮箱（与从节点本地残留配置无关）。
5. 单测：`tests/test_email_config_api.py` 增补非主节点 403 用例；`tests/test_email_notifier.py` 增补收件人优先级用例（集群配置优先于本地残留）。

## 问题 #2：任务链分布式异构支持不完整——落地被 workflow 单模型身份锁死为同模型

> **状态**：调研完成（已定位机制性根因，修复待排期）
>
> **登记日期**：2026-08-07
>
> **严重程度**：中（能力缺口，与"异构分布式主路线"规划不符）
>
> **调研范围**：`src/task_graph.py`、`src/task_worker_protocol.py`、`src/task_worker_adapter.py`、`src/scheduler.py`、`src/api_server.py`、`src/model_sync.py` 及任务链/混合体系规划文档

### 1.1 问题概述

**异构定义：不同节点加载不同模型**（如节点 A 加载 Qwen-1.8B、节点 B 加载 Qwen-3B；或 A 只有 LLM、B 只有 SD 图像模型）。

调研结论：**协议层与调度层已按异构设计，但任务链落地被"workflow 单模型身份"机制锁死，当前一条 LLM 任务链只能同模型执行，LLM+SD 混合链无入口**。即：不同节点加载不同模型**合法**，但**无法组成一条任务链**。

### 1.2 现状与证据

**✅ 已具备（协议/调度层支持异构）**

1. worker 能力上报允许异构：hello capabilities 中 `models` 是**列表**，可含多个精确模型身份（model_id+engine+format+revision+sha256），协议校验无"全集群一致"约束（`src/task_worker_protocol.py:625-713`）。
2. 能力按节点独立存储：协调端按 `peer_id` 各自保存每台 worker 的能力快照（`src/task_worker_adapter.py:213-223`）。
3. worker 上报**实际已加载**的模型，加载什么报什么，模型切换后刷新 hello（`src/scheduler.py:3577-3595, 3782-3802`）——不同节点加载不同模型完全合法。
4. 调度按能力精确匹配：主节点候选筛选要求 `stage_type ∈ supported_stage_types` 且 `supports_model_identity(...)` 精确匹配（`src/api_server.py:3758-3795`）；provider reserve 与 worker 侧 offer 双重校验（`src/task_worker_adapter.py:566-580, 607-621`；`src/scheduler.py:4051-4078`）。
5. 图像 worker 独立匹配维度：v3 hello 用 `image.artifact_manifests`（sha256）而非 model_identity（`src/diffusion/worker_adapter.py:725-738, 823-859`）。
6. 规划文档明确任务链是异构主路线："任务链/DAG 拆分……可跨模型、跨引擎，异构分布式主路线"（`docs/混合分布式推理体系规划.md:42`）；"一个 Stage 调 PyTorch 层流水线、另一个 Stage 调 Android 完整 Worker 或 llama.cpp"（同文档 :52）；verify stage 可用另一模型校验（`docs/三种分布式拆分细化实施方案.md:387-388`）。

**❌ 缺失（落地被锁死的点）**

1. **workflow 级单模型身份**：`WorkflowRecord.model_identity` 是单个可选字段（`src/task_graph.py:245`），`_prepare_stage` 把同一个 `workflow.model_identity` 塞进每个 Stage 的 `StageRequest`（`src/task_graph.py:2216`）；`StageSpec` 没有 per-stage 模型字段——"stage A 用 1.8B、stage B 用 3B"在代码层**无表达入口**。
2. **自动候选强制同模型**：自动 Worker 候选"必须拥有与主节点**完全一致的模型身份**；错模型、缺模型不进入候选集"（`docs/任务链下一阶段实施计划.md:549-556` TC-N2.3）；远端 LLM stage 强制要求精确模型身份（`src/api_server.py:4060-4067`；`src/task_worker_adapter.py:607-612`）。
3. **无 LLM+SD 混合链模板**：API 仅暴露 `dual_candidate`（3 个 LLM stage，`src/task_graph.py:338-351`）与 `image_generate_v1`（单 stage，`src/api_server.py:3683-3696`）；"不开放模型生成任意任务图"（`docs/任务链下一阶段实施计划.md:87`），任意 DAG 属 TC-N3.1 规划（同文档 :613）。
4. **v3 hello 能力互斥**：图像 worker 的 v3 hello 要求 `models` 为空且不可降级（`src/task_worker_protocol.py:675-680, 1179-1186`），LLM 与 SD 只能双通道并存。
5. 对比：**层间流水线/张量并行要求同模型是设计内约束**（`src/model_sync.py:172, 233-245`；`docs/三种分布式拆分细化实施方案.md:1222` "rank 模型严格一致"），不应放宽；任务链是例外场景，当前被上述机制误伤。

### 1.3 影响分析

1. 异构节点（1.8B vs 3B、LLM vs SD）**无法组成一条任务链**，各节点只能各自执行同构任务；与"任务链是异构分布式主路线"的规划相悖。
2. 集群内加载了不同模型的从节点在自动候选模式下**永远不会被选中**（同模型过滤），其算力在任务链场景被闲置。
3. verify/交叉校验类 stage（用另一模型校验结果，规划中已设计）无法落地。

### 1.4 修复方向（建议按序实施）

**最小修复（协议层，P0）**

1. `StageSpec` 增加可选 `model_identity` 字段（缺省继承 workflow 级身份），`_prepare_stage` 按 per-stage 覆盖；`WorkflowRecord.model_identity` 保留为默认值语义。
2. 自动候选过滤从"与主节点一致"改为"**满足该 stage 的 model_identity**"（stage 无身份时沿用现状同模型语义，行为不回归）。

**语义修复（P1）**

3. 新增混合链模板（如 `llm+image`：LLM stage + 图像 stage），放宽 v3 hello 与 v2 的并存约束，验证跨模型链的 offer/result/lease/取消全链路。
4. 任务链计划 TC-N3.1（开放任意任务图）落地时，把 per-stage 模型身份作为一等公民纳入。

**约束保留**

5. 层间流水线/张量并行的同模型（sha256 一致）约束**不动**——那是模型拆分语义，不是任务链语义。

### 1.5 验收标准

1. 构造异构夹具（fake worker A 报 Qwen-1.8B、fake worker B 报 Qwen-3B）：一条 `dual_candidate` 链指定 stage A→worker A、stage B→worker B，两端成功执行并聚合。
2. 自动候选模式：集群内只有异构模型 worker 时，按 stage 模型身份筛选而非一刀切排除。
3. 混合链（LLM stage + SD stage）端到端成功，图像 stage 走 `image.artifact_manifests` 匹配。
4. 回归：现有同模型任务链全部用例不回归；层间流水线/TP 的同模型约束用例不变。
5. 文档同步：`任务链下一阶段实施计划.md` TC-N2.3 同模型描述改为 per-stage 语义。
