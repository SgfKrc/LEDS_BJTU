## 问题 #1：从节点也能自定义管理员邮箱（仅主节点可配置）

> **状态**：✅ 已关闭（2026-08-11；权限与配置一致性修复已由自动回归覆盖）
>
> **登记日期**：2026-08-07
>
> **严重程度**：中（配置一致性 / 权限边界）
>
> **发现途径**：人工走查管理页面（分布式模式下从节点端）

### 1.1 问题概述

管理员收件邮箱是**集群级**配置（主节点宕机/恢复告警、审查投票邮件的收件人），但当前**从节点端管理页面同样显示并可修改该配置**，且后端接口对任何节点开放。预期行为：**只有主节点能显示并修改该条目，从节点不显示**。

### 1.2 复现路径与代码位置

1. **前端**：`frontend/src/components/AdminPanel.jsx` 第 1935 行起"📧 邮件告警"section，注释明确写着 `{/* ---- 邮件告警配置与测试（所有节点） ---- */}`，渲染无 `isMaster` 过滤——而同一文件中其它主节点专属 section 均以 `{isMaster && ( ... )}` 包裹（如 363 行 `const isMaster = myRole?.is_master ?? false;`，1126/1511/1538/1580/1696/1810/2015/2116 行等）。
2. **后端**：`src/api_server.py`
   - `GET /api/cluster/email-config`（6942 行）——查询，无角色校验；
   - `POST /api/cluster/email-config`（6965 行）——`set_admin_email` 持久化到**本机** `node_config.json`，无角色校验；
   - `POST /api/cluster/email-test`（6915 行）——测试邮件，注释"任何节点均可调用"，无角色校验。
3. **语义矛盾**：`src/email_notifier.py` 第 8 行"收件邮箱优先 node_config.json 的 admin_email（UI 可配置），回退 QLH_SMTP_RECIPIENT"；而主节点宕机告警实际由**从节点**触发发送（`src/scheduler.py` 11617-11634：client 侧检测宕机 → `send_master_down_alert`）。于是从节点各自配置的邮箱会成为该节点发送告警的收件人，集群内收件人可能不统一。

### 1.3 影响分析

1. **告警丢失/错投**：从节点若被（误）配置了非管理员邮箱，主节点宕机告警与恢复通知将发到错误地址，管理员收不到。
2. **投票通道失效**：`email_notifier.py` 第 569-572 行 IMAP 轮询只接受"发件人 == 管理员邮箱"的 Y/N 投票；不同节点管理员邮箱不一致时，管理员对部分节点发起的投票会被忽略。
3. **权限边界**：集群关键配置（管理员邮箱）不应由任意从节点单方面改写；与"只有主节点能注册节点/转让身份"等既有约束不一致。
4. **误导性 UI**：从节点页面显示"当前生效：xxx（本机配置）"，暗示该节点可独立控制集群告警收件人。

### 1.4 已实施修复（2026-08-11 复核）

1. **前端权限边界**：`AdminPanel.jsx` 已以 `{isMaster && (...)}` 包裹邮件告警 section，注释与页面文案均明确它是主节点专属的集群级配置。
2. **后端权限边界**：单体与 scheduler-svc 的 `GET/POST email-config`、`POST email-test` 均执行主节点校验；从节点固定返回 `403`，测试覆盖三个端点。
3. **集群配置优先级**：`email_notifier` 读取顺序已变更为主节点 SQLite `cluster_config` → 环境变量 → 本机 `node_config` 兼容回退。从节点遗留的 `admin_email` 不再覆盖集群管理员邮箱；`send_master_down_alert` 复用这一路径。
4. **文档边界**：当前没有独立 `SMTP.md`，本记录和主节点页面已成为配置边界的当前说明；后续从节点部署指南改版时必须保留“仅主节点管理”的表述，不能恢复从节点本地覆盖语义。

### 1.5 验收标准

1. [x] 分布式模式下，从节点管理页面不显示邮件告警配置条目（含测试邮件按钮）。
2. [x] 从节点直接调用 `GET/POST /api/cluster/email-config`、`POST /api/cluster/email-test` 返回 403。
3. [x] 主节点查询/保存/测试邮件接口继续通过；保存时写入集群配置并保留 `node_config` 兼容回退。
4. [x] 收件人选择测试确认集群配置优先于从节点本地残留，宕机告警复用同一 `get_admin_email()` 路径。
5. [x] `tests/test_email_config_api.py` 与 `tests/test_email_notifier.py` 已覆盖权限和优先级；本轮定向回归为 `132 passed / 1 skipped`（并含 IPv6 相关回归）。

## 问题 #2：任务链分布式异构支持不完整——落地被 workflow 单模型身份锁死为同模型

> **状态**：`Validating`（2026-08-12 `L1-2A/B` 开发门完成；真实 Worker 验收仍受 L1-2 阻塞）
>
> **登记日期**：2026-08-07
>
> **严重程度**：中（能力缺口，与"异构分布式主路线"规划不符）
>
> **调研范围**：`src/task_graph.py`、`src/task_worker_protocol.py`、`src/task_worker_adapter.py`、`src/scheduler.py`、`src/api_server.py`、`src/model_sync.py` 及任务链/混合体系规划文档

### 1.1 问题概述

**异构定义：不同节点加载不同模型**（如节点 A 加载 Qwen-1.8B、节点 B 加载 Qwen-3B；或 A 只有 LLM、B 只有 SD 图像模型）。

调研结论更新：**协议层与调度层本已按异构设计，`L1-2A` 已补齐 LLM 任务链的 per-stage 身份表达与逐 Stage 候选筛选，`L1-2B` 已补齐唯一受控的 LLM→SD 模板与跨通道结果契约**。不同节点加载不同 LLM 模型可组成固定任务链，集群内 v2 文本 Worker 与 v3 SD Worker 可组成固定 `llm_sd15_v1`；真实 Worker 验收仍未完成。

### 1.2 现状与证据

**✅ 已具备（协议/调度层支持异构）**

1. worker 能力上报允许异构：hello capabilities 中 `models` 是**列表**，可含多个精确模型身份（model_id+engine+format+revision+sha256），协议校验无"全集群一致"约束（`src/task_worker_protocol.py:625-713`）。
2. 能力按节点独立存储：协调端按 `peer_id` 各自保存每台 worker 的能力快照（`src/task_worker_adapter.py:213-223`）。
3. worker 上报**实际已加载**的模型，加载什么报什么，模型切换后刷新 hello（`src/scheduler.py:3577-3595, 3782-3802`）——不同节点加载不同模型完全合法。
4. 调度按能力精确匹配：主节点候选筛选要求 `stage_type ∈ supported_stage_types` 且 `supports_model_identity(...)` 精确匹配（`src/api_server.py:3758-3795`）；provider reserve 与 worker 侧 offer 双重校验（`src/task_worker_adapter.py:566-580, 607-621`；`src/scheduler.py:4051-4078`）。
5. 图像 worker 独立匹配维度：v3 hello 用 `image.artifact_manifests`（sha256）而非 model_identity（`src/diffusion/worker_adapter.py:725-738, 823-859`）。
6. 规划文档明确任务链是异构主路线："任务链/DAG 拆分……可跨模型、跨引擎，异构分布式主路线"（`docs/混合分布式推理体系规划.md:42`）；"一个 Stage 调 PyTorch 层流水线、另一个 Stage 调 Android 完整 Worker 或 llama.cpp"（同文档 :52）；verify stage 可用另一模型校验（`docs/三种分布式拆分细化实施方案.md:387-388`）。

**✅ `L1-2A` 已修复（LLM TaskGraph 身份边界）**

1. `StageSpec.model_identity` 为可选 `ModelIdentity`；未配置时继承 `WorkflowRecord.model_identity`，配置后由 `_prepare_stage()` 写入对应 `StageRequest`。Stage 快照记录最终生效身份，workflow 身份仍只是默认值，兼容旧调用。
2. 自动候选针对每个 `full_inference` Stage 的生效身份独立调用精确能力筛选，并只把同身份的远端 Provider 放入该 Stage 的 fallback。固定 `dual_candidate` 未声明身份时仍沿用主节点默认模型和原有同模型行为。
3. `tests/test_task_graph_review.py` 的两个 deterministic fake Worker 分别接收 Qwen-1.8B/Qwen-3B，两个候选和本地 aggregate 成功完成；`tests/test_task_graph_api.py` 以两个不同能力的 remote Worker 证明自动规划不会把 B 身份分配到 A。

**✅ `L1-2B` 已修复（唯一 LLM→SD 模板）**

1. `image_prompt_sd15_template()` 固定为 `image_prompt → image_generate`，不接收用户提供的 DAG；v2 Stage 绑定精确 `ModelIdentity`，v3 Stage 继续按 SD artifact manifest 匹配。
2. v2 输出在 Coordinator 内仅绑定为 v3 的 `prompt` 根字段，完成绑定后移除依赖对象，因此 v3 offer 仍满足 Blob-only、`dependencies={}` 的协议约束。
3. `POST /api/diffusion/distributed/mixed` 只接受主节点和双实验门；文本 Worker 必须健康、可用且无歧义，图像 Worker 必须健康且为不同节点。同节点双角色、歧义模型、失败与取消均安全拒绝或清理 workflow blob/lease。
4. 固定成功、过长提示词失败、执行中取消、模板输入绑定和 v2 协议能力均有覆盖；相关定向 `112 passed`，Python 全量 `1994 passed / 8 skipped`。

**❌ 仍缺失（下一阶段范围）**

1. **无任意 LLM+SD DAG**：仅开放固定 `llm_sd15_v1`；用户不可提交模型生成的任意图，后续扩展仍属 TC-N3.1 规划。
2. **v2/v3 仍是独立通道**：图像 Worker 的 v3 hello 保持 `models` 为空；模板要求文本与图像 Stage 来自不同节点，不把双角色能力伪装成单一 hello。
3. 对比：**层间流水线/张量并行要求同模型（sha256 一致）是设计内约束**，不应放宽；本票只改变任务链。

### 1.3 影响分析

1. 1.8B vs 3B 的 LLM Worker 已可按 Stage 组成固定任务链，空闲的异构 Worker 不再被全局同模型过滤错误排除。
2. 固定 LLM+SD、图像 manifest 与 v2/v3 双通道协作已接入；不能据此误报任意 DAG、同节点双角色或真实双机发布已支持。
3. verify/交叉校验类 LLM Stage 已有模型身份表达；实际模板和业务语义仍由后续任务链阶段定义。

### 1.4 修复方向（建议按序实施）

**最小修复（协议层，P0）**

1. [x] `StageSpec` 增加可选 `model_identity` 字段（缺省继承 workflow 级身份），`_prepare_stage` 按 per-stage 覆盖；`WorkflowRecord.model_identity` 保留为默认值语义。

5. 层间流水线/张量并行的同模型（sha256 一致）约束**不动**——那是模型拆分语义，不是任务链语义。

## 问题 #3：PyTorch 分层流水线从节点本地模型状态会粘滞退出，导致主节点静默单机回退

> **状态**：已修复，待使用新 PC 包进行双机实测
>
> **登记日期**：2026-08-08
>
> **严重程度**：高（表面显示集群在线，实际分布式推理未使用从节点）
>
> **影响范围**：PyTorch 层间流水线的 Qwen-1.8B、DeepSeek/Qwen2 系列；GGUF/llama.cpp 不涉及层间拆分。

### 3.1 现象与证据

2026-08-07 的 Qwen-1.8B INT4 请求中，主节点加载后曾下发 `master: 0-21`、`client: 21-24` 的层配置；随后从节点上报“从节点已退出 PyTorch 分层计算”。主节点将该节点排除，日志显示“未分配任何 PC 从节点参与模型层计算”，继而以 `fallback full master` 完成 186 tokens。

该请求没有任何 `LAYER_FORWARD`、张量传输或层结果日志。因此“回答混乱”不是中间 hidden states 丢失造成的：从节点根本没有参加本次推理。小模型 INT4 的输出质量、采样参数和旧会话上下文仍需作为独立质量问题排查。

### 3.2 根因

从节点通过本地模型加载、切换或卸载接口后，会调用 `release_pipeline_worker_for_local_model()` 并向主节点发送 `LAYER_WORKER_OPT_OUT`。此前该退出状态在从节点和主节点均为粘滞状态：后续普通层配置仍被从节点拒绝，主节点也持续把它排除出层分配。即使主节点后来已加载同款模型，也没有一条“主节点重新接管分层 worker”的权威同步路径。

### 3.3 已实施修复

1. 新增一次性主节点权威同步：`Scheduler.request_authoritative_layer_sync()` 在主节点完成 PyTorch 模型加载后调用；收到分布式推理请求而流水线未就绪时也会调用一次。
2. 权威配置包含模型清单：`model_id`、`model_sha256`、`model_type`、`total_layers`、`engine`、主节点量化方式、层范围和配置代际。Qwen 与 DeepSeek/Qwen2 共用同一协议，仍以 SHA256 和层数校验同款模型。
3. 在线、空闲的 PC 从节点收到 `authoritative_sync=true` 后自动撤销旧 opt-out，按现有模型同步流程校验/获取模型并执行 `load_layer_range()`；加载完成后必须回传对应 `config_id` 的 ready ACK 才能参与推理。
4. CPU 从节点允许运行时自动回退 FP32；它不必与主节点 INT4 的运行 dtype 完全相同，但模型身份、架构和权重摘要必须一致。
5. 分布式请求最多等待 `QLH_PIPELINE_MODEL_SYNC_TIMEOUT` 秒（默认 60，范围 1-600）以等待同步 ACK；超时、模型下载/加载失败、连接断开时保持既有主节点全模型安全回退。
6. 同步请求采用计数而非布尔标记，避免并发请求把后一个权威配置错误降级为普通配置。旧安装包若再次明确 opt-out，主节点立即回退，不再无谓等待完整同步超时。

### 3.4 兼容性与实机验证

旧版从节点不认识 `authoritative_sync`，仍可能保持 opt-out；主节点会立即降级为单机推理。这不是张量损坏，必须更新主节点和 PC 从节点到包含本修复的同一版本后再测试。

验收步骤：

1. 主、从节点都启动并显示 TCP 在线；从节点可以先加载完整 PyTorch 模型以模拟旧场景。
2. 主节点加载 Qwen-1.8B 或 DeepSeek/Qwen2 的 PyTorch 模型，确认日志出现“主节点权威模型同步重新启用分层 worker”。
3. 等待从节点完成模型校验/层加载并回传 ready ACK，集群状态应显示其层范围而不是“已退出”。
4. 发起新会话的分布式请求，日志必须出现层前向与从节点任务/worker 指标；若同步失败，响应 metrics 必须明确为 fallback，而不能伪称已分布式执行。

### 3.5 后续演进

当前修复以“主节点加载完成 + 请求前兜底同步”为触发点。后续将模型清单升级为持久化版本（模型版本、权重 SHA256、tokenizer/revision、引擎兼容版本、层配置 generation），由主节点维护期望状态，从节点在注册、重连和模型状态变化时上报实际状态。主节点仅对空闲 worker 执行切换；忙碌 worker 保留当前任务，完成后再对齐，避免打断本地任务或正在进行的流水线。

## 问题 #4：流水线零温度采样触发 CUDA invalid argument 并破坏本地回退

> **状态**：已修复，已完成双机复测
>
> **登记日期**：2026-08-08
>
> **严重程度**：高（真实分布式请求在首个 token 失败，CUDA 上下文失效后完整模型回退也失败）

### 4.1 受控复现

固定 Qwen-1.8B、提示词、空会话、`max_new_tokens=24`、`temperature=0`、`top_p=1`。`local_only` 正常生成“2+2等于4。”；`distributed_required` 完成主节点 `Layer 0-21`、从节点 `Layer 21-24` 的 step 0 前向并收到结果后，在主节点 `torch.multinomial` 报 `CUDA error: invalid argument`。

这证明层配置、首段前向、hidden states 传输和从节点尾层均已执行，错误发生在主节点 token 采样，而不是张量丢失。

### 4.2 根因与修复

单机生成把 `temperature <= 0` 解释为 `do_sample=False` 的贪心解码；流水线此前却将温度钳制为 `1e-8` 后仍执行 softmax + multinomial。FP16/BF16 logits 除以极小值可能产生 Inf/NaN，CUDA multinomial 报错并使同一进程内后续 bitsandbytes 完整模型重载也失败。

流水线现已统一采样语义：零温度直接 `argmax`；正温度先将 logits 转 FP32，再执行 top-p，并在 multinomial 前检查 logits、概率与候选概率和均为有限有效值。异常概率会在破坏 CUDA 上下文前明确终止。

### 4.3 修复后双机验收

在从节点 `client_TABLET-2TLUCNU8` 在线、模型配置同步确认后，使用与复现完全相同的提示词和推理参数重新请求 `distributed_required`：

- HTTP 200，`execution_mode=distributed_pipeline`，`distributed_used=true`，无回退；
- 主节点执行 `Layer 0-21`，从节点执行 `Layer 21-24`，从节点结果 step 0 至 step 6 均返回 `error=none`；
- `workers_used` 包含 `client_TABLET-2TLUCNU8`，任务统计同时计入 `master` 和该从节点；
- 生成结果为“2+2等于4。”，共 6 个 token，未出现张量传输缺失或 CUDA 上下文失效。

因此本次问题已完成真实双机验收；后续仍需在 PC 安装包环境中做一次同参数回归，以覆盖打包后的 CUDA/依赖组合。

## 问题 #8：主节点身份重置仍依赖已退场 PG，且错误广告链路本地地址

### 8.1 根因与地址来源
