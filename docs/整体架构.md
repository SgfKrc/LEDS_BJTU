## 1. 项目目标

QLH 主项目面向异构边缘计算设备，核心问题是分布式推理的可靠执行与优化证据，不再以产品壳的功能数量作为范围。当前设备范围包括：

- Windows/Linux 台式机、工作站、服务器和笔记本；
- 带 NVIDIA CUDA GPU 的独显节点；
- 仅有 CPU 或集成显卡的 PC 节点；
- Android 手机和平板；
- 后续通过明确能力协议接入的其他边缘设备。

Web/Android 界面、安装打包、知识库、运营工具和图像生成不属于主仓主线交付：产品壳与侧车只消费主仓的 HTTP/任务/模型合同；图像生成唯一归 Koakumix。主仓生产路径统一以无 torch 的 llama.cpp/GGUF 为基线。

系统解决的是单个设备受内存、显存、算力或能耗限制时的模型运行与协作问题。默认 Qwen-1.8B 只是基础样例，模型注册表还包含其他 Qwen 和 DeepSeek 实验槽位；模型能否参与层流水线必须经过架构、层数、tokenizer、权重和运行时兼容性校验。

## 2. 当前执行路径

| 执行路径 | 节点与引擎 | 模型格式 | 当前定位 |
|----------|------------|----------|----------|
| PC 本地 llama.cpp | CPU/集显/普通 PC | GGUF | **生产主路径**；完整模型单机推理 |
| llama.cpp RPC 模型分片 | PC/Android host + RPC worker | GGUF | **主攻路径**；目标是节点只承载部分模型，先过单机双进程门 |
| Relay 层接力 | PC 显式实验；L→L 已验证，D→L 长序列失败 | 裁层 GGUF + hidden/`embd` | **架构兼容轨道**；默认关闭，不替代 RPC，不进入 Edge 默认路由 |
| PC PyTorch 层流水线 | 能加载同一 PyTorch 模型工件并通过能力校验的 PC 节点 | Safetensors | **对照实验及 D→L Relay 来源**；不进入边缘或默认生产路由 |
| Android 本地 llama.cpp | Android Full | GGUF | 生产主路径的单机形态 |
| Edge/Android HTTP 回退 | Edge/Android -> PC 主节点 | 可无本地大模型 | 节点故障或资源不足时的绕行策略；不替代 Edge 本地 <=1B 推理，也不等于模型分片 |
| TP 孤岛（`island` 引擎） | 网关 PC 节点 -> 集群外 OpenAI 兼容端点 | 由孤岛后端自管 | 阶段 1 PoC；整请求推理，不参与层拆分 |
| 外部推理服务（`external_api`） | 任意服务节点按请求路由到集群外端点 | 由外部端点自管 | 阶段 1 PoC；整请求外发，受数据作用域门控 |

“Edge”“PC host/worker”“PC Reference P”“故障绕行”是运行角色，不直接等价于互斥产品包。调度器还必须检查实际引擎、模型身份、分片驻留状态、模型就绪状态、内存、加速器和网络状态。Edge 默认优先本地 <=1B 模型；更大模型由分片调度，节点故障时才启用绕行策略。

后两条路径的当前边界必须如实说明，不能写成已验收的生产能力：

- **TP 孤岛**：网关节点以 `engine="island"` 注册，对集群呈现为**单个逻辑高算力节点**，承担整请求推理；行为等同 `llama_cpp` 节点，不接收 `LAYER_FORWARD`（主节点按 `device_info.island.enabled` 过滤 + 网关侧拒收层配置，双保险）。孤岛内部的张量并行 collective 全部发生在孤岛内网，QLH 不感知也不依赖其协议。故障边界为整个逻辑节点，失败后走现有节点下线与重编排路径。部署见 [TP孤岛接入指南](archive/TP孤岛接入指南.md)。
- **外部推理服务**：不引入专职节点，由服务节点按请求决策是否把**整条请求**路由到集群信任域**之外**的 OpenAI 兼容端点。`QLH_EXTERNAL_DATA_SCOPE` 数据作用域门控是硬约束，默认 `opt_in`，取值非法一律 fail-closed 回落 `deny`；外部调用失败自动回退本地路径并记录 `fallback_reason`。部署见 [外部推理服务Provider接入指南](archive/外部推理服务Provider接入指南.md)。
- **投机解码（路线 C-1）** 只有独立实验端点 `POST /api/experimental/speculative`，`QLH_SPEC_ENABLED` 默认关闭时返回 404，**未接入 `model_module` 生产解码循环**，因此不列入上表的执行路径。边界见 [投机解码外部辅助实施说明](archive/投机解码外部辅助实施说明.md)。

## 3. PC 参考路径：PyTorch 层流水线

下面只是一个三节点示例，不是固定拓扑：

```text
前端/API
   -> 主节点：Embedding + 首段 Transformer 层
   -> 从节点 A：中间连续层段
   -> 从节点 B：末段 Transformer 层 + LM Head
   -> 主节点汇总结果并返回
```

当前关键约束（仅用于对照，不是 llama.cpp 主线的实现合同）：

1. 单次执行使用同一款、同一版本且通过身份校验的 PyTorch 模型工件。
2. 主节点参与模型计算，并作为首段 Embedding 锚点至少承担一层；不能仅按设备数量平均分层。
3. 层段必须连续且完整覆盖模型；Embedding 和 LM Head 职责不能落到未加载相应权重的节点。
4. hidden states 在节点间传输，各节点维护自己层段的 KV cache。
5. 节点未完成模型同步、层配置加载和 ready ACK 前不能进入执行路径。
6. 任一阶段失败都必须结束当前 attempt，再按可恢复边界重试或降级，不能把半完成状态继续交给下一节点。

现行消息、就绪与回退细节见[分布式推理流水线实施计划](分布式推理流水线实施计划.md)。

2026-07-26 对控制面做了一批缺陷修复，均经双节点实测验证，影响的是“节点在线判定”与“控制面可用性”而非层拆分语义：客户端接收线程的异常兜底与清理、帧中途超时与空闲超时的区分、注册成功后才推进连接代数、服务端注册后放宽 per-socket 收包超时以匹配心跳容忍、ACK 统一走加锁发送通道、集群管理类 HTTP 端点移出事件循环。具体见[模块接口说明](模块接口说明.md)第 2、5 节与[项目技术说明](项目技术说明.md)§7.2。

## 4. 软件分层

| 层级 | 主要职责 | 当前实现 |
|------|----------|----------|
| 客户端 | 主线聊天、设置、节点与执行状态展示 | 标准库 TUI；Web/Jetpack Compose 属于外部产品壳 |
| 运维/管理端 | 系统状态、节点管理、分层、队列、日志、设置的终端管理入口 | `tui_admin.py`（跨平台 TUI，纯标准库） |
| API/控制面 | 请求入口、节点管理、模型管理、状态与指标 | FastAPI、`api_server.py` |
| 调度面 | 请求队列、层分配、执行编排、取消、回退 | `scheduler.py`、`graph_orchestrator.py` |
| 通信面 | 注册认证、心跳、控制消息、张量传输 | `tcp_comm.py`、HTTP/Tailscale |
| 推理面 | llama.cpp 完整/模型分片推理；PyTorch PC 参考推理 | `llama_engine.py`、RPC host/worker 适配；`model_module.py` 为参考路径 |
| 外部辅助面 | TP 孤岛整请求转发、外部端点整请求路由、投机解码实验 | `island_engine.py`、`external_provider.py`、`speculative.py` |
| 存储面 | 集群配置、会话、节点状态、离线降级 | 主仓本地 SQLite/JSON；外部产品壳自管 Room/DataStore 等存储 |

`tui_admin.py` 是主线 TUI 管理与聊天容器，不是与 Web 并列的产品壳：8 个屏幕覆盖聊天、系统状态总览、节点管理（连接主节点、注销、角色转让、备用主节点）、分布式与分层、请求队列 MLFQ、设备画像、日志查看与设置；分布式页消费 `PipelineLayout` 的只读布局投影，保留旧 `/cluster/layers` 手动覆盖入口。支持方向键导航，非 tty 或老终端自动降级为编号菜单（`--plain`），`--host/--port` 可直接管理远程 Tailscale 主节点；`qlh` 无参与 `qlh chat` 已是统一聊天入口。

## 5. 远期边界

现有 `LAYER_FORWARD` 是 PyTorch 层流水线协议，不会扩展成所有设备和模型格式共用的张量协议。新增 Relay 使用独立 hidden handoff 合同：L→L 已完成同机单进程 16/16 行为等价；D→L 5-token prefill 通过，但 141-token f16/f32 均失败，实时跨进程/网络仍待验证。完整推理 Worker、任务链、张量并行和 GGUF Stage 仍作为独立 Provider 接入统一控制面，详见混合分布式推理体系规划。

张量并行本身的结论没有改变：**它不进 mesh。** 已落地的是“把张量并行留在集群之外、由 QLH 编排整请求”的外部辅助形态（路线 A/B 阶段 1 PoC），不是 mesh 内的 `TensorParallelProvider`；后者仍处于规划阶段，需要同构 GPU 与高速互联条件才能进入实施。三条外部辅助路线的定义、通信数学与里程碑见[张量并行外部辅助与混合拆分调研方案](张量并行外部辅助与混合拆分调研方案.md)。
