# 项目总览与整体架构

> 状态：现行
> 更新日期：2026-07-26
> 适用范围：当前已经落地的 PC、Linux 与 Android 产品边界
> 远期架构：[混合分布式推理体系规划](混合分布式推理体系规划.md)
> 外部辅助路线：[张量并行外部辅助与混合拆分调研方案](张量并行外部辅助与混合拆分调研方案.md)（其中路线 A/B 已有阶段 1 PoC，路线 C 仅为实验端点）

## 1. 项目目标

QLH 面向异构边缘计算设备，不限定为笔记本，也不限定固定节点数量。当前设备范围包括：

- Windows/Linux 台式机、工作站、服务器和笔记本；
- 带 NVIDIA CUDA GPU 的独显节点；
- 仅有 CPU 或集成显卡的 PC 节点；
- Android 手机和平板；
- 后续通过明确能力协议接入的其他边缘设备。

系统解决的是单个设备受内存、显存、算力或能耗限制时的模型运行与协作问题。默认 Qwen-1.8B 只是基础样例，模型注册表还包含其他 Qwen 和 DeepSeek 实验槽位；模型能否参与层流水线必须经过架构、层数、tokenizer、权重和运行时兼容性校验。

## 2. 当前执行路径

| 执行路径 | 节点与引擎 | 模型格式 | 当前定位 |
|----------|------------|----------|----------|
| PC 本地 PyTorch | CUDA PC；必要时可回退 CPU | Safetensors | 完整模型推理 |
| PC PyTorch 层流水线 | 能加载同一 PyTorch 模型工件并通过能力校验的 PC 节点 | Safetensors | 连续 Transformer 层段协作 |
| PC 本地 llama.cpp | CPU/集显 PC | GGUF | 完整模型本地推理 |
| Android 本地 llama.cpp | Android Full | GGUF | 完整模型本地推理 |
| Android 远程模式 | Android Full/Lite -> PC 主节点 | 无本地模型要求 | HTTP 客户端，不参与当前层流水线 |
| TP 孤岛（`island` 引擎） | 网关 PC 节点 -> 集群外 OpenAI 兼容端点 | 由孤岛后端自管 | 阶段 1 PoC；整请求推理，不参与层拆分 |
| 外部推理服务（`external_api`） | 任意服务节点按请求路由到集群外端点 | 由外部端点自管 | 阶段 1 PoC；整请求外发，受数据作用域门控 |

“PC 集显版”“PC 独显版”“Android Full/Lite”是产品和依赖分级，不直接等价于分布式角色。调度器还必须检查实际引擎、模型身份、模型就绪状态、内存、加速器和网络状态。

后两条路径的当前边界必须如实说明，不能写成已验收的生产能力：

- **TP 孤岛**：网关节点以 `engine="island"` 注册，对集群呈现为**单个逻辑高算力节点**，承担整请求推理；行为等同 `llama_cpp` 节点，不接收 `LAYER_FORWARD`（主节点按 `device_info.island.enabled` 过滤 + 网关侧拒收层配置，双保险）。孤岛内部的张量并行 collective 全部发生在孤岛内网，QLH 不感知也不依赖其协议。故障边界为整个逻辑节点，失败后走现有节点下线与重编排路径。部署见 [TP孤岛接入指南](TP孤岛接入指南.md)。
- **外部推理服务**：不引入专职节点，由服务节点按请求决策是否把**整条请求**路由到集群信任域**之外**的 OpenAI 兼容端点。`QLH_EXTERNAL_DATA_SCOPE` 数据作用域门控是硬约束，默认 `opt_in`，取值非法一律 fail-closed 回落 `deny`；外部调用失败自动回退本地路径并记录 `fallback_reason`。部署见 [外部推理服务Provider接入指南](外部推理服务Provider接入指南.md)。
- **投机解码（路线 C-1）** 只有独立实验端点 `POST /api/experimental/speculative`，`QLH_SPEC_ENABLED` 默认关闭时返回 404，**未接入 `model_module` 生产解码循环**，因此不列入上表的执行路径。边界见 [投机解码外部辅助实施说明](投机解码外部辅助实施说明.md)。

## 3. 当前 PyTorch 层流水线

下面只是一个三节点示例，不是固定拓扑：

```text
前端/API
   -> 主节点：Embedding + 首段 Transformer 层
   -> 从节点 A：中间连续层段
   -> 从节点 B：末段 Transformer 层 + LM Head
   -> 主节点汇总结果并返回
```

当前关键约束：

1. 单次执行使用同一款、同一版本且通过身份校验的 PyTorch 模型工件。
2. 主节点参与模型计算，并作为首段 Embedding 锚点至少承担一层；不能仅按设备数量平均分层。
3. 层段必须连续且完整覆盖模型；Embedding 和 LM Head 职责不能落到未加载相应权重的节点。
4. hidden states 在节点间传输，各节点维护自己层段的 KV cache。
5. 节点未完成模型同步、层配置加载和 ready ACK 前不能进入执行路径。
6. 任一阶段失败都必须结束当前 attempt，再按可恢复边界重试或降级，不能把半完成状态继续交给下一节点。

现行消息、就绪与回退细节见[分布式推理流水线实施计划](分布式推理流水线实施计划.md)。

2026-07-26 对控制面做了一批缺陷修复，均经双节点实测验证，影响的是“节点在线判定”与“控制面可用性”而非层拆分语义：客户端接收线程的异常兜底与清理、帧中途超时与空闲超时的区分、注册成功后才推进连接代数、服务端注册后放宽 per-socket 收包超时以匹配心跳容忍、ACK 统一走加锁发送通道、集群管理类 HTTP 端点移出事件循环。具体见[模块接口说明](模块接口说明.md)第 2、5 节与[项目技术说明](项目技术说明.md)§7.2。

## 4. 软件分层

| 层级 | 主要职责 | 当前实现 |
|------|----------|----------|
| 客户端 | 聊天、设置、节点与执行状态展示 | React、Jetpack Compose |
| 运维/管理端 | 系统状态、节点管理、分层、队列、日志、设置的终端管理入口 | `tui_admin.py`（跨平台 TUI，纯标准库） |
| API/控制面 | 请求入口、节点管理、模型管理、状态与指标 | FastAPI、`api_server.py` |
| 调度面 | 请求队列、层分配、执行编排、取消、回退 | `scheduler.py`、`graph_orchestrator.py` |
| 通信面 | 注册认证、心跳、控制消息、张量传输 | `tcp_comm.py`、HTTP/Tailscale |
| 推理面 | PyTorch 完整/分层推理、llama.cpp 本地推理 | `model_module.py`、`llama_engine.py` |
| 外部辅助面 | TP 孤岛整请求转发、外部端点整请求路由、投机解码实验 | `island_engine.py`、`external_provider.py`、`speculative.py` |
| 存储面 | 集群配置、会话、节点状态、离线降级 | PostgreSQL、本地 JSON、Android Room/DataStore |

`tui_admin.py` 是与 Web 前端并列的管理入口，不是新的执行路径：7 个屏幕覆盖系统状态总览、节点管理（连接主节点、注销、角色转让、备用主节点）、分布式与分层、请求队列 MLFQ、设备画像、日志查看与设置；支持方向键导航，非 tty 或老终端自动降级为编号菜单（`--plain`），`--host/--port` 可直接管理远程 Tailscale 主节点。已双节点实测：可列出在线从节点并完成“连接主节点”全流程。

## 5. 远期边界

现有 `LAYER_FORWARD` 是 PyTorch 层流水线协议，不会扩展成所有设备和模型格式共用的张量协议。完整推理 Worker、任务链、张量并行和 GGUF Stage 将作为独立 Provider 接入统一控制面，详见[混合分布式推理体系规划](混合分布式推理体系规划.md)。

张量并行本身的结论没有改变：**它不进 mesh。** 已落地的是“把张量并行留在集群之外、由 QLH 编排整请求”的外部辅助形态（路线 A/B 阶段 1 PoC），不是 mesh 内的 `TensorParallelProvider`；后者仍处于规划阶段，需要同构 GPU 与高速互联条件才能进入实施。三条外部辅助路线的定义、通信数学与里程碑见[张量并行外部辅助与混合拆分调研方案](张量并行外部辅助与混合拆分调研方案.md)。
