## 1. 数据有效性规则

引用 D→L 数据时按以下优先级处理：

1. 当前代码和最新提交对应的实验报告优先；本轮基线以 `610f4b3`（hybrid cache 修复）及其父提交后的代码为准。
2. “上下游都走主仓引擎”必须同时满足：上游使用 `ModelManager.load_layer_range()` / `forward_layers()`，下游使用 `LlamaCppEngine.forward_layers_from_hidden()`。
3. 使用裸 `llama_cpp`、实验区手写前向或旧 runner 的结果可以作为诊断/历史数据，但不能作为最终主仓端到端性能基线。
4. 性能数字必须同时记录模型、层数、切点、dtype/量化、prefill、decode、线程、重复次数、设备和构建指纹；不同口径不得横向比较。
5. 正确性判据与速度判据分离。D→L 的速度不占优不等于容量收益不存在；容量收益必须单独按“单设备必需驻留权重字节”计算，并注明受控预算不等于物理 OOM。
6. 引用“档位 / 速度”前必须核对**实际生效**的 dtype 与开关：主仓层流水线的 `quant_type="int4"` **静默回退 fp16**（按 key 手工物化、不走 `BitsAndBytesConfig`）；上游 compile 在参数量 `< COMPILE_MIN_PARAMS`（1.5B）时被规模门禁用。混合精度档位的 `capacity_gain_x` 只在同精度口径下解释（实测混合精度 < 1×）。

## 2. 当前成立的事实

### 2.1 Windows Triton

README 中“缺失算子只能走 WSL2，Windows 不能用 Triton/fla”已经过时。当前事实是：

- Windows 原生 `torch.compile` 已用 `triton-windows==3.8.0.post28` 实测可用，依赖声明在 `requirements-compile.txt`。
- Windows 启动编译路径还必须设置 `PYTHONUTF8=1`；缺失时可能静默回退 eager。
- WSL2 Ubuntu-22.04 + CUDA/fla 仍是另一条已实测路径，不再是 Windows 的唯一可用路径。
- `flash-linear-attention`/fla 的具体算子收益不能从“compile 可用”直接推出，仍须按模型和算子单独验收。

### 2.3 D→L 的实际价值

- 速度：单机 CUDA 上，完整 llama.cpp GPU 路径通常更快；D→L 不应宣传为通用提速方案。
- 容量：两段切分把单设备必需驻留权重降到两侧最大段，qwen2.5-0.5B 和 qwen3.5-2B 的实测收益约为 1.568× 和 1.547×。
- 可运行性：同一受控 CUDA 预算 3.0 GB 下，整模拒绝而上游 12 层通过；这是受控分配预算证据，不得写成物理显存 OOM。
- 精度：上游使用 PyTorch 全精度、下游使用 GGUF 量化是有意义的“不完整量化”路径。验收必须与同一份下游量化整模对拍，不能拿量化下游与 f16 整模直接比较输出质量。

## 4. 实验基线（P0 已于 2026-09-21 完成）

### P0：主仓双引擎 D→L 重跑 —— ✅ 已完成（2026-09-21）

固定 qwen2.5-0.5B 与 qwen3.5-2B 两个模型，使用同一套公共接口：

- 上游：`ModelManager.load_layer_range()` + `forward_layers()`；
- 下游：`LlamaCppEngine.forward_layers_from_hidden()`；
- 工件：裁层 GGUF 由 `scripts/cut_layers.py`（+ `llama-quantize` 造 Q4_K_M）生成，JSON 内记录源模型与工件 SHA-256、层范围、commit 与运行环境；
- 档位：f32 hidden + 下游 f16、上游 f32 + 下游 Q4_K_M、上游 NF4 + 下游 Q4_K_M；
- 负载：prefill 32/128/512，decode 32/64/256，单序列和 batch 2/4；
- **结果：27/27 逐 token 与同精度整模一致**（切点 9、负载 8、batch 4、混合精度 6）；驱动 `build/cross-framework-layer-poc/relay_mainrepo_both.py`（`p0_matrix.ps1` / `p0_quant.ps1`），数据 `out/p0/*.json`，明细见《跨框架层接力-容量收益实测-2026-09-21》§9；
- 通过条件：同精度整模对照逐 token 一致；compile 若造成分叉，只能作为性能实验，不能进入一致性路径。

**P0 执行中新增的引用规则（引用档位/速度前必读）**：

1. `--upstream-quant int4` **不生效**（`load_layer_range()` 按 key 手工物化、不走 `BitsAndBytesConfig`，dtype 实测仍 fp16）⇒ 引用“上游档位”必须核对实际 dtype；真 NF4 需显式把 `nn.Linear` 替换为 `Linear4bit`（本轮 qwen2.5 84 层 / qwen3.5 93 层）。
2. 上游 compile 被规模门禁用（0.5B/2B < `COMPILE_MIN_PARAMS` 1.5B）⇒ 本矩阵是 **eager 上游**口径，不含 compile 收益。
3. **混合精度下容量收益 < 1**（实测 0.2722–1.2359×）：`capacity_gain_x` 只在**同精度**口径下解释。
4. 主仓下游 `forward_layers_from_hidden()` 在 M-RoPE（qwen3.5，`n_pos_per_embd=4`）上逐 token 一致；该契约目前**只有端到端证据、尚无单测固定**。
5. 下游是 CPU-only 绑定 ⇒ **prefill 是主要开销**（K=12 下游 prefill：32 token ≈ 1.5 s、512 token ≈ 5.7 s），且该计时含首次 ubatch 图开销。

**P0 未覆盖**：3 段及以上外推；跨机 SSH/RPC、弱网、长时 decode；下游 GPU offload；上游 compile 档；混合精度只做 K=12 且判据仅为 32 步贪心单 prompt（不构成质量结论）。

### P1：统一实验驱动与报告 schema —— ✅ 已完成（2026-09-21）

把裸 runner、主仓引擎和 L→L 对照统一到一个只读实验驱动，强制写入 relay experiment record：模型身份、权重格式、量化、层布局、引擎接口、commit、环境锁、设备画像和判据。报告必须区分 `mainrepo_end_to_end`、`raw_binding_probe`、`capacity_only` 三类，避免以后再把不同层级数字混成一张表。

**交付物**：

- `scripts/relay_experiment.py` —— 只读统一驱动，四条链路一条命令：`d2l_mainrepo`（主仓下游端到端）/ `d2l_raw_binding`（裸 `llama_cpp` 下游探针）/ `l2l_llama`（L→L 对照）/ `capacity_scan`（容量专项）。写入前必须过 schema 校验（fail-closed）；`--dry-run` 不加载模型即可预检链路与字段。
- `schemas/relay-experiment-record.schema.json` —— 记录 v1。`kind` 三类互斥；schema 负责结构与字段存在性，`src/relay_experiment_record.py` 的接口注册表负责 **kind/path/engines.*_iface** 的语义一致性（错标直接被拒）。
- `src/relay_experiment_record.py` —— 记录构建/校验与接口→(kind, path) 映射；未登记的新链路必须显式登记才能写记录。
- `tests/test_relay_experiment_record.py` —— 27 项守卫（schema 自检、kind/path/接口错标拒绝、四条链路 dry-run、L→L 通道守卫）。

**落地实测（同代码基线）**：四条链路各出一条记录（`build/relay-records/*.json`），kind/path 由接口自动判定：`capacity_only/capacity_scan`（qwen2.5 K=12，容量 1.568×）、`mainrepo_end_to_end/d2l_mainrepo`（qwen2.5 K=12，32/32）、`raw_binding_probe/d2l_raw_binding`（qwen3.5 K=8，32/32）、`raw_binding_probe/l2l_llama`（qwen2.5 K=12，**fail-loud 默认拒绝**，见下）。

**P1 暴露并已固化为守卫的工程约束**：

1. **L→L 上游通道语义不成立**：pip 绑定的 embeddings 通道 = `output_norm(H)`（证据 `scripts/relay_diag_head_norm.py`，复现命令见该脚本 docstring），L→L 端到端 `first_mismatch=2` ⇒ 驱动默认 `fail-loud`，只有 `--allow-normed-upstream` 才放行，且记录里写 `handoff.upstream_applies_output_norm=true`。正确做法是 PyTorch 上游或自建 llama.cpp 的 keep-head / 层输入通道。
2. **下游 hidden 的形状契约**：各分支一律吃 2D `[n_tokens, n_embd]`、返回 `[n_tokens, n_vocab]`。这条曾是真实 bug（raw 分支返回 ctypes 指针 ⇒ 全 0 输出；L→L 分支把特征维当 token 数 ⇒ 索引越界），已由测试与实现共同固定。

### P2：自适应切点与容量/速度双目标 —— 部分完成（求解器就位；qwen2.5 闭环待补测）

复用设备画像和评分，按候选节点的单位层耗时、可用内存、网络带宽、首 token 延迟和稳定性求解切点。目标函数同时输出：

- `capacity_feasible`：每段权重与不可分层张量能否装下；
- `latency_estimate`：prefill/decode 的端到端估计；
- `risk_penalty`：弱网、热降频、重试和工件不可得性。

先做 qwen2.5 的 2 段 K 扫描，再做 qwen3.5 hybrid 的合法切点约束（`full_attention_interval` 整倍数），最后才扩到 3 段。手工固定切点只保留为对照。

**交付物**：

- `src/relay_cut_objective.py` —— 求解器：`legal_cuts()`（合法切点，含 `cut_multiple` 硬约束）、`plan_relay_cut_n_segments()`（n 段；容量 + 延迟 + 风险三输出，具名拒绝）、`fit_segment_profile()` / `fit_two_segment()`（从实测回归"固定开销 + 每层耗时"）。与既有 `pipeline_capacity.solve_pipeline_capacity`（纯容量放置）、`relay_planner.plan_relay_cut`（2 段保守切点）分工互补。
- `scripts/relay_cut_plan.py` —— 切点重搜报告：读同一次扫描的端到端记录 → 拟合 → 求解 → 与实测最优对比 → 落可复算报告（`build/relay-records/cut-plan-*.json`）。
- `tests/test_relay_cut_objective.py` —— 20 项守卫（合法切点/对称最优/容量不可行/三段连续覆盖/风险进目标/拒绝路径/拟合还原系数/容量核算/候选空间与画像边界/闭环）。

**闭环结果（同代码基线，本机 RTX 4060；权重取纯延迟，容量来自设备画像）**：

| 模型 | 合法切点 | 拟合 r²（上游/下游） | 全域预测切点 | 实测最优 | 闭环判据 |
|---|---|---|---|---|---|
| qwen2.5-0.5b | K=4/8/12/16/20（步长 1） | 0.962 / 0.992 | K=1（未实测，报告已标 `predicted_cut_in_measured_range=false`） | K=4 | 部分：仅复现实测子集，K=1 待补测 |
| qwen3.5-2b | K=8/12/16/20（**步长 4 硬约束**） | 0.791 / 0.958 | K=20 | K=20 | ✅ |

**两条必须带走的结论**：

1. **hybrid（qwen3.5）的每层成本不均匀**（r² 0.79）：`linear_attention` 层与 `full_attention` 层成本不同，单一"每层耗时"线性画像只是近似。⇒ 对这类模型应（a）按层类型分组拟合，或（b）**把实测切点直接当离散候选**（求解器已支持只在这些点上比较）。
2. **合法切点是硬约束**：qwen3.5 的切点必须落在 `full_attention_interval`（=4）的倍数上，否则裁层 GGUF 层类型错位、无法加载。求解器把它做成 `cut_multiple`，缺省 1（dense 模型）。

**3 段的现状（P2 收尾说明）**：求解器已支持任意段数（`plan_relay_cut_n_segments` 的 n 段枚举 + 首段 embedding / 末段 lm_head 归属 + 单测覆盖）。**执行层已于同日打通**，见下节「多段拓扑」。

### P2 续：多段拓扑（1 个 torch 上游 + n 个 llama 下游）—— ✅ 已打通（2026-09-21）

**问题**：链式拼接要求**每个中间段都能"吃 hidden、吐 hidden"**。前半（吃 hidden = `embd` 注入）早已可用；
后半（吐 hidden）在 pip 绑定里**只有 `embeddings` 通道**，而它返回 `output_norm(H)`（见 §3 的否证条目）。

**解（路线 C：补丁版 keep-head 通道）**：

| 环节 | 产物 | 说明 |
|---|---|---|
| 补丁 | `scripts/model_tools/patches/llama-cpp-layer-forward-api.patch`（marker `★ QLH 2026-09-20`，已登记在 `llama_quantize.lock.json`） | 导出 `llama_set/get_embeddings_layer_inp`（第 lid 层**输入** = 前 lid 层输出）与 `set_embeddings_nextn` / `get_embeddings_nextn_ith`（**末层输出，`output_norm` 之前**） |
| 构建 | 用 `android/app/src/main/cpp/llama.cpp`（含补丁，`cb5f7b7a8`）CMake + MinGW 构建 `libllama.dll`（CPU，~70 s） | 命令见 `scripts/model_tools/build_keep_head_shim.ps1` 的提示 |
| shim | `scripts/model_tools/keep_head_shim/qlh_keep_head.c` → `qlh_keep_head.dll` | ⚠️ **必须走 shim**：`llama_context_params` 是按值传参的大结构体，用 pip 的 ctypes 声明调自建 DLL 会字段错位（实测 `Unsupported ctx type`）。shim 与被调 DLL 用**同一份 `include/llama.h`** |
| 绑定 | `src/llama_keep_head.py`（`KeepHeadUpstream`：`forward_tokens_to_hidden` / `forward_hidden_to_hidden`） | 纯 ctypes 调 shim；缺 DLL/符号/工件一律 **fail-loud**（绝不退回 embeddings 通道） |
| 驱动 | `--path l2l_keep_head`（两段）、`--path d2l2l_keep_head`（三段，需 `--mid-model` + `--mid-layers`） | 记录里 `engines.middle_iface` 参与链路签名 ⇒ 三段不会与两段 D→L 撞键 |

**语义验证**（`scripts/relay_diag_head_norm.py` 同族诊断，qwen2.5-0.5B）：
`mode=nextn`（head 裁层工件）与 `mode=layer_inp`（整模 + `cut_layer=K`）给出的 hidden **逐位相同**，
且与 PyTorch 上游 `rel_err=0.00214`（对比旧 embeddings 通道的 `rel_err=11.69`，改善约 **5000×**）。

|---|---|---|---|

### P3：激活与缓存数据流 —— ✅ 前两项完成（多序列与压缩已实证；重叠只做估算）

**① prefill 传整段 / decode 只传末位（已完成，且已显式化）**

链上每一段都是这个策略：prefill 一次给整段 hidden（让下游一次建立本地 KV/recurrent state），
decode 每步只给末位激活。现在它**写进记录**（`load.activation_policy =
prefill:full_sequence+decode:last_position`），引用任何带宽/延迟数字前先核对该字段。

**② 多序列 `seq_ids` / `positions` 显式绑定（已完成）**

| 件 | 内容 |
|---|---|
| shim | `qlh_kh_load(..., n_seq_max)` + 新入口 `qlh_kh_forward_embd_seq(embd, n_tokens, n_past, n_seq_id, seq_ids, positions, out)`（三个数组可 NULL ⇒ 单序列向后兼容） |
| 绑定 | `KeepHeadUpstream.forward_hidden_to_hidden(hidden, n_past=…, seq_ids=…, positions=…)` —— 与 `llama_engine.forward_layers_from_hidden()` **同一契约**；`seq_id ≥ n_seq_max` 直接 fail-loud |
| 驱动 | 三段/两段 keep-head 路径按 `--batch` 传显式 seq/pos（prefill：`[b for b in range(B) for _ in range(L)]` / `[i for _ in range(B) for i in range(L)]`） |

实测（三段 K=8/16，gen=32）：**batch 2 ✅ 32/32、batch 4 ✅ 32/32**（判据 = 每条序列的贪心与整模逐 token 一致）。

⚠️ **回归教训（已固化为用例）**：改造多序列时曾把单序列的 `n_past` 丢掉（NULL positions 时从 0 开始），
表现为**第二步 decode 直接失败**（`tokens ... have inconsistent sequence positions`）。
现在 `qlh_fill_explicit` 在 `positions == NULL` 时回落到 `n_past + i`，并有
`test_single_sequence_positions_stay_consecutive_across_steps` 守卫。

**③ hidden 压缩 / 误差反馈（压缩已实证；反馈未做）**

`--hidden-quant none|f16|bf16|int8_block128`（在每一跳注入前量化、使用前反量化，语义同本地与跨机）：

| 档位 | 每 token 有效字节（896 维） | 三段 gen=32 结果 | 记录 |
|---|---|---|---|
| `none`（f32） | 3584 | ✅ 32/32 | `three-seg-k8-16.json` |
| **`f16`** | **1792（0.5×）** | ✅ 32/32 | `three-seg-k8-16-hq-f16.json` |
| **`bf16`** | **1792（0.5×）** | ✅ 32/32 | `three-seg-k8-16-hq-bf16.json` |
| **`int8_block128`** | **924（0.26×，含每 128 维 1 个 f32 scale）** | ✅ 32/32 | `three-seg-k8-16-hq-int8_block128.json` |

判据是 **per-token argmax**（不是 cosine）；有效字节写入
`device_profile.hidden_bytes_per_token_effective`。
⚠️ **不得外推**：这只是 gen=32、单 prompt、f16 下游、3 段的结果；长序列/多 prompt/弱网下的
误差累积与"误差反馈"回路都还没做（P4 会接量化边界）。

**④ 预取 / 传输与计算重叠（只做估算，不新开实验）**

用已有实测即可给出可重叠上限：三段每 hop 传 896×4 = 3.5 KB/token，同机 loopback
串行化 ≈ 0.03 ms、RTT ≈ 0.1 ms 量级，而每步计算 ≈ 70 ms（上游 ~32 + 中段 ~18 + 末段 ~21）
⇒ 同机可重叠窗口 **< 1%**，与既有"通信/同步仅 0.34%"的结论一致 ⇒ **不同机重投同步微优化**。
跨机时该比例按 `传输时间 / 步时` 重算（`latency_estimate.transfer_*` 已单列），
**弱网下才值得做预取/压缩-计算重叠**，届时先测网络与解码计算的实际重叠窗口。

**P3 遗留项（本机部分已完成，2026-09-21 续）**：

| 项 | 状态 | 证据 |
|---|---|---|
| 长序列 × 多序列 | ✅ 完成 | 三段 K=8/16：prefill 128/512 × batch 2/4 **全 32/32**（`three-seg-k8-16-p*-b*.json`）；中段与末段的 `n_batch` 按 `batch × prefill` 构造（不够会撞 `GGML_ASSERT(n_tokens_all <= cparams.n_batch)`） |
| 跨机多序列 | ✅ 完成（loopback） | 新增 `HIDDEN_SEQ` 帧（payload 带 `seq_ids`/`positions`，meta 白名单校验）；远端 runner 不支持显式绑定则 `hidden_seq_unsupported` fail-loud。跨机三段 batch 1/2/4 **全 32/32**（`net-three-seg-k8-16-b*.json`） |
| 跨连接串味（真实 bug） | ✅ 修 | 同进程服务多条连接时新连接从位置 0 开始会与上一条的 KV 位置冲突（远端 `runner_failed`）⇒ shim 新增 `qlh_kh_reset()`、绑定 `reset()`、worker 加 `reset` op、`relay_mid_service` 每连接 `reset()` |

| 误差反馈 / 残差补偿 | ⛔ 未做 | 只做了 f16/bf16/int8 的**单向**量化往返（见下表） |
| 真实弱网下的预取/重叠 | ⛔ 未做 | 同机估值 < 1%（见上文④）；弱网需真实链路或多机注入延迟 |

**仍未覆盖（需设备/多机才能推进）**：真跨机（SSH 隧道到远端段，本机只到 loopback）；
Android 真机数值验证（JNI + 工件在设备上跑 keep-head 中间段）；弱网（带宽/RTT 受限）下的
重叠与压缩实测；长序列下 int8 压缩的误差累积曲线。

### P4：量化边界与精度预算

把“上游 f32、下游量化”作为明确的混合精度策略，而不是缺陷或默认事实。需要分别回答：

1. 上游全精度是否降低下游量化误差传播；
2. 下游 Q4_K_M/NF4 的误差是否在不同切点累积；
3. f32 hidden 的通信成本是否被 batch、压缩或边缘网络放大；
4. 何时应优先容量可行性，何时应优先质量/速度。

最终输出应是按模型、切点和设备画像选择的策略表，不能全局武断把上游默认改成 f32 或 f16。
