# 跨框架层接力（D→L）容量收益实测 — 2026-09-21

> 本轮回答的问题：**D→L 接力除了速度，容量上到底带来什么？「单机装不下」是否真的变成「可运行」？**
>
> 背景：`CORE-RELAY-XFRAME-01` 原准入判定把「性能」窄化为「速度」（约 20× 慢）⇒ 据此拒绝准入。
> 用户裁定（`dec-6d91cd100fecc798`，2026-09-21）：**速度性能与容量性能都算性能**，故本实验补齐容量一侧的证据。

---

## 0. 结论速览

| 命题 | 结论 | 证据强度 |
|---|---|---|
| **每段必需容量随 K 减小，最优切点在 K=N/2** | ✅ 成立，U 形曲线**完美对称** | 5 个 K × 3 次重复，`std = 0` |
| **容量收益 = M_total / max(上游, 下游)** | ✅ **1.55–1.57×**（两段，实测） | 两个模型独立复现 |
| **同一预算下「整模装不下、拆分装得下」** | ✅ **实测 OOM vs 实测 fits** | 受控预算 3.0 GB，2/2 重复 |
| **数值正确性**（接力 token == 整模贪心） | ✅ qwen2.5-0.5b **32/32 一致**；⚠️ qwen3.5-2b **2/32**（**同模型 L→L 却 16/16 PASS** ⇒ 责任在上游 PyTorch，见 §5） | 见 §5 |

**一句话**：接力把**单设备必需容量**从「全部层」降到「约一半 + 不可分层」，因此**让原本装不下的模型变得可运行**；但收益**有上限**（< 2×），受**不可分层张量**约束。

## 1. 实验设计（单变量）

**唯一变量**：上游保留的层数 `K`（下游 = `N − K`）。

**对照的容量量**：「**单设备必需驻留权重字节**」
* **整模** = 单设备必须同时驻留**全部层** ⇒ `M_total`
* **拆分** = 上游只驻留 K 层、下游装在**另一台设备** ⇒ 单设备最大需求 = `max(上游, 下游)`

**判据**：`容量收益 = M_total / max(上游, 下游)`。

**方法约束（依项目规则）**：
* 上游**必须走主仓引擎** —— `ModelManager.load_layer_range(...)` + `forward_layers(...)`，**不手写前向**；
* 下游用**离线裁层 GGUF**（`scripts/cut_layers.py`，真·层裁切）；
* **单变量分离 + 重复测量 + 给 std**；
* 含一次性成本的过程**分段测量**（加载 / 预热 / 生成分开）。

**资产**：`qwen2.5-0.5b-instruct`（24 层）+ `qwen3-5-2b`（24 层 hybrid）；GPU RTX 4060 Laptop 8 GB；主运行时 `torch 2.13.0+cu126`。

**观察**：
1. **U 形且对称** —— 最优在 **K = N/2**，符合「两段均分」直觉；
2. **收益 < 2×**：两段均分理论上限是 2×，实测 1.55–1.57×；
3. **收益不随模型规模增长**（0.5B 1.568× vs 2B 1.547×）—— 由**不可分张量占比**决定，见 §3；
4. `std = 0` —— 必需权重字节是**确定性**量（不是计时量），重复测量完全一致。

## 3. 为什么收益不是 2×？—— 不可分层张量是硬下限

裁层只切分 **`blk.*`（层）**，而以下张量**必须完整保留**在某一侧：

* `token_embd`（词嵌入）—— **只在上游**（`has_embedding=True`）；
* `output_norm` / `output`（lm_head）—— **只在下游**。

⇒ 设可分层参数 `L`、不可分层 `C`，则 `M_total = L + C`，最优时：

```
上游 = L/2 + C_emb     下游 = L/2 + C_out
收益 = (L + C_emb + C_out) / (L/2 + max(C_emb, C_out))
```

* qwen2.5-0.5b：`C` 占比约 **18%** ⇒ 收益 1.568×
* qwen3-5-2b：`C` 占比约 **24%**（hybrid 的 `ssm_*` 参数 + 更大词表）⇒ 收益 1.547×

⇒ **这就是收益有上限的原因**：词表越大、非层参数越多，收益越低。

**推广到 n 段**：`收益 ≈ (L + C) / (L/n + C_split)` ⇒ **n 越大收益越大，但渐近于 `(L+C)/C_split`**。所以「加设备」的边际收益**递减**，且**不可分层张量给出硬下限**。

## 4. 关键实证：「装不下」→「可运行」

K 扫描给出的是**必需容量**。为证明它真的决定**能不能跑**，在同一**受控 CUDA 预算**下对照：

| 配置 | 预算 **3.0 GB** | 预算 3.9 GB |
|---|---|---|
| **整模**（24 层 + embed + lm_head） | ❌ **`controller_rejected_oom`（0/2 fits）** | ✅ fits，peak **3.8018 GB** |
| **上游 12 层** | ✅ **fits（2/2），peak 2.4186 GB** | — |

OOM 报文（权威）：

```
CUDA out of memory. Tried to allocate 24.00 MiB. GPU 0 has a total capacity of 8.00 GiB
of which 4.16 GiB is free. 2.79 GiB allowed; Of the allocated memory 2.78 GiB is
allocated by PyTorch, and 0 bytes is reserved ...
```

⇒ **同一台设备、同一预算 3.0 GB：整模装不下，切出 12 层的上游段装得下且能前向。**

**边界定位**：整模需 3.8018 GB ⇒ 3.0 GB 拒 / 3.9 GB 通过 ⇒ 边界的 3.80–3.90 GB 之间。

> ⚠️ **口径声明（必读）**：这是**受控预算**（`torch.cuda.set_per_process_memory_fraction`，由 CUDA caching allocator 强制），**不是物理显存耗尽**。选它是因为它**可复现、可定量、可比较**。**不得当作物理 OOM 引用。**
> 之所以不能做物理对照：本机 llama.cpp Python 绑定是 **CPU-only**（`graph splits = 1`），整模走 CPU 且 **mmap**，无法用 GPU 预算约束整模。

## 5. 已知缺口：qwen3.5 的 **D→L** 数值不成立（**不是** M-RoPE 边界）

### 5.1 现象

| 路径 | 上游 | qwen2.5（1D RoPE） | qwen3.5-2b（M-RoPE + hybrid） |
|---|---|---|---|
| **L→L** | llama.cpp | ✅ | ✅ **`accepted:true` / `all_tokens_match` / 16 步全对** |
| **D→L** | PyTorch（主仓引擎） | ✅ **32/32** | ❌ **2/32**（`idx 2` 起分歧，并出现复读） |

⇒ **同一个 qwen3.5-2b、同一份裁层工件**：上游换回 llama.cpp 就全对。**下游、cut 工件、协议都没有问题。**

### 5.2 排查过程（含一次错误的归因，记录在案）

1. **初判（错误）**：看到 relay 序列复读，判定为「**M-RoPE 未解决边界**」。
   ⚠️ **这个归因是错的** —— M-RoPE 的调用方修法**早已存在且已验证**：
   * `build/cross-framework-layer-poc/llama.cpp/tools/hs-extract-batch/relay-gen-dl.cpp:143-159`
     实现了「`pos` 按 `n_pos_per_embd*n_tokens` 提供」（上游 #28963 / #28902 的调用方修法）；
   * `docs/archive/上游llama-embd注入非确定性-复现与issue材料-2026-09-16.md` 记录该修法"问题消失"，
     并注明「本项目接力实验**恰好选用 Qwen3.5-2B（M-RoPE，最坏情况）**」。

2. **真实缺口**：本次使用的 **`relay_mainrepo_upstream.py` 自己没有实现**这个修法
   （原写法是 `b.pos[i] = pos + i`）。**已补齐**（见 §5.3）。

3. **补齐后仍 FAIL** ⇒ 说明还有**第二个、独立的**原因，且**不在** M-RoPE 的 `pos` 契约上。

### 5.3 已做的修正（`relay_mainrepo_upstream.py`）

* 新增 `_n_pos_per_embd()`：用 `gguf` 读 `<arch>.rope.dimension_sections` 的长度
  （`llama_model_meta_val_str` 读不了**数组**键，实测返回 -1）。
* `llama_batch_init(n_tokens * n_pe, ...)` —— 让 **llama.cpp 自己**分配足以容纳
  `n_pe*n_tokens` 个 `pos` 的缓冲，再按 `pos4[j*n_tokens + i] = pos + i` 填值。
  ⚠️ 这一步的写法**有讲究**：换成 Python 缓冲会与 GC 冲突，换成自己
  `libc.malloc` 的块会**跨 CRT**（`msvcrt` vs llama.cpp 的 `ucrtbase`）⇒ 两者实测
  都报 `0xc0000374 STATUS_HEAP_CORRUPTION`（Windows 堆损坏）。**必须走 llama.cpp 的分配器。**
* 效果：探测到 `n_pos_per_embd=4`，输出改变（不再堆损坏），但**分歧依旧**（仍 `2/32`）。

### 5.4 缺口定位（结论）

qwen3.5 是 **hybrid** 架构（`full_attention_interval=4`），其缓存由两部分组成 ——
llama.cpp 日志可见：

```
llama_kv_cache:          size = 40.00 MiB (4096 cells,  5 layers)   ← attention KV
llama_memory_recurrent:  size = 16.05 MiB (    1 cells, 20 layers)   ← SSM/recurrent state
```

⇒ **缺口在「上游 PyTorch 对 hybrid 层段的处理」**（recurrent/SSM 状态的维护），
**不在**下游、不在 cut 工件、不在 M-RoPE 的 `pos` 契约。

> **容量结论不受影响**：容量量是**权重字节**，与位置编码、与数值正确性都无关。
> qwen3.5 的那 4 行容量数据继续可用；**但它的数值结论不可引用**。

**⇒ 记为独立待办**：补齐上游 PyTorch 的 hybrid（SSM）层段前向，使 **D→L 在 hybrid 架构上可验证**。

## 6. 过程诚实性：本轮踩到并修正的 4 个陷阱

| # | 陷阱 | 症状 | 修正 |
|---|---|---|---|
| 1 | **容量池两边不一致** | 整模走 CPU（mmap）、上游走 GPU ⇒ 首轮读出 **0.4986×**（「拆分更差」） | 两边统一到同一池 |
| 2 | **llama.cpp Python 绑定是 CPU-only** | `--whole-gpu-layers -1` 后 CUDA alloc 仍为 **0.000** | 放弃用 CUDA 量整模，改用权重字节 |
| 3 | **进程 RSS 因 mmap 严重低估整模** | 整模文件 948 MB，RSS 只增 **0.107 GB** | 改用 `llama_model_size()` + PyTorch 参数字节作权威量 |
| 4 | **跨 CRT 的 malloc/free 不匹配** | 为 M-RoPE 自己 `libc.malloc` 的 `pos` 块被 llama.cpp（UCRT）`free` ⇒ **`0xc0000374` 堆损坏**；换成 Python 缓冲则与 GC 冲突，同样崩 | 改走 `llama_batch_init` 的分配器（放大容量），全程不跨 CRT |

⇒ **权威容量量 = 必需驻留权重字节**（llama.cpp `llama_model_size` + PyTorch `numel × element_size`），与 mmap 缺页、缓存分配器行为**无关**。

## 8. 对 `CORE-RELAY-XFRAME-01` 的结论

**「容量收益实测」项可结清**：容量收益**存在、可量化、有上限**。

* 速度：约 **20× 慢**（既有结论）⇒ Relay 定位是**能力组合**，非提速；
* 容量：**1.55–1.57×（两段）**，且**让装不下的模型可运行**（§4 实证）。

⇒ 二者同属「性能」。**仅凭速度不占优而拒绝准入，是把「性能」窄化** —— 已按用户裁定改为「**正确性已验证即准入**」，并保留「能单机整模跑时优先单机」的**路由倾向**。

**本实验留下的后续项**：
1. **n 段外推验证**（3 段及以上，检验渐近上限）；
2. **不可分层张量的缩减**（如 shared embedding 强制 shared ⇒ 提高收益上限）；
3. **上游 PyTorch 的 hybrid（SSM）层段前向**（**M-RoPE 的 `pos` 契约已补齐**；
   L→L 同模型 16/16 PASS ⇒ 缺口在**上游**，见 §5）；
4. **长时运行**与**远端资产分发自动化**（原票剩余项）。
