# 投机解码外部辅助实施说明（路线 C-1 阶段 0-1 探索性 PoC）

> 状态：**探索性 PoC 已实现**（`src/speculative.py` + 独立实验端点），默认关闭；**未接入生产解码循环**；四方向增量设计已完成（§8.5，2026-08-19，仅设计·未实现）
> 更新日期：2026-08-19
> 适用范围：路线 C-1 draft-verify 实验端点的实现说明、等价性边界与止损判据
>
> 前置阅读：[张量并行外部辅助与混合拆分调研方案](张量并行外部辅助与混合拆分调研方案.md) §2.3
>
> 一句话：本地小模型每轮起草 γ 个 token，外部大模型一次前向并行校验，接受则一次前进 k+1 个 token；**输出分布等于外部 verify 模型**，本地 draft 只买速度、不影响质量。
>
> ⚠ 边界：这条"分布等价"是**投机采样纯核心**（`verify_draft_tokens` 拿到精确 verify 分布时）的严格性质。本 PoC 经 OpenAI 兼容接口只能拿到 **top-k logprobs**：**接受判定是精确的**（草稿 token 的概率由 `token_logprobs` 精确给出，不做归一化），但**拒绝时的修正 token 采样受 top-k 截断影响**，偏差随 `QLH_SPEC_TOP_LOGPROBS` 增大而收敛——详见 §7.4，不要把它当成端到端的严格等价。

---

## 1. 原理

```text
本地 (draft: Qwen-1.8B INT4)                    外部 (verify: Qwen-7B/14B TP 实例)
  |-- 生成 γ 个草稿 token (本地 KV 推进) --------|
  |== 上行: token ids ≈ γ×4B + 会话头 ==========>|  一次前向并行校验 γ 个位置
  |<== 下行: 接受数 k + 修正 token + logprob ====|  (外部 KV 推进 k+1)
  |-- 接受则一次前进 k+1 token；拒绝处回滚 ------|
  每轮跨 mesh 代价: ~1 KB + 1 RTT，摊薄到 k+1 个 token
```

接受-重采样规则（`verify_draft_tokens()`，标准投机采样）：

1. 逐位置以 `min(1, p_verify[i][t_i] / p_draft[i][t_i])` 的概率接受草稿 `t_i`；
2. 首个被拒绝处，从归一化残差 `max(0, p_verify - p_draft)` 重采样一个**修正 token**并停止本轮，其后草稿全部作废（本地 KV 回滚 γ-k）；
3. γ 个全接受时，额外从 `p_verify[γ]` 采一个**奖励 token**（该轮产出 γ+1 个）。

**当 `p_verify` 是精确的 verify 分布时**，该规则保证产出 token 的分布恒等于 verify 模型。这不是近似论证：`tests/test_speculative.py` 用 20000 次 Monte-Carlo（固定种子 20260726）对五组 draft/verify 分布（含支撑集完全不相交、draft 峰值恰在 verify 谷底）实测逐 token 偏差与总变差，均 < 0.02。

注意这句话的作用域是**纯核心函数**。真实链路上 `p_verify` 由外部端的 top-k logprobs 重建：第 1 步的接受判定仍然精确（草稿 token 的概率来自 `token_logprobs`，不参与归一化），第 2 步的残差重采样则被截断到 `top-k ∪ {草稿 token}` 的支撑集上，见 §7.4。

## 2. 为什么只有它适合跨慢网的"深度辅助"

| 方案 | 每 token 跨 mesh 数据量 | 结论 |
|---|---|---|
| 张量并行（TP）跨 mesh | 每层 all-reduce 激活，MB 级 × 层数 | 必死（§1.2） |
| prefill 卸载（C-2） | 512 token 的 KV ≈ 96MB @FP16 | 跨 mesh 否决，只在孤岛内成立 |
| **draft-verify（C-1）** | **γ 个 token id + 一次 logprobs 响应，KB 级 / 轮** | **唯一可行** |

差异在于传的是"语义级的 token id"而不是"数值级的张量"。C-1 也是三条路线里唯一把外部大算力折算进**每 token 质量**（输出对齐大模型）而不是容量的路线——A/B 都是"把整件事交出去"，C-1 是"每个 token 都由大模型拍板，但由小模型抢跑"。

## 3. 前提条件（缺一不可，均在 §2.3 点名）

1. **外部端返回 per-token logprobs**：`POST /v1/completions` 带 `echo=true, logprobs=N`。纯 chat 接口不够。vLLM / SGLang 满足；本 PoC 在 `connect()` 时做能力探测，不满足就**大声报错**（静默降级会让输出分布不再等于 verify 模型，那已经不是投机解码了）。
2. **top_logprobs 的 key 可还原为 token id**：OpenAI 语义里 key 是 token *文本*，无法用于按 id 构造残差分布。vLLM 启动加 `--return-tokens-as-token-ids`（key 变成 `token_id:12345`）即可；或给 `ExternalVerifyClient(token_id_resolver=...)` 传一个"文本→id"的映射函数。
3. **draft 与 verify 共享 tokenizer / 词表**：如 Qwen-1.8B + Qwen-7B/14B。跨词表需要重编码，PoC 不支持。
4. **外部端有状态 KV，或至少开前缀缓存**：这是 §2.3 点名的**最大工程难点**。OpenAI 兼容接口无会话 KV 语义，每轮 verify 都要重传整段 context。实践替代品是 vLLM 的自动前缀缓存：

   ```bash
   vllm serve Qwen/Qwen2.5-14B-Instruct \
       --tensor-parallel-size 2 \
       --enable-prefix-caching \
       --return-tokens-as-token-ids \
       --host 0.0.0.0 --port 8000
   ```

   开了之后外部端**不再重算 prefill**（KV 命中前缀），但**上行仍然重传整段 token id**——省的是算力不是带宽。这两件事分别由 `bytes_up` 与 `bytes_up_ideal_stateful` 两个指标量化。

## 5. 启用步骤

```bash
# 1) 外部起 vLLM（logprobs + token id + 前缀缓存三个前提一次配齐）
vllm serve Qwen/Qwen2.5-14B-Instruct --tensor-parallel-size 2 \
    --enable-prefix-caching --return-tokens-as-token-ids --port 8000

# 2) QLH 侧开实验开关（默认关闭，只影响实验端点）
export QLH_SPEC_ENABLED=1
export QLH_SPEC_VERIFY_BASE_URL=http://gpu-box.example.com:8000
export QLH_SPEC_GAMMA=6
export QLH_EXTERNAL_DATA_SCOPE=opt_in      # 与路线 B 共用
python src/api_server.py

# 3) 查看状态段（不发起任何对外请求）
curl -s http://<节点IP>:8000/api/status | jq .speculative

# 4) 跑一次投机解码会话（必须显式授权数据出集群）
curl -X POST http://<节点IP>:8000/api/experimental/speculative \
  -H "Content-Type: application/json" \
  -d '{"message": "请用一句话解释投机解码",
       "allow_external": true, "gamma": 6, "max_new_tokens": 90, "seed": 7}'
#   → {"content": "...", "finish_reason": "...", "metrics": {...}, "rounds": [...]}
#   未带 allow_external（opt_in 档位）→ 403，且一个数据包都不外发
#   QLH_SPEC_ENABLED=0 → 404
```

`execution_mode="speculative_assisted"` 已加入 `task_provider.ModelIdentity` 与 `task_worker_protocol` 的引擎校验集合（与 `island`/`external_api` 同处），`speculative_model_identity()` 以"draft 模型 + 脱敏 verify 端点 + verify 模型名"的 sha256 作指纹。但它**没有**被加进 `/api/chat` 的 `execution_mode` Literal——主聊天路径的取值集合仍是 `auto` / `task_graph`，投机解码只能从实验端点进入。

## 6. 指标解读

`metrics` 全字段见 `SpeculativeSession.metrics()`。判断"这次投机到底赚没赚"看三个数：

| 指标 | 含义 | 判据 |
|---|---|---|
| `acceptance_rate` | 接受的草稿 / 全部草稿 | < 1/γ 时 draft 基本在做无用功 |
| `tokens_per_round` | 每次 RTT 换回多少 token（理想 γ+1） | **= 1.0 表示每轮只拿到修正 token，投机完全失效**，此时纯粹是"带额外开销的外部解码" |
| `verify_share` | verify（含 RTT）耗时占整段解码墙钟比例 | 接近 1 说明瓶颈全在网络，加大 γ 才有意义 |

**什么情况下反而更慢**（§2.3 收益上界 `接受率×γ / (1 + RTT×轮数)` 的实操判据）：

> 当 `RTT × 轮数 > 本地单独生成同样多 token 的时间` 时，C-1 比"纯本地解码"慢。
> 轮数 ≈ `emitted_tokens / tokens_per_round`，因此该判据等价于
> `RTT > tokens_per_round / 本地 tok/s`。
> 例：本地 20 tok/s、`tokens_per_round=4` → RTT 必须 < 200ms 才值得；
> `tokens_per_round=1`（接受率 0）→ RTT 必须 < 50ms，几乎注定亏。
> 另一侧的对照是"纯外部解码"（路线 B）：C-1 只有在 `tokens_per_round > 1` 时才比它快，因为 B 的一次 RTT 换回整段回复。

PoC 实测（mock verify 后端，本机 RTT ≈ 43ms，γ=6，字节级 tokenizer）：

| 场景 | rounds | acceptance_rate | tokens_per_round | verify_share |
|---|---|---|---|---|
| draft 命中提示序列（模拟"小模型与大模型高度一致"） | 19 | 0.579 | 4.47 | 0.986 |
| draft 均匀分布（模拟最差 draft） | 24 | 0.000 | 1.00 | — |

两次产出的文本都来自 verify 端的分布——**接受率归零只让速度退化到外部单独解码，采样目标不变**。这就是分布等价性质的实际含义（在 §7.4 的 top-k 截断范围内成立）。

## 7. 已知限制（诚实清单）

1. **未接入生产解码循环**。§2.3 的接入点是 `model_module` 的本地解码循环，本 PoC 只提供一个自洽子系统 + 独立实验端点。容器内没有可用的 PyTorch 运行时（`torch.nn` 缺失），无法验证真实 draft 模型的 KV 推进/回滚，此时改写最核心路径的风险远大于收益。
2. **无状态 KV 的重复 prefill**。每轮把 `context + 草稿` 整段作为 prompt 重传；外部端未开前缀缓存就会重算整段 prefill。`bytes_up` vs `bytes_up_ideal_stateful` 量化上行代价（实测 9340 B vs 5320 B，约 1.8×；context 越长差距越大）。

   口径提醒：`bytes_up` 是**实测 JSON 请求体字节数**（不含 HTTP 头），`bytes_up_ideal_stateful` 是 `256 B 名义会话头 + γ×4 B` 的**估算值**，两者基准不同。context 很短时会出现比值 < 1（独立验证实测到 0.51–0.65）——那是口径差，不代表"无状态重传更省"。只有 context 明显长于几十 token 时该比值才有意义。`bytes_measured` 字段标明 `bytes_up/bytes_down` 是实测还是估算。
3. **下行远超 §2.3 的"~1KB/轮"估算**。标准 completions 的 `echo=true` 会回传**整段 prompt 每个位置**的 logprobs，下行是 `O(context × top_k)` 而不是 `O(γ × top_k)`。实测 19 轮下行 228 KB（≈12 KB/轮），而"只回 γ+1 行"的理想值是 30 KB（≈1.6 KB/轮）。要拿到 §2.3 的量级必须**自建 verify 端点**（只回后缀若干行），这正是 §2.3 "需 completion+logprobs 或自建 verify 端点"的后半句。指标里以 `bytes_down` vs `bytes_down_ideal_suffix` 对照。
4. **top-k 截断会让输出分布偏离真实 verify 分布；但接受判定已修复为精确**。`_rows_from_response` 只在 `top_logprobs ∪ {草稿 token}` 上填值，因此行和 = top-k 概率质量 `M < 1`。关键在于**草稿 token 自身的 `q(t)` 由 `token_logprobs` 精确给出**，与截断无关。

   早期实现把这样的行按分布逐行归一化，参与接受判定的就变成 `q(t)/M`，接受比值被整体放大 `1/M`——草稿被系统性"橡皮图章"。危害不是精度问题而是**语义崩塌**：`M` 越小接受率越趋近 1.0，等于把 draft 小模型的输出照单全收，C-1"质量对齐 verify"的前提直接失效。

   现已修复：`verify_draft_tokens(..., renormalize_verify=False)`（`run_speculative_chat` 走 HTTP 链路时强制传 False），只清洗不缩放。实测对照（zipf 分布，`V=512`，理论精确接受率 0.2837）：

   | `top_logprobs` | `M` | 旧（归一化）接受率 | 新（精确）接受率 | 旧 TV | 新 TV |
   |---|---|---|---|---|---|
   | 20 | 0.611 | 0.3760 | **0.2819** | 0.138 | 0.155 |
   | 64 | 0.764 | 0.3293 | **0.2819** | 0.065 | 0.058 |
   | 200 | 0.899 | 0.3002 | **0.2819** | 0.045 | 0.035 |
   | 512（=全量） | 1.000 | 0.2819 | 0.2819 | 0.035 | 0.035 |

   读法：修复后**接受率恒等于理论精确值、且与 `top_logprobs` 参数无关**——旧行为的接受率会随该参数从 0.376 漂到 0.282，是个不可跨配置比较的假指标。`top_logprobs ≥ 64` 时新行为的输出 TV 也更低；仅在极端截断（`M≈0.6`）下旧行为 TV 略低，那是"虚高接受率放行了 top-k 之外的草稿 token"的巧合补偿，不是原理性优势——代价是输出退化回 draft 分布。

   仍然存在的偏差：**修正 token 的残差采样**只能在 `top-k ∪ {草稿 token}` 的支撑集上构造，本该分给 top-k 之外 token 的概率质量被挤到 top-k 上。这是 OpenAI 兼容接口的固有限制，随 `QLH_SPEC_TOP_LOGPROBS` 增大而收敛（表中 TV 0.155→0.035），自建端点返回完整 logits 才能彻底消除（见 §8 里程碑）。因此 §1 的"分布严格等价"仍是**纯核心**的性质：端到端链路上接受判定精确、修正采样近似。
5. **PoC 的 draft 侧是占位实现**。`StubDraftModel` + `ByteTokenizer` 只为把链路跑通；真实收益必须用同族小模型实测，**不承诺任何加速比**。
6. **取消粒度是轮边界**。`cancel_event` 在每轮起草前与外发前检查；已发出的 verify 请求不会被服务端取消（与路线 A/B 的 best-effort 取消语义一致）。
7. **实验端点不写会话历史、不做追问、不入 `conversation_stats`**，它是测量入口不是产品路径。

### 8.5.1 置信度调度验证（Confidence Scheduling）

- **现状**：γ 是静态 `SPEC_GAMMA`(default 4)，每轮固定请求 γ 个草稿。
- **设计**：γ 按每轮 draft 置信度自适应：
  - 置信度估计器（三选一，可配）：
    1. draft 最后一位的最大概率/1−熵（单轮内置信）;
    2. 历史接受率滚动 EWMA（跨轮置信）;
    3. 两者加权。
  - 策略：高置信 → 放大 γ（上限 `QLH_SPEC_GAMMA_MAX=16`）；低置信/拒绝频繁 → 收缩 γ
    （下限 1），并把拒绝率反馈进下一轮。
- **扩展点**（真实代码结构）：
  - `SpeculativeSession.__init__` 的 `gamma` 语义从 `int` 扩展为 `int | GammaPolicy`；
    `run()` 轮次循环在 `_call_draft(gamma_eff)` 前调用策略计算 `gamma_eff`（现有
    `gamma_eff` 已有 min 上限并会随剩余 token 收缩，接入点干净）。
  - `config.py` 增 `QLH_SPEC_GAMMA_MODE=static|adaptive`、`QLH_SPEC_GAMMA_MAX`、
    `QLH_SPEC_CONF_*`（估计器类型/EWMA 系数/回调窗口）。
- **分布等价**：γ 只影响轮数与成本，接受判定与修正仍精确走 verify → **不变**。
- **验证矩阵**：`tests/test_speculative.py` 增（fake draft 可控置信度）：
  - 高置信 draft → γ 自动放大且接受率不降（Monte-Carlo 分布等价仍成立）；
  - 低置信/拒绝密集 → γ 收缩、`tokens_per_round` 不劣化于静态 γ；
  - 与现有指标（`accepted_ratio`/`tokens_per_round`/RTT）对齐。
- **止损**：自适应 γ 在固定 seed 下收益（tokens/秒）≤ 静态 γ × 1.05 时，本轮关闭自适应，
  保持静态默认。

### 8.5.2 半自回归生成（Medusa 风格多头/块预测）

- **现状**：draft_fn 逐位置产出一个 token 序列（γ 个草稿串联），verify 一次前向校验
  γ+1 个位置。
- **设计**：draft 侧每位置预测 `heads` 个候选，构成**候选树**；verify 沿树取各节点
  logprobs，找最长可接受前缀（tree-aware verify），接受则一次前进 k+1。
  - draft 扩展为 `MedusaDraftFn: (context_ids, heads, gamma) -> (候选树, scores)`；
  - verify 扩展为 `VerifyTreeFn: (context, 候选树) -> 逐节点 logprobs`（vLLM/SGLang 的
    speculative tree / `find_candidates` 批量），并保留对不支持树的后端回退为扁平逐位校验；
  - 接受判定复用 `verify_draft_tokens` 的精确逻辑（每节点在 verify 的 top-k 里取精确 q）。
- **分布等价**：接受/修正由 verify 分布决定 → **不变**（候选树只改变"尝试哪些前缀"）。
- **验证矩阵**：
  - 树前缀 Monte-Carlo 分布等价（沿用现有 60+ 用例的夹具）;
  - `heads=2..4` 下接受长度/TTFT 对比；
  - verify 不支持树时的降级路径（等于扁平 γ）。
- **止损**：heads 引入的 draft/verify 增量成本无法被接受长度摊薄（`tokens_per_round` 不随
  heads 提升），则冻结 Medusa 形态，保留扁平投机。

### 8.5.3 跨节点并行草稿（草稿模型部署在从节点）

- **现状**：draft 是本地进程内 callable（文档演示 draft=本地 Qwen1.8B INT4）。
- **设计**：draft_fn 保持接口 `(context_ids, gamma)->(tokens,probs)` 不变，新增
  `RemoteDraftClient`（复用 `ExternalVerifyClient` 的 HTTP/凭据脱敏/错误分类骨架，
  或复用 `cluster_transport`/task 帧），把草稿请求打到**从节点部署的草稿模型**端点；
  draft 与 verify 可同节点也可不同节点。
  - 配置 `QLH_SPEC_DRAFT_BASE_URL/API_KEY/MODEL`、draft 超时/重试；
  - 回退链：远端 draft 失败/超时 → γ=0（纯 verify bonus）或本地 draft 兜底，绝不阻塞
    主会话。
- **验证矩阵**：
  - fake/远端 draft 端点到本地 verify 的全链路（沿用 mock server 夹具）；
  - 跨节点 RTT 摊薄：`tokens_per_round × 每 token 字节 / RTT` 收益判据；
  - 故障注入（draft 断连/慢/非 JSON）→ 稳定回退，指标记录 fallback reason。
- **止损**：跨节点 RTT 使摊薄收益为负（每轮往返时间 > 本地 γ 提升），则草稿留本地、
  只保留 verify 在远端的组合（现状）。

### 8.5.4 逆向投机解码（探索，语义待定）

- **现状**：无。反向形态需要先定语义，再谈收益，因此本条目**仅给形态界定与止损**：
  - 形态 A（反向角色）：目标大模型充当小批量「草稿」（并行 hint），本地快模型作为
    低成本 verify/拒绝器；适用于"必须大模型输出、但可被快模型低成本否定"的场景。
  - 形态 B（置信驱动回退）：先按现有投机加速跑，acceptance/置信低于阈值时对该位置
    **回退重跑**大模型（把兜底策略参数化）。
- **边界**：A/B 都以"快模型能否可靠拒绝而不错杀"为前提；需先测快 model 的假阴/假阳。
- **排期地位**：语义待与用例对齐后立独立探索票；在 8.5.1/8.5.2 之前不排期。

### 8.6 建议排期与止损

| 票 | 内容 | 依赖 | 理由 |
|---|---|---|---|
| SPC-CS | 置信度调度（8.5.1） | 无（纯 Session 内策略 + 新测试） | 改动最小、直接提吞吐、分布等价可证 |
| SPC-MEDS | 半自回归 Medusa（8.5.2） | verify 树能力门（vLLM/SGLang 支持性实验） | 提升上限最高但需先验证树支持 |
| SPC-REMOTE | 跨节点并行草稿（8.5.3） | 从节点草稿端点可用（SYNC/任务面就绪） | 依赖远端 draft 端 + RTT 实测 |
| SPC-REV | 逆向投机（8.5.4） | 语义定稿 | 探索性，最后 |

总止损仍沿 §8 现有惯例：任一方向实测 `tokens_per_round ≤ 1.5` 或 §6 判据在目标 RTT 下
不成立，则冻结该增量，只保留纯核心（投机采样本身对后续任何本地多模型加速仍有价值）。
