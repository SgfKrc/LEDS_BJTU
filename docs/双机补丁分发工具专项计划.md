# 双机补丁分发工具专项计划

> 状态：规划（S0 设计基线；M1 未开始）
>
> 更新日期：2026-08-17
> 适用范围：双机/多机开发阶段的**代码补丁自动分发**——主节点修复问题后一键提交+推送，从节点收到广播自动强拉到新补丁；只分发**代码**（git 跟踪内容），不分发数据库/模型资产/运行时状态
>
> 立项背景：即将进入双机开发阶段（surface7 修复后），主节点与从节点频繁同步补丁。手动 `git pull` 在多机场景下繁琐易漏；本工具把「commit → push（走 7897 代理）→ 广播 → 从节点自动强拉」串成一条命令。
> **节点定位（2026-08-17 确认）**：surface 等从节点**不参与本项目开发**（只跑部署/验收，不做代码开发）——从节点不存在本地未提交改动，**每次强拉强制覆盖无冲突风险**；dirty 检查从"拒绝"降级为"告警记录"（安全网，仅异常排查用）。

## 1. 目标与边界

### 目标
1. **主节点一键分发**：修复代码后执行一个命令 → 自动 `git commit`（可选 amend/新提交）→ push 到远程 dev 分支（**走 7897 端口代理**）→ 向局域网/Tailscale 网段广播补丁帧。
2. **从节点自动应用**：监听 TCP 广播帧 → 校验帧（commit SHA/仓库/分支）→ 走 7897 代理 `git fetch` + **强拉**（`reset --hard` 对齐 dev 分支）→ 验证工作区一致性。
3. **安全默认**：从节点为纯部署机（不参与开发）——强拉强制覆盖（`reset --hard`）无冲突；dirty 状态仅**告警记录**（不拒绝，供异常排查）；广播帧带签名（复用 Ed25519 发布签名或专用补丁密钥）。

### 不做什么（边界）
- **不自动重启服务**：拉完补丁后由人工/既有流程重启（从节点不自动杀进程——避免状态丢失）。
- **不分发资产**：模型权重/SD 包/SQLite 数据不随本工具（走既有整合包/资产分发链路）。
- **不做冲突合并**：从节点一律对齐远程 dev（`reset --hard` 强制覆盖）；从节点不开发代码，本地无改动（dirty 仅告警）。
- **不替代 CI**：本工具是开发期快捷链路，不替代正式发布门（签名、质量门、验收仍走既有流程）。

## 2. 协议设计（补丁广播帧）

### 2.1 传输
- **主节点 → 从节点**：TCP 广播帧（UDP 广播易丢且不可靠；TCP 需已知从节点地址——**设计两个模式**）：
  - **模式 A：UDP 发现 + TCP 确认**（推荐）：主节点发 UDP 广播（发现），从节点回复自身地址，主节点用 TCP 推送帧（可靠、可重试）。
  - **模式 B：静态清单**（简化）：主节点配置从节点 IP 列表（Tailscale 100.x.x.x），直接 TCP 逐个推帧。
- 端口：`QLH_PATCH_PORT`（默认 **19731**），可配置。
- 帧格式（JSON，≤64KB，UTF-8）：
```json
{
  "schema": "qlh.patch_frame.v1",
  "ts": "2026-08-17T10:00:00+08:00",
  "repo": "https://github.com/sgfd8134/leds_-bjtu_-gitee.git",
  "branch": "dev",
  "commit_sha": "8a2f...",          // 已 push 的补丁提交
  "proxy_port": 7897,               // 从节点拉取用代理端口
  "fallback_repo": "https://gitee.com/sgfd8134/leds_-bjtu_-gitee.git",
  "signature": "base64(ed25519)",   // 对以上字段 canonical JSON 的签名
  "note": "fix: xxx"
}
```
- 帧重试：主节点每帧最多 3 次 TCP 推送（间隔 2s）；从节点收到后回 `ack`（含应用结果）。

### 2.2 签名与认证
- 复用项目 Ed25519 发布密钥体系：主节点用 `packaging/.signing-keys/` 的发布密钥签名帧；从节点内置/配置公钥验签。
- **fail-closed**：帧签名无效/缺签名 → 从节点忽略（记录告警）。
- 网段信任：默认仅接受 Tailscale 网段（`100.64.0.0/10`）与局域网（可配置 CIDR）来源。

## 3. 组件设计

### 3.1 主节点分发器 `scripts/patch_dispatch.py`
```bash
python scripts/patch_dispatch.py -m "fix: xxx"              # commit+push+广播（默认）
python scripts/patch_dispatch.py --no-push                  # 只 commit+广播（不 push）
python scripts/patch_dispatch.py --dry-run                  # 预览将提交/推送/广播内容
python scripts/patch_dispatch.py --nodes 100.64.0.2,100.64.0.3  # 静态清单模式
python scripts/patch_dispatch.py --proxy-port 7897          # 代理端口（默认 7897）
```
流程：
1. `git add -A && git commit -m <msg>`（无改动则提示并退出）
2. 生成帧（commit SHA、repo 远程地址、分支名 `dev`）→ Ed25519 签名
3. `git push origin dev`（**环境变量 `HTTPS_PROXY=http://127.0.0.1:7897` + git `http.proxy` 会话级设置**，仅本次命令生效，不改全局 git 配置）
4. UDP 发现/TCP 推帧（模式 A/B）→ 收集 ack（含从节点应用结果）→ 汇总报告
5. 失败处理：push 失败（代理不通）→ 不广播（fail-closed）；广播部分失败 → 报告未达节点，可 `--retry`

### 3.2 从节点监听器 `scripts/patch_listener.py`（常驻或 systemd 服务）
```bash
python scripts/patch_listener.py --verify-key <pubkey.pem>   # 前台运行
# Linux 从节点：systemd 单元（qlh-patch-listener.service）；Windows：计划任务/启动项
```
流程：
1. 监听 `0.0.0.0:19731`（UDP 发现应答 + TCP 帧接收）
2. 验签（Ed25519）→ 校验 schema/分支（**只接受配置的 repo + dev 分支**）
3. **dirty 检查（告警级）**：`git status --porcelain` 非空 → 记录告警日志（从节点为纯部署机，正常应无改动；异常时排查用），**不拒绝**，继续强制覆盖
4. 强拉：`git fetch origin dev`（代理 7897 会话级）→ `git reset --hard origin/dev` → `git clean -fd`（默认；`--no-clean` 可关）
5. 校验：`git rev-parse HEAD == 帧 commit_sha` → ack=`applied:<sha>`；不一致 → ack=`failed:<reason>`
6. 日志：`build/patch-listener.log`（含帧摘要，不落密钥）

### 3.3 代理纪律（7897）
- **会话级设置，绝不写全局 git config**：命令前 `env HTTPS_PROXY=http://127.0.0.1:7897 HTTP_PROXY=http://127.0.0.1:7897 git ...`（单命令作用域）。
- 代理不可达：主节点 push 失败不广播；从节点 fetch 失败重试 2 次后 ack=failed（不静默）。
- 源兜底：GitHub push 失败可 `--push-gitee` 转推 gitee（两源 dev 分支内容一致）；从节点 `fallback_repo` 在 GitHub 拉取失败时兜底（帧内携带）。

## 4. 与既有机制的关系

| 机制 | 关系 |
|---|---|
| 整合包/资产分发（build_offline_bundle + serve） | 代码走补丁分发，资产走整合包——互不重叠 |
| Launcher 更新（GitHub/Gitee 双源 + 签名） | 复用其双源与 Ed25519 签名先例 |
| 任务链/租约 fencing | 不涉及（补丁分发是开发期工具，不进入运行时） |
| 已知问题记录 | 分发失败/丢改动事件登记 |

## 5. 里程碑与验收

| 里程碑 | 交付 | 验收口径 |
|---|---|---|
| **M1 主节点分发器** | `scripts/patch_dispatch.py` + 单测（mock git/代理/广播） | 干跑/单测：commit 生成、帧签名、`--dry-run` 预览、push 代理环境变量隔离（不写全局 git config）、广播重试 |
| **M2 从节点监听器** | `scripts/patch_listener.py` + 单测 | 单测：验签拒绝、dirty 告警后强制覆盖（不丢应用能力）、强拉对齐 commit_sha、代理不可用重试、ack 协议 |
| **M3 双机实测** | surface7 修复后真机验证 | 主节点改一行代码 → 一键 → 从节点 <30s 内自动对齐新 commit（强拉覆盖成功 + HEAD 一致）；断网/代理挂场景 fail-closed；从节点异常 dirty 仅告警不影响覆盖 |
| 收口 | 文档登记 + 已知问题记录 | 双机开发流程切换为"改代码 → patch_dispatch.py" |

## 6. 依赖与风险

| 项 | 说明 |
|---|---|
| 依赖 | Python 3.10+ 标准库 + git + 7897 代理（本机已具备）；从节点需能访问 GitHub/Gitee（代理 7897） |
| 端口 | 19731 TCP（从节点监听）+ UDP 发现（模式 A）；与 serve（9090）、主服务端口无冲突 |
| 风险 | ① 强拉覆盖——从节点为纯部署机（不开发），无本地改动，覆盖无冲突；dirty 仅告警（异常时人工介入）；② 广播伪造——Ed25519 验签 + Tailscale 网段过滤；③ 代理不稳定——重试 + gitee 兜底 + 失败不静默；④ 从节点服务状态——拉完不自动重启（人工/既有流程） |
| 冲突边界 | 不修改 `src/` 现有代码（新文件限 scripts/ + tests/）；与并行组工作区隔离；从节点为纯部署机不开发，强拉强制覆盖无冲突（dirty 仅告警） |
