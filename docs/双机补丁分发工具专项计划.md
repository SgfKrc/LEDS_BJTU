> 立项背景：即将进入双机开发阶段（surface7 修复后），主节点与从节点频繁同步补丁。手动 `git pull` 在多机场景下繁琐易漏；本工具把「commit → push（走 7897 代理）→ 广播 → 从节点自动强拉」串成一条命令。
> **节点定位（2026-08-17 确认）**：surface 等从节点**不参与本项目开发**（只跑部署/验收，不做代码开发）——从节点不存在本地未提交改动，**每次强拉强制覆盖无冲突风险**；dirty 检查从"拒绝"降级为"告警记录"（安全网，仅异常排查用）。

## 1. 目标与边界

### 目标
1. **主节点一键分发**：修复代码后执行一个命令 → 自动 `git commit`（可选 amend/新提交）→ push 到远程 dev 分支（**走 7897 端口代理**）→ 向局域网/Tailscale 网段广播补丁帧。
2. **从节点自动应用**：监听 TCP 广播帧 → 校验帧（commit SHA/仓库/分支）→ 走 7897 代理 `git fetch` + **强拉**（`reset --hard` 对齐 dev 分支）→ 验证工作区一致性。
3. **安全默认**：从节点为纯部署机（不参与开发）——强拉强制覆盖（`reset --hard`）无冲突；dirty 状态仅**告警记录**（不拒绝，供异常排查）；广播帧带签名（复用 Ed25519 发布签名或专用补丁密钥）。

### 不做什么（边界）
- **不自动重启服务**：拉完补丁后由人工/既有流程重启（从节点不自动杀进程——避免状态丢失）。
- **不分发资产**：模型权重/SD 包/SQLite 数据不随本工具（走既有整合包/资产分发链路）。
- **不做冲突合并**：从节点一律对齐远程 dev（`reset --hard` 强制覆盖）；从节点不开发代码，本地无改动（dirty 仅告警）。
- **不替代 CI**：本工具是开发期快捷链路，不替代正式发布门（签名、质量门、验收仍走既有流程）。

## 2. 协议设计（补丁广播帧）

### 2.0 节点重启指令（设计预留，不属本工具实现）

补丁应用后从节点服务可能需要重启才能生效。**重启功能遵循高内聚低耦合原则：不作为本工具实现**，而是由**主节点的节点管理功能模块**（将来开发）统一提供：

| 项 | 归属 |
|---|---|
| 从节点「保存状态 → 强制重启」逻辑 | **主节点节点管理模块**（将来开发），提供统一 API（如 `POST /api/nodes/{id}/restart`） |
| 补丁分发工具 | **只调用**该 API（`--restart-nodes` 时在广播 ack 后触发），不实现重启本身 |
| 从节点侧 | 节点管理模块的 agent/服务负责保存状态（任务链租约释放、journal flush、会话持久化）→ 强制重启（systemd restart / Windows 计划任务重启） |

**帧协议预留**：补丁帧可携带 `restart_requested: true`（主节点期望应用后重启），但**执行**由从节点的节点管理 agent 处理——监听器只负责把该标记转交给节点管理模块，不自行重启。

**验收口径（将来，节点管理模块）**：从节点收到重启指令 → 状态保存完成（无数据丢失：租约/journal/会话）→ 强制重启 → 服务恢复 → 节点管理 API 返回 `restarted`；补丁分发工具调用该 API 后根据返回汇总报告。

## 2. 协议设计（补丁广播帧）

### 2.1 传输
- **主节点 → 从节点**：TCP 广播帧（UDP 广播易丢且不可靠；TCP 需已知从节点地址——**设计两个模式**）：
  - **模式 A：UDP 发现 + TCP 确认**（推荐）：主节点发 UDP 广播（发现），从节点回复自身地址，主节点用 TCP 推送帧（可靠、可重试）。
  - **模式 B：静态清单**（简化）：主节点配置从节点 IP 列表（Tailscale 100.x.x.x），直接 TCP 逐个推帧。
- 端口：`QLH_PATCH_PORT`（默认 **19731**），可配置。
- 帧格式（JSON，≤64KB，UTF-8）：
```json
{
  "schema": "qlh.patch_frame.v1",
  "ts": "2026-08-17T10:00:00+08:00",
  "repo": "https://github.com/sgfd8134/leds_-bjtu_-gitee.git",
  "branch": "dev",
  "commit_sha": "8a2f...",          // 已 push 的补丁提交
  "proxy_port": 7897,               // 从节点拉取用代理端口
  "fallback_repo": "https://gitee.com/sgfd8134/leds_-bjtu_-gitee.git",
  "signature": "base64(ed25519)",   // 对以上字段 canonical JSON 的签名
  "note": "fix: xxx"
}
```
- 帧重试：主节点每帧最多 3 次 TCP 推送（间隔 2s）；从节点收到后回 `ack`（含应用结果）。

### 2.2 签名与认证
- 复用项目 Ed25519 发布密钥体系：主节点用 `packaging/.signing-keys/` 的发布密钥签名帧；从节点内置/配置公钥验签。
- **fail-closed**：帧签名无效/缺签名 → 从节点忽略（记录告警）。
- 网段信任：默认仅接受 Tailscale 网段（`100.64.0.0/10`）与局域网（可配置 CIDR）来源。

## 3. 组件设计

### 3.1 主节点分发器 `tools/patch_dispatch.py`（M1 已完成 2026-08-17，见 §5）
Windows 主节点可直接双击仓库根目录 `patch_dispatch.bat`；它只设置本次命令的代理环境，不写入全局 Git 配置。节点清单可通过 `QLH_PATCH_NODES` 预置，路径可通过 `QLH_PATCH_PATHS` 预置。
```bash
python tools/patch_dispatch.py -m "fix: xxx"              # commit+push+广播（默认）
python tools/patch_dispatch.py --no-push                  # 只 commit+广播（不 push）
python tools/patch_dispatch.py --dry-run                  # 预览将提交/推送/广播内容
python tools/patch_dispatch.py --nodes 100.64.0.2,100.64.0.3  # 静态清单模式
python tools/patch_dispatch.py --proxy-port 7897          # 代理端口（默认 7897）
```
流程：
1. `git add -A && git commit -m <msg>`（无改动则提示并退出）
2. 生成帧（commit SHA、repo 远程地址、分支名 `dev`）→ Ed25519 签名
3. `git push origin dev`（**环境变量 `HTTPS_PROXY=http://127.0.0.1:7897` / `HTTP_PROXY` 会话级设置**，仅本次命令生效，不改全局 Git 配置）
4. TCP 推帧（静态清单；UDP discovery 尚未实现）→ 收集 ack（含从节点应用结果）→ 汇总报告
5. 失败处理：push 失败（代理不通）→ 不广播（fail-closed）；广播部分失败 → 报告未达节点，可 `--retry`

### 3.2 从节点监听器 `tools/patch_listener.py`（常驻或 systemd 服务）
Windows 从节点可直接双击仓库根目录 `patch_listener.bat`；默认使用仓库内的 release 公钥，并同时尝试 IPv4/IPv6 监听。
```bash
python tools/patch_listener.py --verify-key <pubkey.pem>   # 前台运行
# Linux 从节点：systemd 单元（qlh-patch-listener.service）；Windows：计划任务/启动项
```
流程：
1. 默认监听 IPv4/IPv6 双栈 `0.0.0.0/[::]:19731`（静态清单 TCP 帧接收）
2. 验签（Ed25519）→ 校验 schema/分支（**只接受配置的 repo + dev 分支**）
3. **dirty 检查（告警级）**：`git status --porcelain` 非空 → 记录告警日志（从节点为纯部署机，正常应无改动；异常时排查用），**不拒绝**，继续强制覆盖
4. 强拉：`git fetch origin dev`（代理 7897 会话级）→ `git reset --hard origin/dev` → `git clean -fd -e node_config.json -e node_config.json.tmp`（默认；`--no-clean` 可关）。节点身份实际保存于用户数据目录，不随仓库同步。
5. 校验：`git rev-parse HEAD == 帧 commit_sha` → ack=`applied:<sha>`；不一致 → ack=`failed:<reason>`
6. 日志：`build/patch-listener.log`（含帧摘要，不落密钥）

### 3.3 代理纪律（7897）
- **会话级设置，绝不写全局 Git 配置**：命令前注入 `HTTPS_PROXY=http://127.0.0.1:7897` 与 `HTTP_PROXY=http://127.0.0.1:7897`（单命令作用域）。
- 代理不可达：主节点 push 失败不广播；从节点 fetch 失败重试 2 次后 ack=failed（不静默）。
- 源兜底：GitHub push 失败可 `--push-gitee` 转推 gitee（两源 dev 分支内容一致）；从节点 `fallback_repo` 在 GitHub 拉取失败时兜底（帧内携带）。

### 3.5 可选 SSH 传输层（`SYNC-SSH-S0` 已完成）

现有 TCP listener、签名补丁帧和 `pull/push` 继续作为默认路径与兜底。SSH 只增加受控传输，不改变补丁格式：Ed25519 key-only、host fingerprint/allowlist、固定远程 helper（`status/fetch/apply/verify`）、维护锁、签名 commit/HEAD 校验；禁止密码、任意远程 shell、复制 SQLite/模型/附件、自动重启和绕过 7897 代理纪律。

`tools/ssh_sync_contract.py` 已落实 S0：严格 Ed25519 profile（host key + SHA256 fingerprint 双绑定）、无密码/无首次信任 argv、固定 `qlh-patch-helper` 的 `status/fetch/apply/verify`、精确 commit SHA、签名帧大小上限和远端 maintenance lock；helper result 必须匹配错误码、retry 和 fallback 矩阵。fixture 与回归 `11 passed`，不连接 SSH、不读取私钥、不修改现有 TCP listener。

`tools/ssh_sync_helper.py` 与 `FakeSshServer` 已落实 S1：在临时 bare remote/worker checkout 真实执行 fetch、可达性校验、精确 reset；Ed25519 patch frame 在任何 git 写入前验签并绑定受管 `origin`，repo/state/verify-key 均禁止位于 checkout 内，dirty workspace/维护锁/断连/篡改/重复或错误复用 operation fail-closed，应用后丢 ACK 通过外置 ledger 幂等恢复，forced command 只解析固定 token 序列。专项 `9 passed`，S0+S1+既有补丁工具联合 `48 passed`。不连接真实 SSH；S2 需部署 forced-command 账号和 helper。

`tools/ssh_sync_client.py` 已落实 S2 主节点侧：每次请求先按 S0 重建，覆盖独立 managed known_hosts 后执行无 shell 的 OpenSSH argv；仅接收一行 contract-valid JSON，OpenSSH `255`/超时映射 `transport_unavailable`，已认证命令的非零退出或协议输出异常映射 `remote_helper_rejected`。`patch_dispatch.py --write-frame <外置文件>` 为同一签名 frame 提供可审计输入。真实验收顺序固定为 `status -> fetch(target) -> apply(frame) -> verify(target)`；`fetch` 不变更 HEAD。2026-08-19 已证实从节点 SSH 端口、host key 和免密身份均可达，但固定 `qlh-patch-helper status` 返回 Windows 命令不存在，故真实 helper 未被调用。下一动作仅限从节点管理员本地建立专用 `qlh_sync` key-only/forced-command 帐号并配置检出外 helper state/verify key，禁止降级密码或普通 shell。

分期为 S0 契约、S1 fake SSH 断连/重放/脏工作区回归、S2 真实 LAN/Tailscale 双机、S3 可选 GUI/TUI 传输选择。SSH 不可用时必须明确回退到现有 `pull/push`，不阻塞分布式推理开发。
