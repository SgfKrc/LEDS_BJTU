## 1. 背景

DeepSeek-V4.1-Flash（2026-09-10 发布）在官方文档里明确了两件事：**KV cache 体量大幅下降**（对比上一代：HBM 仅需 **1/4**、SSD 存储仅需 **1/8**），以及**缓存命中费用常占 agent 成本的大头**。同时，由于 **Sliding Window Attention（SWA）**，上下文缓存的**匹配规则变了**——这直接改变了"怎么写提示词才省钱"的工程含义。

本机现状：`reasonix` 的 provider 清单里当前 ref 为 `opencode-go-2ae…/deepseek-flash`，而 `deepseek-flash` 正是 V4.1-Flash 的官方模型名（旧名 `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp` 的请求已被路由到 V4.1 并按 Flash 价计费）。也就是说，**项目当前调用路径已经在用 V4.1**。

## 2. 事实登记：V4.1 的缓存机制

### 2.1 磁盘上下文缓存（默认开启）

每个用户请求都会触发构建**磁盘缓存**；后续请求若与历史前缀重叠，重叠部分从缓存读取，计为 "cache hit"。缓存不需要改代码，开箱即用；构建需要数秒，闲置后自动清理（数小时到数天）；整体是 best-effort，**不保证 100% 命中**。

### 2.2 SWA 带来的"单元匹配"（本计划的关键事实）

官方原文：*"Due to the Sliding Window Attention mechanism, the storage and matching of cached prefixes differs from before."* 新规则是：

- 每个缓存前缀是**独立的、完整的单元**；后续请求**必须完整匹配某个单元**才算命中；
- 单元在三种时机被持久化：
  1. **请求边界**：每次请求会在"用户输入结束位置"和"模型输出结束位置"各产生一个单元；
  2. **公共前缀检测**：系统发现多个请求共享的前缀时，把它固化为独立单元；
  3. **固定 token 间隔切分**：长输入/长输出会按固定间隔切出单元，避免"永远到不了边界"而完全无法缓存。
- 行为示例：第一轮 `A+B`、第二轮 `A+B+C` → 命中 `A+B`；但 `A+B` → `A+C` **不命中**，此时系统把公共前缀 `A` 固化为单元，**第三轮 `A+D` 才命中 `A`**。

**工程含义**：想让前缀命中，必须让**前缀逐字节稳定**，并且**对齐到单元边界**。任何插在前面的动态内容（时间戳、随机 id、绝对路径、动态工具清单）都会让整段前缀作废。

### 2.3 命中观测与计费

- 响应 `usage` 提供 `prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`；
- 价格（V4.1-Flash，每 1M input tokens）：**cache hit $0.003–0.006**，**cache miss $0.15–0.30** → **相差 25–50 倍**；输出 $0.6–1.2；
- 官方明确"缓存命中费用在 agent 成本中占比很大，压缩缓存能显著降本"。

### 2.4 架构侧（同期发布，供对照）

V4.1-Flash 为 552B MoE 的**非对称 Causal Encoder–Decoder**：输入侧仅 **8B 激活参数**、输出侧 **16B**；1M 上下文、384K 最大输出；原生多模态。这些属于预训练/架构层成果，QLH 只能跟踪（见 §4 C 档）。

## 4. 落地动作

### A 档：零成本、立刻可做

- **A1 前缀稳定性规范 + 自检**：明确"稳定前缀（系统提示、工具清单、固定示例）在前，动态内容（任务、路径、时间）在后"的布局规范；提供一个轻量自检（例如检查系统提示里是否混入时间戳/绝对路径/随机 id）。适用范围：bridge worker 提示词、harness 系统提示、Codex 侧 MCP 工具定义。
- **A2 缓存命中观测**：`BRIDGE_LOG` 增加 cache hit/miss 字段（**前提是 CLI 透传 usage**，需先探测）；harness 侧在 provider 调用处记录 usage 命中量。本地路线（llama.cpp）用其 prompt cache 做同类度量。
- **A3 模型名与预设核对**：已把 `presets.example.json`、bridge 接线清单和文档维护 Agent 示例统一为 V4.1 口径（`deepseek-flash` = V4.1-Flash），并注明旧名仅作兼容说明；真实社区工件 slug 与 API model ref 分开记录，避免"以为在用 V4"的误解。

### CACHE-01 实施记录

- `scripts/check_prompt_cache.py` 接受 UTF-8 prompt 文件或 `--text`，只报告行号和规则，不回显匹配内容；当前检查时间戳、Windows/UNC/POSIX 绝对路径、UUID、运行时插值和带值的 job/request/session/trace/checkpoint ID。
- bridge 的 read/write worker 系统提示与 harness 内置系统提示均把稳定策略放在前面；运行时任务、路径、时间和请求标识留在调用消息或结果中。
- 离线验收：`.venv-test\Scripts\python.exe -m pytest tests/test_prompt_cache.py -q` 为 `3 passed`；bridge 两份 prompt 的直接检查均为 `OK`。

### CACHE-02 实施记录

- bridge 的 `BRIDGE_LOG` 现在只从 CLI stdout/stderr 中解析结构化 usage 数字，记录 `prompt_tokens`、`completion_tokens`、`prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`；不记录任务、正文或 worker 输出。
- CLI 没有透传 cache usage 时明确记录 `status=unavailable` 与 `reason=cli_usage_not_forwarded`；输出被截断时记录 `cli_output_truncated`，不猜测命中率。
- harness QLH provider 保留完成式和流式 metrics 中的 cache hit/miss 字段；真实 provider 未提供字段时保持空 usage，不伪造命中数据。
- 验收覆盖：bridge 透传/未透传两态、日志正文脱敏、QLH 完成式/流式 usage 映射；不改变缓存开关、请求参数或生成行为。

### CACHE-03 实施记录

- `PagedKVCache` 新增显式参数 `cold_cache_dir` 与 `cold_max_pages`。`max_pages` 仍是内存热页上限，冷层页数单独受 `cold_max_pages` 限制；未传冷层参数时保持原有纯内存行为。
- 冷页采用每实例隔离目录、原子写入的 PyTorch 页文件和原子更新的 `manifest.json`；页元数据包含 SHA-256、形状、已用 token 数和文件大小。冷读先校验文件存在性、哈希、schema、形状和 used 范围，失败时明确报错，不静默使用损坏数据；当前不扫描旧实例目录，不承诺跨进程恢复。
- 冷层读取按逻辑页表返回临时设备页，避免为一次读取扩大热层常驻上限；尾部截断会删除完整冷页，部分截断会先校验并回升尾页。`RLock` 串行保护追加、读取、截断、清理和设备迁移。
- `KVHost.init()` / `from_profile()` 已透传冷层配置，`KVHost.status()` 暴露冷层启用状态、冷页数和命中数；`get_stats()` 增加逻辑容量、驻留峰值、冷读耗时和冷层字节数。
- 验收覆盖：热页峰值保持在 `max_pages`、冷页命中和逻辑顺序、缺失/哈希损坏 fail-closed、尾部页失效、并发读取、`KVHost` 接线及 `append_kv_single()` 容量边界；`.venv-test\Scripts\python.exe -m pytest tests/test_paged_kv_cache.py tests/test_paged_kv_cold_cache.py tests/test_inference_service_protocol.py -q` 为 `119 passed`。

### CACHE-04 实施记录

- 新增 `src/cache_unit_layout.py`，冻结 `CacheUnitLayout`、完整单元边界、按单元 SHA-256 摘要和完整单元前缀匹配规则；`unit_size` 必须整除 `page_size`，未完成单元的尾部不计入可复用前缀。
- `PagedKVCache` 新增可选 `cache_unit_size`，默认等于 `page_size`；统计增加单元大小、每页单元数、已完成单元数和尾部余量，并提供 `cache_unit_boundaries()` 检查接口。`KVHost` 与 `/v1/kv/init` 完成透传。
- 新增 `scripts/cache_unit_experiment.py` 和 [缓存单元对齐实验](缓存单元对齐实验-2026-09-14.md)：固定 `page_size=8`、`unit_size=4` 的实验中，完整单元后追加命中 `8` token，边界变化命中 `4` token，单元内部变化命中 `0` token。
- 验收覆盖：页/单元整除关系、完整边界、跨请求单元摘要匹配、主缓存统计/API 接线和机器可读实验报告；`.venv-test\Scripts\python.exe -m pytest tests/test_cache_unit_layout.py tests/test_paged_kv_cache.py tests/test_paged_kv_cold_cache.py tests/test_inference_service_protocol.py -q` 为 `125 passed`。

### B 档：工程改造（适合排票或毕设）

- **B1 `paged_kv_cache` 两级缓存**：内存热页 + 磁盘冷页（冷页按策略下沉，读取校验后按需加载；写入和尾部修改时回升），验收看**命中率、峰值内存下降、冷读延迟**三项；对 16GB 内存的开发机与边缘设备收益最直接。
- **B2 缓存单元对齐**：已冻结分页 KV 的页/单元整除关系和完整单元摘要匹配；跨请求复用仍需真实 tokenization、provider/跨进程持久化和收益数据后置验证。
- **B3 非对称分工论证**：已合并既有 `speculative.py`（draft-verify）与亚1B 岗位化实验，产出一页对照分析和可验证假设；不新开架构方向。

### C 档：只跟踪，不做

- **C1 架构级压缩**：等 V4.1 的开源推理支持（llama.cpp/GGUF 等）成熟后，再评估在 CPU/Android 路线的接入；在此之前不宣称任何"等价能力"。

## 6. 风险与边界

1. **不能为命中牺牲正确性**：前缀工程只调整"内容摆放顺序"，不得为了缓存把动态内容（如当前任务、路径约束）塞错位置导致语义漂移。
2. **命中率不是质量指标**：它是成本/延迟指标；README 与汇报口径里不得把"高命中率"说成"模型更好"。
3. **本地模型没有 provider 缓存**：`llama.cpp` 的 prompt cache 与 DeepSeek 的服务端磁盘缓存不是一回事，度量方法可以类比，结论不可互推。
4. **磁盘冷层新增一致性面**：页失效、并发读写与崩溃恢复都要有测试；不得让冷层成为静默正确性风险。
5. **不复制不可复现的能力**：架构级压缩（1/4 HBM、1/8 SSD）不纳入本项目承诺，仅在 C 档跟踪。
6. **成本口径透明**：缓存计费是 provider 侧行为，任何"省了多少"的结论必须给出 hit/miss 原始读数与单价来源。
