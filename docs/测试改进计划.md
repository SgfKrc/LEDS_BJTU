### 4.5 分期执行计划（2026-08-14，采纳 §4.4 建议并分期防糙）

> 原则：每阶段小而完整、可独立验收；先低成本高价值，再覆盖补充；**重命名/重组既有测试文件为高风险低收益动作，仅对新增测试应用新分类命名，不重命名既有文件**（避免大 diff 与 git 历史断裂）。

| 阶段 | 范围 | 验收标准 | 防糙机制 |
|---|---|---|---|
| **T-1 测试纪律基线** | 全量测试切换到 `.venv-test` 隔离环境；`pytest.ini` 的 `-n auto`/`--timeout=300` 在该环境验证稳定（xdist 并行是否引入 flaky）；`run_test_channels.py` 固化多通道入口 | `.venv-test` 全量绿；并行与串行各跑 2 次结果一致（无 xdist 引入的 flaky）；通道脚本可复现 | 先跑通再写结论；环境矩阵留证据 |
| **T-2 脆性修复（最高价值）** | 硬编码文本/路径断言迁移至 `error_code`/常量；固定 `sleep` 换 Event/就绪信号（可靠审计低危项）；`sd15_*` 质量门参数化 | 逐项修复清单 + 定向回归；重复运行 3 次无 flaky；全量绿 | 每项附带"触发场景"说明，防止为修而修 |
| **T-3 边界/负向覆盖** | 补 20-30 个边界/负向用例：qwen3 pipeline dry-run 失败场景、KV handoff 极端值参数化、安全拒绝/超时/异常恢复空洞 | 覆盖空洞清单逐项关闭；新增用例按新分类命名（`test_*_contract.py`/`test_*_negative.py`）；全量绿 | 先列空洞清单再写用例（防凑数） |
| **T-4 组织优化（低优先）** | 质量门抽象 regression suite；按新分类生成定期报告脚本 | suite 可复用；报告脚本输出 JSON+摘要 | 不重命名既有文件；不改测试语义 |

**排序理由**：T-1 是环境地基（当前测试环境刚分离，先固化）；T-2 是脆性源头（糙活最多的地方）；T-3 补真正的覆盖空洞；T-4 收益最低放最后、可砍。

**当前状态**：T-1 进行中（2026-08-14）。已完成：`.venv-test` 切换、`pytest-timeout` 就位、主环境恢复干净。**实测发现并修复 2 个问题**：
1. **并行 flaky**（`-n auto` 全量）：`test_parallel_cancellation_reaches_all_providers_and_releases_slots` 的 `thread.join(5)` 在并行负载下取消传播超时 → 已放宽至 20s（取消语义不变）；
2. **桌面崩溃事件**（`-n auto` = 20 worker）：torch 测试并发 import/初始化 CUDA，内存峰值击穿 16GB（实测 `-n 4` 即占用峰值 11.2GB/余量 4.4GB）→ pytest.ini 固定 `-n 4`（与 run_test_channels 默认一致）+ 注释说明，`QLH_TEST_WORKERS` 可覆盖；**全量跑前需关闭重负载应用或降 `-n 2`**。
剩余：修复后全量并行复跑（待桌面稳定窗口，避免再次击穿内存）。

### 4.2.1 Review 端点授权契约（2026-08-12 决策，测试实现依据）

**背景**：项目当前**无请求级节点认证**（HTTP 层无节点 token/签名；节点身份靠 TCP 注册 + cluster secret；MF-AUTH 的 Bearer 是用户登录，不适用于节点）。既有 create/vote 校验（`scheduler._effective_role()`、`can_node_vote(node_id)`）是**本机角色**校验——约束"运行 API 的这台机器"的角色，即部署位置约束，而非调用者身份校验。以下契约沿用该模式。

| # | 端点 | 授权策略 | 非授权响应 |
|---|---|---|---|
| 1 | `POST /api/cluster/review/create` | 仅 master 机器（已有） | 403 |
| 2 | `POST /api/cluster/review/vote` | 仅具投票资格节点机器（已有：PC+CUDA）+ 值校验 + 工单存在 | 403 / 400 / 404 |
| 3 | `GET /api/cluster/review/tickets` | **开放**（网络信任域内） | — |
| 4 | `GET /api/cluster/review/tickets/{id}` | **开放** + 工单不存在 | 404 |
| 5 | `GET /api/cluster/review/can-vote` | 开放自查询（现状合理，无敏感信息） | — |
| 6 | `POST /api/cluster/review/expire-check` | **仅 master**（新增） | 403 |
| 7 | `DELETE /api/cluster/review/tickets/{id}` | **仅 master**（新增） | 403 |
| 8 | `DELETE /api/cluster/review/tickets` | **仅 master**（新增） | 403 |
| 9 | `POST /api/cluster/review/mail-poll` | **仅 master**（新增；真实 IMAP 拉取 + SMTP 副作用） | 403 |

**策略理由**：
- **读开放（3/4/5）**：已注册节点需要读待审查工单才能投票决策，列表/详情是投票流程的必要输入；工单内容（target_node_id、votes）是集群管理信息，在 Tailscale/受信 CIDR 网络信任域内透明可接受。无节点身份机制下，"开放"的边界就是网络信任域（HTTP 不暴露公网）。
- **写收紧为仅 master（6/7/8/9）**：expire-check（状态变更 + SMTP 通知）、delete（管理操作）、mail-poll（真实 IMAP + 可能触发结果通知）均为副作用/破坏性操作，与 create 的"仅 master"一致；从节点不应能删除工单或触发轮询。
- **vote 保持现状**：资格门（PC + CUDA）已是语义正确的授权。

**实现模式**（与 create 同模式）：
```python
if scheduler._effective_role() != "master":
    raise HTTPException(status_code=403, detail="仅主节点可执行此操作")
```

**验收测试矩阵**（已纳入 `tests/test_api_security_boundaries.py`）：
- 非 master 角色（monkeypatch `scheduler._effective_role` 返回 `"client"`）调用 6/7/8/9 → **403**；
- master 角色调用 6/7/8/9 → 正常执行（expire-check 返回计数、delete 返回 deleted、mail-poll 返回轮询结果）；
- 读端点 3/4/5 不因角色变化而 403（保持开放）；vote 的资格门 403 已覆盖。

**演进边界**：将来若引入请求级节点认证（MF-AUTH 扩展为节点身份），本契约升级为"调用者身份"校验；当前按部署位置约束，测试注明本机角色语义。

### 4.5 T-RACE 竞态与时序专项（规划，未宣称实现）

现有单测已覆盖不少状态机，但真实连接暴露出“旧 socket 迟到写入、重复 active connection、注册确认与 ACK 屏障错序、层配置释放时序”等需要独立门控的风险。新增 `T-RACE-0` 至 `T-RACE-6`：状态转移盘点、可控时钟/事件屏障、连接生命周期、层配置与任务 lease、SQLite 崩溃恢复、随机化压力/soak，最后才进入真实双机验收。

最低场景包括同时注册、close 期间发送、重复心跳、ACK 早于本地加载、旧 `config_id`/`generation` 迟到、重复 winner、取消与 lease expiry 交叉、SQLite 提交中 kill、补丁应用中断。新测试不得用固定 sleep 作为完成判定；每次失败保存 seed、状态转移和 request/generation/attempt/config/lease 证据。连续三轮无未分类终态、重复 winner 或 reservation 泄漏，才允许进入真机门。
