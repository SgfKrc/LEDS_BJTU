# QLH 异构分布式形态决策（2026-09-14）

> 状态：**生效**（用户三裁决：三形态正式化 / llama.cpp RPC 对照实验 / ExecuTorch 远期选项）。
> 关联：[QLH 定位与模块归属终局决策](QLH定位与模块归属终局决策-2026-09-14.md)（v3 双引擎）、[TP 孤岛接入指南](TP孤岛接入指南.md)、[张量并行外部辅助与混合拆分调研方案](张量并行外部辅助与混合拆分调研方案.md)。
> 缘起：用户指出"llama.cpp 最初被选是替代安卓无法运行 PyTorch；至今 llama.cpp 分布式未完全解决，worker 像临时处理"——本文以调研（外部来源）+ 代码核对回答"怎么办"。

## 1. 调研结论（2026-09-14；外部调研子代理，官方来源）

1. **llama.cpp RPC 能做跨机层拆分**：主 host `--rpc host:port,...` + 多个 `ggml-rpc-server` worker；GGUF 模型按各设备内存比例切权重与 KV；**但官方定性：proof-of-concept、"fragile and insecure"、禁止开放网络**（来源：llama.cpp `tools/rpc/README.md`）。通信层在补强（RDMA/RoCEv2、Thunderbolt 5），但安全性/成熟度定性未变。
2. **llama.cpp 的 TP**：仅**单机多 GPU** 且 EXPERIMENTAL（强制 flash-attn、KV 不可量化、多架构报错）。layer（pipeline）模式"容忍慢互联"——与"异构低带宽集群"方向吻合，但 RPC 整体未转正。
3. **安卓跑完整 PyTorch 依旧不现实**：官网 Android 入口已转向 **ExecuTorch**；**ExecuTorch v1.0+** 官方支持 **Qwen3 0.6B/1.7B/4B**（Android AAR、XNNPACK/QNN/Vulkan），性能与 llama.cpp 同量级（Llama3.2-1B 4bit ≈ 50 tok/s @OnePlus 12）；代价=模型集受限 + AOT 导出链。
4. **跨框架层接力（PyTorch ↔ llama.cpp 一次 forward）没有可用的中间张量交换标准**——工程上等于自研分布式引擎；调研建议**不做**。
5. **唯一跨生态零风险形态 = 任务级/整请求级分发**（OpenAI 兼容 HTTP 是两者最低公共层）——与项目 `island_engine` 的"整岛=逻辑节点"设计一致。
6. 内部核对：项目**三种形态本已存在**（自研层拆分 `model_module.layer_range`+`tcp_comm`；TP 孤岛 `island_engine`；任务级 `task_worker`）——"worker 像临时处理"的根源是**缺正式定名与选型规则**，不是能力缺失。

## 2. 三形态定案（正式架构）

| # | 形态 | 适用节点 | 实现载体 | 语义 |
| --- | --- | --- | --- | --- |
| **① 层拆分（pipeline parallel）** | **PyTorch 档** PC 节点（mesh 内） | `model_module.py`（`layer_range` 层装载）+ `tcp_comm.py`（张量传输）+ `qwen3_pipeline_*`/`inference_service` 宿主 | **同一模型跨节点层流水线**（自研，已 PoC/双机验收） |
| **② TP 孤岛（逻辑节点）** | 同构 GPU 子集群（岛内 ≥1GbE，RTT<1ms） | `island_engine.py`（把 OpenAI 兼容端点整岛封装；**不参与层拆分**） | **整岛 = 集群一个高算力节点**（整请求转发） |
| **③ 任务池（任务级分布式）** | **安卓 / GGUF 轻节点**（物理上装不了 torch） | `task_worker_protocol.py`/`task_provider.py`/`task_chain` | **任务分发/路由/回传**——**正式形态，非临时补丁**（安卓唯一可行路径，调研背书） |

## 3. 选型规则（形态怎么挑）

- **输入**：`device_profiler` 画像（显存/内存/算力/平台）+ 节点能力表（能否装 torch、互联带宽）；
- **规则**：
  - 同构高带宽 PC 节点集合 → ① 层拆分；
  - 同构 GPU 岛（内网高速）→ ② 孤岛（逻辑节点）；
  - **装不了 torch / 异构轻节点（安卓、从节点低配）→ ③ 任务池**；
- **协议纪律**：跨生态一律走 **OpenAI 兼容 HTTP**（最低公共层）+ 任务协议；**禁止跨框架层接力**（§1.4）。

## 4. llama.cpp RPC 对照实验（票设计，待执行）

- **目的**：产出"**为何不采用 llama.cpp RPC**"的实测论据（结题/论文素材）。
- **设计**：本机（或本机+从节点）起 **2 个 `ggml-rpc-server` worker + 1 个 `llama-cli --rpc` host**；测：① 能否跨 rpc 完成层拆分推理（GGUF）；② 正确性（输出对照）；③ 吞吐/时延 vs 单机；④ 官方安全/成熟度定性记录；⑤ 从节点（Windows）编译 rpc-server 可行性。
- **验收**：一页实验报告（数据 + 官方定性引用）→ 结论并入本文 §1。
- **边界**：仅对照实验，**不作为生产路线**（除未来 RPC 转正）。

## 5. ExecuTorch（远期选项，记录）

- **触发条件**：安卓侧需要 PyTorch 生态模型，或 GGUF 覆盖不足时评估；
- **已知**：Qwen3 0.6B/1.7B/4B 官方支持、Android AAR、AOT 导出链、性能同量级；代价 = 模型集受限与导出工程量；
- **当前动作**：不动（安卓维持 GGUF/③ 任务池形态）。

## 6. 不变式

1. 双引擎策略（L=GGUF / D=PyTorch）与画像选档不变（本文是三形态的"分布式侧"细化）；
2. 二阶段验收结论（双机真机 ✓）与剩余后置验收项不变；
3. 不自研分布式引擎内核（跨框架层接力不做）——三形态皆复用既有载体。
