## 4. 子项目独立化评估（harness / docagent 是否独立仓库 + submodule）

### 4.1 现状
两个子项目已满足"不 import 主项目、仅共享工件/契约"边界，monorepo 内独立包（`harness_workbench/`、`tools/docagent/`），主项目 CI/测试已覆盖。

### 4.2 结论：**值得独立，但分批有序**
| 子项目 | 独立理由 | 风险 | 建议时机 |
|---|---|---|---|
| **docagent** | "跨项目通用工具"定位最硬（minimal profile 就是为第二项目设计的）；CI/发布独立价值高 | 低 | **现在可做**（作为通用化样板） |
| **harness** | 玩具/自用 + 契约（qlh adapter）与主项目有漂移风险；独立后契约测试负担转移 | 中 | **大创结题后再做**（答辩材料引用路径稳定，且真实运行时验收（C1）未完成前独立收益低） |

### 4.3 实施步骤（docagent 示例）
1. 从 monorepo 建独立仓库（GitHub，可先 private）：`git init` + 保留 `tools/docagent/` 为仓库根（历史可选 `git filter-repo` 保留，或新仓库从当前状态起）
2. 主项目：`tools/docagent/` 删除 → 添加 submodule（引用独立仓库 commit，参考 llama.cpp submodule 先例——主项目 bump = 提交 gitlink 更新）
3. 双 CI：子项目自带 pytest/CI；主项目 CI 增加 submodule 拉取 + 冒烟（确保 bump 不破坏）
4. 文档：README 文档索引更新 + 主项目计划登记（本仓库指向子项目仓库）

### 4.4 如果不做独立的核心理由（当前单人开发 + 答辩期）
双仓库 = 双 CI/双 issue/双 release 维护 + submodule 的"别人 clone 后 init"体验负担；monorepo 的原子提交（子项目与主项目契约一起改）对单人反而高效。**答辩期不做是理性的**；结题后按 docagent → harness 顺序做。
