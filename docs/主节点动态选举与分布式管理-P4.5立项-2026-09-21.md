# P4.5 立项：主节点动态选举与配套分布式管理（2026-09-21）

> 状态：**立项（设计）**，未实现。本文只定义目标、机制与验收判据，不含实现承诺。
> 触发：P4 收口后发现当前实现的一个结构性不合理 —— 见 §1。

## 1. 问题：主节点身份是"部署时钉死"的，而且理由已经消失

**当前实现（源码证据）**：

| 位置 | 事实 |
| --- | --- |
| `src/config.py:450` | `NODE_ROLE` 默认值 = `"master" if getattr(sys, "frozen", False) else "client"` —— 角色来自**环境变量/打包形态** |
| `src/config.py:452` | `_normalize_node_role(_initial_role)` —— 角色是一次性解析的常量 |
| `src/config.py:485` | `CLIENT_MASTER_HOST` / `CLIENT_MASTER_PORT` —— 从节点连谁，是**静态配置** |
| `src/bootstrap.py:76` | `select_advertised_master_host()` —— 只决定"广播哪个 host 当入口"，**不是选举** |
| `src/api_server.py:7470` | 已有 `presence_generation` / `presence_lease_id` —— 存在**租约与代次**的概念，但用于 Android presence，**没有用于主节点身份** |

**为什么这是结构性问题**：

1. **主节点的职责已经与 GPU 算力解绑**。P0–P4 之后，主节点承担的是控制面：设备画像、容量计划、
   层段合同、准入、租约与 epoch fencing、任务图调度。它**不需要 CUDA**，也不是吞吐瓶颈所在。
   ⇒ 但"谁是主节点"仍然由**部署时的一个环境变量**决定 —— 于是整个集群的管理角色被钉在
   一台**与它的实际能力无关**的机器上（可能是最弱的那个）。
2. **边缘集群的算力排序本来就会变**：设备上/下线（y700 会休眠、Surface 会合盖）、负载波动、
   热降频、网络路径变化。静态身份无法跟随，只能靠人工改配置重启。
3. **代价不对称**：主节点选错（选到弱机）会持续拖慢整个集群的调度与准入；而"谁是主节点"
   恰恰是**最容易按能力自动决定**的一件事。

用户裁定（2026-09-21）：
> 主节点身份就不该是永久的，而是自行选择 CPU 算力最强的那个；还要实现配套的分布式管理机制。

## 2. 目标

| # | 目标 | 可验证形态 |
| --- | --- | --- |
| G1 | **自选**：主节点由集群从**当前在线节点**中按"管理能力"选出，而不是部署时指定 | 集群启动/成员变化后，无需人工配置即产生唯一主节点 |
| G2 | **可迁移**：更强的候选上线、或现任主节点降级/掉线时，主节点身份可以**交接** | 交接完成后旧主不再是主，且新主 epoch 严格递增 |
| G3 | **不脑裂**：任何时刻**至多一个**能提交状态的主节点 | 旧主一旦失去有效租约，其写入必须被拒（fail-closed），而不是"尽力而为" |
| G4 | **不改数值面**：主节点迁移**不得**改变任何推理结果的判据 | 迁移前后同一 prompt 的 per-token argmax 一致（沿用现有判据） |

G4 是边界：P4.5 是**控制面**重构，必须证明它对数值面是透明的（这也是"系统软件内核 / 用户软件外壳"
分层里，控制面可以演进的那部分 —— 见 README「这是什么软件」一节）。

## 3. 设计

### 3.1 能力评分（候选排序）

主节点候选按**管理能力**打分，而不是按推理能力。建议维度（都可本地采集，无需特权）：

| 维度 | 采集方式 | 权重意图 |
| --- | --- | --- |
| CPU 逻辑核数 | `os.cpu_count()` | 主要项（用户明确要求"CPU 算力最强"） |
| CPU 基准分 | 启动时跑一次固定微基准（矩阵乘/哈希，~100 ms，结果入缓存） | 区分同核数不同代次 |
| 可用内存 | `psutil.virtual_memory().available` | 控制面内存需求与容忍度 |
| 当前负载 | 采样 1/5/15 分钟负载或进程 CPU | 避免选到已被推理占满的机器 |
| 稳定性 | 在线时长 + 近期心跳丢失次数 | 移动端/休眠设备降权 |
| 网络位置 | 与多数节点的 RTT 中位数（tailnet 直连/中继） | 减少控制面延迟 |
| 角色约束 | 是否被运维显式钉为 `client`（opt-out） | 尊重人工意愿 |

**输出**：每个节点一个 `master_score`（浮点）+ `master_score_version`（评分算法版本，
避免不同版本节点互相比较）。评分**不参与数值面**，只影响排序。

**关键取舍**：评分是**启发式**，因此选举必须能容忍"选错"。为此 G2（可迁移）比"选得绝对准"更重要 ——
先保证能换，再逐步调准。

### 3.2 选举与续租（谁持有租约，谁是主）

复用既有的 `presence_generation` / `presence_lease_id` 思路，把它从"Android presence"扩展成
**主节点租约**：

1. 所有节点周期性广播 `NodePresence{node_id, master_score, epoch, lease_id, ttl}`（走现有 tailnet 发现通道）；
2. **租约持有者即主节点**。现任主节点在 TTL 内持续续租（心跳），并递增自己的 `generation`；
3. 若租约过期（主节点掉线/被分区），候选集中 **score 最高且在线时长足够的节点**发起竞选：
   广播 `ClaimMaster{node_id, score, proposed_epoch, lease_id}`；
4. 竞选采用**先到先得 + 退让规则**：收到更高 score 的合法 claim 时退让（避免同时宣告）；
5. 胜出者成为主节点，`epoch = max(seen_epoch) + 1`。

**防脑裂（G3，硬约束）**：任何**状态提交**（容量计划、层段合同、任务图、租约）都必须携带
`(epoch, lease_id)`；接收方**只接受严格大于**自己已见 epoch 的提交，且必须验证 `lease_id`
在当前租约窗口内有效。旧主即使仍在运行，其提交也会被拒绝 —— **fail-closed，不做"尽力合并"**。
这是本仓既有纪律的直接延续（错误码白名单化、判据 fail-closed）。

### 3.3 交接（handoff）

主节点迁移不是"重新开始"，要交接四类状态：

| 状态 | 交接方式 | 失败时的行为 |
| --- | --- | --- |
| 任务图（`TaskGraphCoordinator` 的在途任务与预约） | 增量快照 + 未完成任务的显式转移；接收方确认后才算完成 | 旧主在确认前**不释放**预约；超时则任务标记为 `handoff_timeout` 并如实上报 |
| 容量计划 / 层段分配（`pipeline_capacity` / `pipeline_reshard`） | 传 manifest（已是可序列化契约） | 新主重新求解，不猜测旧主状态 |
| 租约与预约（worker 预约、模型加载预约） | 按 `epoch` 转移；旧 epoch 的预约在新 epoch 下**默认失效** | 默认失效而非默认继承（避免幽灵预约占用算力） |
| presence / 心跳表 | 新主从自己的视角重建，旧主数据仅作参考 | 允许短期不一致，以心跳为准 |

**交接的原子性**：`epoch` 递增 + 状态 manifest 提交是一次**原子的 epoch 提交**（仓库已有
`pipeline_reshard` 的"epoch 原子提交"先例，可直接复用其模式）。

## 4. 分阶段

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| **P4.5.0 观测** | 只在 TUI 与日志里显示"如果现在选举，谁是主"（score 排序 + 假想 epoch），**不改变任何行为** | 一份"当前集群里主节点选错了多少次"的证据 |
| **P4.5.1 自选** | `NODE_ROLE=auto` 生效：按 §3.2 选主，但**不迁移**（只在原主消失时换） | 任意节点下线 → N 秒内出现新主 |
| **P4.5.2 迁移** | 更强的候选上线时主动交接（§3.3） | 交接后 epoch 递增、旧主写入被拒、任务不丢 |
| **P4.5.3 仲裁** | 引入多数派仲裁（quorum）或至少"人为分区时保守降级" | 网络分区下**无**双主提交 |

**顺序理由**：先观测（知道现状有多糟、避免凭感觉改），再自选（最小可用），再迁移（风险最高），
最后仲裁（成本最高、最容易过度设计）。

## 5. 验收判据（fail-closed）

1. **唯一性**：任意时刻，接受状态提交的节点数 ≤ 1；构造分区实验时，少数派一侧的提交必须被拒，
   并且**报错要进错误码白名单**（不得泄露内部异常）。
2. **迁移可观测**：每次主节点变化都有 `(old_epoch, new_epoch, reason)` 记录；无变化时不得产生噪声。
3. **任务不丢**：交接期间在途任务必须落到"完成 / 显式转移 / `handoff_timeout` 上报"三者之一，
   不得静默消失。
4. **数值透明（G4）**：迁移前后跑同一 prompt，per-token argmax 一致（沿用 P3/P4 的判据与记录 schema）。
5. **弱机不被选**：在给定集群里，主节点 score 必须 ≥ 所有在线节点 score 的中位数（否则判定"选错"）。

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 移动端（Android）休眠被误判为掉线 → 频繁换主 | 稳定性维度降权 + 任期最短存活时间（避免抖动）+ 交接需确认 |
| 低算力节点因心跳快而抢到主节点 | 主节点资格设**下限**（如 score ≥ 阈值），不足则从下一名顺延 |
| 交接期状态不一致导致幽灵预约占住算力 | **旧 epoch 的预约默认失效**（§3.3），宁可让用户重买一次算力 |
| 跨机推理正在进行时换主 | 只影响控制面：在途的层段接力按已签发的层段合同继续跑完；合同变更走下一轮 |
| 评分算法版本不一致导致排序无意义 | 记录 `master_score_version`；版本不一致时**按 node_id 字典序**保守裁决 |

## 7. 边界（不做的事）

- **不做**推理层的重排或重分片（那是 P2/pipeline_reshard 的职责）——P4.5 只换"谁在管"；
- **不做**跨 tailnet 的通用共识协议（不引入 Raft/Paxos 全套）：边缘集群规模小（个位数节点），
  租约 + epoch 足够，先要"不脑裂"，不要"强一致";
- **不做**自动跨节点权重分发（与既有裁决一致：不内网传权重）。
