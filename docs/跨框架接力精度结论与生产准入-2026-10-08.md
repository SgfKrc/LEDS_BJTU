# 跨框架接力：精度结论与生产准入（2026-10-08）

> 状态：**结论性**
>
> 适用范围：`XFRAME-1..6` 六票收敛后的**可执行结论** —— 跨框架层接力（PyTorch D→L ↔ llama.cpp/GGUF L→L）
> 的精度边界、推荐载体、必须退让的场景，以及对产品路径验收判据的约束。
> 机理与逐票证据见 `docs/跨框架接力数值差异机理-2026-10-05.md` 与
> `docs/分票规划-稳定分布式版本与架构泛用性后置-2026-10-04.md`（XFRAME 段）。

## 一句话结论

跨实现（PyTorch ↔ llama.cpp）之间的数值差异**不是工程 bug，而是 `float32` 加法非结合**的必然结果；
单层 GEMM 的下界为 `O(K·ε)`（`n_embd`=2048 时 `rel ≈ 3.5e-04`），**递推不会额外放大**（XFRAME-6）。
⇒ **"逐 token 与整模一致"不能作为跨框架接力的硬验收判据**；要严格一致必须让两侧**共享量化网格并整型累加**。

## 生产结论

### 1. 可证的精度边界

- **单层**：跨实现差异 `rel ≈ 3.5e-04`（f32、`n_embd`=2048）—— 这是**可证下界**，不是调参能消除的。
- **递推（多步 decode / 层段接力）**：差异**不放大**（XFRAME-6）⇒ 总差异 ≈ 每步 `O(K·ε)`，与步数无关。
- **是否分叉**：取决于 **`累计差异` 与 `argmax margin` 的比较**（XFRAME-3 已实测 margin 量级 0.32–9.6）。
  ⇒ 短序列（margin 充足）**全同**；长上下文逐步逼近 margin ⇒ 存在**必然分叉点**。

### 2. 推荐载体（按可用性排序）

1. **整型累加 + 两侧共享量化网格**（**推荐**，也是唯一"结构性消除"的路径）：
   整数加法满足结合律 ⇒ 归约顺序**不影响结果**；且 int8 相对 f32 把权重/激活压到 **约 1/4**
   ⇒ **容量反而下降**，与既有的"量化是容量旋钮"结论同向。已有端到端证据（XFRAME-3：8/8）。
2. **共享分块/线程策略**（两侧归约树完全一致）：理论差为 0，但需锁定两侧 SIMD 宽度与线程划分，
   对 llama.cpp/ggml 而言是**侵入式**改动 ⇒ 仅适合"成本可承担且要严格一致"的场景。
3. **float64 累加**：**仅作机理证明**。它不改变权重/激活/KV 的存储（累加器在寄存器/栈）⇒ 容量不变，
   代价是**吞吐**（SIMD 宽度减半、寄存器压力）且**必须两侧同改**（单侧改反而引入新的不一致）。

### 3. 必须退让的场景（不可消除）

- 两侧都用 f32 SIMD 且**不共享量化网格** ⇒ 差异 ≥ `O(K·ε)`，**无法保证逐 token 一致**；
- **长上下文 / 长生成**：累计差异逼近 margin ⇒ 存在必然分叉点（与"实现好坏"无关）；
- **低 margin 决策点**（近并列的 argmax）⇒ 一旦 `累计差异 > margin` 必分叉。

## 对产品路径的约束（验收判据）

1. **不得**把"与整模逐 token 完全一致"作为跨框架接力（D→L / L→L）的**硬验收判据**；
2. 应改为**行为等价 + 可证边界**：① 逐 token 一致**在其中 margin 充足的范围内**成立（实测 8/8、218/218）；
   ② 一旦分叉，必须能**归因到 margin**（而不是"实现不确定"）；
3. 若产品需要**严格一致**（例如可复现性要求）：必须走**载体 1**（量化网格 + 整型累加），
   并在**切点**处统一约定累加域与网格（层段传递的是 f32 hidden ⇒ 需在切点两侧显式量化/对齐）；
4. **层段接力的 hidden 传递**属于"每步一次"，其误差属 XFRAME-4 的 `O(K·ε)`，**不额外累积**（XFRAME-6）
   ⇒ 现有 D→L 接力设计**不需要**为"误差随层数/步数爆炸"担忧；需要关注的是**单步 margin**。

## 证据与复跑方式

| 目的 | 命令 |
|---|---|
| 逐层/跨引擎差异画像 | `python scripts/xframe_divergence_report.py --hf-dir models/qwen3-5-2b --layer-profile --layer-artifacts K:path …` |
| 只改归约语义（RMSNorm） | 同上加 `--hf-rmsnorm ggml-like` |
| 递推误差阶（XFRAME-6） | `python scripts/xframe6_recursion_report.py --hf-dir models/qwen3-5-2b --gen-steps 192` |
| **归约顺序下界 / 换累加数域（XFRAME-4/5）** | `python scripts/xframe_reduction_order_report.py --lib build/keephead/qlh_shared_rms_norm.dll` |
| 单测 | `tests/test_xframe_divergence_report.py`、`tests/test_xframe6_recursion_report.py`、`tests/test_xframe_reduction_order_report.py` |

**XFRAME-4/5 的复跑结果与"数字对不上"的正确理解（2026-10-08）**：工具跑 `order × K` 网格，实测
`f32` 下「只改归约顺序」的 `rel` 随 K 增长（K=128→8192：`4.37e-07 → 3.25e-06`），
而**换 f64 累加后全部为 `0.000e+00`** ⇒ 两条定性结论可复现。

⚠️ **绝对量级依赖数据与种子**（本工具 seed=1234、`M=8/N=64` 时 K=2048 为 `1.80e-06`；票面此前记的
`3.5e-04` 来自另一组输入形态/随机数据，两者相差约 200×）。**因此可复现、可用于判定的，是
「阶随 K 增长」与「f64 归零」这两条定性结论，而不是某个具体数字** —— 引用量级时必须同时给出
数据生成方式（seed + 形状 + 分布）。

产物落在 `build/keephead/`（gitignored）。

**工具自身的语义等价必须先自证**（本轮教训）：`--hf-rmsnorm ggml-like` 曾在 Qwen3.5 上连撞两个缺陷
（`Qwen3_5RMSNormGated` 两参签名、`Qwen3_5RMSNorm` 的 `1+weight` 权重语义），一度把**工具 bug**
误报成"一步内 token 分叉"。⇒ 任何数值对照结论都必须先证明对照工具与原实现**语义等价**。

## 未闭合项

- f64 档未在 `qwen3-5-2b` 上实操（本机内存不足：f64 需 ~16 GB，可用 ~6 GB）⇒ 用"同实例替换归约语义"
  等价构造对照；若将来有更大内存机器，可补一次 f64 整模对照；
- 量化网格路径（载体 1）在**层段接力**上的端到端验证尚未做（XFRAME-3 是整模级）；
- 长上下文分叉点：**已扫到 ~1050 位置**（2026-10-08，`--min-new-tokens 1024` 强制长度，三个 prompt）。
  结果：`argmax` **全同**（1050/1050、1050/1050、1048/1048），`rel_first ≈ 9.8e-08` 且
  `rel_last ≤ 2.4e-07`，回归斜率 ≈ ±3e-11 ⇒ **无额外累积、无分叉**。
  与更短长度点连成趋势（见下）说明 `tail/head` 随长度**下降**（越长越不累积）。
  **≥4k 仍待更大内存机器**（本机可用约 8 GB；已把逐位置内存从 GB 级降到 KB 级，但模型/激活本身受限）。
