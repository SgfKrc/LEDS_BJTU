## 1. 目标与结论

本计划面向远期的“下载即部署”体验：用户不再手工寻找文件名、拼接目录、复制 `.env` 或逐台设备同步模型。用户可以从受控目录选择模型，也可以填写 Hugging Face 仓库、GGUF 文件或本地路径；系统完成下载、检查、注册、设备匹配、分发、试加载、启用和回滚。

目标体验对标 Ollama，但不是简单包一层 Ollama：

1. 提供类似 `pull / create(import) / list / show / delete` 的稳定操作语义和可观察下载进度。
2. 支持 Hugging Face Safetensors/Transformers 仓库和 GGUF 文件，允许后续增加 ModelScope、Diffusers 与私有制品库适配器。
3. 为 QLH 的 PyTorch、llama.cpp、完整 Worker、任务链和后续图像 Worker 生成明确的部署计划。
4. 用户可以登记自己的 Tailscale 地址和主节点，设备首次接入不需要远端数据库密码。
5. 主节点本地数据库始终可用；远端 PostgreSQL 不可达时，模型管理、节点接入和本地推理不停止。
6. 相同模型名称不能代替相同工件身份。参与同一次 PyTorch 层流水线或 GGUF 执行池的节点必须使用完全一致的内容摘要。

核心架构结论：

- 模型权重使用**内容寻址工件库**，数据库只保存元数据、引用、任务和部署状态，不保存大文件。
- 主节点采用**本地 SQLite 事务库 + outbox** 作为控制面事实源，远端 PostgreSQL 是可选投影、查询库和备份目标，而不是推理执行前提。
- 下载、适配、部署和激活分为不同状态。下载成功不等于模型可加载，单机可加载也不等于可参加分布式推理。
- Tailscale 负责设备准入后的加密网络和稳定寻址；QLH 仍保留集群 ID、共享集群密钥、角色和模型摘要校验。

## 2. 为什么不能直接复制 Ollama

Ollama 已经验证了以下用户体验是合理的：

| Ollama 能力模式 | QLH 应吸收的设计 | QLH 额外要求 |
|---|---|---|
| pull 流式返回清单、分片、校验和完成状态 | 下载任务必须可查询、可取消、可恢复 | 下载后还需按节点能力生成部署计划 |
| create/import 接受 Safetensors、GGUF、adapter 与参数 | 本地导入和模型配方应成为一等对象 | 必须区分 PyTorch、GGUF、Diffusers 和分布式执行能力 |
| list/show/delete | 提供稳定的模型生命周期 API | show 必须包含来源 revision、摘要、部署节点和真实健康状态 |
| SHA256 blob 与 manifest | 相同内容只存一份，标签只引用摘要 | 分发到 Worker 后仍要逐文件和聚合摘要校验 |
| 模型名与 tag | 给用户保留易读别名和版本 | 调度不能只按别名，必须锁定不可变 artifact digest |

QLH 不在第一阶段追求与 Ollama API 字节级兼容。优先实现一致的用户体验和内部正确性；兼容 `/api/pull`、`/api/show`、`/api/tags` 等接口可以作为后续适配层，不能反向污染 QLH 的分布式部署契约。

## 3. 当前基础与真实缺口

### 3.1 可以复用的基础

| 现有模块 | 可复用能力 |
|---|---|
| `src/model_config.py` | 内置模型元数据、Hugging Face ID、模型类型和显存建议 |
| `src/model_sync.py` | 主节点模型 manifest、Range 断点续传、逐文件 SHA256、聚合摘要和目录镜像 |
| `src/model_downloader.py` | Hugging Face/ModelScope 下载引导与模型文件存在性检查 |
| `src/model_module.py`、`src/llama_engine.py` | PyTorch/Safetensors 与 llama.cpp/GGUF 的真实加载入口 |
| `src/bootstrap.py`、`src/node_config.py` | Tailscale 候选发现、首次接入、主节点地址和集群密钥持久化 |
| `src/task_journal.py` | 主节点本地 SQLite WAL、事件 ID、恢复和幂等边界的已有实践 |
| `control/` 模型注册域 | 用户模型 CRUD 与本地 JSON 原子写基础 |
| Android SAF/Room | Android 本地模型目录选择与本地持久化基础 |

### 3.2 不能误写为已完成的能力

- 当前下载器主要围绕 Qwen-1.8B 和固定文件名，不是通用模型中心。
- 当前注册表存在 Python `cluster_config`、TypeScript JSON 和内置 Python 列表多条路径，尚无统一事实源。
- 当前 `model_sync.py` 解决的是主节点向 PyTorch Worker 同步同一工件，不等于面向用户的 Hub 下载、许可证确认和多模型部署控制器。
- 当前数据库不可用时，部分域回退内存或 JSON；节点、模型、配置、下载任务和会话没有统一的本地事务语义。
- 当前从节点首次接入已具备 Tailscale 基础，但没有多集群档案、主节点端点编辑、连接测试和显式切换体验。
- 当前 GGUF 可以本地完整推理，但不能参加 PyTorch hidden-state 层流水线。
- 当前 SD 1.5 是独立侧车，不得被普通 LLM 目录扫描器误注册为文本模型。

### 3.3 与微服务改造的关系

本计划按目标拓扑设计，不继续扩写即将退役的旧控制面：

- `control-svc`：模型目录、下载任务、集群档案、本地数据库和远端同步。
- `scheduler-svc`：节点选择、模型放置计划、Worker 分发与参与证明。
- `inference-svc`：模型检查、试加载、引擎健康、预热、卸载和推理。
- `api-gateway`：对 PC/Android/TUI 提供稳定 API、SSE 进度和鉴权入口。

在[微服务架构改造计划](微服务架构改造计划.md)的清理门通过前，只做接口和数据模型设计，不把新能力同时实现到 Python 单体和 TypeScript 控制面两套事实源中。

## 4. 目标用户流程

### 4.1 添加集群

```text
打开“集群” -> 添加集群
  -> 输入档案名称
  -> 输入主节点 Tailscale IP 或 MagicDNS 名称
  -> 测试 /api/bootstrap/info
  -> 显示 cluster_id、主节点名、版本和证书/共享密钥状态
  -> 用户确认
  -> 完成 first-connect 并保存本机 cluster profile
```

“登记 Tailscale 地址”只登记已加入 tailnet 的 QLH 主节点端点，不调用 Tailscale 管理 API，也不替用户把设备加入 tailnet。

### 4.2 一键获取模型

```text
模型 -> 模型目录 -> 选择模型/量化档
  -> 展示许可证、来源、revision、下载大小和设备适配结论
  -> 用户确认
  -> 主节点下载到 staging
  -> 校验文件、摘要、格式和架构
  -> inference-svc 隔离试加载
  -> 注册不可变 artifact
  -> 生成部署计划
  -> 分发/预热选定节点
  -> 达到激活门后切换别名
```

### 4.3 用户自定义来源

支持三种输入：

1. Hugging Face 仓库：`repo_id + revision + 可选文件/量化档`。
2. GGUF：Hugging Face 仓库中的单个或分片 GGUF，或本地 GGUF 路径。
3. 本地目录：完整 Transformers/Safetensors 目录；后续支持 Diffusers pipeline、LoRA 和 ControlNet 专用入口。

用户必须先看到检查结果，再允许“部署”。未知架构、缺 tokenizer、缺 chat template、需要未批准远程代码或摘要不完整时，界面只能显示“待适配/不可部署”，不能盲目调用 loader。

## 5. 总体架构

```text
PC / Android / TUI
        |
        v
api-gateway
        |
        +--------------------+
        |                    |
        v                    v
control-svc             scheduler-svc
  Model Catalog            Placement Planner
  Pull Job                 Worker Distribution
  Artifact Registry        Activation / Rollback
  Cluster Profiles              |
  Local SQLite + Outbox          v
        |                   inference-svc / Worker
        |                     inspect / load / warmup
        v
optional PostgreSQL projection

Artifact bytes:
staging -> blobs/sha256/<digest> -> manifests/<model>/<tag>.json
```

职责必须保持单向：

- control-svc 决定“有哪些工件、任务和集群档案”。
- scheduler-svc 决定“哪些节点部署、哪些节点实际参与”。
- inference-svc 决定“该工件能否由指定引擎加载”。
- Worker 不访问远端 PostgreSQL，不保存数据库密码，也不自行从公开 Hub 选择模型版本。

Hugging Face 下载使用独立 `model-fetcher` 工具进程和专用工具环境，由 control-svc 通过结构化内部协议驱动。该环境只包含 `huggingface_hub`、Safetensors/GGUF 元数据工具和下载依赖，不导入或升级推理环境中的 PyTorch、Transformers、Diffusers、bitsandbytes；真正的 loader 验证仍由对应 runtime profile 的 inference-svc sidecar 完成。

## 6. 模型目录与工件身份

### 6.1 两层目录

模型目录分为两层：

| 层 | 内容 | 是否可变 |
|---|---|---|
| Curated Catalog | 项目维护的模型配方、来源、兼容性、许可证提示和推荐设备 | 可通过有版本的 catalog 更新 |
| User Registry | 用户实际导入的模型、别名、参数和部署策略 | 用户可增删；历史 artifact 不原地修改 |

目录条目不能直接指向“main 最新版”作为运行身份。解析下载前可以使用 branch/tag，下载完成后必须记录 Hub 返回的完整 commit revision 和 QLH 聚合 SHA256。

### 6.2 工件清单

建议 manifest：

```json
{
  "schema_version": 1,
  "artifact_id": "sha256:<aggregate_digest>",
  "source": {
    "provider": "huggingface",
    "repo_id": "Qwen/Qwen2.5-7B-Instruct",
    "requested_revision": "main",
    "resolved_revision": "<full_commit_hash>"
  },
  "format": "safetensors",
  "engine": "pytorch_transformers",
  "family": "qwen2",
  "files": [
    {"path": "config.json", "size": 0, "sha256": "..."}
  ],
  "capabilities": {
    "full_worker": true,
    "pytorch_layer_pipeline": false,
    "llama_cpp": false,
    "task_stage": true
  },
  "requirements": {
    "min_ram_bytes": 0,
    "min_vram_bytes": 0,
    "disk_bytes": 0,
    "runtime_profile": "llm-cuda-v1"
  },
  "license": {
    "id": "...",
    "acceptance_required": false
  }
}
```

manifest 还应记录 tokenizer、chat template、上下文上限、量化方式、分片关系、adapter/base 依赖、信任策略和适配器版本。不得把访问 token、集群密钥或数据库密码写入 manifest。

### 6.3 内容寻址存储

建议布局：

```text
<QLH_MODEL_STORE>/
  staging/<job_id>/
  blobs/sha256/<first-two>/<digest>
  manifests/<namespace>/<name>/<tag>.json
  deployments/<node_id>/<artifact_id>.json
  quarantine/<job_id>/
```

要求：

- 下载只写 staging；全部校验通过后用同一文件系统内原子 rename 提交。
- 相同 SHA256 blob 去重；删除别名只减少引用，垃圾回收另行执行。
- GC 不删除 active、rollback、正在分发或未完成 outbox 引用的工件。
- 模型目录必须位于本地文件系统。不要把 SQLite、staging 或活跃模型映射到 SMB/Tailscale 网络共享盘。
- 启动时扫描不直接信任文件名；先读 manifest，再核对实际文件摘要。

## 7. 下载与来源适配器

### 7.1 Hugging Face 适配器

使用 `huggingface_hub` 的结构化 API，不再拼接 shell 命令：

- `snapshot_download()`：下载完整 Transformers/Diffusers 仓库。
- `hf_hub_download()`：下载指定 GGUF、配置或 adapter 文件。
- `revision=<完整 commit>`：创建可复现工件。
- `allow_patterns` / `ignore_patterns`：避免把无关框架权重全部下载。
- dry-run：下载前计算实际缺失文件和空间需求。
- 独立 `cache_dir`：不得修改用户全局 `HF_HOME` 或项目全局 Python 解释器。

私有或 gated 仓库：

- 用户在本机完成授权并输入 token。
- token 存入操作系统凭据库；开发模式可使用进程环境变量。
- 数据库和日志只保存 credential reference，不保存 token 明文。
- 用户必须显式确认仓库许可证/访问条款；QLH 不绕过 gated model 审批。

### 7.2 GGUF 适配器

GGUF 不是“任意单文件都能跑”。适配器应解析：

- `general.architecture`、模型名称和参数量。
- `general.file_type` / quantization。
- tokenizer、chat template、context length 和 rope 参数。
- 分片编号与总数。
- 多模态 projector 或 adapter 依赖。

随后使用项目锁定 commit 的 llama.cpp 做 `load -> tokenize -> short generate -> unload` 冒烟。只有当前构建明确支持该 architecture，才标记 `llama_cpp=true`。

llama.cpp 的 `-hf` 能力可以作为调研和命令行兜底，但正式 QLH 部署仍应先落入自身内容寻址仓库，避免各 Worker 各自解析“latest”并得到不同工件。

### 7.3 Safetensors/Transformers 适配器

通用入口只负责读取 AutoConfig、tokenizer 和静态元数据；真正加载由 family adapter 决定：

| 适配等级 | 含义 |
|---|---|
| `catalog_verified` | 项目固定 revision 并完成真实加载/生成测试 |
| `family_supported` | 架构属于已支持 family，但该具体工件只完成静态检查 |
| `full_worker_only` | 可完整推理，不支持 PyTorch 层拆分 |
| `inspection_only` | 可识别，但尚不能部署 |
| `rejected` | 格式、依赖、远程代码或安全检查不通过 |

默认 `trust_remote_code=false`。确需远程代码的老模型只能使用经过项目审查、锁定 revision 和文件摘要的 curated recipe，并在隔离 sidecar 中运行；用户填写任意仓库时不得自动执行仓库 Python 文件。

### 7.4 第一批适配矩阵

| 模型族/格式 | 首期引擎 | 首期目标 | 分布式边界 |
|---|---|---|---|
| Qwen-1.8B Safetensors | PyTorch | 保持现有兼容、纳入统一 manifest | 层流水线需全节点同 digest |
| Qwen2.5 7B/14B Safetensors | PyTorch | 完整 Worker + family adapter | 层流水线另行真实准入 |
| DeepSeek-R1-Distill-Qwen 1.5B/7B/14B/32B | PyTorch | 完整 Worker + tokenizer/chat 检查 | 不因同属 Qwen 系自动宣称层拆分通过 |
| Qwen/DeepSeek GGUF | llama.cpp | PC/Android 完整推理 | 同一执行池使用相同 GGUF digest；不进入 PyTorch 层流水线 |
| 任意已支持 architecture 的 GGUF | llama.cpp | 静态检查 + 本机冒烟后注册 | 默认完整 Worker/任务 Stage |
| SD 1.5 Diffusers | diffusion sidecar | 保留独立图像模型入口 | 不进入 LLM 目录或文本模型切换器 |

后续增加 Llama、Mistral、Gemma、embedding、reranker 和多模态模型时，必须分别补 family adapter、固定工件和端到端测试；不能以 Transformers 能 `from_pretrained` 为由自动宣称全部模型受支持。

## 8. 一键部署状态机

### 8.1 下载任务状态

```text
created
  -> resolving
  -> awaiting_license
  -> downloading
  -> verifying
  -> inspecting
  -> smoke_loading
  -> registered
  -> planning
  -> distributing
  -> warming
  -> active
```

终止状态：`cancelled`、`rejected`、`failed`、`quarantined`、`rolled_back`。

每次状态转换写入本地事务库，并附 `job_id`、幂等键、错误码、当前字节数、总字节数和可重试标志。服务重启后从最后一个持久状态恢复；不能只把进度保存在进程内。

### 8.2 部署必须分两阶段

1. **Prepare**：Worker 下载/接收工件，校验摘要，检查磁盘/内存/引擎，完成隔离试加载。
2. **Activate**：达到部署策略要求后，由 scheduler 一次性切换 active artifact/alias epoch。

部分节点 prepare 失败时不得偷偷把任务标成 active。系统应展示：目标节点、已准备节点、失败节点、实际激活策略、是否回退主节点。

### 8.3 激活与回滚

- active alias 指向 `artifact_id + deployment_epoch`，不修改原工件。
- 保留上一版 rollback 指针，直到新版本通过健康窗口。
- 运行中请求继续使用创建时锁定的 artifact；新请求使用新 epoch。
- 分层流水线中任何节点缺少相同 digest 时，整条流水线不得启动。
- GGUF 完整 Worker 可以按任务重派，但结果统计必须记录实际执行节点和 artifact digest。

## 9. 设备匹配与放置策略

用户点击下载前，系统先给出部署建议：

| 输入 | 决策用途 |
|---|---|
| 模型格式、参数量、量化、上下文 | 估算 RAM/VRAM/磁盘和引擎 |
| 节点 CPU/GPU、显存、内存、平台 | 过滤不可部署节点 |
| runtime profile 与依赖版本 | 避免把 CUDA 模型部署到集显包，或把未支持 GGUF 发给旧 llama.cpp |
| 网络 RTT/吞吐和剩余磁盘 | 决定主节点转发、P2P/主节点分发和并发数 |
| 分布式能力声明 | 区分层流水线、完整 Worker、任务 Stage、TP 孤岛和图像 Worker |

首期使用确定性规则，不用不透明评分替代硬约束。评分只在全部硬门满足后排序：

```text
compatible = format && engine && memory && disk && runtime && policy
score = compute_score - transfer_cost - load_cost - current_pressure
```

部署计划必须允许用户选择：仅主节点、推荐节点、指定节点、整个兼容执行池。Android Lite 默认不接收模型；Android Full 只有用户启用本地模型后才进入 GGUF 候选。

## 10. Tailscale 集群档案与主节点登记

### 10.1 Cluster Profile

客户端本地保存多个集群档案：

```json
{
  "profile_id": "home-lab",
  "display_name": "家庭集群",
  "cluster_id": "qlh-...",
  "master_host": "qlh-master.tailnet-name.ts.net",
  "master_api_port": 8000,
  "master_tcp_port": 8888,
  "node_id": "client-...",
  "last_verified_at": "...",
  "last_successful_endpoint": "..."
}
```

共享集群密钥由现有安全存储层保存，不能出现在 profile 导出、日志或二维码明文中。若当前产品继续接受“已进入 tailnet 即已由网络所有者审核”的风险模型，则不增加逐设备人工审批；但集群 HMAC 仍用于防止端口误连和跨集群串线。

### 10.2 地址规则

- 接受 Tailscale IPv4/IPv6 和 MagicDNS/FQDN。
- 主节点设置中区分 `advertised_tailnet_endpoint` 与 LAN 候选地址。
- first-connect 返回经过验证的 canonical endpoint；客户端保存最近成功端点。
- 多个主节点候选时由用户明确选择，不自动加入第一个扫描结果。
- 不信任任意 `X-Forwarded-For`；反向代理必须显式配置可信代理。
- 主节点登记不等于备用主节点提升。角色切换仍需 cluster epoch/fencing。

### 10.3 不依赖远端数据库发现

发现顺序调整为：

1. 当前 cluster profile 的最近成功端点。
2. 用户输入或固定 `QLH_MASTER_HOST`。
3. Tailscale peer/MagicDNS 候选探测。
4. 可选的远端 PostgreSQL 目录查询。

远端数据库只能提供候选，不能覆盖已经通过 bootstrap 验证并保持 TCP 在线的主节点。数据库离线不得让 UI 同时显示“TCP 已连接”和“主节点离线”。

## 11. 主节点本地数据库与远端数据库降级

### 11.1 目标语义

远端 PostgreSQL 不可用时，主节点必须继续完成：

- 读取/保存集群设置和用户模型注册。
- 节点 bootstrap、节点目录和主节点自身身份恢复。
- 创建、恢复和取消模型下载任务。
- 保存 artifact、deployment、alias 和 rollback 状态。
- 本地会话、审查票和必要控制面事件持久化。
- 本地推理、完整 Worker 和任务图执行。

Worker 永远不直接访问远端 PostgreSQL。主节点通过 API/TCP 向 Worker 提供所需配置和工件身份。

### 11.2 推荐架构：local-first，不做双主数据库

```text
control-svc write
      |
      v
SQLite transaction: domain rows + outbox event
      |
      +--> immediate local read
      |
      `--> async projector --> PostgreSQL
```

选择 local-first 的原因：

- 如果正常时只写远端数据库，断线瞬间的本地库必然可能落后，自动切换会丢最近状态。
- SQLite 与业务进程同机，启动和恢复不依赖 DNS、Navicat 可达性或公网链路。
- outbox 把“本地业务提交”和“远端同步待办”放在同一事务，避免写一半。
- 远端 PostgreSQL 可以继续承担跨设备查询、备份、报表和后续灾备，但不阻断边缘执行。

这不是 SQLite/PostgreSQL 双主。远端库的 QLH 业务表在切换后只接受 projector 写入；通过 Navicat 直接修改业务行不保证被反向同步。确需外部修改时必须经过管理 API，或执行有审计的“导入远端变更”流程。

### 11.3 数据域划分

| 数据 | 本地 SQLite | 远端 PostgreSQL | 说明 |
|---|---|---|---|
| cluster/profile/settings | 权威 | 投影 | 配置带版本号 |
| nodes 与能力快照 | 权威持久快照 | 投影 | 高频 heartbeat 留内存，只周期落快照 |
| model catalog/registry/artifact | 权威元数据 | 投影 | 权重只在 artifact store |
| pull/deployment jobs | 权威 | 投影 | 支持重启恢复 |
| alias/activation/rollback | 权威 | 投影 | 需 epoch/fencing |
| task journal | 保持独立 SQLite journal | 只同步摘要 | 不把大 payload 写入控制库 |
| conversations/reviews | 权威或按用户策略保存 | 可选投影 | 遵守隐私开关 |
| secrets/tokens/passwords | 不保存明文 | 不保存明文 | 使用 OS credential store |

### 11.4 建议表

- `schema_migrations`
- `clusters`、`cluster_endpoints`
- `nodes`、`node_capability_snapshots`
- `model_catalog_entries`、`model_recipes`
- `artifacts`、`artifact_files`、`artifact_refs`
- `pull_jobs`、`pull_job_events`
- `deployments`、`deployment_targets`、`model_aliases`
- `settings`、`sessions`、`messages`、`review_tickets`
- `outbox_events`、`projection_checkpoints`

所有可同步实体使用稳定 UUID、`aggregate_version` 和 `updated_at`。outbox 使用全局唯一 `event_id`；PostgreSQL 以 `event_id` 去重，以 `aggregate_version` 拒绝旧事件覆盖新状态。

### 11.5 运行模式与健康状态

| 状态 | 含义 | 用户界面 |
|---|---|---|
| `local_only` | 未配置远端库 | 本地数据库正常；远端同步未配置 |
| `local_primary_synced` | 本地提交，远端投影已追平 | 正常 |
| `local_primary_pending` | 远端不可达或存在积压 | 本地正常；显示待同步事件数和最早积压时间 |
| `recovering_projection` | 远端恢复，正在幂等回放 | 本地正常；显示恢复进度 |
| `local_readonly` | 本地磁盘/SQLite 写入失败 | 明确故障；禁止需要持久化的变更，推理按既有模型受控继续 |

不能继续使用笼统的“数据库无法连接，只能使用内存模式”覆盖所有情况。远端同步失败和主节点本地持久化失败是两个严重程度完全不同的状态。

### 11.6 SQLite 约束

- 只允许 control-svc 成为控制数据库写者；其他服务走内部 API，避免 Python/Node 多进程争抢写锁。
- SQLite 驱动必须先完成 Windows/Linux 打包取舍：固定 Node 运行时支持时优先评估内置 `node:sqlite`，否则评估原生驱动；任何方案都必须通过 SEA/随包 Node、安装、升级和卸载冒烟后才能冻结。
- 启用 WAL、busy timeout、foreign keys 和固定迁移版本。
- 数据库位于本地文件系统，不放网络文件系统。
- 定期执行 `PRAGMA quick_check`，使用 SQLite backup API 创建轮换快照。
- 磁盘不足、只读目录、损坏和迁移失败必须 fail closed，不回退为无提示内存写。
- task journal 保持独立数据库和实例命名空间，避免控制面大事务拖慢任务提交。

### 11.7 主节点故障边界

本地数据库只解决“远端数据库断开”，不自动解决“主节点整机损坏”。在没有可靠状态复制前：

- `local_primary_pending` 状态下禁止自动提升备用主节点。
- 手工转移主节点前先导出签名快照或等待远端投影追平。
- 后续可增加主节点到备用主节点的加密快照复制，但不能把 SQLite 文件直接放到共享盘并双端打开。
- cluster epoch、master node ID 和 artifact alias epoch 必须一并转移，旧主节点恢复后不得继续接受写入。

## 13. 故障与恢复设计

| 故障 | 必须行为 |
|---|---|
| Hub/DNS/代理不可用 | 下载任务进入可重试状态，已激活模型继续运行 |
| 下载中断 | 使用来源 ETag/revision 与 partial 元数据续传；来源变化则重建 staging |
| SHA256 不匹配 | 移入 quarantine，不注册、不分发 |
| 文件名相同但内容变化 | 创建新 artifact，不覆盖旧 digest |
| 磁盘不足 | dry-run/配额阶段拒绝；不得下载到一半挤爆状态目录 |
| inference-svc 试加载崩溃 | sidecar 失败，主控制面继续运行；工件标记 load_failed |
| 某 Worker 分发失败 | 部署为 partial/failed；不伪报该节点参与 |
| 激活后健康失败 | alias epoch 回滚，运行中旧请求不被破坏 |
| 远端 PostgreSQL 不可达 | 本地事务继续，outbox 积压，UI 不阻塞 |
| 远端恢复 | 按 event_id 幂等回放，展示积压和冲突 |
| 本地 SQLite 不可写 | 控制面进入只读故障，禁止假成功 |
| 主节点重启 | 从 SQLite 恢复下载/部署状态，重新探测 Worker，不从进程内状态猜测 |
| Tailscale 地址改变 | profile 保留 cluster_id，重新验证 endpoint；不得创建重复集群 |
| 两个主节点同时出现 | cluster epoch/fencing 拒绝旧主写入和旧激活结果 |

## 14. 安全、许可证与供应链

- 默认只允许 HTTPS Hugging Face/ModelScope 官方端点和用户明确配置的私有镜像。
- 禁止任意 HTTP 重定向到本机、链路本地地址或受保护网段；主节点模型分发端点是单独的受信路径。
- 所有相对路径经过 traversal 检查；压缩包导入防止 Zip Slip、符号链接逃逸和超额展开。
- `trust_remote_code` 默认关闭；需要时必须是 curated、固定 revision、固定摘要和隔离运行。
- 下载 token、数据库密码和集群密钥不进入日志、manifest、SQLite/PostgreSQL 业务表或前端状态响应。
- 模型卡许可证、gated 状态和用户接受时间写入审计元数据；这不替代用户遵守模型许可证。
- 主节点向 Worker 分发时使用现有集群认证并增加请求签名、时间窗、artifact digest 和 Range 响应校验。
- 删除模型采用引用计数与延迟 GC；正在推理、回滚保留或任务 journal 引用的工件不可删除。

1. 下载进度和最终摘要可验证，失败不会覆盖当前模型。
2. 远端数据库不可用时，不出现启动长阻塞、内存假持久化或主节点误离线。
3. 主节点本地数据库重启恢复通过，且本地写失败会明确报错。
4. 分布式任务能证明实际参与节点和完全一致的 artifact digest。
5. 安装包不修改用户全局 Python、Hugging Face cache 或系统代理。
6. 私有 token、集群密钥和数据库密码不进入日志与导出文件。

## 18. 风险与止损

| 风险 | 对策/止损 |
|---|---|
| 试图支持任意 HF 模型导致适配无限膨胀 | 目录分级；未知模型只 inspection，不自动部署 |
| 双数据库冲突 | local-first + 单向 outbox；不支持 Navicat 直接双向写 |
| SQLite 多进程写锁 | control-svc 单写者，其他服务走 API |
| 大模型耗尽磁盘 | dry-run、配额、保留空间和引用安全 GC |
| Worker 重复下载占满出口 | 主节点缓存优先；后续评估 P2P，但以摘要为准 |
| 模型名相同内容不同 | 运行和调度只信 artifact digest |
| remote code 供应链风险 | 默认关闭；curated + revision + digest + sidecar |
| 自动主节点切换造成脑裂 | 本地投影未追平时禁止自动提升；cluster epoch fencing |
| 为兼容 Ollama 引入第二套存储 | 兼容 API 只映射现有 artifact/job，不复制 blob |

## 19. 推荐实施顺序

```text
微服务清理门
   -> M0 契约
   -> M1 本地事务数据库
   -> M2 工件库/导入
   -> M3 HF/GGUF 一键 pull
   -> M4 Tailscale 集群档案
   -> M5 跨节点部署
   -> M6 Ollama 类完整体验
   -> M7 扩展来源与模型族
```

M1 必须早于真正的一键下载任务：没有本地事务状态，下载中断、进程重启和远端数据库断线都会重新产生“表面有进度、实际不可恢复”的问题。M5 必须晚于真实 PC Worker 准入：模型分发成功不能替代推理链路正确性。

## 21. 本计划完成定义

只有同时满足以下条件，`L4-MODEL-FLEET` 才能由 Candidate 转为 Completed：

1. 空安装用户可以从目录或自定义 HF/GGUF 来源完成解析、下载、校验、试加载和首次推理。
2. 用户可以登记 Tailscale/MagicDNS 主节点，PC 与 Android 重启后自动恢复正确 cluster profile。
3. 远端 PostgreSQL 完全关闭时，主节点本地数据库可持续运行并在重启后恢复；远端恢复后投影幂等追平。
4. 两台真实 PC 完成至少一个 PyTorch 与一个 GGUF 工件的分发、激活、实际推理和回滚。
5. UI/TUI/API 的模型状态一致，且任务统计只显示真实参与节点。
6. 供应链、密钥、许可证、磁盘和故障注入发布门全部通过。
