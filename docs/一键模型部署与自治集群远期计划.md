## 1. 目标与结论

本计划面向远期的“下载即部署”体验：用户不再手工寻找文件名、拼接目录、复制 `.env` 或逐台设备同步模型。用户可以从受控目录选择模型，也可以填写 Hugging Face 仓库、GGUF 文件或本地路径；系统完成下载、检查、注册、设备匹配、分发、试加载、启用和回滚。

目标体验对标 Ollama，但不是简单包一层 Ollama：

1. 提供类似 `pull / create(import) / list / show / delete` 的稳定操作语义和可观察下载进度。
2. 支持 Hugging Face Safetensors/Transformers 仓库和 GGUF 文件，允许后续增加 ModelScope、Diffusers 与私有制品库适配器。
3. 为 QLH 的 PyTorch、llama.cpp、完整 Worker、任务链和后续图像 Worker 生成明确的部署计划。
4. 用户可以登记自己的 Tailscale 地址和主节点，设备首次接入不需要远端数据库密码。
5. **主节点 SQLite 是最终事实源**：干净安装、升级、模型管理、节点接入、本地推理和认证都能在没有远端数据库时完整运行。
6. 远端 PostgreSQL 只保留用户主动开启的兼容导出/迁移能力，不能成为 QLH 的运行前提；未来可以删除该依赖而不迁移用户资产到开发组。
7. 相同模型名称不能代替相同工件身份。参与同一次 PyTorch 层流水线或 GGUF 执行池的节点必须使用完全一致的内容摘要。

核心架构结论：

- 模型权重使用**内容寻址工件库**，数据库只保存元数据、引用、任务和部署状态，不保存大文件。
- 主节点采用**本地 SQLite 事务库**作为唯一控制面事实源；远端 PostgreSQL 降级为默认关闭的兼容导出/迁移层，既不是投影事实源，也不是备份前提。
- 下载、适配、部署和激活分为不同状态。下载成功不等于模型可加载，单机可加载也不等于可参加分布式推理。
- Tailscale 负责设备准入后的加密网络和稳定寻址；QLH 仍保留集群 ID、共享集群密钥、角色和模型摘要校验。
- QLH 登录采用主节点本地 Auth App/TOTP，不绑定 email；Tailscale 只用于 tailnet/用户/节点绑定和网络授权，不把 Tailscale 账号误写成 QLH 的通用身份提供方。
- 用户、TOTP 密钥、恢复码、Tailscale 绑定和认证审计均由用户自己的主节点管理，默认不进入开发组服务、公共账号目录或远端 PostgreSQL 投影。
- 用户自己的模型工件、adapter、配置、集群档案、任务记录、会话、认证数据和备份都属于用户自持资产；QLH 开发组不保留远端副本、不提供远程 reset，不影响上游模型许可证和第三方内容权利。

## 2. 为什么不能直接复制 Ollama

Ollama 已经验证了以下用户体验是合理的：

| Ollama 能力模式 | QLH 应吸收的设计 | QLH 额外要求 |
|---|---|---|
| pull 流式返回清单、分片、校验和完成状态 | 下载任务必须可查询、可取消、可恢复 | 下载后还需按节点能力生成部署计划 |
| create/import 接受 Safetensors、GGUF、adapter 与参数 | 本地导入和模型配方应成为一等对象 | 必须区分 PyTorch、GGUF、Diffusers 和分布式执行能力 |
| list/show/delete | 提供稳定的模型生命周期 API | show 必须包含来源 revision、摘要、部署节点和真实健康状态 |
| SHA256 blob 与 manifest | 相同内容只存一份，标签只引用摘要 | 分发到 Worker 后仍要逐文件和聚合摘要校验 |
| 模型名与 tag | 给用户保留易读别名和版本 | 调度不能只按别名，必须锁定不可变 artifact digest |

QLH 不在第一阶段追求与 Ollama API 字节级兼容。优先实现一致的用户体验和内部正确性；兼容 `/api/pull`、`/api/show`、`/api/tags` 等接口可以作为后续适配层，不能反向污染 QLH 的分布式部署契约。

## 3. 当前基础与真实缺口

### 3.1 可以复用的基础

| 现有模块 | 可复用能力 |
|---|---|
| `src/model_config.py` | 内置模型元数据、Hugging Face ID、模型类型和显存建议 |
| `src/model_sync.py` | 主节点模型 manifest、Range 断点续传、逐文件 SHA256、聚合摘要和目录镜像 |
| `src/model_downloader.py` | Hugging Face/ModelScope 下载引导与模型文件存在性检查 |
| `src/model_module.py`、`src/llama_engine.py` | PyTorch/Safetensors 与 llama.cpp/GGUF 的真实加载入口 |
| `src/bootstrap.py`、`src/node_config.py` | Tailscale 候选发现、首次接入、主节点地址和集群密钥持久化 |
| `src/task_journal.py` | 主节点本地 SQLite WAL、事件 ID、恢复和幂等边界的已有实践 |
| `control/` 模型注册域 | 用户模型 CRUD 与本地 JSON 原子写基础 |
| Android SAF/Room | Android 本地模型目录选择与本地持久化基础 |

### 3.2 不能误写为已完成的能力

- 当前下载器主要围绕 Qwen-1.8B 和固定文件名，不是通用模型中心。
- 当前注册表存在 Python `cluster_config`、TypeScript JSON 和内置 Python 列表多条路径，尚无统一事实源。
- 当前 `model_sync.py` 解决的是主节点向 PyTorch Worker 同步同一工件，不等于面向用户的 Hub 下载、许可证确认和多模型部署控制器。
- 当前数据库不可用时，部分域回退内存或 JSON；节点、模型、配置、下载任务和会话没有统一的本地事务语义。
- 当前从节点首次接入已具备 Tailscale 基础，但没有多集群档案、主节点端点编辑、连接测试和显式切换体验。
- 当前 GGUF 可以本地完整推理，但不能参加 PyTorch hidden-state 层流水线。
- 当前 SD 1.5 是独立侧车，不得被普通 LLM 目录扫描器误注册为文本模型。

### 3.3 与微服务改造的关系

本计划按目标拓扑设计，不继续扩写即将退役的旧控制面：

- `control-svc`：模型目录、下载任务、集群档案、本地数据库和远端同步。
- `scheduler-svc`：节点选择、模型放置计划、Worker 分发与参与证明。
- `inference-svc`：模型检查、试加载、引擎健康、预热、卸载和推理。
- `api-gateway`：对 PC/Android/TUI 提供稳定 API、SSE 进度和鉴权入口。

在[微服务架构改造计划](微服务架构改造计划.md)的清理门通过前，只做接口和数据模型设计，不把新能力同时实现到 Python 单体和 TypeScript 控制面两套事实源中。

## 4. 目标用户流程

### 4.1 添加集群

```text
打开“集群” -> 添加集群
  -> 输入档案名称
  -> 输入主节点 Tailscale IP 或 MagicDNS 名称
  -> 测试 /api/bootstrap/info
  -> 显示 cluster_id、主节点名、版本和证书/共享密钥状态
  -> 用户确认
  -> 完成 first-connect 并保存本机 cluster profile
```

“登记 Tailscale 地址”只登记已加入 tailnet 的 QLH 主节点端点，不调用 Tailscale 管理 API，也不替用户把设备加入 tailnet。

### 4.1A 首次登录、Auth App 注册与 Tailscale 绑定

QLH 的本地登录和 Tailscale 的网络身份必须分开。Tailscale 官方明确说明其自身不是身份提供方、没有 Tailscale 密码；因此“已有 Tailscale 账号能登录 QLH”在本计划中解释为完成 Tailscale 授权/绑定后进入 QLH，QLH 的会话认证仍由 Auth App/TOTP 完成，不收集 Tailscale 或第三方 IdP 密码。

```text
首次打开主节点
  -> 在本机创建 owner 用户（用户名/显示名即可，不要求 email）
  -> 生成一次性 TOTP 密钥：Base32 字符串 + otpauth:// URI + 二维码
  -> 用户用 Aegis 或其他兼容 Auth App 扫码/手工录入
  -> 输入首个 6 位验证码确认，随后显示一次性恢复码
  -> 选择“已有 Tailscale”或“创建 Tailscale tailnet”
       已有：打开官方登录/授权页或本机 tailscale up，用户用自己的 IdP/passkey 完成认证
       没有：跳转官方 Get Started/注册流程，完成后回到 QLH
  -> QLH 读取本机 Tailscale 状态，或在可选 OAuth 授权路径拿到一次性设备授权
  -> 绑定 tailnet_id + tailscale_user_id + 绑定节点 ID，完成本地用户创建
```

Tailscale 的 `loginName` 可能是 emailish 字符串，只作展示和诊断，不作 QLH 主键；绑定主键使用 Tailscale API 的稳定 `user.id` 与 `tailnetId`。QLH 不为用户代注册第三方 IdP，也不代管 Tailscale 账号。

### 4.1B 用户更换 tailnet

更换网络必须由当前用户在主节点发起，并用当前 TOTP 或恢复码重新认证。主节点先建立 `pending` 新绑定，要求用户在新的 tailnet 完成官方授权，再原子地撤销旧 token/节点授权、切换 `active_binding` 并记录审计事件；新授权失败时保留旧绑定，不进入半切换状态。历史绑定只保留不可用的审计摘要，不允许旧 tailnet 继续访问 QLH。

### 4.2 一键获取模型

一键部署的模型**地址与源由开发团队提供默认源**（随发布版本内置的源清单 + curated recipe，见 §7.1），用户零配置即可使用；也**允许用户自己更换源**（见 §4.3）。

```text
模型 -> 模型目录 -> 选择模型/量化档
  -> 展示默认源（开发团队 curated recipe：endpoint、来源、revision、许可证）
  -> 展示下载大小和设备适配结论
  -> 用户确认（或更换源后重新 resolve 再确认）
  -> 主节点下载到 staging
  -> 校验文件、摘要、格式和架构
  -> inference-svc 隔离试加载
  -> 注册不可变 artifact
  -> 生成部署计划
  -> 分发/预热选定节点
  -> 达到激活门后切换别名
```

默认源由开发团队提供并随版本更新，包含：

- 默认 endpoint（Hugging Face / ModelScope 官方地址与可配置镜像回退）；
- 固定 revision 的 curated recipes（Qwen/DeepSeek 等，见 §7.5）；
- 许可证、gated 状态与设备适配提示。

用户更换源后，下载前展示的 source 以实际使用的源为准，并在 manifest 中记录（§6.2）。

### 4.3 用户自定义来源与更换源

支持三种输入：

1. Hugging Face 仓库：`repo_id + revision + 可选文件/量化档`。
2. GGUF：Hugging Face 仓库中的单个或分片 GGUF，或本地 GGUF 路径。
3. 本地目录：完整 Transformers/Safetensors 目录；后续支持 Diffusers pipeline、LoRA 和 ControlNet 专用入口。

除输入自定义仓库外，用户还可以**更换下载源**（端到端配置见 §7.1）：

- 在“源管理”中新增/编辑/禁用源（endpoint base URL、token、优先级），默认源清单由开发团队提供，可一键恢复出厂；
- 更换源后必须**重新 resolve 并锁定新源返回的 commit revision**，不得跨源沿用旧摘要或旧 manifest；
- 下载前界面展示当前实际使用的源与 endpoint，用户必须先看到检查结果，再允许“部署”。

未知架构、缺 tokenizer、缺 chat template、需要未批准远程代码或摘要不完整时，界面只能显示“待适配/不可部署”，不能盲目调用 loader。

## 5. 总体架构

```text
PC / Android / TUI
        |
        v
api-gateway
        |
        +--------------------+
        |                    |
        v                    v
control-svc             scheduler-svc
  Model Catalog            Placement Planner
  Pull Job                 Worker Distribution
  Artifact Registry        Activation / Rollback
  Cluster Profiles              |
  Local SQLite + Outbox          v
        |                   inference-svc / Worker
        |                     inspect / load / warmup
        v
optional PostgreSQL projection

Artifact bytes:
staging -> blobs/sha256/<digest> -> manifests/<model>/<tag>.json
```

职责必须保持单向：

- control-svc 决定“有哪些工件、任务和集群档案”。
- scheduler-svc 决定“哪些节点部署、哪些节点实际参与”。
- inference-svc 决定“该工件能否由指定引擎加载”。
- Worker 不访问远端 PostgreSQL，不保存数据库密码，也不自行从公开 Hub 选择模型版本。

Hugging Face 下载使用独立 `model-fetcher` 工具进程和专用工具环境，由 control-svc 通过结构化内部协议驱动。该环境只包含 `huggingface_hub`、Safetensors/GGUF 元数据工具和下载依赖，不导入或升级推理环境中的 PyTorch、Transformers、Diffusers、bitsandbytes；真正的 loader 验证仍由对应 runtime profile 的 inference-svc sidecar 完成。

## 6. 模型目录与工件身份

### 6.1 两层目录

模型目录分为两层：

| 层 | 内容 | 是否可变 |
|---|---|---|
| Curated Catalog | 项目维护的模型配方、来源、兼容性、许可证提示和推荐设备；每个 recipe 绑定**开发团队默认源**（endpoint + 固定 revision），随发布版本更新 | 可通过有版本的 catalog 更新 |
| User Registry | 用户实际导入的模型、别名、参数和部署策略；条目可**更换源**（默认源 → 用户自定义源），历史 artifact 不原地修改 | 用户可增删；历史 artifact 不原地修改 |

目录条目不能直接指向“main 最新版”作为运行身份。解析下载前可以使用 branch/tag，下载完成后必须记录 Hub 返回的完整 commit revision 和 QLH 聚合 SHA256。

### 6.2 工件清单

建议 manifest：

```json
{
  "schema_version": 1,
  "artifact_id": "sha256:<aggregate_digest>",
  "source": {
    "provider": "huggingface",
    "repo_id": "Qwen/Qwen2.5-7B-Instruct",
    "requested_revision": "main",
    "resolved_revision": "<full_commit_hash>"
  },
  "format": "safetensors",
  "engine": "pytorch_transformers",
  "family": "qwen2",
  "files": [
    {"path": "config.json", "size": 0, "sha256": "..."}
  ],
  "capabilities": {
    "full_worker": true,
    "pytorch_layer_pipeline": false,
    "llama_cpp": false,
    "task_stage": true
  },
  "requirements": {
    "min_ram_bytes": 0,
    "min_vram_bytes": 0,
    "disk_bytes": 0,
    "runtime_profile": "llm-cuda-v1"
  },
  "license": {
    "id": "...",
    "acceptance_required": false
  }
}
```

manifest 还应记录 tokenizer、chat template、上下文上限、量化方式、分片关系、adapter/base 依赖、信任策略和适配器版本。不得把访问 token、集群密钥或数据库密码写入 manifest。

### 6.3 内容寻址存储

建议布局：

```text
<QLH_MODEL_STORE>/
  staging/<job_id>/
  blobs/sha256/<first-two>/<digest>
  manifests/<namespace>/<name>/<tag>.json
  deployments/<node_id>/<artifact_id>.json
  quarantine/<job_id>/
```

要求：

- 下载只写 staging；全部校验通过后用同一文件系统内原子 rename 提交。
- 相同 SHA256 blob 去重；删除别名只减少引用，垃圾回收另行执行。
- GC 不删除 active、rollback、正在分发或未完成 outbox 引用的工件。
- 模型目录必须位于本地文件系统。不要把 SQLite、staging 或活跃模型映射到 SMB/Tailscale 网络共享盘。
- 启动时扫描不直接信任文件名；先读 manifest，再核对实际文件摘要。

## 7. 下载与来源适配器

### 7.1 来源配置：开发团队默认源与用户更换源

**默认源由开发团队提供**，随发布版本内置，保证用户开箱即用的一键部署：

- **默认源清单**：每个发布版本内置 `sources.json` 之类的源清单，至少包含 Hugging Face 官方（`https://huggingface.co`）、ModelScope（`https://modelscope.cn`）以及可选的国内镜像回退（如 `https://hf-mirror.com`）；解析器/下载器通过注入 endpoint 使用当前源。模型网络层按 `QLH_HTTP_PROXY > 用户持久化配置 > 直连` 选择代理，不沿用或修改 `HF_ENDPOINT`、系统代理和全局 Hugging Face 配置。
- **默认源优先级**：同一模型可配置多源回退顺序（如官方源 → 镜像源），源不可用时按优先级自动回退；回退后必须重新 resolve，锁定回退源返回的 revision。
- **curated recipes 绑定默认源**：recipe 固定绑定开发团队默认源与固定 revision（见 §7.5 与 `control/src/data/curated-catalog.ts`），解析/下载全程可复现，用户无需填写任何地址即可一键部署。

**用户允许自己更换源**：

- **源管理**：设置中提供“源管理”（新增/编辑/禁用源），每个源包含：名称、endpoint base URL、访问 token（凭据库引用，不落库不落日志）、优先级、启用状态；用户可将任一源设为当前默认源，也可一键恢复开发团队默认源。
- **更换源流程**：更换源后，该源下的一键部署必须重新执行 resolve（dry-run）→ 展示新源返回的 revision/文件清单/大小 → 用户确认 → 下载；**不得跨源沿用旧 digest、旧 manifest 或旧 staging 文件**，manifest 的 `source` 记录实际使用的 provider/endpoint/revision（§6.2）。
- **约束**：更换源只改变“从哪里取”，不改变校验、试加载、注册与分发流程；自定义源与默认源走同一套准入（未知架构 fail-closed，`trust_remote_code` 恒 false）。

### 7.2 Hugging Face 适配器

使用 `huggingface_hub` 的结构化 API，不再拼接 shell 命令：

- `snapshot_download()`：下载完整 Transformers/Diffusers 仓库。
- `hf_hub_download()`：下载指定 GGUF、配置或 adapter 文件。
- `revision=<完整 commit>`：创建可复现工件。
- `allow_patterns` / `ignore_patterns`：避免把无关框架权重全部下载。
- dry-run：下载前计算实际缺失文件和空间需求。
- 独立 `cache_dir`：不得修改用户全局 `HF_HOME` 或项目全局 Python 解释器。

私有或 gated 仓库：

- 用户在本机完成授权并输入 token。
- token 存入操作系统凭据库；开发模式可使用进程环境变量。
- 数据库和日志只保存 credential reference，不保存 token 明文。
- 用户必须显式确认仓库许可证/访问条款；QLH 不绕过 gated model 审批。

### 7.3 GGUF 适配器

GGUF 不是“任意单文件都能跑”。适配器应解析：

- `general.architecture`、模型名称和参数量。
- `general.file_type` / quantization。
- tokenizer、chat template、context length 和 rope 参数。
- 分片编号与总数。
- 多模态 projector 或 adapter 依赖。

随后使用项目锁定 commit 的 llama.cpp 做 `load -> tokenize -> short generate -> unload` 冒烟。只有当前构建明确支持该 architecture，才标记 `llama_cpp=true`。

llama.cpp 的 `-hf` 能力可以作为调研和命令行兜底，但正式 QLH 部署仍应先落入自身内容寻址仓库，避免各 Worker 各自解析“latest”并得到不同工件。

### 7.4 Safetensors/Transformers 适配器

通用入口只负责读取 AutoConfig、tokenizer 和静态元数据；真正加载由 family adapter 决定：

| 适配等级 | 含义 |
|---|---|
| `catalog_verified` | 项目固定 revision 并完成真实加载/生成测试 |
| `family_supported` | 架构属于已支持 family，但该具体工件只完成静态检查 |
| `full_worker_only` | 可完整推理，不支持 PyTorch 层拆分 |
| `inspection_only` | 可识别，但尚不能部署 |
| `rejected` | 格式、依赖、远程代码或安全检查不通过 |

默认 `trust_remote_code=false`。确需远程代码的老模型只能使用经过项目审查、锁定 revision 和文件摘要的 curated recipe，并在隔离 sidecar 中运行；用户填写任意仓库时不得自动执行仓库 Python 文件。

### 7.5 第一批适配矩阵

| 模型族/格式 | 首期引擎 | 首期目标 | 分布式边界 |
|---|---|---|---|
| Qwen-1.8B Safetensors | PyTorch | 保持现有兼容、纳入统一 manifest | 层流水线需全节点同 digest |
| Qwen2.5 7B/14B Safetensors | PyTorch | 完整 Worker + family adapter | 层流水线另行真实准入 |
| DeepSeek-R1-Distill-Qwen 1.5B/7B/14B/32B | PyTorch | 完整 Worker + tokenizer/chat 检查 | 不因同属 Qwen 系自动宣称层拆分通过 |
| Qwen/DeepSeek GGUF | llama.cpp | PC/Android 完整推理 | 同一执行池使用相同 GGUF digest；不进入 PyTorch 层流水线 |
| 任意已支持 architecture 的 GGUF | llama.cpp | 静态检查 + 本机冒烟后注册 | 默认完整 Worker/任务 Stage |
| SD 1.5 Diffusers | diffusion sidecar | 保留独立图像模型入口 | 不进入 LLM 目录或文本模型切换器 |

后续增加 Llama、Mistral、Gemma、embedding、reranker 和多模态模型时，必须分别补 family adapter、固定工件和端到端测试；不能以 Transformers 能 `from_pretrained` 为由自动宣称全部模型受支持。

### 7.6 NVIDIA UVM、显存分页与主动预取调研（2026-08-09）

**结论：主动预取值得做，但当前 Windows 产品路线不应以 UVM 实现。** 对本项目当前 RTX 4060 Laptop 8 GB / Windows WDDM 环境，UVM 超额订阅是硬性 `No-Go`。MF-MEM-N1 已证明 pinned host memory + `cudaMemcpyAsync` 的 raw transport 明显优于 pageable，但 WDDM 下双/三槽 event 排程未形成足以抵消长尾的吞吐收益；下一步只允许 64 MiB、双槽、隔离 sidecar 的条件验证，三槽冻结。原生 Linux 上的 UVM 主动预取保留为限时 `Conditional Go`，没有数据前不得设为默认 allocator。

| 路线 | 当前决策 | 原因 |
|---|---|---|
| Windows WDDM `cudaMallocManaged` 超额订阅 | `No-Go` | 本机 `managedMemory=1`，但 `concurrentManagedAccess=0`；CUDA 12.6 规定 GPU oversubscription、GPU 目标 `cudaMemPrefetchAsync`、`SetPreferredLocation(GPU)` 和 `SetAccessedBy(GPU)` 均要求该属性非零 |
| WSL 2 UVM | `No-Go` | NVIDIA 明确说明 WSL 2 不提供 Full Managed Memory、并发 CPU/GPU access 不受支持，可能出现高系统内存占用和性能下降；不能把 WSL 当成绕开 WDDM 的 UVM 路径 |
| Windows 显式 pinned-memory 分层 pager | `Conditional Go（N2 隔离侧车）` | pinned raw H2D/D2H 已证明；双槽 pipeline 吞吐只提升 0.56%-1.02% 且 P95 stall 约为单槽 1.85-1.98 倍，因此先验证容量和真实层执行，不设为默认 |
| Windows 三槽 pager | `No-Go（冻结）` | 相对单槽 pipeline 为 -0.88%-+1.20%，P95 stall 达 2.72-2.97 倍，且 pinned/VRAM 固定池扩大到三倍 |
| 原生 Linux UVM demand paging | `No-Go（只作负对照）` | PyTorch 2.13 官方不建议 DL 工作负载使用 UVM；显存饱和后会先逐出到 CPU、再搬入新页，形成昂贵双向传输和长尾停顿 |
| 原生 Linux UVM + 主动预取 | `Conditional Go（限时 PoC）` | 仅在 `concurrentManagedAccess=1`、32 GB+ RAM、固定模型和 Nsight 证据齐备时评估；必须胜过或接近显式 pager，否则冻结 |
| KV cache host offload / paged attention | `独立候选` | KV 的生命周期、复用和逐请求淘汰与只读权重不同；先采用块级显式管理，不把 KV 与权重一起交给 UVM |

#### 7.6.1 本机事实与容量下界

本轮只做只读能力探测和临时内存微基准，不修改源码：

- GPU：`NVIDIA GeForce RTX 4060 Laptop GPU`，compute capability 8.9，物理显存 8,585,216,000 bytes（`nvidia-smi` 显示 8,188 MiB），驱动模式 `WDDM`；PyTorch 2.13.0+cu126 使用 CUDA Runtime 12.6。
- CUDA 属性：`managedMemory=1`、`pageableMemoryAccess=0`、`concurrentManagedAccess=0`、`pageableMemoryAccessUsesHostPageTables=0`、`directManagedMemAccessFromHost=0`。因此“能分配 Managed Memory”不等于“能按需分页或超额订阅”。
- 4 MiB `cudaMallocManaged` 临时分配成功；对 GPU 0 调用 `cudaMemPrefetchAsync` 和 `cudaMemAdviseSetPreferredLocation` 均返回 `cudaErrorInvalidDevice (101)`，与 Runtime API 的属性前置一致。
- 系统 RAM 总计 16,782,925,824 bytes，本轮探测时空闲约 5.42 GB。Windows pagefile 不能替代 pinned/managed RAM：换页会叠加磁盘长尾，且 WDDM UVM 本身不允许超过物理显存。
- 256 MiB pinned buffer、12 轮临时拷贝的单次本机测量为 H2D 12.142 GB/s、D2H 13.033 GB/s。按此计算，每 token 每新增 1 GiB 冷权重至少增加约 88 ms H2D 下界；若发生 UVM 逐出再搬入，互连流量与停顿还会更高。7B BF16 若每 token 需要搬运约 14 GB 权重，仅 H2D 理论下界就约 1.15 s，尚未包含计算、映射、kernel、KV 和调度。

UVM 不增加物理总容量，只统一地址和迁移机制。当前 16 GB RAM + 8 GB VRAM 也不足以把 7B BF16、OS、CUDA context、KV cache 和临时张量作为安全常驻组合；7B BF16/14B UVM 真模型基准必须使用 32 GB+ RAM 的原生 Linux 主机。当前 Windows 可先用合成只读层、7B INT8/NF4 或 14B NF4 做显式 pager 容量/时延验证。

#### 7.6.2 API 语义与不能混淆的边界

| API / hint | 实际作用 | 本项目约束 |
|---|---|---|
| `cudaMemAdviseSetReadMostly` | 允许处理器建立只读副本；写入会使其他副本失效 | 只适用于冻结权重；KV cache、activation、量化临时 buffer 不设置 |
| `cudaMemAdviseSetPreferredLocation` | 只给迁移策略一个偏好，不立即迁移；GPU preferred 要求 `concurrentManagedAccess=1` | 不对全模型设 GPU preferred；官方说明该 hint 可能覆盖防抖策略并导致页面持续 thrash |
| `cudaMemAdviseSetAccessedBy` | 预建页表映射、减少首次 fault，不决定物理驻留，也不搬数据 | 可与 CPU preferred 组合做 Linux zero-copy/冷层负对照；不能冒充 prefetch |
| `cudaMemPrefetchAsync` | stream-ordered 地请求将范围迁往 CPU/GPU；后续同 stream 操作会等待其完成 | 只在 capability gate 通过后使用；下一层在 copy stream 预取，compute stream 用 event 等待，不依赖首次 kernel fault |
| `cudaMemcpyAsync` + pinned host memory | 显式维护 host/device buffer 并调用 copy engine | 当前 Windows 主路线；实现较繁琐，但数据移动、双缓冲和失败点最可控 |
| PyTorch `CUDAPluggableAllocator` / `torch.cuda.MemPool` | 可在 C/C++ allocator 与局部 memory pool 中尝试不同 CUDA 分配器 | 不全局替换现有 caching allocator；UVM 只在隔离 sidecar 和选定权重 pool 内实验 |

主动预取只能去掉 GPU 缺页处理、重复 fault、页表更新和不可预测调度的一部分开销，**不能消除 PCIe 必须搬运的权重字节**。NVIDIA 的连续访问实验中，on-demand migration 在 PCIe 上约 5.4 GB/s，预取约 10.9 GB/s，显式 copy 约 11.4 GB/s；另一组 oversubscription 实验显示结果会随平台、超订比例和访问模式相差最高 100 倍，随机访问在 x86 fault-driven 路径可跌到数百 KB/s。对顺序 Transformer 层，预取有机会接近 bulk copy；对 batch=1 自回归 decode，每层计算通常不足以完全掩盖搬运，DeepSpeed ZeRO-Inference 的短序列实验也未观察到 CPU offload prefetch 收益。

#### 7.6.3 首期 pager 设计边界

首期只分页**不可变权重**，不分页 KV cache、activation、CUDA graph workspace 和量化 scratch：

```text
CPU pinned / managed read-only layer store
        |
        | copy/prefetch stream: layer i+1
        v
GPU slot A/B  <---- event ---->  compute stream: layer i
        |
        +---- release/discard previous layer only after last-use event
```

1. 启动时冻结层顺序、每层字节数、不可拆模块、常驻热模块和 GPU budget；embedding、首尾层、lm_head、KV/activation 优先留在 GPU。
2. 首期显式 pager 只使用 2 个固定 device slot 和 64 MiB tile；host staging 必须 pinned，并由有界预取队列填充下一 tile，再以独立 copy stream 发起 H2D。只有对应 event 完成后 compute stream 才能执行；三槽除非新证据推翻 N1 长尾结论，否则不得恢复。N2 侧车已实现该队列，但 WDDM overlap 仍为 0%，因此只证明生命周期/正确性，不提升为默认吞吐策略。
3. Linux UVM 变体按层或连续 tile 建立 managed range：冻结权重设 `ReadMostly`，冷层以 CPU preferred + GPU `AccessedBy` 做 zero-copy 负对照，工作层用 `PrefetchAsync` 主动迁移。不得给全模型设置 GPU preferred。
4. 不在 forward 中静默切换策略。runtime profile 必须显式为 `resident`、`accelerate_auto`、`explicit_layer_pager`、`uvm_prefetch` 或 `uvm_demand_negative_control`；manifest/runtime record 写入 OS、driver mode、CUDA 属性、tile 大小、prefetch distance 和 host/device budget。
5. 任一 capability 不满足时排队前返回 `resource_rejected/unsupported_runtime_profile`；Windows/WSL 不能偷偷退回 demand paging。

**N2F 真实固定 tile 证据（2026-08-09）**：`scripts/model_fleet_n2r_compare.py` 的 `explicit-layer-pager-64` 使用 64 MiB host/device tile、2 个槽位，输出落在 `build/experiments/mf-mem-n2f-fixed-tile-20260809-v1/summary.json`，计划 `3/3 passed`。ctx128 完整生成 1 token 时 28 层 page-in/out 各 28 次、bridge 336 个分块、H2D/D2H 各 3.039 GiB；ctx128 与 ctx8192 均在 `cancel_after_layer=1` 后完成首层回收并返回 `cancelled=1`。补充输出 32/128 token 均完成，tok/s 分别为 0.293/0.297，128 token 约 431.7 s，层迁移分别约 104.4/417.7 GB（H2D 与 D2H 各计一次）。桥接器峰值模块为 116.5 MiB，VRAM allocated/reserved 约 2.75/5.63 GiB；因此 64 MiB 是单次搬运上限，不是完整模型显存上限，也没有形成吞吐优化结论。新增 `tests/test_model_fleet_n2f_fixed_tile.py` 与 N2R 回归共 9/9，未接生产 runtime；下一票为 N2P 预取/重叠和延迟决策。

**N2P 真实预取/延迟证据（2026-08-09）**：`build/experiments/mf-mem-n2p-latency-20260809-v1/summary.json` 的 `plan-model-fleet-n2p-latency-v1` 为 `3/3 passed`，固定同一 7B NF4 工件、ctx128、batch=1、输出 8。resident NF4 的 TTFT/inter-token P95/max 为 `1.403 s / 78.5 / 80.0 ms`，serial explicit pager 为 `3.739 s / 3557.6 / 3576.8 ms`；distance=1 后为 `3.989 s / 3429.6 / 3438.6 ms`。三者 output digest 均为 `e958d843…`。distance=1 的 host staging 与层计算区间重叠率为 `100%`，但实际 CUDA H2D stream overlap 仍为 `0%`；相对 serial pager，E2E 约慢 `1.0%`、TTFT 约慢 `6.7%`，inter-token P95 仅改善约 `3.6%`，不足以抵消复杂度。补充 `cancel_after_layer=1` 回收门通过。因此 N2P 结论为 `Freeze`：双槽 host prefetch 只保留审计/容量 profile，不进入默认吞吐路径；Windows/WSL UVM 仍不进入实现。

固定对照至少覆盖 context 128/2048/8192、输出 32/128 token、batch=1 与吞吐 batch；记录 TTFT、inter-token P50/P95/max、tok/s、CPU 占用、峰值 RAM/pinned/VRAM、H2D/D2H bytes、GPU page-fault groups、迁移次数、输出 digest/误差和取消后回收。不能只报告“成功加载”。

UVM Promote 门：同 artifact、同 GPU budget 下，`uvm_prefetch` 的 tok/s 不低于显式 pager 95%，P95 inter-token latency 不高于显式 pager 110%，最大停顿不超过中位数 2 倍，warmup 后目标层无 demand GPU fault，且实现复杂度或内存占用有可量化收益。任一不满足即 `Frozen`。显式 pager 本身若既不能比 CPU-only 提升至少 25%，也不能让更高质量模型达到可接受延迟，则不进入产品默认，只保留容量实验 profile。

## 8. 一键部署状态机

### 8.1 下载任务状态

```text
created
  -> resolving
  -> awaiting_license
  -> downloading
  -> verifying
  -> inspecting
  -> smoke_loading
  -> registered
  -> planning
  -> distributing
  -> warming
  -> active
```

终止状态：`cancelled`、`rejected`、`failed`、`quarantined`、`rolled_back`。

每次状态转换写入本地事务库，并附 `job_id`、幂等键、错误码、当前字节数、总字节数和可重试标志。服务重启后从最后一个持久状态恢复；不能只把进度保存在进程内。

### 8.2 部署必须分两阶段

1. **Prepare**：Worker 下载/接收工件，校验摘要，检查磁盘/内存/引擎，完成隔离试加载。
2. **Activate**：达到部署策略要求后，由 scheduler 一次性切换 active artifact/alias epoch。

部分节点 prepare 失败时不得偷偷把任务标成 active。系统应展示：目标节点、已准备节点、失败节点、实际激活策略、是否回退主节点。

### 8.3 激活与回滚

- active alias 指向 `artifact_id + deployment_epoch`，不修改原工件。
- 保留上一版 rollback 指针，直到新版本通过健康窗口。
- 运行中请求继续使用创建时锁定的 artifact；新请求使用新 epoch。
- 分层流水线中任何节点缺少相同 digest 时，整条流水线不得启动。
- GGUF 完整 Worker 可以按任务重派，但结果统计必须记录实际执行节点和 artifact digest。

## 10. Tailscale 集群档案与主节点登记

### 10.1 Cluster Profile

客户端本地保存多个集群档案：

```json
{
  "profile_id": "home-lab",
  "display_name": "家庭集群",
  "cluster_id": "qlh-...",
  "master_host": "qlh-master.tailnet-name.ts.net",
  "master_api_port": 8000,
  "master_tcp_port": 8888,
  "node_id": "client-...",
  "last_verified_at": "...",
  "last_successful_endpoint": "..."
}
```

共享集群密钥由现有安全存储层保存，不能出现在 profile 导出、日志或二维码明文中。若当前产品继续接受“已进入 tailnet 即已由网络所有者审核”的风险模型，则不增加逐设备人工审批；但集群 HMAC 仍用于防止端口误连和跨集群串线。

### 10.2 地址规则

- 接受 Tailscale IPv4/IPv6 和 MagicDNS/FQDN。
- 主节点设置中区分 `advertised_tailnet_endpoint` 与 LAN 候选地址。
- first-connect 返回经过验证的 canonical endpoint；客户端保存最近成功端点。
- 多个主节点候选时由用户明确选择，不自动加入第一个扫描结果。
- 不信任任意 `X-Forwarded-For`；反向代理必须显式配置可信代理。
- 主节点登记不等于备用主节点提升。角色切换仍需 cluster epoch/fencing。

### 10.3 不依赖远端数据库发现

发现顺序调整为：

1. 当前 cluster profile 的最近成功端点。
2. 用户输入或固定 `QLH_MASTER_HOST`。
3. Tailscale peer/MagicDNS 候选探测。
4. 仅在用户显式启用兼容模式时查询用户自有的远端目录；默认不连接 PostgreSQL。

远端目录只能提供候选，不能覆盖已经通过 bootstrap 验证并保持 TCP 在线的主节点。远端出口离线不得让 UI 同时显示“TCP 已连接”和“主节点离线”，也不得阻塞 local-only 模式。

### 10.4 认证与 Tailscale 身份边界

- **QLH 身份**：由主节点本地 `user_id`、用户名/显示名、角色、状态和 Auth App/TOTP 凭据组成；不要求 email，不把 Tailscale `loginName` 当作登录名或唯一键。
- **Tailscale 绑定**：保存 `tailnet_id`、`tailscale_user_id`、绑定节点 ID、授权方式、绑定时间和撤销时间。`tailnet_id + tailscale_user_id` 是当前绑定的外部身份，名称/IP/MagicDNS 只作可变展示字段。
- **一一绑定约束**：一个 QLH 用户只能有一个 `active` Tailscale 绑定；一个主节点内一个 `tailnet_id + tailscale_user_id` 只能绑定一个 active QLH 用户。换网先完成新授权，再撤销旧绑定，历史记录不复活权限。
- **数据所有权**：`local_users`、TOTP 密钥引用、恢复码哈希、绑定记录和认证审计是用户主节点的本地事实源，不进入开发组服务、公共账号目录或远端 PostgreSQL projector。远端数据库即使由用户自行配置，也不接收这些认证秘密；备份只能是用户主动导出的加密包。

### 10.5 本地用户数据模型

建议在主节点 SQLite 增加独立认证域（与模型/任务域分离）：

```json
{
  "user_id": "qlh-user-...",
  "username": "local-name",
  "display_name": "可选显示名",
  "role": "owner|admin|member",
  "status": "active|suspended|revoked",
  "totp_secret_ref": "os-credential://qlh/totp/...",
  "totp_algorithm": "SHA1",
  "totp_digits": 6,
  "totp_period": 30,
  "recovery_code_hashes": ["argon2id-or-scrypt-hash", "..."],
  "tailscale_binding": {
    "tailnet_id": "stable-tailnet-id",
    "tailscale_user_id": "stable-user-id",
    "node_id": "node-id-or-null",
    "state": "active",
    "bound_at": "..."
  }
}
```

TOTP 原始密钥只通过 OS credential store/主节点密钥封装保存，数据库只存引用和算法参数；恢复码只存带盐哈希。认证日志记录用户 ID、结果、原因和时间，不记录验证码、密钥、恢复码或第三方 token。

### 10.6 Auth App 下发方式与实现选择

注册必须同时提供两种等价下发方式：

1. **字符串**：显示 Base32 secret，并提供可复制的 `otpauth://totp/...` provisioning URI；用户在 Auth App 中选择手工添加。
2. **二维码**：二维码只编码同一条 `otpauth://` URI，不在二维码中加入 QLH 之外的网络凭据；页面只显示一次，确认首个验证码后立即失效。

默认参数取兼容性优先的 TOTP SHA-1/6 位/30 秒，服务器允许一个有限时间步偏差并拒绝成功后的重复验证码；具体参数、随机密钥、密钥保护和安全存储遵循 RFC 6238。Aegis 作为推荐的外部 Auth App（支持 HOTP/TOTP、二维码和手工录入、加密 vault 与备份），QLH 不依赖其在线服务。

实现路线按风险排序：

- **默认**：QLH 实现标准兼容的 TOTP provisioning/验证，用户自行选择 Aegis、Google Authenticator、2FAS 等兼容客户端。
- **可选**：QLH 项目组维护自己的开源 Auth App，但必须另设 Android vault、密钥备份、升级签名和独立安全审计门。
- **不建议第一阶段**：直接复制/内嵌 Aegis 代码。Aegis 仓库声明 GPL-3.0，若形成衍生或再分发包，必须履行许可证义务并保留相应版权/许可证文本；把 Aegis 作为用户自行安装的外部应用不产生 QLH 运行时依赖。

### 10.7 Tailscale 官方能力与协议门

调研结论（2026-08-09）：

- Tailscale 官方身份文档明确其不是身份提供方，用户通过受支持的 IdP/SSO 或 passkey 注册/登录，不能把 Tailscale 账号密码交给 QLH。
- Tailscale OAuth clients 是 OAuth 2.0 **client credentials** API 访问令牌，按 scope 授权且 token 默认约 1 小时，不是通用用户登录协议。
- Tailscale “device provisioning with OAuth apps” 使用 authorization-code flow，但当前为 alpha，只允许 OAuth app 与授权用户处于同一个 tailnet；一次性 `auth_keys:create:once` 没有 refresh token，不能作为跨 tailnet 的全局 QLH 登录依赖。
- 因此默认实现不注册开发组统一 OAuth app，不把用户 token 上传开发组，也不依赖 Tailscale 商务合作；通过用户自己在官方页面/本机客户端完成授权，再由主节点保存最小绑定信息。

仅在未来需要自动创建设备、审计到个人用户或集中 OAuth 体验时，新增“每个用户 tailnet 自带 OAuth app”的实验适配器；正式发布前必须完成 Tailscale API 条款、alpha 能力、scope 最小化、token 存储和是否需要合作/批准的法务与合作方评审。跨 tailnet 切换不得假设单个 OAuth app 可复用。

### 10.8 第三方协议/许可证矩阵

| 第三方/能力 | 默认方案 | 是否需要项目组先谈协议 | 开放条件 |
|---|---|---|---|
| Tailscale 官方客户端、网页注册/登录、用户自有 tailnet | 由用户自行注册和授权，QLH 只保存最小绑定元数据 | 不以签署合作为前置；仍须遵守当前服务条款和 API 限制 | `MF-AUTH-N2` 只做真实用户授权与绑定，不代管密码 |
| Tailscale OAuth client / OAuth Apps | 不作为默认登录，`MF-AUTH-N3` 才评估 BYO app | 中央 app、白标、集中 token 或生产化 alpha 能力必须先做条款/合作/批准评审 | 最小 scope、单 tailnet、无 refresh token 和撤销流程可证明后才实验 |
| Aegis Authenticator（GitHub 仓库） | 用户自行安装的外部 Auth App；QLH 只实现标准 TOTP | 不调用 GitHub API，不以 GitHub 合同为前置 | 若复制、修改或再分发，必须履行 Aegis GPL-3.0；不把 Aegis 代码内嵌进第一阶段 QLH |
| GitHub OAuth 登录 | 不纳入当前需求；Tailscale 的 GitHub SSO 由用户自行选择 | 若未来加入 QLH 直接 GitHub 登录，需注册 OAuth App、审查条款/隐私和数据范围 | 未完成前不得把 GitHub 账号写成 QLH 登录主键 |
| RFC 6238 / `otpauth://` | 标准兼容实现和二维码编码 | 不需要商业协议 | 通过互操作、密钥保护、时间漂移和恢复门 |

## 11. 主节点 SQLite 事实源与远端数据库退场

### 11.0 存储主权与用户资产契约

QLH 的长期设计不是“开发组维护一个远端账号/数据库，用户只是客户端”。主节点才是用户的控制面和资产边界：

- 干净安装不要求 PostgreSQL、远端账号、外部数据库密码或开发组服务可达；`DATABASE_URL` 为空时仍必须完成首次登录、模型导入、Tailscale 绑定、任务恢复和本地推理。
- SQLite 保存所有核心事实：用户与 Auth App 引用、Tailscale 绑定、cluster/profile、模型 catalog/artifact 引用、pull/deployment、任务 journal、会话/设置、审计和备份索引。大模型 blob 仍落在用户指定的 artifact store，不上传开发组。
- 用户可以导出加密的主节点备份并在自己的新主节点恢复；备份密钥由用户掌握。开发组不拥有解密密钥，也不提供跨用户的中央恢复或远程重置。
- 远端 PostgreSQL 如继续存在，只能是用户明确配置的兼容出口或一次性迁移目标，必须显示 `legacy_remote_enabled`，不参与启动、登录、调度、资产读取和故障恢复。
- 远端退场后，删除 projector/outbox/远端凭据不会改变本地 SQLite、artifact store 或用户备份的语义。所有迁移必须先通过本地导出/恢复演练，再允许删除远端配置。
- “用户拥有资产”是 QLH 的存储和控制权原则，不替代 Hugging Face、ModelScope、模型作者或其他第三方许可证、版权和使用条款。

### 11.1 目标语义

在默认 `local_only` 模式下，主节点必须独立完成：

- 读取/保存集群设置和用户模型注册。
- 节点 bootstrap、节点目录和主节点自身身份恢复。
- 创建、恢复和取消模型下载任务。
- 保存 artifact、deployment、alias 和 rollback 状态。
- 本地会话、审查票和必要控制面事件持久化。
- 本地推理、完整 Worker 和任务图执行。

Worker 永远不直接访问远端 PostgreSQL。主节点通过 API/TCP 向 Worker 提供所需配置和工件身份；远端数据库即使启用，也不能绕过主节点控制面。

### 11.2 推荐架构：local-only，兼容导出隔离

```text
control-svc write
      |
      v
SQLite transaction: all core domain rows
      |
      +--> immediate local read
      |
      `--> optional user-triggered export --> legacy PostgreSQL / encrypted backup
```

选择 local-only 的原因：

- SQLite 与业务进程同机，启动、认证和恢复不依赖 DNS、Navicat、公网链路或开发组服务。
- 核心提交只需要一次本地事务，不因为远端网络抖动生成“本地成功、远端未提交”的双状态。
- 用户可以把加密备份放在自己的磁盘、NAS 或对象存储，远端 PostgreSQL 不是灾备前提。
- 兼容导出明确是用户主动操作，不得把它重新实现成第二个写入事实源。

这不是 SQLite/PostgreSQL 双主。默认不创建远端 projector/outbox；兼容期若启用导出，远端只接受带版本的用户主动导出，远端直接修改不回写主节点，也不能覆盖本地事实。

### 11.3 数据域划分

| 数据 | 本地 SQLite | 远端 PostgreSQL | 说明 |
|---|---|---|---|
| cluster/profile/settings | 权威 | 退场兼容导出 | 用户主节点控制网络和配置 |
| nodes 与能力快照 | 权威持久快照 | 退场兼容导出 | 高频 heartbeat 不依赖远端 |
| model catalog/registry/artifact | 权威元数据 | 退场兼容导出 | 权重只在用户 artifact store |
| pull/deployment jobs | 权威 | 退场兼容导出 | 支持本地重启恢复 |
| alias/activation/rollback | 权威 | 退场兼容导出 | 需 epoch/fencing |
| task journal | 保持独立 SQLite journal | **禁止默认导出** | 不把大 payload 写入远端 |
| conversations/reviews | 权威或按用户策略保存 | **禁止默认投影** | 内容留在用户主节点 |
| local_users/tailscale_bindings/auth_audit | 权威 | **禁止远端投影** | 只允许用户主动导出加密备份 |
| secrets/tokens/passwords | 不保存明文 | **禁止远端存储** | 使用 OS credential store |

### 11.4 建议表

- `schema_migrations`
- `clusters`、`cluster_endpoints`
- `nodes`、`node_capability_snapshots`
- `model_catalog_entries`、`model_recipes`
- `artifacts`、`artifact_files`、`artifact_refs`
- `pull_jobs`、`pull_job_events`
- `deployments`、`deployment_targets`、`model_aliases`
- `settings`、`sessions`、`messages`、`review_tickets`
- `local_users`、`tailscale_bindings`、`auth_audit_events`（认证域仅本地主节点）
- `outbox_events`、`projection_checkpoints`（仅兼容导出迁移；默认不启用）

所有本地实体使用稳定 UUID、`aggregate_version` 和 `updated_at`。兼容导出如启用，使用全局唯一 `event_id` 和 `aggregate_version`，但远端事件不得回写或覆盖本地主节点事实。

### 11.5 运行模式与健康状态

| 状态 | 含义 | 用户界面 |
|---|---|---|
| `local_only` | 用户主节点独立运行，未启用远端出口 | 默认正常；不显示远端故障 |
| `legacy_remote_enabled` | 用户主动开启远端兼容导出 | 显示“用户自管兼容出口”，不能阻塞本地 |
| `legacy_export_pending` | 兼容导出暂有积压 | 本地正常；显示待导出数量，不改变核心状态 |
| `legacy_export_recovering` | 兼容出口恢复，正在重试用户导出 | 本地正常；显示导出进度 |
| `local_readonly` | 本地磁盘/SQLite 写入失败 | 明确故障；禁止需要持久化的变更，推理按既有模型受控继续 |

不能继续使用笼统的“数据库无法连接，只能使用内存模式”覆盖所有情况。默认没有远端数据库；兼容出口失败只影响用户主动导出，本地持久化失败才是控制面故障。

### 11.6 SQLite 约束

- 只允许 control-svc 成为控制数据库写者；其他服务走内部 API，避免 Python/Node 多进程争抢写锁。
- SQLite 驱动必须先完成 Windows/Linux 打包取舍：固定 Node 运行时支持时优先评估内置 `node:sqlite`，否则评估原生驱动；任何方案都必须通过 SEA/随包 Node、安装、升级和卸载冒烟后才能冻结。
- 启用 WAL、busy timeout、foreign keys 和固定迁移版本；每次升级先执行 schema migration，再执行 `quick_check`。
- 数据库位于本地文件系统，不放网络文件系统。
- 定期执行 `PRAGMA quick_check`，使用 SQLite Backup API 创建用户可读的轮换快照，并提供加密导出/恢复演练。
- 磁盘不足、只读目录、损坏和迁移失败必须 fail closed，不回退为无提示内存写。
- task journal 保持独立数据库和实例命名空间，避免控制面大事务拖慢任务提交。
- 远端 PostgreSQL 相关配置、驱动和导出器必须是可选组件；主节点默认安装不应因缺少它们而启动失败。

### 11.7 主节点故障边界

本地数据库是默认事实源，但不自动解决“主节点整机损坏”。在没有用户主动创建可靠加密备份前：

- `legacy_export_pending` 状态下禁止把远端出口提升为备用主节点。
- 手工转移主节点前先导出并验证用户签名/加密快照；不要求等待远端数据库。
- 后续可增加主节点到用户自有备用主节点的加密快照复制，但不能把 SQLite 文件直接放到共享盘并双端打开。
- cluster epoch、master node ID 和 artifact alias epoch 必须一并转移，旧主节点恢复后不得继续接受写入。

## 13. 故障与恢复设计

| 故障 | 必须行为 |
|---|---|
| Hub/DNS/代理不可用 | 下载任务进入可重试状态，已激活模型继续运行 |
| 下载中断 | 使用来源 ETag/revision 与 partial 元数据续传；来源变化则重建 staging |
| SHA256 不匹配 | 移入 quarantine，不注册、不分发 |
| 文件名相同但内容变化 | 创建新 artifact，不覆盖旧 digest |
| 磁盘不足 | dry-run/配额阶段拒绝；不得下载到一半挤爆状态目录 |
| inference-svc 试加载崩溃 | sidecar 失败，主控制面继续运行；工件标记 load_failed |
| 某 Worker 分发失败 | 部署为 partial/failed；不伪报该节点参与 |
| 激活后健康失败 | alias epoch 回滚，运行中旧请求不被破坏 |
| 远端 PostgreSQL 不可达 | `local_only` 无影响；兼容导出模式仅暂停用户主动导出，本地事务和推理继续 |
| 远端恢复 | 兼容导出按用户确认重试；不得把远端数据回写覆盖本地事实 |
| 本地 SQLite 不可写 | 控制面进入只读故障，禁止假成功 |
| 主节点重启 | 从 SQLite 恢复下载/部署状态，重新探测 Worker，不从进程内状态猜测 |
| Tailscale 地址改变 | profile 保留 cluster_id，重新验证 endpoint；不得创建重复集群 |
| TOTP 时钟漂移 | 只允许有限时间步窗口并记录 drift；超出窗口要求用户修正主节点时间，不扩大长期接受范围 |
| Auth App 连续失败/恢复码重放 | 限速并临时锁定；成功消费的恢复码立即失效，管理员操作也需本地审计 |
| Tailscale 换网授权失败 | 保留旧 active binding，pending 状态过期自动清理，不创建半绑定用户 |
| 两个主节点同时出现 | cluster epoch/fencing 拒绝旧主写入和旧激活结果 |

## 14. 安全、许可证与供应链

- 默认源清单由开发团队提供并随发布版本内置（HTTPS Hugging Face/ModelScope 官方端点，见 §7.1）；用户更换源时必须显式配置并确认，仅允许 HTTPS 官方端点与用户明确配置的自定义源/私有镜像。
- 禁止任意 HTTP 重定向到本机、链路本地地址或受保护网段；主节点模型分发端点是单独的受信路径。
- 所有相对路径经过 traversal 检查；压缩包导入防止 Zip Slip、符号链接逃逸和超额展开。
- `trust_remote_code` 默认关闭；需要时必须是 curated、固定 revision、固定摘要和隔离运行。
- 下载 token、数据库密码和集群密钥不进入日志、manifest、SQLite/PostgreSQL 业务表或前端状态响应。
- Auth App/TOTP 密钥只在用户主节点生成和保存；字符串/二维码 provisioning 只显示一次，页面、日志、遥测和导出诊断不得留存原文。
- 默认 TOTP 使用随机独立密钥、30 秒时间步和有限漂移窗口；登录失败限速、连续失败锁定、恢复码一次性消费、换绑/撤销和管理员操作写入本地审计。
- 用户丢失 Auth App 与恢复码时，开发组没有远程重置能力；只能由用户本人通过主节点离线恢复/备份流程恢复或重建账户。
- Tailscale `tailnet_id`/`tailscale_user_id` 只保存最小绑定元数据；不收集 Tailscale 密码，不把用户的第三方 IdP token 或 OAuth secret 上传开发组。
- 第三方协议门：默认流程只依赖 Tailscale 官方客户端/网页、RFC 6238 和外部 Aegis，不新增 GitHub OAuth 登录；若集中注册 Tailscale OAuth app、白标/再分发 Tailscale 能力或引入 GitHub OAuth，必须先完成条款、scope、隐私和合作方审批，未通过前保持 `Planned`。
- 模型卡许可证、gated 状态和用户接受时间写入审计元数据；这不替代用户遵守模型许可证。
- 主节点向 Worker 分发时使用现有集群认证并增加请求签名、时间窗、artifact digest 和 Range 响应校验。
- 删除模型采用引用计数与延迟 GC；正在推理、回滚保留或任务 journal 引用的工件不可删除。

### 17.3 发布硬门

以下任一项不满足，不得宣传“一键部署”或“数据库自动接管”：

1. 下载进度和最终摘要可验证，失败不会覆盖当前模型。

3. 主节点本地数据库重启恢复通过，且本地写失败会明确报错。
4. 分布式任务能证明实际参与节点和完全一致的 artifact digest。
5. 安装包不修改用户全局 Python、Hugging Face cache 或系统代理。
6. 私有 token、集群密钥和数据库密码不进入日志与导出文件。
7. Auth App/TOTP 和 Tailscale 绑定的本地主节点所有权、恢复与撤销门通过；未通过时不得宣传“账号可切换 tailnet”或“无需用户自行保管认证数据”。

## 18. 风险与止损

| 风险 | 对策/止损 |
|---|---|
| 试图支持任意 HF 模型导致适配无限膨胀 | 目录分级；未知模型只 inspection，不自动部署 |
| 双数据库冲突 | local-first + 单向 outbox；不支持 Navicat 直接双向写 |
| SQLite 多进程写锁 | control-svc 单写者，其他服务走 API |
| 大模型耗尽磁盘 | dry-run、配额、保留空间和引用安全 GC |
| Worker 重复下载占满出口 | 主节点缓存优先；后续评估 P2P，但以摘要为准 |
| 模型名相同内容不同 | 运行和调度只信 artifact digest |
| remote code 供应链风险 | 默认关闭；curated + revision + digest + sidecar |
| 自动主节点切换造成脑裂 | 本地投影未追平时禁止自动提升；cluster epoch fencing |
| 为兼容 Ollama 引入第二套存储 | 兼容 API 只映射现有 artifact/job，不复制 blob |
| 丢失 Auth App 与恢复码导致用户锁死 | 首次注册强制确认恢复码；主节点提供用户主动的加密备份/离线恢复；开发组不保留 reset 能力 |
| 把 Tailscale loginName/email 当永久身份 | 只绑定 API `user.id` + `tailnetId`，名称变更只更新展示字段 |
| Tailscale OAuth alpha/单 tailnet 或协议变化 | 默认不依赖；BYO app 仅实验；能力/条款门未通过就冻结 N3 |

## 19. 推荐实施顺序

```text
微服务清理门
   -> M0 契约
   -> M1.1 SQLite 本地事实源基线
   -> M1.2 SQLite 资产自持与备份恢复
   -> M1.3 远端 PostgreSQL 退场准备
   -> M2 工件库/导入
   -> M3 HF/GGUF 一键 pull
   -> M4 Tailscale 集群档案
   -> MF-AUTH-N1 本地认证/用户管理
   -> MF-AUTH-N2 Tailscale 一一绑定与换网
   -> M5 跨节点部署
   -> M6 Ollama 类完整体验
   -> M7 扩展来源与模型族
```

M1 必须早于真正的一键下载任务：没有本地事务状态，下载中断、进程重启和远端数据库断线都会重新产生“表面有进度、实际不可恢复”的问题。M5 必须晚于真实 PC Worker 准入：模型分发成功不能替代推理链路正确性。

## 21. 本计划完成定义

只有同时满足以下条件，`L4-MODEL-FLEET` 才能由 Candidate 转为 Completed：

1. 空安装用户使用开发团队默认源即可完成解析、下载、校验、试加载和首次推理；也可更换自定义源后完成同样流程。
2. 用户可以登记 Tailscale/MagicDNS 主节点，PC 与 Android 重启后自动恢复正确 cluster profile。
3. 干净安装在没有 PostgreSQL、远端账号和开发组服务时仍可启动、认证、导入、部署、重启恢复和本地推理；远端 PostgreSQL 若存在，只能作为用户主动开启的兼容导出出口。
4. 两台真实 PC 完成至少一个 PyTorch 与一个 GGUF 工件的分发、激活、实际推理和回滚。
5. UI/TUI/API 的模型状态一致，且任务统计只显示真实参与节点。
6. 供应链、密钥、许可证、磁盘和故障注入发布门全部通过。
7. 认证域在用户自己的主节点闭环：Auth App 字符串/二维码注册、TOTP 登录、恢复码、限速/撤销和加密备份通过；认证数据不进入开发组服务或远端 PostgreSQL。
8. QLH 用户与 `tailnet_id + tailscale_user_id` 一一绑定，已有 Tailscale 账号和首次注册引导均可完成；换 tailnet 为 pending/confirm/revoke 原子流程，旧绑定不能继续访问。
9. 任一集中 Tailscale OAuth、GitHub OAuth 或 Aegis 衍生再分发方案都先通过条款/许可证/合作方评审；未通过时默认路径仍不依赖它们。
10. 用户可以在自己的设备/NAS/对象存储上完成加密备份和新主节点恢复，模型工件、配置、任务、会话和认证数据不依赖开发组或远端数据库；第三方模型许可证仍按来源条款执行。
