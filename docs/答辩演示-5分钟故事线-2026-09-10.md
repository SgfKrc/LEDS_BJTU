# QLH 答辩演示：5 分钟故事线

> 票号：`DEF-A1`  
> 适用环境：当前无小模型、性能一般的开发机  
> 演示目标：证明控制面可复现、可观察、可恢复，并清楚限定证据边界  
> 硬口径：全程使用脱敏 fixture；不加载模型、不访问外网、不宣称物理双机或模型性能

## 开场前准备（不计入 5 分钟）

先重置上一轮本票残留，再运行机器预检并校验故事线本身：

```powershell
scripts\demo\reset.bat --apply
scripts\demo\checklist.bat
scripts\demo\story.bat
```

重置只终止身份重新验证通过的本票进程，保留全部演示证据；安全边界见[环境重置说明](答辩演示-环境重置说明-2026-09-10.md)。

依次生成故障与 benchmark 的本机彩排证据，最后保持现行前端运行：

```powershell
scripts\demo\demo.bat --mode failure --report build\defense-demo\failure-story.json
scripts\demo\benchmark.bat --report build\defense-benchmark\story.json --chart build\defense-benchmark\story.svg
scripts\demo\performance_report.bat --benchmark build\defense-benchmark\story.json
scripts\demo\demo.bat --mode fixtures --scenario topology --open
```

Unix 使用等价的 `story.sh`、`demo.sh`、`benchmark.sh`。准备四个可切换画面：

1. Edge 的脱敏拓扑页；
2. `build/defense-demo/failure-story.json`；
3. [性能结题表](答辩演示-性能结题表-2026-09-10.md)，旁边保留 `build/defense-benchmark/story.svg` 与 `story.json`；
4. 本开发票计划的 `DEF-P1`～`DEF-P4` 完成记录。

启动计时前确认拓扑页顶部确实显示 `FIXTURE / REDACTED / NOT LIVE`。若未显示，禁止开始讲解。

## 5 分钟总览

| 分段 | 时间 | 主题 | 必须落到的证据 |
| --- | --- | --- | --- |
| `S1` | 0:00–0:35 | 先讲证据边界 | fixture、脱敏、非实时、非模型性能 |
| `S2` | 0:35–1:20 | 一个可复现入口 | 三条固定剧本、启动门、自动清理 |
| `S3` | 1:20–2:15 | 拓扑与 readiness | 3/3 检查、节点状态、L0–L23 |
| `S4` | 2:15–3:20 | 故障注入与恢复 | 断连、expired、一次重派、completed |
| `S5` | 3:20–4:15 | 有边界的 benchmark | 固定负载、单机双进程、非模型性能 |
| `S6` | 4:15–5:00 | 收束与下一道门 | P1–P4 证据闭环、真实模型票仍排队 |

## S1｜0:00–0:35｜先讲证据边界

屏幕：停在拓扑页标题和黄色声明条，不滚动。

讲词：

> 今天展示的是分布式控制面的可复现性、可观察性和故障恢复，不是模型效果展示。当前开发机没有合适的小模型，所以页面和报告均明确标记 fixture、脱敏、非实时；也不把本机双进程冒充物理双机，不把控制面毫秒数冒充 TTFT 或 tokens/s。

动作：依次指向 `FIXTURE / REDACTED / NOT LIVE` 和 `READ-ONLY EVIDENCE`。

成功标记：两处声明都在首屏可见。

翻车兜底：浏览器没有自动打开时，复制启动器打印的 loopback URL 到 Edge。Vite 无法启动时，打开[拓扑快照源](../frontend_cybergothic/src/data/defense-topology.json)，并明确说“本轮 UI 未成功复演，以下展示固定证据”，不能说页面已正常运行。

## S2｜0:35–1:20｜一个可复现入口

屏幕：拓扑页 fixture 条；必要时快速切到[场景清单](../scripts/demo/scenarios.json)或 `topology-run-final.json`。

讲词：

> 一个命令只启动现行 `frontend_cybergothic`，在宣布就绪前校验对话、图像、拓扑三条固定剧本及页面成功标记。启动等待有 120 秒硬上限，退出只回收本票创建的进程；异常残留也必须经过创建时间、目录和命令白名单复核。报告只保留状态和标记，不保存凭据、模型输出、绝对路径或动态端口。

动作：指出报告中的 `fixture-dialog`、`fixture-image`、`fixture-topology`、`startup-budget`。不现场进入已废弃的 `frontend` 目录。

成功标记：四个步骤均为 `ok=true`。

翻车兜底：若 preflight 失败，直接读出 fail-closed 原因并说“本轮入口不可用”；随后展示[启动器回归](../tests/test_defense_demo.py)和[启动器源码](../scripts/demo/defense_demo.py)，不反复改端口拖延计时。

## S3｜1:20–2:15｜脱敏拓扑与 readiness

屏幕：拓扑页 readiness、节点和层段三个区域。

讲词：

> 快照有三项通过的 readiness 检查。三个节点只使用稳定别名：`node-master` 与 `node-worker-a` 就绪，`node-standby` 离线并被排除在活动分配外。内部采用 end-exclusive 契约 `0–8`、`8–24`，页面呈现为 `L0–L7`、`L8–L23`，24 层连续、无重叠、无空洞。

动作：从 master 沿连线指到 worker，再指向灰色 standby；最后沿层段条从 0 指到 23。说明 canvas 是装饰，真实可访问证据在 DOM 与 JSON。

成功标记：`3 / 3`、两个 ready、一个 offline、`L0–L7`、`L8–L23`。

翻车兜底：canvas 或样式异常时直接读 DOM；DOM 也不可用时打开[唯一快照源](../frontend_cybergothic/src/data/defense-topology.json)。敏感文本和窄屏门见[拓扑 E2E](../frontend_cybergothic/tests/p4_defense_topology.spec.js)。

## S4｜2:15–3:20｜故障可观察、恢复可验证

屏幕：`failure-story.json` 的 `steps` 与 `failure_injection.workflow`。

讲词：

> 这里确实启动了第二个 worker 进程，它通过 task-worker v2 在 loopback 上接收 fixture stage，随后以固定退出码 23 退出。生产传输层观察到 `remote_worker_disconnected`，第一次 attempt 进入 `expired`；安全的 pure stage 只重派一次到确定性本地恢复，lease epoch 从 1 变成 2，最终 workflow 为 `completed`，输出内容保持脱敏。

动作：按顺序指 `worker-ready → worker-exit → stage-reassigned → workflow-complete`，再对比两次 attempt 的 state 与 lease epoch。

成功标记：退出码 `23`、原因 `remote_worker_disconnected`、`retry_count=1`、attempt 为 `expired/completed`。

翻车兜底：现场复演未完成时必须说“本轮故障注入未成功完成”。若上一次脱敏报告存在，可作为历史彩排证据展示；否则只展示[故障 worker 源码](../scripts/demo/failure_worker.py)和[确定性回归](../tests/test_defense_demo.py)，不可把测试结果说成当前现场运行。

## S5｜3:20–4:15｜测量，但不越过证据边界

屏幕：[性能结题表](答辩演示-性能结题表-2026-09-10.md)的表 1/2/4；需要图形时并排展示 `story.svg`，结尾切到 `story.json` 的 `claim_guard` 和 `physical_dual_host`。

讲词：

> 固定负载是 12 次计量、2 次预热、每轮一个 TaskGraph fixture stage、288 字节载荷。第一组是单机单进程，第二组是真实 loopback worker 的单机双进程；这里按当前图表依次读出两组 median/p95。这些数只描述本机 TaskGraph 控制面 fixture 开销，不是模型 TTFT、tokens/s、生成质量或双机加速比。物理双机字段仍是 `not_run`。

动作：先指图上的 `FIXTURE · SINGLE HOST · NOT MODEL PERFORMANCE`，再读负载与当前图表数值，最后指 `physical_dual_host_data_pending`。不要背诵旧开发机数值，以开场前新生成的 `story.json` 为准。

成功标记：固定 workload SHA 存在；两组 `host_count=1`；声明门均为 `false`；物理双机不可用于结论。

翻车兜底：SVG 打不开则展示 JSON。最新报告不存在时，只讲[benchmark 实现和声明门](../scripts/demo/defense_benchmark.py)，完全省略具体数字，不能借用其他机器或旧截图的数值。

## S6｜4:15–5:00｜收束到工程证据与下一道门

屏幕：回到[开发票计划](开发票计划-审计收口与答辩演示-2026-09-09.md)中 P1–P4 的完成记录。

讲词：

> 这条链路给出了四类可复建证据：P1 的单入口与启动门、P4 的脱敏拓扑、P2 的真实进程断连与确定性恢复、P3 的固定负载与口径保护。结论是控制面演示已可重复，不是模型能力已经验收。真实 runtime smoke 与模型切换仍需合适的模型资产和运行时，条件满足后再关闭对应票。

动作：逐项指向 `DEF-P1`、`DEF-P2`、`DEF-P3`、`DEF-P4`，最后停在仍排队的 `AUD-RT-01`、`AUD-SW-01`。

成功标记：在 5:00 前说完“fixture 不关闭真实模型门”，随后停止演示。

翻车兜底：若只剩 45 秒，停止切屏，只说“四个已完成证据 + 两个待真实模型环境的门”。不要为了补画面超时。

## 90 秒紧急版

1. 0:00–0:20：指声明条，只定义 fixture、脱敏、非实时、非模型性能。
2. 0:20–0:45：展示拓扑 `3/3`、两个 ready、standby offline、L0–L23。
3. 0:45–1:10：展示故障链 `exit → expired → retry=1 → completed`。
4. 1:10–1:30：展示 benchmark 声明门，说明 P1–P4 已闭环、真实模型两票仍等待环境。

## 高频追问口径

**“这算真正的分布式推理吗？”**  
不算真实模型分布式推理。本票证明 task-worker 协议、双进程调度、断连检测和重派路径可运行；物理双机和真实模型仍需后续环境验收。

**“为什么 fixture 仍有价值？”**  
它固定输入、事件顺序和声明边界，让启动、拓扑与恢复行为可以重复回归；它验证工程控制面，不替代模型效果或性能数据。

**“如何证明没有泄露机器信息？”**  
拓扑节点使用严格字段白名单与 alias 格式，启动器拒绝 IPv4 和越权字段；页面专项测试还断言不出现原节点名和硬件文本。

**“为什么不现场加载小模型？”**  
当前机器缺少合适资产且性能条件不足。强行加载会把不可控环境噪声带入答辩，所以真实 runtime 与切换票保持未完成，不用 fixture 冒充。
