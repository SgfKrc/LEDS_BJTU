## 1. 现状（实测，非推断）

### 1.1 两条独立的数据面通道

| | 产品路径（`/api/chat` + `routing_preference`） | v3 task_worker 路径 |
|---|---|---|
| 协议 | 旧版 `LAYER_CONFIG` / `LAYER_FORWARD` / `LAYER_RESULT` | `hello` / `stage_offer` / `stage_accept` |
| 层段类型 | `start_layer`/`end_layer` 整段，PyTorch 权重 | `stage_type`（`full_inference` / `layer_forward`） |
| master 侧入口 | `_execute_chat_full` → `scheduler_pipeline` | `_execute_task_graph_chat_with_slot`（`execution_mode="task_graph"`） |
| 节点过滤 | `getattr(node, "node_type", "pc") == "pc"`（`scheduler_pipeline.py:152-159`） | `node.node_type in {"pc","android"}`（`scheduler_task_worker.py:714-718`） |
| android | **被排除**（代码注释："Android 的 llama.cpp worker 只能走 v3 task_worker stage offer"） | **支持**（`worker_kind == "android_full_worker"`，`task_worker_adapter.py:548`） |

⇒ 用户在 Y700 真机上看到的 `容量候选跳过 android-c3f9d855: reason=not_eligible` 正是第 4 行那条过滤。

### 1.2 v3 链路的 android 支持**已经存在**（不需要新写）

- 协议层：`task_worker_protocol.py` 的 `stage_offer` 支持 `layer_forward` + hidden 交接字段（`:54`、`:551-606`）
- 适配层：`task_worker_adapter.py:548` 有 `android_full_worker` 的 resource_gate 判据
- 注册层：`scheduler_task_worker.py:727-738` 按 `node_type` 推导 `expected_kind`
- 完整模型判据：`scheduler_task_worker.py:866-879` 对 android 额外要求 `resource_gate.admitted`
- App 侧：`AndroidWorkerCapabilities` 已产出 `stage_types`/`engines`/`models`/`resource_gate`/`layer_ranges`
  （`android/.../worker/AndroidWorkerCapabilities.kt:128+`）

### 1.3 真实 gap（三点，按阻塞度）

1. **★ `capabilities` 与 `pipeline_worker`/`backend_id` 自相矛盾**（**根因已坐实**）。
   实测 `GET /api/cluster/nodes` 的 android 节点：
   `"pipeline_worker": true, "backend_id": "llama_cpp", "capabilities": []`。
   根因在 **App 侧**（不是 master 映射 bug）：
   `android/.../MainViewModel.kt:1187-1192` 发 **task worker** 的 device_info 时
   ```kotlin
   val deviceInfo = buildAndroidPresenceDeviceInfo().toMutableMap().apply {
       put("connection_type", "tcp_task_worker")
       put("pipeline_worker", true)     // 无条件硬写
       put("task_worker", true)
       put("backend_id", "llama_cpp")   // 无条件硬写
   }
   ```
   而 `capabilities` 仍来自 `buildAndroidPresenceDeviceInfo()`（`MainViewModelLogic.kt:209`），
   其条件是 `runtime?.nativeRuntimeAvailable == true && !isLite` ⇒ 该 native runtime 未就绪时
   落成 `[]`，与刚硬写的 `pipeline_worker=true` / `backend_id=llama_cpp` **互相打脸**。
   影响：`_client_supports_forward_layers`（`api_server.py:4832`）与 `_node_supports_forward_layers`
   （`scheduler.py:252-282`）都优先读 `capabilities`；本机实测这两处**靠 `backend_id` 兜底**才
   判成 True（故 skip 理由落在下游的 `not_eligible`，而不是 `no_forward_layers`）——
   即：**能力门现在被"硬写的 backend_id"蒙过去了，一旦设备 native runtime 真没就绪，
   这两个字段会一起说谎**。
   修法（阶段 0）：App 侧三处字段必须**同源** —— `pipeline_worker`/`backend_id`/`capabilities`
   统一由同一个 `nativeRuntimeAvailable` 派生，不得硬写。
   **✅ 已实施（2026-09-30，`e3b1554`）**：抽出纯函数 `buildTaskWorkerDeviceInfo(presence)`
   只补 worker 专属字段；真机复验 master 侧变为
   `pipeline_worker=False backend_id=[] caps=[] task_worker=True`（**三字段自洽**）。
   测试 150 passed，含「该红必须红」守卫（改回硬写版即失败）。

1b. **★ 实测暴露的既有问题：该设备 `nativeRuntimeAvailable` 恒为 false**（阶段 1 的**真正前置**）。
   真机 logcat：
   ```
   20:28:00.793 W/MainViewModel: native 运行时未就绪：不上报 pipeline_worker/backend_id（上报值=false, 能力=[]）
   20:28:00.817 D/nativeloader:  Load …/base.apk!/lib/arm64-v8a/libqlh_llama_jni.so
   ```
   即**能力采集（0.793s）早于 native 库装载（0.817s）**，而之后 30s 再查仍是
   `pipeline_worker=False` ⇒ 不只是启动瞬间的竞态。探测路径：
   `MainViewModel.createPassiveRuntimeStatus` / `InferenceService.getRuntimeStatus`
   的 `System.loadLibrary("qlh_llama_jni")` 与 `eng.checkNativeRuntime()`（`:411`、`:419`）。
   后果：**android 永远不声明 `forward_layers`** ⇒ 即便阶段 1 接了 stage 链路，
   能力门也会挡下它。⇒ 阶段 1 之前必须先修这条探测（或让 `TaskWorkerService` 在
   装载完成后再上报一次 presence）。
2. **product 路径未发起 `stage_offer`**。全仓搜 `send_stage_offer` 无 master 侧调用点；
   现有入口是 `task_graph`（`execution_mode="task_graph"`）+
   `TASK_WORKER_EXPERIMENTAL_ENABLED`（默认 false，`config.py:361`）。
3. **开关与准入门**：v3 还需 `manual_stage_dispatch_enabled`
   （`task_worker_adapter.py:346` 由 `connected` 决定；`scheduler_task_worker.py:484` 用它拒收）。

## 2. 方案

### 阶段 0：先修 `capabilities` 映射（前置，独立可验证）

- 定位 `buildAndroidPresenceDeviceInfo` 的 `capabilities` 字段在 master 侧被落成 `[]` 的环节
  （重点查 `inference_service/peer.py` 的 presence/device_info 组装、`cluster_join` 的归一化路径）。
- 判据：`GET /api/cluster/nodes` 的 android 节点 `capabilities` 从 `[]` 变为 `["forward_layers"]`
  （与 `pipeline_worker: true` 自洽）。**该红必须红**：先写一个断言"同条件字段必须同取值的用例"。

### 阶段 1：让 product 路径把层段派给 android（核心）

两条备选实现路线，**建议 A**：

**路线 A（推荐）—— 在 `scheduler_pipeline` 内新增 stage 委派分支**
- 在 `_push_layer_config_to_clients_locked`（`:152`）的 `node_type == "pc"` 过滤旁，
  **新增**一条：`node_type == "android"` 且该 worker 的 v3 `stage_offer` 可用时，
  把它按 **relay/exempt 语义**纳入 `eligible_node_ids`，其层段由 stage 链路承载
  （而不是发 `LAYER_CONFIG`）。
- 理由：与既有 `relay_middle` 的做法同构 —— relay worker 也是"零层 + 由远端代跑"，
  已在 `_append_relay_assignments`（`scheduler.py:408`）落地并有三机验收证据。
  照此模式，android 只需在 `layer_assignments` 里声明它认领的层区间，
  实际执行走 stage offer。
- 改动面（预估）：`scheduler_pipeline.py`（过滤 + 委派）、`scheduler.py`
  （`_split_relay_nodes` 同位置加 android 分流）、`api_server.py`（开关贯通）、
  `task_worker_adapter`/`scheduler_task_worker`（把 stage 结果接回 pipeline 的 token 流）。
- 风险：**执行回路拼接**是主要风险 —— stage 返回的是 hidden/token 帧，
  要接回 `_run_pipeline` 的逐 step 循环；这是本路线大部分工作量所在。

**路线 B（更保守）—— 让 product 路径在 `execution_mode` 层转发到 task_graph**
- 当 `routing_preference=distributed_required` 且集群里只有 android 参与时，
  `_execute_chat_full` 内部改调 `_execute_task_graph_chat_with_slot`（已验证的 v3 链路）。
- 优点：不新写执行回路，直接复用 v3 全链（协议/适配上文 §1.2 已具备）。
- 缺点：需要在 `api_server` 加一处显式分流，且要处理"PC + android 混合"时的拓扑选择。

### 阶段 2：真机证据（用户原本要的）

沿用本轮已固化的真机链路（`scripts/android_validation.py` 已支持 `am start` + logcat 证据）：
- 模型分片请求（层段确实下发到 android）
- 连续生成（≥32 decode，判据 per-token argmax）
- 取消（ABORT）
- 断线/重连
- 热/电量采样（`thermal_status` 已在 `buildAndroidPresenceDeviceInfo` 里上报）

## 3. 收口建议

- 阶段 0 独立可做、风险低，建议优先。
- 阶段 1 若选路线 A，建议先写"执行回路契约"的失败用例（stage 结果 → pipeline step）
  再动实现；这是唯一需要新设计的部分。
- 阶段 2 依赖前两阶段；证据口径沿用三机验收的 per-token argmax。
