### 2.2 分布式执行形态对照（《文档状态与维护规则》第 10 条）

"分布式"不用是/否表示。当前可选执行形态如下：

| 执行模式 | Provider | 参与节点（统计口径） | 故障边界 | 降级路径 |
|---|---|---|---|---|
| `pytorch_layer` | 本地 PyTorch 层段（`scheduler` + `model_module`） | 主节点 + 同 artifact 的 PC 从节点 | 节点下线 → 重编排 → 当前 attempt 失败 | 回退主节点完整模型 |
| `task_graph` | `local_full_model` / `remote_full_worker` | 主节点 + 已认证 PC Full Worker（仅完成 attempt 的计入 `nodes_participated`） | attempt / lease / epoch / winner fencing | 跨 Provider 重派 → 本地 `local_full_model` |
| `island`（路线 A） | 网关节点的 island 引擎 | 孤岛计 **1 个**逻辑节点；岛内 N 张卡不得计入 | 网关探活失败 = 该逻辑节点下线 | 复用现有节点下线 → 重编排路径 |
| `external_api`（路线 B） | `ExternalOpenAIProvider` / `ExternalChatClient` | 外部端点**不入图**、不计为集群节点 | HTTP 4xx/5xx/超时按 `retryable` 分类 | 回退本地路径并记 `fallback_reason` |
| `speculative_assisted`（路线 C） | 本地 draft + `ExternalVerifyClient` | 本机 + 外部 verify 端点 | 取消粒度为轮边界；已发出的 verify 不可服务端取消 | **无生产降级路径**——未接入 `/api/chat`，仅实验端点可达 |

## 3. 本轮完成了什么（2026-07-26）

### 3.1 分布式控制面：6 项已验证缺陷 + 3 项附带问题

**做了什么。** 这 6 项都不是"代码不好看"，而是在真实集群里会表现为具体运行故障——对答辩与结题材料而言，这一列比修复本身更有说明力：

| 缺陷 | 此前会怎样表现为运行故障 |
|---|---|
| 客户端接收循环异常未终结连接 | **僵尸连接**：心跳仍在发、主节点仍视其在线、该节点永不重连；派下去的任务无人执行 |
| 帧中途超时未复位读取状态 | 字节流失步，其后所有帧解析错位 |
| 注册失败使重连线程被孤儿化 | 恢复延迟最长 **60 秒** |
| 服务端 5s 收包超时架空 12s 心跳容忍 | 从节点卡顿 6 秒即被**误踢**，并触发**全量重推分层**——一次网络抖动等于整集群重编排 |
| 三处 ACK 绕过发送锁 | 帧交叉损坏 |
| 9 个 async 端点同步阻塞事件循环 | 连接不可达主节点时**前端整站假死约 50 秒** |

附带修复三项：`Scheduler._tcp_client` 未初始化、健康监控首轮假"恢复"误报、一个在原始基线即失败的测试夹具缺陷。

**怎么验证的。** 双节点实测（单机双进程模拟）：注册 20 ms、`SIGKILL` 后约 1 秒标记离线、重连秒级恢复、30 秒无抖动。

**还剩什么。** 真机双设备联调。**从节点硬件仍在维修**；此前的上线失败是硬件故障而非软件缺陷，但这也不能反过来当作"真机已验证"。见 P0-2。

### 3.4 外部辅助三条路线（《调研方案》§2 的 A / B / C）

**路线 A「TP 孤岛」——阶段 1 PoC 已实施并验证。** `src/island_engine.py`，`engine="island"`，后端为 OpenAI 兼容端点。孤岛对集群呈现为**单个逻辑高算力节点**，承担整请求推理，**不参与 PyTorch 层拆分**（主节点画像过滤 + 网关侧拒收 `LAYER_CONFIG` 双保险）。`QLH_ISLAND_*` 含聚合能力声明，用于画像与排序加权。验证：专项单测 + 双节点 e2e。指南见《TP孤岛接入指南》。剩余：真实 vLLM/SGLang 孤岛实测、`internal_benchmark_passed` 门控、A-1 层段形态。

**路线 B「外部推理服务 Provider」——阶段 1 PoC 已实施并验证。** `src/external_provider.py`，`engine/execution_mode="external_api"`。**数据作用域门控是硬约束**：`deny` / `opt_in`（默认）/ `allow_all`，非法取值 fail-closed 回落 `deny`；请求需显式 `allow_external`，并由 `prefer_external` 或长度阈值触发；外部失败回退本地并记 `fallback_reason`；流式为真流式逐 token。验证：专项单测 + e2e（`deny` 档位下用户正文零出网、凭据零泄漏）。审查中另修复 6 个真实缺陷，其中两个值得记录：**外部失败回退绕过流水线预约/转发约束，导致已预约的 worker 误加载整模型**；**`/api/status` 同步探活冻结事件循环 3 秒**。剩余：会话粘性、成本上限、前端开关。

**路线 C「draft-verify 投机解码」——阶段 0-1 探索性 PoC 已实施，未接生产。** `src/speculative.py`；入口是独立实验端点 `POST /api/experimental/speculative`，`QLH_SPEC_ENABLED` 默认关闭时返回 404；**未接入 `model_module` 生产解码循环**。验证：专项单测含 20 万次抽样的逐 token 边缘分布、6 万次会话联合分布等价性验证，以及 8 个注入缺陷全部被杀死的变异测试。已知边界（详见《投机解码外部辅助实施说明》§7）：

- 接受判定**精确**——不对 top-k 截断行做归一化。曾因归一化把接受比值放大 `1/M`、草稿被橡皮图章（`M` 越小接受率越趋近 1.0，输出退化回 draft 分布），已修复。
- 修正 token 的残差采样仍受 top-k 截断：`QLH_SPEC_TOP_LOGPROBS` 20 → TV 0.155、64 → 0.058、200 → 0.035、全量 → 0.035。
- 标准 `completions` 的 `echo=true` 使下行约 12 KB/轮（《调研方案》估 1 KB/轮）；要达该量级须自建只回后缀行的 verify 端点。
- `top_logprobs` 的 key 是 token 文本，vLLM 需 `--return-tokens-as-token-ids`。
- **`PagedKVCache.truncate(n)` 已完成**：按“移除尾部 n 个 token”语义同步截断页表、回退尾页 `used` 并回收完整空页；独立 pytest、固定种子随机状态机和 CUDA 快速冒烟均通过。它尚未接入真实 draft/生产循环，不能据此宣称投机解码已生产化。
- draft 侧目前是占位实现；真实收益必须用同族小模型（Qwen-1.8B draft + Qwen-7B/14B verify，共享 tokenizer）实测，**不承诺加速比**。
