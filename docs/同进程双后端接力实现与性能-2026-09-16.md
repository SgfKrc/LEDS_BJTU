# 同进程双后端接力：实现与性能（2026-09-16）

> 背景：实测跨进程 D→L 为 **1.44 s/步**（64 步 92 s），其中约 1.3 s 被判定为 Python 进程间通信开销。
> 用户裁决：**消除 D→L 的进程边界（同进程双后端）**；多卡/多节点方向排除（边缘设备集群凑不出规模）；
> **D 档永远有存在理由**（天然适合层间流水线 + 可做对照实验）。
>
> 性质：**实现 + 实测**。关联：[引擎单序列与并发性能对比](引擎单序列与并发性能对比-2026-09-16.md) · [网络接力辨析](跨框架接力与异构内存分层-辨析-2026-09-16.md)

| 项 | 结果 |
| --- | --- |
| **同进程双后端是否可行** | ✅ **可行**，且**数值与跨进程版完全一致**（64/64 步） |

## 1. 实现：为什么不需要 fork

上游 `llama.cpp` 的 `relay-gen-dl.cpp` 仅 176 行，其 hidden 注入机制是：

```cpp
llama_batch batch = llama_batch_init(n_tokens, n_embd_inp, 1);
memcpy(batch.embd, hidden.data(), hidden.size() * sizeof(float));
llama_decode(ctx, batch);
```

**`batch.embd` 是 llama.cpp 的标准 `llama_batch` 字段**（不是本项目 patch 的 API）。
因此 **PyPI 版 `llama-cpp-python` 的底层绑定即可完成同进程注入，无需重新编译、无需 fork**。

### 1.1 关键调用链（`llama-cpp-python` 0.3.28，基于 ctypes）

| 步骤 | API |
| --- | --- |
| 加载裁层模型 | `llama_model_load_from_file(path, model_params)` |
| 建 context | `llama_init_from_model(model, ctx_params)` |
| 每步清 KV | `llama_get_memory(ctx)` + `llama_memory_clear(mem, True)` |
| 构造批次 | `llama_batch_init(n_pos_per_embd * n_tokens, n_embd_inp, 1)` |
| **注入 hidden** | `ctypes.memmove(batch.embd, hidden.ctypes.data, hidden.nbytes)` |
| 解码 | `llama_decode(ctx, batch)` |
| 取 token | `np.ctypeslib.as_array(llama_get_logits_ith(ctx, n-1), shape=(n_vocab,)).argmax()` |

**版本提示**：本项目 `.venv-xframe` 装的是 **0.3.28**（主仓 `requirements-edge.txt` 要求 **0.3.35**）；
0.3.28 的绑定为 **ctypes**（`batch.embd` 是 `LP_c_float`），不是 cffi，故写入用 `ctypes.memmove`。

### 1.2 ⚠️ 两个踩坑记录（都有明确根因）

#### 坑 1：`0xC0000139 STATUS_ENTRYPOINT_NOT_FOUND`（exit=127）

**症状**：脚本导入 `llama_cpp` 后立即以 `127` 退出。

**根因**：为运行 MSYS2/MinGW 编译的 C++ exe 而 `export PATH="/c/msys64/ucrt64/bin:$PATH"`，
这个 PATH 让 `llama_cpp` 的 DLL **误加载 MSYS2 的 libstdc++**，入口点不匹配。

**修法**：**Python 进程不要注入 MSYS2 PATH**（那是给 C++ exe 的必要条件，对 pip 装的 DLL 反而有害）。

> 📌 与既有经验不冲突：`export PATH="/c/msys64/ucrt64/bin:$PATH"` 是**跑 MinGW exe** 的硬要求；
> 而 `llama-cpp-python` 的 DLL 自带运行时，**两者不能混在同一个进程环境里**。

#### 坑 2：`0xC0000374 STATUS_HEAP_CORRUPTION`（堆损坏）

**症状**：`llama_batch_free(batch)` 时崩溃。

**根因**：`#28963` 的调用方修法要求 **pos 数组按 `n_pos_per_embd * n_tokens` 提供**，
而 `llama_batch_init(n_tokens, ...)` 只分配 `n_tokens` 个槽位。
我最初的做法是**把 `batch.pos` 指针替换成 Python 的 ctypes 数组** —— 但 `llama_batch_free()`
会对它调用 C 的 `free()`，**释放一个非 malloc 指针 → 堆损坏**。

**修法**：**直接 `llama_batch_init(n_pos_per_embd * n_tokens, n_embd_inp, 1)`**，
让 llama.cpp 自己分配足够大的 pos（分配与 `free()` 天然配对），然后只把 `batch.n_tokens` 设为真实 token 数。
代价是 `embd` 也多分配 `n_pos_per_embd` 倍（本场景 ≤16 MB，可忽略）。

## 2. 实测：同进程 vs 跨进程（严格同配置）

**配置**：prompt = `The capital of France is`（5 token），gen = 64，下游 = `qwen35-2b-f16-cut.gguf`（从 layer 4 起），
上游 = torch f32 + eager，`threads=8`，下游纯 CPU（`gpu_layers=0`）。

| 版本 | 传输机制 | 总墙钟（64 步） | 一致步数 |
| --- | --- | ---: | ---: |
| **跨进程** | stdin/stdout 二进制管道（子进程） | **182 s** | 64/64 |
| **同进程** | `ctypes.memmove`（进程内内存） | **167 s** | 64/64 |
| 差异 | — | **−15 s（−8%）** | — |

**同进程版内部耗时拆解**（167 s）：

| 环节 | 耗时 | 占比 |
| --- | ---: | ---: |
| torch 上游加载 | 7.0 s | 4% |
| llama.cpp 下游加载 | 0.6 s | 0.4% |
| **下游 decode（64 步）** | **37.5 s**（**586 ms/步**） | 22% |
| **上游 torch 前向（64 步）** | **≈122 s**（**1.9 s/步**） | **73%** ⚠️ |

## 3. 分析：为什么只快 8%

### 3.1 IPC 确实被消除了，但它不是主要成本

原判「1.3 s/步是 IPC 开销」**过于乐观**。同进程后下游变成 586 ms/步，可见 IPC 的绝对量在**百毫秒级**，
而不是秒级。原因：`relay-gen-dl.cpp` 每步只传 **整段 hidden**（5→69 token × 2048 × 4 B ≈ 40–565 KB），
在本地管道上并不昂贵；且该子进程**常驻**（模型只加载一次），省掉了进程启动成本。

### 3.2 真正的瓶颈：上游 torch（1.9 s/步）

两个叠加原因（**均非实现缺陷，而是配置问题**）：

1. **无 KV 复用**：每步调用 `model(input_ids=full_seq, output_hidden_states=True)`，
   序列从 5 增长到 69，复杂度 **O(n²)**；而 llama.cpp 侧有 KV cache（O(n)）。
2. **算子回退**：transformers 明确警告
   - `causal_conv1d_fn` → *"falling back to its reference PyTorch implementation because `causal_conv1d` is not installed"*
   - `chunk_gated_delta_rule` → *"...`flash-linear-attention` is not installed"*

   **Qwen3.5 是 hybrid 架构（Gated Delta Net）**，这两条正是它的关键优化算子；
   缺失时回退到参考实现，**"much slower"**（transformers 原文）。

| 对照 | 单步耗时 |
| --- | ---: |
| 上游 torch（全段重算 + 无优化算子） | **1900 ms** |
| 下游 llama.cpp（5 层，全段重算） | 586 ms |
| （参考）llama.cpp **整模 28 层 GPU** | **13.5 ms**（74 t/s） |

### 3.3 结论（⚠️ 已被 §4 的实测修正）

> 初版结论说「消除进程边界是必要条件但不是充分条件」。**实测证明这个判断仍然过于乐观**：
> **进程边界根本不是主要成本（仅 8%），真正的杠杆是 KV 复用（3.15×）**。详见 §4。

## 4. 第二轮：双侧 KV 复用（决定性优化）

### 4.1 实现

`relay_sameproc_kv.py` 在 `relay_sameproc.py` 基础上让**两侧都走增量**：

| 侧 | 改动 |
| --- | --- |
| **上游** | 传 `past_key_values` + `use_cache=True`；prefill 喂整段，其后每步只喂 1 个 token |
| **下游** | 不再每步 `llama_memory_clear`；只注入**新增的末位 token** 的 hidden（`n_tokens=1`），`pos` 用绝对位置递增 |
| 传输量 | ~565 KB/步 → **8 KB/步** |

**⚠️ 实现中踩到的坑**：初版在 prefill 那一步**只传了最后 1 个 token 的 hidden**
（因为 `past` 已被赋值，无法区分首步），导致下游缺少前 4 个 token 的 KV，
输出退化为 `369 369 369 ...`。修法：在覆盖 `past` **之前**先记录 `is_prefill`，prefill 传整段。

### 4.2 实测（同配置，gen=64）

| 版本 | **总墙钟** | 上游/步 | 下游/步 | 一致步数 |
| --- | ---: | ---: | ---: | ---: |
| 跨进程 + 全段重算 | 182 s | 1900 ms | 586 ms | 64/64 |
| 同进程 + 全段重算 | 167 s | 1900 ms | 586 ms | 64/64 |
| **同进程 + 双侧 KV** | **53 s** | **287 ms** | **151 ms** | **64/64** |
| **累计加速** | **3.4×** | **6.6×** | **3.9×** | ✅ 一致保持 |

**分解各手段的单独收益**：

| 手段 | 收益 |
| --- | --- |
| 消除进程边界（同进程） | **8%**（182 → 167 s） |
| **KV 复用（两侧增量）** | **3.15×**（167 → 53 s）✅ |

### 4.3 结论修正

> **真正的杠杆在算法/数据流层面，不在传输层面。**
> 消除进程边界只值 8%；**KV 复用值 3.15×**。这与用户在「分块流水线」上的一贯判断一致 ——
> llama.cpp 的优势同样来自 prefill 分块与 KV 复用，而非传输。
>
> **KV 复用不破坏数值一致性** —— 64/64 逐 token 一致（增量与全段重算在 argmax 判据下等价）。

### 4.4 但仍远未可用

| 对照 | 每步耗时 |
| --- | ---: |
| 本项目跨框架（**同进程 + KV**） | **828 ms** |
| llama.cpp 原生整模 GPU（28 层） | **13.5 ms** |
| **差距** | **61 倍** ⚠️ |

**残留开销定位**：

1. **上游 287 ms**：`output_hidden_states=True` 每步都需保留 hidden；且 **Gated Delta Net 算子回退** ——
   `flash-linear-attention` 依赖 **triton**，而 **triton 无 Windows 官方 wheel** → 本机无法启用；
   `causal-conv1d` 需 nvcc 编译，pip 安装失败。**⚠️ 这是环境限制，不是架构限制**（Linux 上可用）。
2. **下游 151 ms**：按 llama.cpp 整模折算 5 层应约 **15 ms**，**存在 ~10 倍固定开销** ——
   指向 Python 调用 llama.cpp 的**逐次固定成本**（`llama_batch_init`/`llama_batch_free` 的 malloc 对、
   每次取 248320 元素 logits）。

### 4.5 下一步（更新版）

| 优先级 | 动作 | 针对性 |
| ---: | --- | --- |
| **1** | **复用 `llama_batch`**（不在每步 `init`/`free`，只改字段） | 下游 ~10× 固定开销 |
| **2** | 只取 logits 的 **argmax**，避免构造整个 numpy 视图 | 同上 |
| 3 | 下游开 GPU offload（`--gpu-layers`） | 与层间流水线场景对齐 |
| 4 | **Linux 上复测**（triton 可用，可启用 fla 加速算子） | 隔离 Windows 环境限制 |
| 5 | 上游改用 `model.model.layers[:4]` 手动前向，避免无谓跑完 28 层 | 上游 287 ms |

## 5. 对 D 档（PyTorch 引擎）的含义

用户裁决「**D 档永远有存在理由**」在本轮得到支撑：

| D 档的不可替代性 | 本轮证据 |
| --- | --- |
| **天然适合层间流水线** | 同进程双后端已验证可行（`relay_sameproc.py`），且是**层流水线的最简载体**（层切分点可任意移动） |
| **可做对照实验** | 同一模型两条实现路径对拍：跨进程 / 同进程 / 纯 llama.cpp / 纯 torch，四条路径并存且可逐 token 比较 |
| ⚠️ **但性能仍需证明** | 当前端到端 **2.6 s/步**（167 s / 64 步）**远慢于** llama.cpp 原生 GPU（13.5 ms/步）——**D 档的价值在当前实现下是"能力"而非"性能"** |

**⚠️ 必须诚实的边界**：本文**没有**证明 D 档在性能上有竞争力。
它目前证明的是：**跨框架接力在正确性上可靠、在进程边界上可消除**，而**性能瓶颈在上游 PyTorch 侧**。
