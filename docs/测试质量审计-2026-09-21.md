# 测试质量审计报告（2026-09-21）

> 范围：主仓 `tests/`（213 个文件 / 60764 行 / 单元通道 3074 用例）。
> 方法：**只读审计 + 重复执行取证**，本轮**未改动任何代码**（被测代码与测试代码均未动）。
> 结论均可复现，命令见附录。

## 0. 摘要

### 0.1 实测结论：并行执行确实是 flaky 的来源，且串行会掩盖它

| 执行方式 | 结果 | 耗时 |
| --- | --- | --- |
| 全量单元通道 **并行**（`-n 4 --dist loadscope`）第 1 次 | **1 error** | 12.52 s |
| 全量单元通道 **并行** 第 2 次 | 3059 passed / 16 skipped | 275.04 s |
| 全量单元通道 **并行** 第 3 次 | **1 failed** / 3058 passed / 16 skipped | 264.68 s |
| 全量单元通道 **并行** 第 4 次 | 3059 passed / 16 skipped | 240.53 s |
| 全量单元通道 **并行** 第 5 次 | 3054 passed / **21 skipped** | 231.93 s |
| 全量单元通道 **串行**（`-n 0`） | 3058 passed / 16 skipped | 539.89 s |

- **并行 5 次里 2 次异常（≈40%）**，而**串行 1 次全绿**。串行不是"更稳"，而是**把并行暴露的
  竞态窗口挤掉了**——这正是需要防范的掩盖效应。
- 另外注意**第 5 次 skip 数从 16 漂到 21**：连"条件跳过"都不稳定（见 §3.4）。
- 定位到的 flaky 用例（第 3 次）：`tests/test_island_engine.py::test_backend_down_raises_clean_transport_error`，
  期望"后端不可达 ⇒ 干净传输错误"，实际拿到 **HTTP 502**（见 §3.3）。

### 0.2 制度性缺陷（三条，均与"看不见"有关）

1. **两条并行路径的语义不一致**：`pytest.ini` 只写 `-n 4`（`--dist` 默认 `load`，**按单个测试**分发），
   而 `scripts/run_test_channels.py` 显式 `--dist loadscope`（**按模块/类**分发）。同一份测试，
   两种粒度下"同模块内是否并发"不同 ⇒ 复现问题的难度与暴露面都不同（§2）。
2. **隔离/降级标记形同虚设**：`@pytest.mark.slow`、`@pytest.mark.external`、`@pytest.mark.requires_gpu`、
   `@pytest.mark.quality_gate` 用量**全为 0**（只有 `real_model` 4 处）。因此单元通道里那句
   `-m "not external and not ... and not slow and not requires_gpu"` **实际排除不掉任何东西**
   —— 需要外部资源的用例混在"单元通道"里跑（§4.2）。
3. **flaky 不可观测**：`pytest-rerunfailures` / `@pytest.mark.flaky` / `@pytest.mark.xfail` / `pytest-randomly`
   用量**全为 0**，`--junitxml` 未在通道脚本中落盘 ⇒ 失败一旦发生就**没有工件**（本次审计中第 1 次
   的 `1 error` 详情就是因为没留日志而丢失，只能重跑才拿到 §3.3 的证据）。

## 1. 审计方法

- **静态**：对 `tests/*.py` 做模式统计（并发原语、端口、时序、隔离习惯、弱断言），并对可疑项
  逐条核验（例如"固定端口 8888"与"`os.environ` 改动"两条都被证据否掉，见 §4.1）。
- **动态**：选并发/网络原语最密集的 7 个文件做高风险子集，并行×3 + 串行×2；再做全量单元通道
  并行×3 + 串行×1（另有一次更早的并行异常，未留日志）。
- **归因**：对失败用例读源码、核验端口分配方式、核验代理环境变量（排除法）。

## 2. 执行模型（这是本次审计最关键的一节）

| 入口 | 并行参数 | 分发粒度 | 同模块内测试 |
| --- | --- | --- | --- |
| `pytest`（读 `pytest.ini`） | `-n 4` | `--dist load`（默认） | **可能并发** |
| `scripts/run_test_channels.py`（unit 通道） | `-n <workers> --dist loadscope` | 模块/类 | **串行** |

后果：

- 走通道脚本时，**同一模块内的用例被绑在同一 worker 顺序执行**。若某个模块的用例本该"互相干扰"
  （共享端口、共享文件、共享内存态），它们在通道脚本里**永远不会互相踩到**；而在直接 `pytest` 下会。
- 更隐蔽的是：**"并发覆盖"实际上取决于测试自身是否构造并发**。`-n 4` 只让**测试之间**并行，
  若测试内部不起线程，产品代码里的竞态依旧测不到（§5 的覆盖差距就是这么来的）。
- `--maxfail=3` 会在第 3 个失败处停止 ⇒ 一旦出现 flaky 失败，**后面的用例根本没跑**，
  统计上会低估问题规模（也解释了 §0.1 第 1 次表现为"1 error 就结束"）。

## 3. 实测证据

### 3.1 高风险子集（7 个并发/网络密集文件，596 用例）

| 轮次 | 结果 | 耗时 |
| --- | --- | --- |
| 并行 run1 | 596 passed | 38.62 s |
| 并行 run2 | 596 passed | 37.70 s |
| 并行 run3 | 596 passed | 39.78 s |
| 串行 run1 | 596 passed | 80.18 s |
| 串行 run2 | 596 passed | 73.52 s |

⇒ 这个子集**本身是稳定的**（并行/串行都绿），说明 flaky 不在"看起来最像并发"的那批文件里，
而在**全量交叉影响**下才出现 —— 这与"端口被别的模块复用"的归因一致。

### 3.2 全量：并行不稳、串行全绿

见 §0.1 表。并行最慢一次 275 s、串行 540 s，说明 `-n 4` 的加速比约 2×（不是 4×，因为大量用例
受 GIL/IO/单核冷启动限制）。

### 3.3 定位到的 flaky 用例与归因

失败信息（RUN3）：

```
tests\test_island_engine.py:338: in test_backend_down_raises_clean_transport_error
    engine.load_model(base_url=f"http://127.0.0.1:{port}", ...)
E   island_engine.IslandHTTPError: 岛后端 HTTP 请求 GET http://127.0.0.1:59049/v1/models 返回状态码 502
```

该用例**已经知道**这个问题并做了缓解（源码注释原文）：

```python
# _closed_port 释放端口后存在竞态窗口（全量运行时端口可能被其他测试复用），
# 连接成功（未抛异常）时换端口重试，最多 5 次。
for attempt in range(5):
    port = _closed_port()
    ...
```

`_closed_port()` 的实现是典型的 TOCTOU：

```python
sock = socket.socket()
sock.bind(("127.0.0.1", 0))      # 系统分配一个空闲端口
port = sock.getsockname()[1]
sock.close()                     # ← 关掉后端口就"自由"了
return port
```

归因（逐条排除后）：

1. **不是代理环境泄漏**：本机 `http_proxy`/`https_proxy`/`no_proxy` 均为空；`tests/` 里只有
   `NO_PROXY` 的 `monkeypatch.setenv`（会被自动还原），没有设置代理的用例。
2. **不是产品代码的竞态**：502 是**服务端真实返回的状态码**（`src/island_engine.py:261`
   `if response.status_code != 200: raise IslandHTTPError(...返回状态码 {response.status_code})`）。
3. ⇒ **是测试基础设施的竞态**：`_closed_port()` 放出的端口在"放"与"用"之间被**同一批并行执行中的
   另一个测试的 mock server**（本文件的 `ThreadingHTTPServer` 等）绑上，于是"期望连不上"变成
   "连上了并返回 502"。5 次重试只是降低概率，没有消除窗口。

**这类问题正是"串行会掩盖"的样板**：串行时端口不会被别的用例抢走，用例稳定通过。

### 3.4 skip 数漂移（16 → 21）

第 5 次并行运行比其余各次多了 5 个 skip。说明有测试的**跳过判定依赖运行时状态**
（资源可用性/时序/前序用例状态），而不是纯静态条件。这会带来两个后果：① 覆盖率在运行之间
不可比；② 某些并发问题会被"跳过"而不是"失败"，更难发现。

## 6. "没有统计学断言 flaky"应当怎么理解

先纠一个措辞：仓库里**统计类断言是有的** —— `pytest.approx` 72 处、阈值断言（`< 0.` / `> 0.`）
20 处、`percentile/p95/p99` 27 处。欠缺的不是"用统计方法写的断言"，而是**把 flaky 当成可观测量**。

- 现有断言绝大多数是**确定性判定**（等值、集合相等、阈值），因此**不会**因为"统计波动"而随机失败。
  这也是为什么"看起来没有统计意义上的 flaky"。
- 但**竞态的本质是时序相关的一次性事件**：同一输入、同一代码，两次运行结果不同。它天然不是
  "统计分布"问题，而是"是否碰到那个窗口"的问题。**所以统计断言解决不了竞态**，能解决它的只有三件事：
  1. **重复执行**（把偶发变成可观测）；
  2. **真并发 / 确定性交错**（`Barrier` + 假传输 + 种子可复现）；
  3. **失败留证**（JUnit/日志/失败用例名），否则一切归因都是猜。
- 本仓当前恰好**三条都缺**（§0.2 第 3 条 + §2 的 `--maxfail=3` 截断 + §5 的覆盖差距），
  于是"经常有并发 flaky"就只能停留在体感层面 —— 本次审计用 5 次重复执行把它变成了 40% 的
  可复现数字，这正是缺观测性的直接代价。

## 7. 建议（按优先级，均不需要改产品代码）

### P0 — 观测性（成本最低、收益最大）

1. 通道脚本落 `--junitxml`，并把失败运行的完整日志留档（`build/audit/` 下已示范）；
2. 增加**重复执行**入口（`pytest-repeat` 或自建循环），只用于**记录** flaky（失败用例名 + 次数），
   **不要**用 `rerunfailures` 把失败重试成绿——那是把问题藏起来；
3. 引入**随机顺序**（`pytest-randomly`）并在失败时输出种子：这是暴露"顺序依赖/残留状态"最便宜的手段，
   当前顺序固定等于放弃这一整类问题的探测能力。

### P0 — 修已定位的 flaky 用例

4. `test_island_engine.py::test_backend_down_raises_clean_transport_error`：把 `_closed_port()`
   从"bind→close→return"改为**保持 socket 打开**直到请求发出（或使用不可路由地址如
   `127.0.0.1:<保留端口>`/`192.0.2.1`），使"不可达"成为**结构性保证**而不是概率保证；
   断言也应放宽为"必须是不可达/超时错误"，与现在的重试语义一致。
5. 搜同族辅助函数（`_closed_port`、`free_port`、`_free_port` 等）统一处理。

### P1 — 通道可信度

6. 给实际需要外部资源/重资源的用例补 `external` / `slow` / `requires_gpu` 标记，
   让单元通道的 `-m` 排除条件**真的生效**；
7. 统一并写清并行语义：默认用 `--dist loadscope`（模块内串行，降低互扰）**同时**保留一个
   "真并发通道"（`-n 4 --dist load`）专门用于暴露互扰；两者都进 CI，结果分开记录。

### P2 — 竞态覆盖

8. 对 `tui_textual` / `api_server` / `tcp_comm` / `task_worker_adapter` 补 `Barrier` 型确定性交错测试
   （照 `test_task_graph_fencing.py` / `test_t_race5_soak.py` 的写法）；
9. 把以 `time.sleep` 充当"等就绪"的地方改为 `Event.wait(timeout=...)`（既更快也更少 flaky）。
