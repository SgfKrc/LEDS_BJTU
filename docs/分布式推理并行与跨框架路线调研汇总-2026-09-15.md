## 0. 执行摘要

四份调研（A 并行手段 / B 开源引擎 / C 跨框架逐层接力 / D ExecuTorch）以及本次 Silica Cluster 外部复核指向同一结论：

**在本机（RTX 4060 Laptop 8GB + 16GB RAM / 无 CUDA 从节点 / ~1GbE）组合下，唯一被证据支持的并行化方向是"只传 token"的并发与能力分工（continuous batching、draft-verify、级联/路由、prefix cache）；所有"模型切分"方向（张量并行、序列并行、跨框架层接力）目前没有可行落地路径；开源侧也不存在可直接集成的跨异构推理引擎。**

本次新增的 [Silica Cluster](https://github.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI) 证明了“Android 原生应用承载 llama.cpp RPC worker”这条工程路径可以实现，但没有证明 QLH 所需的跨节点连续 `layer_range` 协议已经存在。它应进入 Android/GGUF RPC 的验证候选，而不是改写 D 档主线。

| 调研 | 一句话结论 | 证据强度 |
| --- | --- | --- |
| **A 异构并行手段** | 真瓶颈是弱节点算力与每步同步，**不是带宽**；可行项=只传 token 类 | 中（含仓内代码证据；体积/时延为算术估算） |
| **B 开源分布式推理引擎** | **无可直接集成者**；值得借鉴 `accelerate device_map` / `petals` / `ktransformers` / `exo`；新增对照候选 `distributed-llama` 与 Silica Cluster | 中（部分版本/star/近况未核实；Silica 代码已核对） |
| **C 跨框架逐层接力**（远期） | **当前不推荐开工**：llama.cpp 无公开中间层 hidden 读写 API，上游 issue 仍 open | 强（上游原文 + issue） |
| **D ExecuTorch**（**实验先行**，用户裁决） | **不设前置条件，实验立即立项**（`CORE-ET-EXP-01`，独立环境）——Qwen3-4B `.pte` 导出 → 真机对照 → 产出决策证据；**是否接入主项目另行裁决**。事实基础：Qwen3 支持=Llama 示例参数化复用（1.4 起新增 Qwen3-VL export/eval 覆盖）；无官方 Qwen3 端侧数据；Android API 已在 1.4 **完成** Java→Kotlin 迁移 | 中（官方 release notes；无 Qwen3 真机数据） |

## 1. 调研 A：异构设备上的非线性并行手段

### 1.1 事实基线（本地代码核实）

| 证据 | 位置 | 含义 |
| --- | --- | --- |
| `PIPELINE_MAX_CONCURRENT = 1` | `src/config.py:366` | D 档层流水线当前**串行**：同一时刻只有一个节点在算 |
| `PipelineQueue` / `compute_layer_assignment` | `src/scheduler.py:387/2448` | 已有层分配与队列基础，但未做 micro-batch 交叠 |
| 单序列 `llama_decode`（`n_batch = 64`） | `src/llama_engine.py:663-697` | L 档侧当前是**单请求**解码，未启用 continuous batching |

### 1.2 手段评估

| 手段 | 原理 | 本机可行性 | 关键限制 |
| --- | --- | --- | --- |
| Continuous batching（llama-server） | 多请求在服务端动态合批 | ✅ 可行 | 依赖 llama-server 常驻；QLH 侧需接线 |
| 多请求流式交叠 | 串行流水线内交错 micro-batch | ✅ 可行（改造量大） | 需要调度层重写 + 队列/取消/超时语义 |
| 非均匀层分配 | 按显存/算力比例切层 | ✅ 可行 | 需真实标定每层耗时（当前缺失） |
| draft-verify / 投机解码 | 小模型草稿 + 大模型校验 | ⚠️ 受限 | 见 `EX-SPEC-ROLE-01`：本机实测混合词表族不可用、最好仅 1.342× 且分布一致性 fail |
| 级联 / 路由 | 小模型先答、大模型兜底 | ✅ 可行 | 需要质量判据与回退策略（纯调度层，无新依赖） |
| 本地 prefix cache / 会话级 KV 复用 | 复用前缀命中 | ✅ 可行 | 单机内收益明确；跨节点迁移不划算 |
| 跨节点张量并行（TP） | 层内切分 | ❌ 不可行 | 要求同构 GPU + 高带宽互联 |
| 序列/上下文并行 | 序列切分 | ❌ 不可行 | 每步同步 + 带宽门槛 |
| 专家并行（MoE-EP） | 专家分布 | ❌ 不可行 | 本机模型非 MoE；异构下通信开销压倒收益 |
| prefill/decode 分离 | 两阶段分离部署 | ❌ 不可行 | KV 需跨节点搬运（~200KB/token 估算） |
| KV 迁移 / 跨节点缓存 | 缓存移动 | ❌ 不可行 | 同上网带宽门槛 |

### 1.3 伪并行清单（必须避免）

跨节点 TP、跨框架逐层接力、prefill/decode 分离与 KV 迁移、训练式 1F1B/zero-bubble、hidden 压缩、RAM 受限的多副本——这些在本机组合下"看起来并行、实际受带宽或串行依赖限制"。

### 1.4 D 档三个优先改进（按性价比）

1. **真实标定 + 非均匀层分配**：先测每层真实耗时与内存，再按比例切层（当前分配缺依据）；
2. **多请求流式交叠**：在 `PipelineQueue` 上引入 micro-batch 交错（把 `PIPELINE_MAX_CONCURRENT=1` 变成可配置且可解释）；
3. **会话级 KV 复用 + 队列优先级**：先做单机收益最大的缓存复用，再叠加优先级调度。

> 估算说明（非实测）：decode 每跳 hidden 约 4KB（1.8B/24 层/hidden 2048/bf16 估算）、KV 约 200KB/token——两者差 50×，这是"带宽不是瓶颈、同步才是"的判断依据。

## 2. 调研 B：开源分布式推理引擎

### 2.1 核心结论

**2026-09 不存在"生产级 + 跨异构（8GB CUDA + 无 CUDA 节点）+ Transformer 层/张量拆分"的开源方案。** QLH 的三形态决策正落在这个真空里；没有"直接换引擎"的选项。

### 2.2 分档推荐

| 档位 | 项目 | 理由 / 风险 |
| --- | --- | --- |
| **值得借鉴设计**（不直接引入） | `accelerate` `device_map` | 零新依赖的同机异构**上界基线**（做对照极合适） |
| | `petals` | 层流水线 + 私有 swarm 语义最贴近 QLH 形态；**2024-09 后停更** |
| | `ktransformers` | CPU 侧 AMX/AVX2 kernel 与 hot/cold 放置思路可借鉴 |
| | `exo` | 拓扑感知放置协议；但 Linux 侧目前仅 CPU 后端 |
| **仅作对照实验** | `b4rtaz/distributed-llama`（**新发现**） | 纯 C++ 跨机张量并行、无 torch、CPU worker 可参与；限制：节点数必须 2ⁿ、节点上限 = KV heads 数、量化组合受限（q40/f32） |
| | llama.cpp `--rpc` | 上游自述 PoC/fragile/insecure（本地主线计划 §2.2 已登记） |
| | PowerInfer / MLC-LLM / Xinference / OpenLLM | 定位或异构能力不匹配 |
| **不建议** | TensorRT-LLM / LMDeploy / TGI | 强绑定 NVIDIA 栈或已转维护模式（TGI 为未证实传闻） |

#### 2.2.1 新增候选：Silica Cluster（Android + llama.cpp RPC）

- **已确认**：仓库提供 Android 应用、`libllama.so` 主节点和 `librpc.so` worker 的运行路径；README 说明 worker 处理模型张量并通过 pipeline parallelism 协作。
- **源码核对**：[BinaryRunner.kt](https://raw.githubusercontent.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI/main/app/src/main/java/io/github/shintochakkiath/silicacluster/BinaryRunner.kt) 通过 `--rpc` 接入节点；没有层数元数据时使用比例 `--tensor-split`，有层数时把剩余层数传给 `-ngl`。后者是“最多装载多少层”的 offload 参数，不是跨节点连续层段描述。
- **工程边界**：[SilicaService.kt](https://raw.githubusercontent.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI/main/app/src/main/java/io/github/shintochakkiath/silicacluster/SilicaService.kt) 的 full-offload 路径会先把完整 GGUF 上传到主 worker，再启动远端引擎；节点身份、模型摘要、层段租约、故障恢复和认证协议尚未达到 QLH 的生产合同要求。README 也明确提示本地 RPC 未加密。
- **结论**：Silica 是 Android/GGUF RPC 的真实候选和实现参考，不是 QLH PyTorch 层流水线的替代品，也不构成“跨 Android 节点精确按层拆分”已被验证的证据。
- **许可证**：仓库采用 AGPLv3；QLH 只参考协议边界和验证方法，不复制其 Android 代码，若未来直接集成必须单独做许可证与发布形态评估。

### 2.3 三个关键问答

- **a. 混合设备（含无 CUDA 节点）跑 Transformer 有成熟方案吗？** 没有。现有分布式引擎都以"同构加速器 + 高带宽互联"为隐含前提。
- **b. 若增强 D 档层流水线，最值得试点什么？** `accelerate device_map` 零依赖上界基线（同机异构分层放置）与 `distributed-llama` 2 节点对照；最小验证：同一模型两种放置下对拍输出 + 计时。
- **c. 有没有方案能替代"L 档 llama.cpp 单机 + 任务池"？** 没有更优解；Xinference/OpenLLM 的"分布式"只是副本层且强绑 torch 生态。

## 3. 调研 C：跨框架逐层接力（远期方向，2026-09-15 结论：不推荐开工）

### 3.1 核心障碍（上游原文支撑，强度：强）

| 障碍 | 事实 | 来源 |
| --- | --- | --- |
| llama.cpp **无公开中间层 API** | 公开接口只提供 token embedding（`llama_batch.embd`，`n_embd` 维）与 logits；post-block residual 无公开读写通道 | llama.cpp 上游 issue **#27112**（open，2026-08-15）："没有公开方式读取中间层，需要的人都在维护私有 fork" |
| 层间观测需自研补丁 | 只能走 `ggml_backend_sched_set_eval_callback` 一类内部钩子 | 同上（ggml-backend.h 全文抓取） |
| 先例不对口 | Petals = **同框架**（PyTorch）层接力；KTransformers = **算子级**混合（非 hidden 交接）；distributed-llama = **张量并行**（非层接力） | 各自 README（抓取） |
| 层语义差异（待 PoC 核对） | QKV 融合布局、RMSNorm eps、GQA 布局、RoPE 实现、attention mask 约定——GGUF 与 HF 导出逐层差异需 `convert_hf_to_gguf.py` / `gguf-py` 逐项核实 | **标注为待核对**（本次未逐项验证） |
| 量化误差累积 | **未查到**公开的跨框架逐层误差测量 | 未查到 ≠ 不存在 |

### 3.2 最小 PoC（若将来重启，5 步 + 判据）

1. 单机内用带钩子的 llama.cpp 补丁取第 k 层 hidden；
2. 同一权重在 PyTorch 侧复现前 k 层，逐层对拍；
3. 未量化路径判据：**cosine ≥ 0.999** 视为对齐（否则终止）；
4. 换 Q4_K_M 路径重测，记录误差是否随层数放大；
5. 只有前两步成立，才评估跨节点传输与协议设计。

### 3.3 重启条件（满足任一）

- llama.cpp 上游提供**公开**中间层读写 API（issue #27112 关闭）；
- QLH 需要一个**无法用"只传 token"方案解决**的异构分工场景（例如某设备只能承担特定层且必须跨框架）；
- D 档串行流水线被证明是首要瓶颈，且 micro-batch 交叠已到上限；
- 出现成熟的第三方跨框架层接力项目可直接引用。

## 4. 调研 D：ExecuTorch（2026-09-15 用户裁决：实验先行、接入另议）

### 4.1 关键事实（官方页面与 release notes，抓取于本次会话）

| 维度 | llama.cpp/GGUF（QLH 现状） | ExecuTorch | 结论 |
| --- | --- | --- | --- |
| Qwen3 支持 | 完整（GGUF 转换 + K-quant 全谱） | **本质是 Llama 示例的参数化复用**（官方原文："Qwen 3 uses the same example code as our optimized Llama model"，仅 `model_class` + config 差异） | 无独占优势 |
| 端侧性能数据 | QLH 侧**无真机基线**（未测） | 官方**无 Qwen3 数据**；只有 Llama 3.2 1B/3B（OnePlus 12：3B 4bit SpinQuant 19.7 t/s）与 Llama 3 8B（S22 7.85 / S24 10.91 t/s） | 不可直接比较 |
| Android API 稳定性 | 自有 JNI（`libqlh_llama_jni.so`，`android/app/src/main/cpp/CMakeLists.txt:50,52`） | **Java→Kotlin 迁移已完成**：v1.4.1（2026-08-14）release notes 原文 "Migrated Android Module, TrainingModule, SGD, and LLM extension APIs from Java to Kotlin"，Kotlin 成为主 API（stable 文档尚停在 1.3 的 Java library 表述） | "会返工"的风险已解除，绑定时机成熟度上升 |
| 官方覆盖进展（1.4 新增） | — | **SmolLM2 与 Qwen3-VL 的 export/evaluation 覆盖**（1.4 Highlights）；`GenerationConfig` 新增 `grammar`/`grammar_type`（结构化输出） | 对 QLH 的 Qwen3-VL-4B 工件是利好，列入观察指标 |
| 量化/NPU | K-quant 全谱 | low-bit kernels "still experimental"、NPU LLM 量化 "work underway"、Vulkan LLM 在 "What is coming next" | ExecuTorch 当前更弱（实验要核实的关键差异点） |
| 多模态 | **已接 MTMD（mmproj GGUF）** | 未查证 | 现状领先 |
| 分发体积 | .gguf 单文件 | AAR 按后端拆分（xnnpack/qnn/vulkan），仅 arm64-v8a / x86_64；**具体体积未查到** | 实验采集项 |

### 4.2 决策（用户 2026-09-15）：实验先行，接入另议

**策略变更**：不再采用"等 GGUF 硬缺口或真机 >1.5× 才立项"的条件式观察；改为**主动实验**——ExecuTorch 实验本身**立即立项**（票 `CORE-ET-EXP-01`，独立环境，不阻塞主线），**是否接入主项目（第三引擎 / Android 端侧替代）另行裁决**；实验价值不依赖接入结论。

**实验目标（不预设结论）**：
1. 独立环境用官方链路导出 Qwen3-4B `.pte`（int4），记录转换链路与算子覆盖；
2. Android 真机跑通，采集 TTFT / decode t/s / RSS / 体积；
3. 与现有 GGUF + llama.cpp（`libqlh_llama_jni.so`）在同机同量化级别对照；
4. 产出可复现证据（数据 + 命令 + 版本号），作为后续裁决依据。

**接入裁决条件（实验后再评估，需至少满足其一）**：
- GGUF 出现**硬能力缺口**（某目标模型无法转换/量化）且 Android 有明确需求；
- 真机同量化级别 **decode t/s 领先 > 1.5×**（实测量，非官方页面数字）；
- Kotlin 生态集成在工程成本/维护性上**显著优于**现有 JNI 路径（需量化对比）。

### 4.3 实验步骤（已立项：`CORE-ET-EXP-01`）

① 独立环境导出 Qwen3-4B `.pte`（int4）→ ② 真机验证与现有 JNI **同进程共存** → ③ TTFT / decode t/s / RSS / 体积对照 → ④ 记录算子覆盖与输出质量差异 → ⑤ 出报告交裁决（接入与否另议）。

环境隔离要求：实验依赖**不进入** L 档边缘安装与主仓运行时（"无 torch 可运行"硬约束保持）；实验产物与脚本独立存放，不并入主线发行。
