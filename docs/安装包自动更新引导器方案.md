## 1. 结论与当前边界

QLH 需要把“安装/修复/更新”与“运行推理应用”拆开。完整应用含 torch、transformers、模型检查、Tailscale、数据库和 Web 服务；任一运行依赖损坏时，都不应把更新入口一并拖垮。因此当前实现采用游戏启动器式的独立 Bootstrap：

```text
QLH Launcher Setup（小、独立）
        │
        ├── GUI / TUI 双前端
        ├── 检测已安装应用与 CPU/CUDA 变体
        ├── 并行查询更新清单
        ├── 下载到 .part、大小校验、SHA-256 校验、原子改名
        └── 启动主应用或系统安装器

QLH Edge Inference Setup（大、完整）
        ├── torch / transformers / llama.cpp / FastAPI / 前端
        ├── 模型、集群、数据库和推理运行时
        └── 原有启动页与应用运行生命周期
```

当前两个 Setup **已经在源码和构建脚本层面分离**：

- `packaging/setup-launcher.iss`：只安装 `QLH-Launcher.exe`，使用独立 AppId 和 `%LOCALAPPDATA%\Programs\QLH-Launcher`。
- `packaging/setup.iss` / `setup-cuda.iss`：继续安装完整 CPU/CUDA 主应用，不依赖 Launcher 才能运行。
- `packaging/qlh_launcher.py`：独立 GUI/TUI Bootstrap，不导入 torch、transformers、FastAPI 或推理模块。
- `packaging/update_core.py`：纯标准库清单、版本、下载和校验核心。
- `packaging/updater.py`：CLI 更新入口；可由 GUI、TUI 和 `bjtu update` 复用。

当前仍没有宣称完成以下能力：

- Windows/Linux 主应用安装后的真实发现、切换、失败回滚和干净机验收尚未完成；这不等同于 Launcher ZIP 双槽闭环已完成。
- 主应用差分更新和 Android 应用内更新尚未完成；发布清单默认必须通过内置 Ed25519 信任集验签，`--allow-unsigned` 仅保留给显式 CLI 调试路径。
- 没有 Android 应用内更新。
- 本轮不做分布式真机测试，启动器实现不改变推理/分布式代码。

## 2. 为什么必须与主应用分离

旧形态由 `QLH-Edge-Inference.exe` 同时承担启动页和应用启动。它能显示进度、选择 GUI/TUI，但仍属于完整 PyInstaller 应用的一部分，存在三个结构性问题：

1. 主应用缺 DLL、Python 包或资源时，用户可能连修复入口都打不开。
2. 更新主应用时进程会占用自身文件，覆盖和回滚边界不清晰。
3. 每次只想检查版本，也要先承担大应用的启动成本。

独立 Launcher 的稳定契约应保持很小：标准库网络、JSON、SHA-256、进程启动和一个轻量 GUI。推理依赖只能存在于主应用边界内。

Setup 和 Launcher 的职责不同：

| 组件 | 职责 | 是否包含推理环境 | 生命周期 |
|---|---|---:|---|
| Launcher Setup | 首次安装/更新独立 Bootstrap | 否 | 可单独升级和修复 |
| Launcher | 发现应用、选择 GUI/TUI、检查/下载/启动更新 | 否 | 主应用停止时仍可运行 |
| 主应用 Setup | 安装完整 CPU/CUDA 应用 | 是 | 由系统安装器负责覆盖/卸载 |
| 主应用 | 模型、集群、数据库、推理、Web/TUI | 是 | 不负责替换自身文件 |

## 3. 当前实现

### 3.1 入口

Windows 开发环境：

```powershell
bjtu launcher        # 打开独立 GUI Launcher
bjtu ui              # 经 Launcher 启动普通界面
bjtu tui             # 经 Launcher 启动管理 TUI
bjtu update          # 只检查更新
bjtu version         # 显示当前应用版本
```

独立 CLI：

```powershell
python packaging/qlh_launcher.py --gui
python packaging/qlh_launcher.py --tui
python packaging/qlh_launcher.py check --json
python packaging/qlh_launcher.py download --variant cpu
python packaging/qlh_launcher.py install --variant cuda --yes --allow-unsigned
```

Linux `.deb` 构建会安装：

```text
/opt/qlh-edge-inference/bin/qlh-launcher   # 新 Bootstrap
/opt/qlh-edge-inference/bin/qlh-app        # 旧应用启动载荷
/opt/qlh-edge-inference/bin/update_core.py
/opt/qlh-edge-inference/bin/updater.py
```

Linux Bootstrap 启动主应用时优先调用包内 `venv/bin/python` 执行 `qlh-app`，使推理依赖与系统
Python 隔离；仅为兼容旧包才回退到 `qlh-app` 自身的 shebang。

### 3.2 应用发现

Launcher 按以下顺序发现主应用：

1. `QLH_APP_HOME` 环境变量；
2. Launcher 状态文件中的 `app_path`；
3. Launcher 同目录/父目录；
4. Windows 的 Program Files 和用户级 Programs 常用安装目录；
5. 开发仓库中的 `packaging/launcher.py`。

未发现应用时，Launcher 保持可用并提示先安装；不会因为主应用缺失而崩溃。

### 3.3 设备变体

自动画像只用于给出默认值：找到 `nvidia-smi` 时默认 `cuda`，否则默认 `cpu`。GUI 下拉框和 TUI 菜单允许用户显式改为 CPU 或 CUDA，避免 NVIDIA 机器无法主动安装通用集显包。

| 平台 | 变体 | 清单匹配 |
|---|---|---|
| Windows | `cpu` | 集显/通用 Setup EXE |
| Windows | `cuda` | CUDA Setup EXE |
| Linux | `cpu` / `cuda` | 对应 `.deb` |
| Android（预留） | `full` / `lite` | 对应 APK/AAB |

### 3.4 更新源

默认查询内网分发源和 Git release 清单；也可通过 `--source`、`QLH_UPDATE_SOURCE` 或状态文件覆盖。多个源**并行**查询，选择可用清单中的最高项目版本，失败源只作为诊断信息返回，避免串行超时累加。

项目版本兼容三段和四段形式，例如：

```text
0.1.8 < 0.1.8.1
0.1.8.1-rc.1 < 0.1.8.1
```

更新检查不在每次应用启动的关键路径中自动执行。无网络或校园网链路异常不能阻塞用户启动已安装版本。

## 4. 清单协议

`packaging/serve.py` 已实现 `GET /latest.json`。清单只暴露与 `src.__version__` 当前版本一致的安装资产，旧版本文件即使仍留在 `packaging/dist/` 也不会混入当前清单。

```json
{
  "schema_version": 1,
  "tag": "0.1.8.1",
  "channel": "stable",
  "generated_at": "2026-08-08T00:00:00+00:00",
  "assets": [
    {
      "name": "QLH-Edge-Inference-Setup-v0.1.8.1.exe",
      "url": "/QLH-Edge-Inference-Setup-v0.1.8.1.exe",
      "size": 158019537,
      "sha256": "64 hex characters",
      "platform": "windows",
      "variant": "cpu",
      "arch": "x86_64",
      "kind": "installer"
    }
  ]
}
```

约束：

- `schema_version` 当前只能为 `1`。
- 资产名必须是安全 basename，不接受 `/`、`\`、`.`、`..`。
- URL 只接受 HTTP/HTTPS；相对 URL 以清单 URL 解析。
- `size` 和 SHA-256 必须同时匹配。
- `serve.py` 以 `mtime_ns + size` 缓存大文件摘要，文件未变化时不重复计算。
- 同版本同变体只能发布一个正式资产；生成器按版本过滤旧文件。

## 5. 下载与安装事务

当前下载事务：

```text
目标目录创建
  → 已有目标文件：大小 + SHA-256 一致则复用
  → 删除失效目标和旧 .part
  → 流式下载到 <asset>.part，并限制不得超过清单 size
  → 校验 size + SHA-256
  → os.replace 原子改名
  → 写 pending_install 状态
  → 经用户确认后启动系统安装器
```

这能保证“下载失败不覆盖完整缓存”，但还不是完整的应用安装事务。当前 EXE 覆盖、进程锁和卸载仍由 Inno Setup 处理；Linux `.deb` 只提示 `dpkg -i`，Launcher 不提权。

后续 UP-N3（原子版本切换）需要引入：

```text
app/
├── launcher/                         # 独立、不可被主应用覆盖
├── versions/
│   ├── 0.1.8.1-cpu/
│   └── 0.1.9-cpu/
├── current.json                      # 当前版本指针
├── previous.json                     # 回滚指针
├── models/                           # 不进入版本目录
├── config/                           # 不进入版本目录
└── logs/                             # 不进入版本目录
```

只有在新版本完成解包、摘要验证、启动健康检查后才能切换 `current.json`；失败立即恢复旧指针。不能直接在运行目录逐文件覆盖来冒充原子更新。

## 6. 安全模型

SHA-256 只能证明下载内容与清单一致，不能证明清单来自项目发布者。Tailscale 网络身份能降低公网暴露，但不能替代发布签名。

当前安全行为（UP-N2 之后）：

- HTTPS 使用系统证书校验；内网 HTTP 源仅作为显式配置/默认受控源。
- 多源不会用“同名同大小”互相背书；每份清单独立解析。
- 清单出现 `signature` 不会自动变成可信状态：**只有内置 pubkeys 信任集中 Ed25519 验签通过才置 `signature_verified=True`**。
- 篡改清单正文/签名、未知 `key_id`、缺失或畸形 `signed_at`、伪造的密钥授权、过期密钥均 fail-closed（`signature_verified=False` 并附原因）。
- 自动检查可以下载；自动执行安装必须等待可信公钥验签完成（或用户显式 `--allow-unsigned`）。
- GUI/TUI 安装流程不再传递 `--allow-unsigned`：验签未通过时安装被拒绝并显示原因。

UP-N2 签名方案（已实现，`packaging/signing.py` + `packaging/pubkeys/`）：

1. 固定项目发布公钥随 Launcher 发布（`pubkeys/root.pub.json` + `pubkeys/release-*.pub.json` 打包进 Launcher bundle 与 Linux `.deb`）；私钥只存在于发布者本机 `packaging/.signing-keys/`（gitignore，不进入仓库和构建机普通环境）。
2. 对规范化清单正文做 Ed25519 签名（排序+紧凑 UTF-8 JSON，去除 `signature` 字段）；清单包含 `key_id`、`signature`、`signed_at`。`serve.py` 配置 `QLH_SIGNING_KEY` 后自动签名 `/latest.json`，也可用 `qlh-signing sign` 离线签名。
3. Launcher 先验签，`signature_verified=True` 才允许免 `--allow-unsigned` 安装。
4. Windows 可叠加 Authenticode（本轮未实施，两者分别保护清单和 EXE，不互相替代）。
5. 支持公钥轮换：新 key 必须由旧 key 或离线根 key 的私钥签发授权记录（`qlh-signing authorize`），授权链可追溯到 `root.pub.json` 才受信任。

## 7. GUI / TUI 约束

GUI 与 TUI 只能共享 Controller 和更新核心，不能互相嵌套事件循环。

共同能力：

- 启动普通 UI；
- 启动管理 TUI；
- 展示 Launcher/应用版本；
- 选择 CPU/CUDA 更新包；
- 后台检查更新；
- 明确确认后下载并启动安装器；
- 主应用丢失或损坏时保持修复入口可用。

GUI 网络操作运行在线程中，不冻结 Tk 事件循环；TUI 保持纯文本可用。Launcher 自身不需要 Textual/httpx，因此不会改变全局 Python 解释器或主项目依赖。

- 清单字段、危险资产名、变体/架构匹配；
- `signature_present` 不等于 `signature_verified`；
- Ed25519 验签：签名/篡改清单正文/未知 key/缺或畸形 `signed_at`/伪造授权/未知授权者/过期 key 全部 fail-closed（`tests/test_signing.py`）；
- 密钥轮换：新发布 key 由旧 key 或 root 授权（链式）后受信任，授权被篡改或授权者不受信任时拒绝；
- `.part` 下载、大小/SHA-256、原子改名和缓存复用；资产内容被篡改时下载事务失败（fail-closed）；
- 多更新源并行容错与最高版本选择；
- `serve.py` 只发布当前版本并正确分类 CPU/Full/Lite；配置 `QLH_SIGNING_KEY` 后 `/latest.json` 带 Ed25519 签名；
- Bootstrap 应用发现、变体传递、headless 退出码和缺应用错误。
- UP-N3 版本目录 staging、ZIP/tar 安全解包、健康门失败保持 current、current 损坏恢复 previous、rollback 和 CLI/BJTU 接线（`tests/test_version_store.py`、`tests/test_version_store_cli.py`）。
- UP-N4 Launcher A/B 槽 staging、ZIP 路径/链接安全检查、`health.ok` 标记与 `--health-check` 子进程探针、稳定入口委托、失败回滚和脱敏诊断包（`tests/test_launcher_slots.py`）。
- UP-N6.0 安装清单严格字段/路径、用户数据排除、签名篡改、原子落盘、staging 的签名身份绑定、Windows/Linux 构建接线，以及发布源到 A/B 槽的真实 HTTP 下载和冻结验签器 smoke（`tests/test_install_manifest.py`、`tests/test_launcher_publish_e2e.py`）。
- UP-N6.1 的运行时 verify：签名先行、关键启动文件 quick、全量清单 full/deep、同尺寸篡改、`health.ok` 缺失、JSON/退出码、`qlh-launcher`/`bjtu` 路由，以及仅按签名清单枚举路径从而不读取用户数据根（`tests/test_install_manifest.py`、`tests/test_launcher_bootstrap.py`）。`full` 对大于 64MiB 的文件只验证大小与固定区段可读性；schema v1 没有签名的抽样摘要，完整防篡改判断必须使用 `deep`。
- UP-N6.2 diagnose：稳定的 10 类本地症状知识库、签名清单 quick 证据、CUDA 包的无 shell `nvidia-smi` 探测、磁盘/权限只读检查、CLI/JSON/GUI/TUI；原始错误文本不持久化，诊断 ZIP 仅附状态目录内的脱敏无路径摘要（`tests/test_diagnose.py`、`tests/test_launcher_bootstrap.py`、`tests/test_launcher_slots.py`、`tests/test_updater.py`）。诊断不发起网络请求，不扫描模型或用户数据。
- UP-N6.3 repair：本机 deep 预检、同版本已验签更新清单的 `repair-index`、索引对本机签名基线的逐项反校、同 origin 载荷、全量预下载校验、`.bak` 快照、原子替换和 deep 复验/回滚（`tests/test_repair.py`、`tests/test_launcher_bootstrap.py`、`tests/test_packaging_serve.py`）。仅允许 `missing/size/hash` 的签名程序文件；超过 10 个文件或 64MiB 时不联网不写入，用户数据根零触碰。
- UP-N6.4 数据保留重装：只移动 `models`、`chat_history`、`logs`、`config`、`local_docs`，不读取内容；只接受同文件系统的 `os.replace`，拒绝链接/reparse、根嵌套、目录冲突和覆盖。外置 `.qlh-retention.json` 绑定 retained/reassociated 状态；`reinstall` 先 retain 再调用不带 `--allow-unsigned` 的既有安装流。Windows Inno 和 Linux maintainer scripts 只在 marker 存在时回迁（`tests/test_data_retention.py`、`tests/test_launcher_bootstrap.py`、`tests/test_install_manifest.py`）。

### UP-N4 实现边界

稳定安装目录中的 Launcher 永远是维护入口。新的 `QLH-Launcher-v<version>.zip` 先下载到 `.part`、验证大小和 SHA-256，再解压到非活动槽；`health.ok`、入口文件检查和隔离子进程 `--health-check` 全部通过后，才原子写入 `current.json`。普通 GUI/TUI/主应用命令才委托活动槽，`launcher-*`、版本管理和 `diagnostics` 始终由稳定副本处理。

活动槽启动失败时，稳定副本尝试以 `previous.json` 做健康回滚；没有可用旧槽则保留稳定副本并继续提供修复入口。诊断包只收集槽指针、有限状态/日志文本，并对 token、secret、password、authorization 等字段脱敏；模型、私钥和完整环境变量不进入诊断包。

当前 N4 发布门：Launcher ZIP 已实际构建并验证发布链路（2026-08-08 `build-launcher.bat` 产出 `packaging/dist/QLH-Launcher-v0.1.8.1.zip` 16,158,275 bytes，含 `QLH-Launcher.exe` + `health.ok`；签名源站 `/latest.json` 发布 `kind=launcher` 资产，`launcher-check` 真实 HTTP 验签通过，`launcher-download → stage → health 探针 → activate → rollback` 双槽闭环实测通过；契约测试见 `tests/test_launcher_bootstrap.py` 与 `tests/test_packaging_serve.py`）。剩余：Windows 安装后真实切换/回滚、Linux `.deb` 和断网/权限场景干净机验收。N4 不覆盖 Android APK 更新（归 UP-N5）。

发布前还必须手工验证：

1. Windows 独立目录安装 Launcher Setup、无主应用时检查更新、静默卸载已通过；仍需干净用户目录复验。
2. 分别安装 CPU/CUDA 主应用，Launcher 能正确发现、启动 UI/TUI。
3. 校验错误、下载中断、无网络和一个源超时时，旧应用仍可启动。
4. Linux `.deb` 中 `qlh-launcher` 与 `qlh-app` 权限、systemd headless、`bjtu` 路由正确。
5. 卸载主应用不误删 Launcher；卸载 Launcher 不误删模型、配置、日志和主应用。

## 10. 维护规则

1. Launcher 禁止导入推理运行时；spec 必须继续排除 torch、transformers、FastAPI 和 uvicorn。
2. 应用版本由安装目录 `version.txt` 或 `QLH_CURRENT_VERSION` 提供；Launcher 版本单独记录，不能混为一个数字。
3. 更新源地址可配置；不得把检查网络放入“启动已安装应用”的强制路径。
4. 发布新版本时同步 `src/__init__.py`、Setup、Linux/Android 版本和 `packaging/version.txt`。
5. 清单协议变更必须提升 `schema_version`，旧 Launcher 对未知 schema fail-closed。
6. UP-N2 验签已接入（2026-08-08 验收），GUI/TUI 不再提示“发布签名尚未接入”；后续任何对信任集、验签或密钥轮换的改动都必须重跑 `tests/test_signing.py` 并保持 fail-closed 语义。
7. UP-N3 只管理独立版本目录；Inno Setup/`.deb` 的系统安装事务仍不等同于热切换。版本包必须先 staging、再健康检查、最后切换 current；current 损坏时只能 recover 到 previous，不得猜测目录。
8. UP-N6.0 的 `install-manifest.json` 是发布方签名的程序文件基线，不覆盖 `models/`、`chat_history/`、`logs/`、`config/`、`local_docs/`。UP-N6.1 的 runtime quick/full/deep 只枚举该清单中的程序路径，绝不扫描或写入这些用户数据根；大文件需要完整防篡改保证时必须使用 `deep`。没有 `QLH_SIGNING_KEY` 的构建不得生成可发布安装包。
9. UP-N6.2 diagnose 只能使用内置知识库和本机受限探测，不能把原始启动错误、令牌、安装绝对路径或失败文件路径写入诊断 ZIP；附加 JSON 必须位于 Launcher 状态目录的 `diagnostics/` 下且不超过 1MiB。UP-N6.3 repair 只能由用户显式触发，必须以本机签名基线和同版本、已验签的 `repair-index` 双重约束写入；索引、阈值或最终 deep 复验任一失败均不得继续修改用户数据或放宽为整包自动重装。
10. UP-N6.4 只能在用户显式确认后移动固定用户目录；不读取内容、不删除、不合并、不覆盖，且跨文件系统必须拒绝而不是 copy-and-delete。`reinstall` 只可复用现有的已验签安装流；外置 marker 缺失、状态不匹配或新安装目录非空时不得自动回迁。
