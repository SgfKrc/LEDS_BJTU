## 1. 主线裁决

QLH 主仓只解决一个问题：**在异构设备上把推理任务可靠地跑起来，并用可复现证据证明内存、时延、吞吐和故障边界**。

主仓由四个相互约束的部分组成：

| 部分 | 责任 | 是否交付能力 |
| --- | --- | --- |
| Engine L | GGUF/llama.cpp 轻量引擎、CPU/弱 GPU 路径、KV/缓存/投机和边缘入口 | 是；边缘版必须可独立运行 |
| Engine D | PyTorch/Safetensors 层流水线、张量传输、层装载和多节点推理 | 是；面向 PC/工作站集群 |
| Control | 节点、能力画像、调度、租约、任务路由、集群状态和降级 | 是；控制面与数据面同仓但分层 |
| Contracts & evidence | 模型画像、manifest、协议、质量门、性能实验和回归测试 | 是；没有证据的能力不能进入“支持” |

**主项目交互入口是 TUI。** 当前统一入口是 `qlh chat`；零第三方的 `python -m src.tui_admin --plain` 仍是 Edge/排障基线。`qlh_edge` 提供极简 HTTP 供远程任务和外部壳调用；Web、Android 和图形启动器不是主仓的交付入口。

主仓不再新增下列能力：图像生成/编辑、通用知识库和长期记忆、Web 产品界面、Android 产品界面、安装器/更新器、答辩演示、联网 Fetch、邮件通知和面向用户的运营工作台。这些能力的归属与迁移顺序见支线计划。

## 2. 双引擎与模型舰队

### 2.1 两档运行基线

| 档位 | 引擎 | 模型格式 | 目标设备 | 依赖边界 |
| --- | --- | --- | --- | --- |
| **L（Light/Edge）** | llama.cpp / `llama-cpp-python` | GGUF | CPU、集显、低内存 PC、Android Full | 不装 torch；可用 CPU；按设备能力动态选模型 |
| **D（Distributed）** | PyTorch | Safetensors 等原生权重 | PC/工作站、多节点、高内存或 CUDA | 允许 torch；用于层流水线和真实多节点推理 |

模型舰队只登记**模型身份、格式、引擎、能力、资源预算、模板和工件摘要**。权重仍由用户选择、下载和持有。用户通过 TUI 的模型列表/画像/选择操作决定使用文本模型或可选多模态模型；QLH 不把某一个视觉模型写成所有设备的必选依赖。

没有本地模型不等于主程序不能启动：正常启动仍进入控制面、TUI 和模型下载工作区，用户可以先从模型舰队选择或下载模型；只有 `--check-only` 这类严格诊断模式才要求本地模型资产存在。无模型时推理请求应明确报告缺失并保持可下载/可选择状态，而不是阻塞进入主程序。

多模态是**可选模型能力**而不是主线产品形态：模型画像必须声明 `vision`、输入格式、上下文预算、内存预算和平台支持；设备没有对应资源时要明确降级到文本模型。主仓保留能证明分布式推理边界所需的多模态协议/运行时，但边缘最小安装不预装多模态大件。

### 2.2 三种正式分布式形态

| 形态 | 主线归属 | 适用范围 | 当前结论 |
| --- | --- | --- | --- |
| **PyTorch 层流水线** | D 档主线 | PC/工作站节点按连续层段协同 | 主研发和验收路线；GGUF 不直接接入该隐状态协议 |
| **任务池/整请求分发** | L 档主线 | Android、GGUF 轻节点、异构低配节点 | 正式形态，不是临时 Worker 补丁；跨生态统一走任务协议/HTTP；Silica 式 Android RPC 仍是候选实验 |
| **TP 孤岛** | 控制面适配 | 同构 GPU 子集群作为一个逻辑节点 | 外部运行时整请求接入；不参与 QLH 层流水线 |

llama.cpp 当前还提供两类与 GGUF 相关的能力，但要分开表述：

- 同一主机的 `--split-mode layer/row/tensor` 和 `--tensor-split` 是本地多设备拆分能力；`tensor` 仍按上游标注保守处理。
- `ggml-rpc-server` + `--rpc` 可以把 GGUF 权重/KV 按设备内存比例放到远端设备，**但上游仍标为 proof-of-concept、fragile、insecure**。QLH 只把它作为隔离网络下的对照实验，不作为生产分布式路线。
- 外部 [Silica Cluster](https://github.com/ShintoChakkiath/Silica-Cluster-Decentralized-Mobile-AI) 进一步证明 Android 可以承载 `libllama.so`/`librpc.so` 并接入 `--rpc`；其源码中的 `-ngl`/`--tensor-split` 是 offload/比例 split，不是 QLH 的连续 `layer_range` 协议。Android RPC 因此升级为 `CORE-GGUF-RPC-01` 的候选验证项，但不改变 D 档 PyTorch 层流水线主线。

GGUF **不进入当前 PyTorch 层流水线**：现有层流水线使用 PyTorch hidden state 和 Safetensors 层描述。要做 GGUF 按层隐藏态接力，需要另立引擎协议和验收票，未立项前禁止在 TUI、README 或模型画像中宣称支持。

Qwen 在 Android 的现实选项是两条并行路线：QLH 当前基线为 llama.cpp/GGUF；ExecuTorch 是可选的 AOT 端侧路线，官方已有 Qwen3 0.6B、1.7B、4B 示例和 Android 后端支持。它不等于完整 PyTorch 运行时直接进入 Android，也不改变 QLH 的 L/D 双档边界。

## 3. 边缘版硬基线

边缘版是主线的硬交付约束，不是删减后的宣传名：

| 项目 | 基线 |
| --- | --- |
| 运行档位 | L 档 GGUF；CPU 路径永远可用 |
| 交互 | 标准库 TUI（当前 `python -m src.tui_admin --plain`，目标统一为 `qlh chat`）；最小 HTTP 仅用于状态、健康、推理和任务协议 |
| 依赖 | `llama-cpp-python`/llama.cpp、FastAPI、Uvicorn、psutil、httpx 等最小集合；禁止 torch 进入边缘安装 |
| 环境体积 | venv 目标不超过 300 MB；当前开发测量约 120 MB |
| 冷启动 | 健康检查目标不超过 15 秒；当前开发测量约 0.57 秒 |
| 资源 | 默认优先小模型和 Q4；能力画像必须在加载前检查 RAM、上下文和工件摘要 |
| 可选能力 | 多模态随模型舰队按需选择；没有对应模型或预算时保持文本路径可用 |
| 明确排除 | Web/Android UI、图像生成、RAG、邮件/审批、安装器、演示、联网工具和重型实验依赖 |

边缘版可以作为单机产品运行，也可以作为任务池节点加入集群；“边缘”不等于只能被远程调用。主仓必须持续保留一条不依赖 CUDA、torch 或产品壳的可运行路径。

## 4. 角色与依赖纪律

```text
TUI / qlh_edge
        |
        v
Control  ------ task / model / capability contracts ------>  Engine L or Engine D
        |                                                    |
        +---------------- scheduling / lease ----------------+

External shell / Koakumix / Patchouli
        \\------------ HTTP + schemas only ------------> QLH
```

- Control 可以调用 Engine；Engine 不得 import Control。
- TUI 只依赖稳定的 HTTP/协议和模型能力摘要，不读取内部路径、凭据或实验临时文件。
- 产品壳、Koakumix 和 Patchouli 只能通过协议、manifest 或模型工件边界接入，不复制主仓推理实现。
- 实验和质量门中与推理优化直接相关的代码留主仓；演示、报告排版、网络探针和环境编排外置。

## 6. 当前不做与止损

- **不把 llama.cpp RPC / Android RPC Worker 在"未验收前"接成默认生产路由**（**2026-09-15 用户裁决后改写**）：原表述为"不接默认"（保守止损）；现改为**分阶段准入**——`CORE-GGUF-RPC-01` 的 S1/S2 PoC 通过，**且**层段合同可校验、节点身份/模型校验/传输保护/回滚/soak 证据齐备后，**允许作为 Android/GGUF 侧的正式路径接入**（形态④，见[形态决策](QLH异构分布式形态决策-2026-09-14.md) §2）。**止损对象由"方向"收窄为"未验收前的默认开启"**；依据与落地路径见[调研汇总 §2.2.1](分布式推理并行与跨框架路线调研汇总-2026-09-15.md)。
- 不把 ExecuTorch 作为 QLH 第三引擎**立即合入**；**但实验先行**（用户 2026-09-15 裁决：采用更激进策略，至少完成 ExecuTorch 实验）——由 `CORE-ET-EXP-01` 在独立环境执行，**是否接入主项目/Android 端另行裁决**；止损只约束"立即合入"，不约束实验。支撑事实（Qwen3 支持是 Llama 示例的参数化复用、官方无 Qwen3 端侧性能数据、Android API 已于 1.4 完成 Java→Kotlin 迁移、1.4 新增 Qwen3-VL/SmolLM2 覆盖）与接入裁决条件见[分布式推理并行与跨框架路线调研汇总](分布式推理并行与跨框架路线调研汇总-2026-09-15.md) §4。
- 不自研 GGUF 与 PyTorch hidden state 的跨框架逐层协议（**2026-09-15 调研结论支持维持**：llama.cpp 无公开中间层 hidden 读写 API，上游 issue #27112 仍 open；跨框架层接力亦无对口开源先例——见[调研汇总](分布式推理并行与跨框架路线调研汇总-2026-09-15.md) §3；重启条件：上游开放中间层 API / 出现第三方成熟项目 / "只传 token"方案已到上限）。
- 不因产品壳尚未外置而扩充 Web/Android 功能；外壳只消费已冻结合同。
- 不为了让旧票“看起来完成”而恢复已裁撤的生图、微服务或旧前端路径。

主线票据文档不再作为持续维护入口；邮件通知、SMTP/IMAP 配置和邮件投票已在本轮从主仓移除，审查工单仍通过 TUI/API 查询、投票和过期处理。
